# Issue #47816 — Use fresh environment block on new terminals in Windows

[https://github.com/microsoft/vscode/issues/47816](https://github.com/microsoft/vscode/issues/47816)

## Summary

Keep open: new Windows terminals still derive their environment from existing process snapshots, rather than freshly reading persisted user and system variables. The request has substantial community support, and neither the available settings nor a verified older canonical covers it.

## Change summary

Allow newly created Windows terminals to pick up changed user and system environment variables without restarting VS Code.

## Best solution

Provide fresh persisted Windows environment values for new local terminal sessions, with explicit precedence rules that preserve deliberate launch, profile, settings, and extension overrides. Coordinate with the related refresh-command proposal, which addresses existing sessions rather than automatic freshness on terminal creation.

- **Fit:** aligned
- **Reason:** Refreshing new terminal environments without restarting every workspace improves the integrated terminal developer workflow.

- **Validation:** On Windows, start VS Code, then add and change a persisted test variable and add a directory containing a test executable to user PATH from outside VS Code. Create a new local terminal with '+' and verify it sees the updated variable and resolves the executable without restarting VS Code; verify an already-running terminal is unchanged. Cover persisted-variable deletion, machine/user precedence, intentional CLI launch values, and settings/profile/extension overrides under the agreed contract, with automated environment-merging tests.
- **Behavior:**

  > While VS Code remains running on Windows, newly created local terminals should reflect changes to persisted user and system environment variables, including PATH changes made by installers. This must not require restarting other windows or mutate already-running shell sessions. Acceptance includes detecting a newly added executable and an updated test variable in a new terminal while respecting the agreed precedence for deliberate environment overrides.
- **Trace:**

  > TerminalProcessManager._resolveEnvironment in src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts obtains a base environment and then applies terminal configuration and extension collections. LocalTerminalBackend in src/vs/workbench/contrib/terminal/electron-browser/localTerminalBackend.ts memoizes its environment getters; the shell environment comes from a one-time preload promise, and PtyService.getEnvironment in src/vs/platform/terminal/node/ptyService.ts returns a process.env snapshot. createTerminalEnvironment in src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts handles strictEnv, sanitization, and settings/launch overrides, which must retain their intended semantics. The source establishes why new persisted Windows values are not automatically fetched, but does not settle how they should interact with intentional CLI launch values or deleted persisted variables. Keep remote terminals, existing shell sessions, and unrelated Electron-variable filtering outside this request. https://github.com/microsoft/vscode/pull/299941 is an open, related manual-refresh proposal for existing sessions, not a landed solution to this creation-time request.
- **Open decisions:**
  - When an intentionally supplied CLI launch variable differs from a subsequently changed persisted Windows value, which value should a newly created terminal receive?
  - When a persisted Windows variable is deleted while VS Code runs, should new terminals remove the inherited value, and how should that differ from a variable supplied only by the launching process?
