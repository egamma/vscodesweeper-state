# Issue #99295 — Allow for "random access" undos

[https://github.com/microsoft/vscode/issues/99295](https://github.com/microsoft/vscode/issues/99295)

## Summary

A real capability gap remains on current main: workspace undo still requires the target operation to be the newest element in every affected resource. This team-authored Backlog request should remain open and be classified as under discussion because conflict detection and non-linear undo semantics require design work.

## Change summary

Allow a cross-file operation to be undone after later non-conflicting edits instead of requiring it to be at the top of every affected file's undo stack.

## Best solution

Define safe selective-undo semantics for text edits, including how intervening edits are checked or transformed, then extend the undo/redo model so a workspace edit can be reversed without discarding compatible later changes.

## Plan brief

- **Likely files:** `src/vs/platform/undoRedo/common/undoRedo.ts`, `src/vs/platform/undoRedo/common/undoRedoService.ts`, `src/vs/platform/undoRedo/test/common/undoRedoService.test.ts`, `src/vs/editor/common/model/editStack.ts`
- **Validation:** Add a targeted undoRedoService test where a workspace edit is followed by a non-overlapping resource edit, then verify selective undo reverses only the workspace edit while preserving the later edit and maintaining coherent redo behavior.
- **Behavior:**

  > After a cross-file operation such as rename, a later edit that does not conflict with the affected range should not necessarily prevent undoing the earlier operation across all files. The later edit must remain intact, while conflicting edits must produce a safe and predictable outcome rather than corrupting text. Redo behavior and ordinary linear undo must remain coherent. Acceptance should cover non-overlapping, overlapping, and multi-file intervening edits.
- **Trace:**

  > ResourceEditStack in src/vs/platform/undoRedo/common/undoRedoService.ts maintains linear past and future arrays, and _undo always operates on getClosestPastElement(). _checkWorkspaceUndo rejects a workspace element unless it is the closest past element in every affected stack, then falls back to splitting through _tryToSplitAndUndo. Text operations retain detailed TextChange data in SingleModelEditStackData in src/vs/editor/common/model/editStack.ts, but that information is not part of the generic IUndoRedoElement contract in src/vs/platform/undoRedo/common/undoRedo.ts. The uncertainty begins at how selective undo should prove compatibility and preserve or transform intervening operations. Preserve existing linear undo, grouped undo, workspace confirmation, and partial-undo behavior. Related context: https://github.com/microsoft/vscode/issues/99159.
- **Open decisions:**
  - Should compatibility be determined by exact text ranges, line-level overlap, or operation-specific logic supplied by undo elements?
  - Should selective undo transform and replay intervening edits, or be allowed only when those edits can remain untouched?
  - What redo history should result after removing a non-top operation from the past stack?
  - Should random-access undo be automatic for workspace operations or exposed through an explicit user-facing choice?
