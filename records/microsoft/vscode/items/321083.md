- **Validation:** Retest the reported declarative-agent setup against the production MCP URL, recording the selected issuer, discovery results, and registration response without credentials. If a client defect is confirmed, capture that response sequence in a deterministic regression test that fails before the fix and passes afterward; verify that legitimate manual-registration fallback remains available.
- **Behavior:**

  > The reporter adds https://cloudimanage.com/mcp/work as an MCP action during declarative-agent creation and receives a static client-registration prompt despite advertised DCR support. For a compatible server whose discovered metadata advertises DCR and whose registration endpoint accepts the client, setup should register automatically without manual client details. First confirm the production failure and distinguish missing metadata from rejected registration. Servers without usable DCR must retain their existing manual-registration path.
- **Trace:**

  > createAuthMetadata in src/vs/workbench/api/common/extHostMcp.ts derives the authorization server from protected-resource metadata or the MCP URL's origin, then calls fetchAuthorizationServerMetadata in src/vs/base/common/oauth.ts. $registerDynamicAuthProvider in src/vs/workbench/api/common/extHostAuthentication.ts attempts DCR when registration_endpoint is present and falls back to the same manual-registration dialog after registration errors. This makes the screenshot insufficient to distinguish discovery failure from registration failure; the actual selected issuer and response sequence remain unknown. The Toolkit ownership explanation is at https://github.com/OfficeDev/microsoft-365-agents-toolkit/issues/16135#issuecomment-4686991400. Its later independent discovery workflow is a workaround, not demonstrated coverage of the built-in path. Keep unrelated OAuth flows and legitimate static-client configuration out of scope.

## Evidence

- **Actionable report:** https://github.com/microsoft/vscode/issues/321083 supplies the affected server URL, declarative-agent setup steps, observed registration dialog, OS, and VS Code version. The linked Toolkit report additionally states that the corresponding DEV environment completes DCR successfully.
- **Core ownership:** https://github.com/OfficeDev/microsoft-365-agents-toolkit/issues/16135#issuecomment-4686991400 explains that Toolkit writes the MCP server configuration and VS Code core handles metadata discovery, registration, and the displayed authentication dialog. This is not evidence of an extension-caused defect.
- **Discovery path:** src/vs/workbench/api/common/extHostMcp.ts:createAuthMetadata reads the WWW-Authenticate challenge, discovers protected-resource metadata, selects authorization_servers[0], and otherwise falls back to the resource origin. src/vs/base/common/oauth.ts:fetchAuthorizationServerMetadata then attempts OAuth authorization-server and OpenID discovery. Public availability of the origin metadata alone does not establish which issuer this flow actually selects.
- **Ambiguous fallback:** src/vs/workbench/api/common/extHostAuthentication.ts:264-300 attempts fetchDynamicRegistration when registration_endpoint exists, but presents manual registration both when that field is absent and when registration throws. src/vs/base/common/oauth.ts:947-1003 can throw for HTTP rejection or an invalid registration response. The reported dialog therefore does not prove that discovery was skipped.
- **Later workaround, not a core fix:** https://github.com/OfficeDev/microsoft-365-agents-toolkit/issues/16135#issuecomment-4998327109 says Toolkit 6.12.0 supports dynamic tool discovery with DCR without relying on VS Code tool discovery. That changes the available setup workflow but does not demonstrate resolution of this built-in-client report.
- **Canonical search:** Searches for cloudimanage, MCP DCR, and OAuth registration metadata found no verified open canonical for this production-server failure. https://github.com/microsoft/vscode/issues/320654 and https://github.com/microsoft/vscode/issues/334970 concern unwanted OAuth prompts for static-header servers; https://github.com/microsoft/vscode/issues/337052 concerns corruption after registration. Those are distinct reported behaviors, not established duplicates.
