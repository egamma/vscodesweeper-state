# Issue #338932 — Existing Local chat session remains usable after managed Agent Host sandbox policy applies

[https://github.com/microsoft/vscode/issues/338932](https://github.com/microsoft/vscode/issues/338932)

## Summary

Team-authored (MEMBER), freshly filed (0 days old), security-sensitive bug describing a managed sandbox policy enforcement gap — an existing Local chat session is not migrated/blocked when managed Agent Host sandboxing is applied. This is protected from judgment closes, carries a real version milestone (1.141.0), and touches sandbox/security enforcement, so it must stay open regardless of staleness.

## Change summary

An existing chat session created on Local keeps running on Local (bypassing Agent Host sandbox enforcement) after enterprise-managed sandbox policy is retrieved and applied, until the user manually switches harness.

## Best solution

Have the managed-settings application path in the agentHost enablement/session code detect sessions already running on Local when a managed sandbox policy newly applies, and either migrate them to Agent Host or block continuation until the user switches — likely in src/vs/platform/agentHost (enablement service / session launcher) based on the active sandbox-policy code there.

Expected: the session is either migrated to Agent Host or the user is prevented from continuing it until Agent Host is selected. - **Trace:**

Related: https://github.com/microsoft/vscode/issues/338570 tracks a different (dev containers) harness-selection bug per the issue body.
