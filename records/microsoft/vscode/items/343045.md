Current main still separates downloading a System update from applying it; the supplied file checks and CLI commands suffice to retest the damaged state without treating Restart Manager correlation as proven causation.

## Change summary

- **Validation:** In an isolated Windows VM with System setup, capture installer logs and filesystem deletion events while exercising a pending update and an elevated installer with Code running in another session. After failure or cancellation, verify that the launcher's active revision retains resources/app/out/cli.js and main.js, code --disable-extensions --version succeeds, and the editor and terminal still start.
- **Behavior:**

  > The reported active System installation retains its executable and metadata but loses resources/app/out, preventing CLI startup and breaking workers in existing sessions. A pending update must leave the active version usable, and an unsuccessful installation or rollback must leave a complete version that the launcher can start. Acceptance requires checking the active revision's files and launching both the CLI and editor after an induced installer failure, not merely observing the updater's Ready state.
- **Trace:**

  > The current download path in src/vs/platform/update/electron-main/updateService.win32.ts sets Ready without automatically applying the package for a System target. build/win32/code.iss contains non-background InstallDelete entries for versioned resources and post-install versioned cleanup, but this inspection does not connect either operation to deletion of the reporter's active revision. Preserve the distinction between those proven historical conditions and this occurrence's unverified cause, and do not change unrelated update or extension behavior.
