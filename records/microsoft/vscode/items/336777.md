# Issue #336777 — Agent plugins: Install Plugin From Source deletes plugins installed from a marketplace on the same repository

[https://github.com/microsoft/vscode/issues/336777](https://github.com/microsoft/vscode/issues/336777)

## Summary

Confirmed on current main: `_doInstallFromSource` builds a ref-less source descriptor, so `GitHubPluginSource._getRepoDir` resolves to the same parent folder a ref-scoped marketplace clone (`ref_<ref>`) lives under; `ensure` sees the folder already exists and skips cloning, then `cleanupPluginSource` deletes it recursively because the shared-cache guard is only invoked when `otherInstalledDescriptors` is passed, which this call site omits. This breaks a plugin installed from the default `github/awesome-copilot` marketplace.

## Change summary

Running 'Chat: Install Plugin From Source' on a repo that is also configured as a ref-pinned marketplace deletes that marketplace's cloned files, orphaning any plugin installed from it.

## Best solution

Fix the folder-collision/cleanup gap in src/vs/workbench/contrib/chat/browser/pluginSources.ts and pluginInstallService.ts — a maintainer should pick among the three approaches the reporter already outlined (distinct ref-less folder segment, git-worktree check before skipping clone, or only deleting what this call created) since they trade off cache layout compatibility differently; the dropped `#ref` parsing in `_doInstallFromSource` should be fixed alongside it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/pluginInstallService.ts`, `src/vs/workbench/contrib/chat/browser/pluginSources.ts`, `src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts`
- **Validation:** A repository-service/install-service test that installs a ref-pinned marketplace, then runs installPluginFromSource on the same owner/repo without a ref, and asserts the ref-pinned clone and its installed plugin's files still exist afterward.
- **Behavior:**

  > Running 'Chat: Install Plugin From Source' on a GitHub repo or git URL that is also configured (with a ref) as a plugin marketplace must not delete that marketplace's existing clone or break plugins already installed from it, whether the source install succeeds or fails. A source install should also honor any `#ref` the user types instead of always cloning the default branch. Acceptance: the added test (or an equivalent manual repro of the reporter's steps) passes — the ref-pinned clone and `installed.json` entry survive a same-repo, ref-less source install.
- **Trace:**

  > Root cause is a folder-naming collision plus a cleanup blind spot: GitHubPluginSource._getRepoDir (pluginSources.ts:275-279, and the analogous GitUrlPluginSource) maps a ref-less descriptor to the same folder that is the *parent* of a ref-scoped marketplace clone (`ref_<ref>` segment appended by gitRevisionCacheSuffix). AbstractGitPluginSource.ensure (pluginSources.ts:91-100) treats that existing parent folder as already cloned and skips cloning; pluginInstallService._doInstallFromSource (pluginInstallService.ts:90-168) then calls cleanupPluginSource without otherInstalledDescriptors (line 159) when no plugins are found, so agentPluginRepositoryService.cleanupPluginSource's shared-cache guard (lines 440-450, an exact-path `isEqual` check) never triggers and the whole directory is deleted recursively. The boundary: do not change how ref-scoped marketplaces are cached, and do not alter the discovery/'no plugins found' UX — only the folder-collision and cleanup-scoping logic. Separately, `_doInstallFromSource` (line 92-94) discards a parsed `#ref` from the descriptor it builds, so ref handling on this path needs the same look.
- **Open decisions:**
  - Give ref-less source clones a distinct folder segment (e.g. a `default` segment) so they can never collide with a `ref_<ref>` folder, or keep the current layout and instead check that an existing folder is a real git work tree before skipping the clone?
  - Should cleanupPluginSource on this path track and delete only the files/dirs the current install actually created, rather than deleting an entire pre-existing directory?
  - Should the dropped `#ref` in `_doInstallFromSource`'s descriptor be fixed as part of this change or tracked separately?

## Evidence

- **descriptor omits ref:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts:92-94 builds `sourceDescriptor` from `reference.githubRepo`/`cloneUrl` only, dropping any `#ref` the user typed.
- **folder collision:** GitHubPluginSource._getRepoDir (src/vs/workbench/contrib/chat/browser/pluginSources.ts:275-279) returns `github.com/<owner>/<repo>` with no suffix when ref/sha are absent (via `gitRevisionCacheSuffix`), the same parent that a `ref_<ref>` marketplace clone lives under.
- **skip-clone then delete:** AbstractGitPluginSource.ensure (pluginSources.ts:91-100) sees the folder exists and skips cloning; back in pluginInstallService.ts:159, `cleanupPluginSource(tempPlugin)` is called with no `otherInstalledDescriptors`, so the shared-cache guard in agentPluginRepositoryService.ts:440-450 never runs and the whole directory (including the nested `ref_marketplace` clone) is deleted via `_fileService.del(cleanupDir, { recursive: true })`.
- **no fix on main:** git log on pluginInstallService.ts and agentPluginRepositoryService.ts shows no recent change touching this path; current HEAD is d3c24c3c, unrelated to this code.
