# Issue #336777 — Agent plugins: Install Plugin From Source deletes plugins installed from a marketplace on the same repository

[https://github.com/microsoft/vscode/issues/336777](https://github.com/microsoft/vscode/issues/336777)

## Summary

Confirmed on main: a source install without a ref reuses/deletes the parent folder of an existing ref'd marketplace clone. The reporter's trace-level logs match the exact code paths in pluginInstallService.ts, pluginSources.ts, and agentPluginRepositoryService.ts, and no fix has landed on main. Keeping open for a design decision on the best fix among the reporter's proposed approaches.

## Change summary

Running 'Chat: Install Plugin From Source' on a repository already used (with a ref) as a configured marketplace deletes that marketplace's cloned cache and breaks plugins installed from it.

## Best solution

Thread the currently-installed plugin descriptors into the cleanup call in `_doInstallFromSource` (as `_discoverPluginSources().remove()` already does), and make the shared-cache check in `cleanupPluginSource` detect nested cache directories (ancestor/descendant), not just exact-path matches — combined with giving ref-less clones their own cache-folder segment so `ensure()` doesn't wrongly reuse a ref'd repo's parent directory as a valid checkout.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/pluginInstallService.ts`, `src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts`, `src/vs/workbench/contrib/chat/browser/pluginSources.ts`, `src/vs/workbench/contrib/chat/test/browser/plugins/agentPluginRepositoryService.test.ts`
- **Validation:** Extend the existing `cleanupPluginSource` test suite in agentPluginRepositoryService.test.ts (see the 'skips deletion when another installed plugin shares the same cleanup target' case) with a scenario where the shared descriptor's cache target is nested under (not exactly equal to) the cleanup target, asserting deletion is skipped; plus a source-install test asserting a ref-less install request against a repo with an existing ref'd installed plugin does not delete that plugin's cache.
- **Behavior:**

  > Running 'Chat: Install Plugin From Source' with `owner/repo` (no ref) must never delete the on-disk cache of an already-installed plugin from the same repository installed with a ref (e.g. via a configured `owner/repo#ref` marketplace), and it should still correctly discover/report plugins from the ref-less clone instead of misreporting 'No plugins found' due to reusing the wrong cached directory. Existing successful source installs and existing marketplace installs must be unaffected.
- **Trace:**

  > Root cause traced across three files: (1) pluginInstallService.ts `_doInstallFromSource` (lines 90-164) builds a `sourceDescriptor` with no `ref`, and its failure-path cleanup call at line 159 omits `otherInstalledDescriptors` (unlike the safe pattern in agentPluginServiceImpl.ts's `remove()`, ~lines 858-869); (2) pluginSources.ts `gitRevisionCacheSuffix`/`GitHubPluginSource._getRepoDir` (lines 36-44, 275-279) place a ref'd clone nested inside the exact folder path a ref-less clone targets, so `AbstractGitPluginSource.ensure` (lines 91-100) wrongly treats the existing parent folder as 'already cloned' and skips cloning; (3) agentPluginRepositoryService.ts `cleanupPluginSource`'s shared-cache guard (lines 431-450) uses strict `isEqual`, so even with descriptors passed it would not detect the ancestor/descendant relationship. Do not change the `otherInstalledDescriptors`-based skip mechanism itself or the RelativePath/Npm/Pip source kinds, which are unaffected. Where the uncertainty starts: whether to fix this via a permanent cache-layout change (ref-less clones get a distinct folder segment, e.g. GitHubPluginSource._getRepoDir), via git-worktree validation before skipping a clone, or via safe-delete-only-what-was-created — these differ in on-disk compatibility with existing installs.
- **Open decisions:**
  - Should ref-less source clones get a permanently distinct cache-folder segment (changing on-disk layout, potentially orphaning already-cloned ref-less caches for existing users), or should `ensure()` instead validate that an existing folder is actually a usable git checkout before skipping the clone?
  - Should the shared-cache guard in `cleanupPluginSource` be generalized to treat any ancestor/descendant relationship between cleanup targets as 'shared' (not just exact equality), even outside the source-install-failure path?
  - Should the `#ref` parsed from a source-install string (e.g. `owner/repo#branch`) be threaded into the descriptor so a source install honors that ref instead of always cloning the default branch — a related but distinct gap the reporter also flagged?

## Evidence
