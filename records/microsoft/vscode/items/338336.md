# Issue #338336 — MCP Apps: App-provided tools registered via App.registerTool() are not exposed to Copilot agent

[https://github.com/microsoft/vscode/issues/338336](https://github.com/microsoft/vscode/issues/338336)

## Summary

Confirmed real gap on main: the host's `_handleInitialize` in chatMcpAppModel.ts ignores the App's declared `appCapabilities.tools` and the host's own `McpUiHostCapabilities` never advertises a `tools` capability back — App-provided tools are simply not wired up yet, which matches the report exactly. This is new, actively-evolving MCP Apps functionality rather than a regression, so it's a feature gap, not a broken existing behavior.

## Change summary

App-declared tools registered via App.registerTool() are never discovered (no tools/list) or routed (no tools/call) by the VS Code MCP Apps host, so Copilot can't invoke them.

## Best solution

Extend the MCP Apps host integration (src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts and src/vs/platform/mcp/common/modelContextProtocolApps.ts) to read `appCapabilities.tools`, issue tools/list to the live App view, register the results as agent-visible tools scoped to that view's lifetime, and route tools/call back to the originating instance instead of re-invoking the MCP server tool.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts`, `src/vs/platform/mcp/common/modelContextProtocolApps.ts`, `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`
- **Validation:** An integration/unit test that registers an app-provided tool via a mocked App.registerTool()-style init, asserts VS Code issues tools/list to the app and exposes the tool to the language-model tool registry, and that a subsequent invocation sends tools/call to the same live app instance rather than re-invoking the originating MCP server tool.
- **Trace:**

  > Established so far: `_handleInitialize` in chatMcpAppModel.ts discards `appCapabilities.tools`; hostCapabilities never advertise app-tool support; no tools/list or host-initiated tools/call exists. Uncertainty starts at design: whether app-provided tools become entries in the same registry as MCP server tools (mcpLanguageModelToolContribution.ts) or a separate ephemeral pool tied to the chatMcpAppModel instance, how their lifetime (tied to the View staying alive) is represented, and how a later agent turn is routed to the existing instance instead of spawning a new one.
- **Open decisions:**
  - Should app-registered tools be surfaced through the same language-model tool registry as server tools, or a separate ephemeral mechanism scoped to the live View?
  - How long does an app-provided tool remain callable — only while the View/webview is alive, or does it need explicit teardown/registration semantics?
  - When the agent wants to call an app tool again, how does VS Code identify and reuse the existing App instance instead of invoking the originating MCP server tool and creating a new View?

## Evidence

- **unused param:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts `_handleInitialize(_params: McpApps.McpUiInitializeRequest['params'])` never reads `_params.appCapabilities`, so a declared `tools` capability is silently dropped.
- **no tools capability sent:** The `hostCapabilities` object returned from `_handleInitialize` only sets `serverTools`/`serverResources`/etc. — there is no acknowledgement of app-provided `tools`, and no `tools/list` or `tools/call` case is sent host→app anywhere in the file (only `tools/call` app→host is handled at line ~450).
- **type exists, unused:** src/vs/platform/mcp/common/modelContextProtocolApps.ts defines `McpUiAppCapabilities.tools` ("App exposes MCP-style tools that the host can call") but no code in the workbench reads or acts on it — confirms this is a documented-but-unimplemented protocol capability.
- **recency:** MCP Apps support is very new (Insiders-only, protocol version 2026-01-26); git log on both files shows no unrelated recent work touching this capability.
