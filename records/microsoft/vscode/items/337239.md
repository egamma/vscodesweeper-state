# Issue #337239 — Agent host applies the CAPI proxy to all Copilot CLI requests,   breaking MCP to PAC-DIRECT hosts

[https://github.com/microsoft/vscode/issues/337239](https://github.com/microsoft/vscode/issues/337239)

## Summary

Well-diagnosed, source-confirmed bug: on the PAC-discovery fallback path, `CopilotAgent._resolveProxyForSdk()` resolves a proxy for a single external URL (the CAPI endpoint) and `_createCopilotCliEnvironment()` injects that one value as process-wide `HTTP_PROXY`/`HTTPS_PROXY` for the whole Copilot CLI subprocess, which breaks MCP servers a PAC script routes `DIRECT`. This is real and unrelated to #333614's fix (which only covers the explicit `http.noProxy`/inherited `no_proxy` case, not PAC's per-host semantics).

## Change summary

The agent host collapses a PAC script's per-host proxy decision into one process-wide `HTTP_PROXY` value for the Copilot CLI subprocess, so PAC-routed-DIRECT internal MCP hosts get incorrectly proxied and fail.

## Best solution

Route the Copilot CLI's outbound HTTP through a per-request PAC-aware mechanism (e.g. a local forwarding/loopback proxy, similar in spirit to the existing `loopbackProxyServer.ts` infrastructure used elsewhere in agentHost) instead of collapsing PAC resolution to one static env-var value; the current single-URL-resolve-then-broadcast design in `_resolveProxyForSdk`/`_createCopilotCliEnvironment` is fundamentally incompatible with PAC once `http.proxy`/`http.noProxy`/env proxy vars are all absent.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentHostProxyResolver.ts`, `src/vs/platform/agentHost/node/shared/loopbackProxyServer.ts`
- **Validation:** A reproduction/regression check that a PAC returning DIRECT for one host and a proxy for another results in the CLI subprocess reaching the DIRECT host without going through the resolved proxy (e.g. via a fake PAC + mock upstream in the proxy resolver tests).
- **Behavior:**

  > When OS proxy configuration comes from a PAC script (no `http.proxy`, no `http.noProxy`, no inherited proxy env vars) and no fixed host-level answer applies, the Copilot CLI subprocess's outbound requests should honor the PAC's per-host DIRECT/PROXY answer for each destination — including MCP servers on hosts the PAC maps to DIRECT — rather than having every request forced through the proxy resolved for one external endpoint. Acceptance: a PAC-DIRECT-mapped MCP host is reachable directly from the CLI subprocess while other (proxy-required) traffic still uses the resolved proxy.
- **Trace:**

  > `_resolveProxyForSdk()` in src/vs/platform/agentHost/node/copilot/copilotAgent.ts (~line 5317) resolves a proxy for exactly one URL (the CAPI endpoint) via `IAgentHostProxyResolver.resolveProxy(url)` (single-URL API, src/vs/platform/agentHost/node/agentHostProxyResolver.ts:50), and `_createCopilotCliEnvironment()` (~line 5285) then broadcasts that one value as `HTTP_PROXY`/`HTTPS_PROXY` for the whole subprocess environment; `_readNoProxy()` (~line 5273) only contributes a flat NO_PROXY list from explicit config or inherited env vars, never PAC output. The boundary: do not touch the explicit `http.proxy`/`http.noProxy` paths (already correct per #333614) or the resolver's Electron/session proxy-lookup internals — only the PAC-discovery fallback's env-var-broadcast strategy is in scope. Where the uncertainty starts: whether the fix should route CLI subprocess traffic through a local per-request PAC-aware forwarding proxy (leveraging the existing loopback-proxy pattern in src/vs/platform/agentHost/node/shared/loopbackProxyServer.ts), or take a narrower mitigation (e.g. skip the process-wide proxy injection entirely when the source is PAC-only and no static host list is derivable) — a maintainer needs to weigh subprocess complexity/perf against the design.
- **Open decisions:**
  - Should PAC-derived proxy decisions be honored per-request via a local forwarding proxy (adding a persistent loopback proxy in front of the CLI subprocess), or should the host instead just avoid injecting a static proxy at all when the only signal is PAC (accepting the CLI falls back to its own OS proxy discovery, if any)?
  - If a local forwarding proxy is chosen, should it apply to all Copilot CLI traffic (CAPI + MCP) uniformly, or only to MCP server connections since CAPI already works correctly today?
