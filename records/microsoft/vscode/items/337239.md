# Issue #337239 — Agent host applies the CAPI proxy to all Copilot CLI requests,   breaking MCP to PAC-DIRECT hosts

[https://github.com/microsoft/vscode/issues/337239](https://github.com/microsoft/vscode/issues/337239)

## Summary

The defect remains on current main: Agent Host resolves the system proxy for one CAPI URL and exports that result process-wide, so the Copilot CLI cannot honor a PAC file's different DIRECT decision for an MCP host. This is distinct from the explicit NO_PROXY case fixed by https://github.com/microsoft/vscode/pull/333614.

## Change summary

Preserve per-destination PAC routing when Copilot CLI sessions access CAPI and streamable-HTTP MCP hosts with different proxy decisions.

## Best solution

Keep CAPI connectivity through the PAC-selected proxy while allowing MCP and other subprocess requests to follow their own per-URL PAC decisions; do not collapse one URL's resolved proxy into process-wide routing. The implementation should cover every runtime-owned HTTP client rather than special-casing only the reported hostname.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentHostProxyResolver.ts`, `src/vs/platform/agentHost/common/agentHostClientProxyChannel.ts`, `src/vs/platform/agentHost/test/node/copilotAgent.test.ts`
- **Validation:** Add a regression scenario with a URL-sensitive PAC/proxy resolver that returns a proxy for CAPI and DIRECT for a streamable-HTTP MCP URL; verify CAPI remains reachable through the proxy, the MCP connection is direct, and explicit `http.proxy`, `http.noProxy`, and inherited proxy-environment precedence remain unchanged.
- **Behavior:**

  > With only OS PAC configuration present, each Copilot CLI HTTP destination must follow the PAC decision for that destination. A CAPI URL that resolves to PROXY must remain reachable through that proxy, while an MCP URL that resolves to DIRECT must connect directly without requiring users to duplicate PAC rules in `http.noProxy`. Explicit VS Code proxy settings and inherited proxy environment variables must retain their existing precedence. Acceptance requires a URL-sensitive regression scenario proving the proxied CAPI and direct MCP requests both succeed.
- **Trace:**

  > Current main resolves only the CAPI URL in `CopilotAgent._resolveProxyForSdk` at src/vs/platform/agentHost/node/copilot/copilotAgent.ts, then `_createCopilotCliEnvironment` exports that result as process-wide `HTTP_PROXY`/`HTTPS_PROXY`. The host proxy bridge in src/vs/platform/agentHost/common/agentHostClientProxyChannel.ts and src/vs/platform/agentHost/node/agentHostProxyResolver.ts retains per-URL PAC semantics, but that information is collapsed before the CLI subprocess makes CAPI, MCP, and other requests. https://github.com/microsoft/vscode/pull/333614 only supplies static NO_PROXY data and therefore cannot represent dynamic PAC decisions. Preserve the established precedence for explicit `http.proxy`, `http.noProxy`, and inherited environment values; do not regress CAPI access in PAC-only environments or narrow the solution to one MCP hostname. The uncertainty starts at the child-runtime boundary: the current environment contract cannot express a per-request PAC function.
- **Open decisions:**
  - Should PAC-only mode gain a per-request proxy-resolution path inside the Copilot CLI/runtime, or should Agent Host stop exporting the resolved CAPI proxy globally even though that can remove CAPI connectivity where the PAC requires a proxy?
  - Must the selected per-request behavior cover every HTTP destination owned by the Copilot CLI subprocess, or only configured MCP transports in addition to CAPI?

## Evidence

- **current source:** On current main, src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5599-5628 calls `_proxyResolver.resolveProxy(capiUrl)` for a single CAPI URL, while lines 5567-5586 copy that result into global `HTTP_PROXY` and `HTTPS_PROXY` values for the Copilot CLI subprocess.
- **PAC-capable host bridge:** src/vs/platform/agentHost/common/agentHostClientProxyChannel.ts documents that `resolveProxy(url)` obtains the Electron session's per-URL PAC result; src/vs/platform/agentHost/node/agentHostProxyResolver.ts:108-109 exposes that URL-specific lookup. The loss of per-destination semantics occurs when the CAPI result is converted to subprocess environment variables.
- **confirmed reproduction:** The reporter supplied a PAC where CAPI resolves to PROXY and the internal MCP host resolves to DIRECT, showed the injected child environment, and isolated the failure with three curl comparisons: the globally injected proxy times out, while NO_PROXY or an internal-capable proxy succeeds.
- **related fix boundary:** https://github.com/microsoft/vscode/pull/333614, merged as 9f9213b45855b326a6cd8427fe4a34945ea2f625, forwards explicit `http.noProxy` and inherited NO_PROXY values but intentionally leaves OS/PAC discovery as the fallback. PAC supplies a per-URL function rather than a static bypass list, so that fix does not cover this report.
