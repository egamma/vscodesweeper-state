# Issue #337239 — Agent host applies the CAPI proxy to all Copilot CLI requests,   breaking MCP to PAC-DIRECT hosts

[https://github.com/microsoft/vscode/issues/337239](https://github.com/microsoft/vscode/issues/337239)

## Summary

Confirmed on current main: the agent host resolves a single process-wide proxy for the Copilot CLI subprocess from one CAPI URL and injects it as HTTP_PROXY/HTTPS_PROXY, so a PAC script's per-host DIRECT answers for internal MCP hosts are never honored — there's no bypass list PAC can even express. This is a real, distinct remaining gap after #333614's NO_PROXY-forwarding fix, not a duplicate of it.

## Change summary

When only an OS PAC script configures the proxy (no explicit http.proxy/http.noProxy and no inherited proxy env vars), the agent host collapses PAC's per-host routing decision into one proxy value for the whole Copilot CLI subprocess, breaking direct access to internal MCP servers the PAC maps to DIRECT.

## Best solution

This needs a per-request proxy decision path for the CLI subprocess rather than a single injected HTTP_PROXY value — e.g. a local forwarding proxy inside the agent host that calls the existing per-URL `IAgentHostProxyResolver.resolveProxy(url)` (already used by `_resolveProxyForSdk`/`agentHostRequestService.ts`) for each outbound request, with HTTP_PROXY pointed at that local forwarder. That's an architectural/design choice a maintainer should weigh before implementation.
