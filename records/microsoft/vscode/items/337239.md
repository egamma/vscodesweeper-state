# Issue #337239 — Agent host applies the CAPI proxy to all Copilot CLI requests,   breaking MCP to PAC-DIRECT hosts

[https://github.com/microsoft/vscode/issues/337239](https://github.com/microsoft/vscode/issues/337239)

## Summary

Confirmed from source on main: when no explicit proxy/env config is present, the agent host resolves a single collapsed proxy for one endpoint (`_resolveProxyForSdk`, `copilotAgent.ts`) and injects it as process-wide `HTTP_PROXY`/`HTTPS_PROXY` for the whole Copilot CLI subprocess, so a PAC's per-host `DIRECT` answers for internal MCP targets are never honored. Real, well-diagnosed gap distinct from the already-fixed #333614/#326185 `http.noProxy` forwarding — no fix commit exists on main.

## Change summary

Agent host collapses PAC-based per-host proxy resolution into a single static HTTP_PROXY/HTTPS_PROXY pair for the Copilot CLI subprocess, breaking MCP connections to hosts the PAC maps to DIRECT.

## Best solution

Route the Copilot CLI's outbound HTTP through a per-request, PAC-aware mechanism instead of static env vars — e.g. a local loopback forwarding proxy (the repo already has this pattern for Claude/Codex CAPI routing in copilotSessionLauncher.ts's BYOK loopback proxy and node/shared/loopbackProxyServer.ts) that calls `IAgentHostProxyResolver.resolveProxy(url)` per destination before forwarding, rather than precomputing one proxy for `capiUrl` in `_resolveProxyForSdk`/`_createCopilotCliEnvironment`.

- **Behavior:**

  > When the OS proxy is configured via PAC (no explicit `http.proxy`/`http.noProxy`/inherited proxy env vars) and the Copilot CLI subprocess makes an HTTP request to a host the PAC maps to `DIRECT` (e.g. an internal MCP server), that request must go direct, matching the PAC's per-host answer — not through the proxy resolved for an unrelated endpoint (api.githubcopilot.com). Requests to hosts the PAC does route through a proxy should still use that proxy. Acceptance: a test exercising a PAC-like resolver with differing per-host answers shows the CLI's actual outbound connection for each host follows its own PAC answer, not a single global value.
- **Trace:**

  > `_resolveProxyForSdk` (copilotAgent.ts ~6186-6217) only calls `this._proxyResolver.resolveProxy(capiUrl)` for one URL, and `_createCopilotCliEnvironment` (~6154-6184) applies that single result as static `HTTP_PROXY`/`HTTPS_PROXY` for the whole CLI subprocess — this is the reported bug. `IAgentHostProxyResolver` (agentHostProxyResolver.ts) already supports per-URL PAC-aware resolution (`resolveProxy(url)`, `fetch()`) via `@vscode/proxy-agent`, but nothing exposes that per-host logic to the externally spawned CLI, which can only read static env vars at launch. Do not change the already-working explicit `http.proxy`/`http.noProxy`/env-var precedence paths (`_readConfiguredProxy`, `_readNoProxy`) — those are correct and covered by the prior #333614 fix; the gap is specifically the OS/PAC final-fallback branch with no bypass list. Where the uncertainty starts: whether the fix is a loopback forwarding proxy (consulted per-request, following the existing BYOK loopback pattern in copilotSessionLauncher.ts/loopbackProxyServer.ts) or some other mechanism to get per-host decisions into the subprocess.
- **Open decisions:**
  - Should the Copilot CLI's traffic be routed through a new per-request loopback forwarding proxy (consulting resolveProxy(url) per destination), or some other mechanism to carry PAC per-host decisions into an external subprocess?
  - If a loopback proxy is introduced, should it apply universally whenever a PAC/system proxy is in effect, or only as a fallback when no static http.proxy/http.noProxy is configured (preserving today's explicit-config fast path)?
  - Are there performance or security implications (every CLI request now round-tripping through the agent host) that need to be weighed against the correctness gain, especially for high-volume MCP traffic?

- **precedent pattern:** src/vs/platform/agentHost/node/shared/loopbackProxyServer.ts and copilotSessionLauncher.ts's BYOK loopback proxy show the agent host already uses local loopback proxies to route SDK traffic through host-controlled logic, which is the natural mechanism to extend to per-host PAC resolution.
