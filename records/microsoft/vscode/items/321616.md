# Issue #321616 — Accessibility: Built-in VSCode webviews fails for Name, Role, Value (Level A) SC 4.1.2 (WCAG 2.2)

[https://github.com/microsoft/vscode/issues/321616](https://github.com/microsoft/vscode/issues/321616)

## Summary

Keep open: current source still places role="document" on webview body elements, contrary to ARIA-in-HTML authoring requirements. The document semantics have an established screen-reader purpose, so addressing the conformance failure must preserve that behavior.

## Change summary

Built-in webviews fail accessibility validation because VS Code places role="document" on the body element.

## Best solution

Make the webview bootstrap and generated content conform to HTML role restrictions while preserving screen-reader browse-mode access within the surrounding application. Validate both conformance and assistive-technology behavior rather than removing document semantics indiscriminately.

## Evidence

- **Current source confirms the reported markup:** src/vs/workbench/contrib/webview/browser/pre/index.html:15 explicitly gives the bootstrap body role="document". In the same file, toContentHtml at lines 861–864 injects that role into the content body whenever the supplied HTML has no body role. This directly accounts for the checker finding reported after opening a built-in webview.
- **Normative role restriction:** https://www.w3.org/TR/html-aria/#el-body specifies that body permits no role other than generic, which itself SHOULD NOT be explicitly used. The source therefore establishes the reported authoring-conformance defect; no runtime audit or screen-reader regression was measured.
- **Established accessibility behavior:** https://github.com/microsoft/vscode/issues/132275#issuecomment-914654290 records the decision to default webviews to document semantics while permitting extension overrides. https://github.com/microsoft/vscode/issues/132275#issuecomment-915217310 confirms the resulting improvement with NVDA.
