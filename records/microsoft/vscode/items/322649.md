# Issue #322649 — Guardrail status in the Agent window

[https://github.com/microsoft/vscode/issues/322649](https://github.com/microsoft/vscode/issues/322649)

## Summary

A real Agents Window observability gap remains: current main exposes coarse session state and PR CI results, but not a unified account of required checks, advisory versus blocking outcomes, auto-fixes, and completion blockers. Route this to the Agents Window and agent-observability owners for product design.

## Change summary

Show an agent run's guardrail status, including which checks ran, their outcomes, auto-fixes, enforcement level, and anything preventing completion.

## Best solution

Define a provider-neutral guardrail-result contract and present it as a calm, accessible status summary in the Agents Window across local validation and PR CI, preserving the result after the run finishes.

## Plan brief

- **Likely files:** `src/vs/sessions/services/sessions/common/session.ts`, `src/vs/sessions/contrib/changes/browser/checksWidget.ts`, `src/vs/sessions/contrib/blockedSessions/browser/blockedSessions.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`
- **Validation:** End the plan with model and UI tests covering a run with passed, failed-blocking, failed-advisory, skipped, and auto-fixed checks, plus an Agents Window fixture verifying the same states have keyboard-accessible labels and remain inspectable after completion.
- **Behavior:**

  > While an agent runs and after it finishes, the Agents Window shows which configured guardrails ran and whether each passed, failed, was skipped, or was auto-fixed. Each result clearly states whether it is advisory or blocks completion, and an unfinished run identifies the outstanding blocker. The status must be keyboard and screen-reader accessible and must not imply that absent or unknown checks passed.
- **Trace:**

  > The shared session facade in src/vs/sessions/services/sessions/common/session.ts currently carries only coarse SessionStatus values. CIStatusWidget in src/vs/sessions/contrib/changes/browser/checksWidget.ts displays GitHub PR checks, while BlockedSessions in src/vs/sessions/contrib/blockedSessions/browser/blockedSessions.ts recognizes only user input and failing CI as blockers; no provider-neutral run-validation model connects these surfaces. Agent Host adaptation is owned under src/vs/sessions/contrib/providers/agentHost/browser/, while shared presentation must remain provider-neutral. Preserve the distinction between PR CI and agent-run validation, and do not treat missing status as success. https://github.com/microsoft/vscode/issues/302292 may inform configurable task-completion guardrails but does not replace this presentation request.
- **Open decisions:**
  - Which guardrail sources are in the initial product contract: explicitly configured local commands, agent-reported validation, PR CI, or all three?
  - Which outcomes prevent an agent from reporting completion, and may users or workspace policy choose whether a check is blocking or advisory?
  - Is guardrail status scoped per chat or aggregated per session, and how long must completed-run results remain visible?
  - How should the UI distinguish a check that did not run, a check whose status is unknown, and a check that was intentionally skipped?

## Evidence

- **current session model:** src/vs/sessions/services/sessions/common/session.ts exposes only Untitled, InProgress, NeedsInput, Completed, and Error through SessionStatus; it has no structured guardrail/check results or blocking-versus-advisory state.
- **partial existing capability:** src/vs/sessions/contrib/changes/browser/checksWidget.ts defines CIStatusWidget specifically as PR CI status and renders running, pending, failed, and successful checks. It does not cover required local checks, auto-fix outcomes, enforcement level, or why an agent cannot complete.
- **partial blocking model:** src/vs/sessions/contrib/blockedSessions/browser/blockedSessions.ts limits BlockedSessionReason to NeedsInput and FailingCI. This provides useful attention routing but cannot represent the broader guardrail lifecycle requested here.
- **related issue:** https://github.com/microsoft/vscode/issues/302292 is older and open, but asks how users configure task_complete guardrails rather than how the Agents Window reports their execution and outcomes. It is related design input, not a same-symptom canonical under the re-review duplicate rule.
- **canonical search:** The open keyword candidates concern mode drift, billing, execution scope, or custom guardrail configuration; none owns this issue's observable request for a unified guardrail-status surface.
