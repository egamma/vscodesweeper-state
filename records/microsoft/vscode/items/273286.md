# Issue #273286 — Git - Optionally use git commits with notes for agent checkpoint

[https://github.com/microsoft/vscode/issues/273286](https://github.com/microsoft/vscode/issues/273286)

## Summary

A real gap remains: current main can represent some Agent Sessions checkpoints as synthetic Git commits under private session refs, but it neither advances the user's commit graph nor attaches Git notes, and there is no option for that workflow. The request is accepted in the Backlog and has no verified canonical issue or open implementation PR, so it should remain open for design.

## Change summary

Add an opt-in checkpoint mode that records agent turns as Git commits with attached notes for visible history, provenance, and cross-agent interoperability.

## Best solution

Design an opt-in Git-backed checkpoint mode that preserves the existing restore behavior while giving users an intentional, inspectable commit-and-note history. The design should define branch behavior, note metadata, supported agent surfaces, and safe handling of pre-existing user changes before implementation.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeCheckpointServiceImpl.ts`, `extensions/copilot/src/extension/chatSessions/common/chatSessionWorktreeCheckpointService.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** The plan should end with focused Git-backed checkpoint tests using a temporary repository: with the option enabled, two completed agent turns produce the chosen commit topology and expected notes and remain restorable; with it disabled, the existing checkpoint behavior and repository branch remain unchanged.
- **Behavior:**

  > Users can explicitly opt into representing agent checkpoints through Git commits with attached provenance notes. The resulting history is inspectable with standard Git tooling, checkpoints remain restorable, and users retain control over whether that history is retained or later squashed. The default behavior must remain unchanged, and enabling the mode must not silently absorb unrelated user changes.
- **Trace:**

  > Ordinary local chat checkpoints are modeled by ChatEditingSession and ChatEditingCheckpointTimelineImpl under src/vs/workbench/contrib/chat/browser/chatEditing, where file baselines and operations support restore without writing Git history. Agent Sessions worktrees additionally use ChatSessionWorktreeCheckpointService in extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeCheckpointServiceImpl.ts: `_writeWorktreeTree` builds a temporary index, and `_createCheckpoint` creates a chained synthetic commit and places it under `refs/sessions/...`; there is no Git-notes call and these commits do not advance the user's branch. `chat.checkpoints.enabled` only controls whether checkpoints are enabled, not their persistence format. The boundary is checkpoint persistence and provenance: preserve current restore semantics and default behavior, and do not alter unrelated Git commit generation or include user-owned dirty changes without an explicit policy. https://github.com/microsoft/vscode/issues/241081 confirms that baseline automatic checkpointing is an existing capability, but it does not settle this Git-history integration.
- **Open decisions:**
  - When enabled, should each checkpoint advance the currently checked-out branch, or should it use a dedicated session branch that the user explicitly integrates later?
  - What stable Git-notes namespace and metadata contract should represent agent identity, session, turn, and assistance provenance for cross-tool interoperability?
  - Should this mode apply only to isolated Agent Sessions worktrees, or also to ordinary local Chat agent checkpoints?

## Evidence
