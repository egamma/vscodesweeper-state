# Issue #179023 — Feature Request: `enablement` property on `MessageItem`s and `QuickPickItem`s

[https://github.com/microsoft/vscode/issues/179023](https://github.com/microsoft/vscode/issues/179023)

## Summary

Keep this accepted API request open: current extension APIs still cannot display individually disabled QuickPickItems or MessageItems. A maintainer endorsed the capability; the remaining work needs a public API design decision, not a staleness close.

## Change summary

Allow extensions to keep unavailable quick-pick choices and message actions visible but disabled, including environment-dependent enablement.

## Best solution

Define an item-level enablement contract for both extension APIs, with consistent visual, keyboard, and accessibility behavior. Resolve whether extensions supply a boolean or a context expression, and establish the contract for modal message actions before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`, `src/vs/workbench/api/common/extHostMessageService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadQuickOpen.ts`, `src/vs/workbench/api/browser/mainThreadMessageService.ts`, `src/vs/platform/quickinput/common/quickInput.ts`, `src/vs/platform/quickinput/browser/quickInputList.ts`
- **Validation:** The plan should specify executable extension API and UI checks: unavailable items remain visible, cannot be accepted by mouse or keyboard, and expose their disabled state accessibly; enabled items retain existing behavior. Cover showQuickPick, createQuickPick, single and multiple selection, and modal and non-modal message actions, with explicit cancellation checks.
- **Behavior:**

  > Extensions need to show unavailable choices rather than remove them when moving between desktop, web, or virtual environments. Unavailable QuickPickItems and MessageItems should be visibly disabled and unable to invoke their associated operation, while available items retain their current behavior. Acceptance must cover mouse and keyboard interaction, accessible disabled-state communication, and existing cancellation behavior. The exact public enablement representation and modal-message contract remain to be agreed.
- **Trace:**

  > The current QuickPickItem and MessageItem declarations in src/vscode-dts/vscode.d.ts have no item-level enablement property. ExtHostQuickOpen in src/vs/workbench/api/common/extHostQuickOpen.ts explicitly serializes supported fields in both quick-pick APIs, while ExtHostMessageService and extHost.protocol.ts transfer message titles, close affordances, and handles only. MainThreadMessageService always enables notification actions and constructs modal prompt buttons without an item-level disabled state. The internal IQuickItem.disabled flag in src/vs/platform/quickinput/common/quickInput.ts is documented for multiselect checkboxes, so its presence is not evidence that this public capability exists. Preserve existing enabled-item behavior, whole-widget enablement, separators, and cancellation semantics; the modal rendering boundary needs further investigation. The maintainer endorsed the goal at https://github.com/microsoft/vscode/issues/179023#issuecomment-1494730873, and https://github.com/microsoft/vscode-azurestaticwebapps/issues/819 records a dependent use case. Uncertainty starts at the public representation and its evaluation lifetime, plus the supported semantics for modal MessageItems.
- **Open decisions:**
  - Should item enablement be an extension-supplied boolean or a context-key expression like command-manifest enablement; if expressions are supported, should visible items reevaluate when context changes?
  - Should disabled MessageItems be supported in both modal and non-modal messages, and what should cancellation do when the item marked isCloseAffordance is disabled?
