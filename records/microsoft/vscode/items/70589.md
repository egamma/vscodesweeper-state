# Issue #70589 — Settings UI is overwhelming for extensions with lots of settings

[https://github.com/microsoft/vscode/issues/70589](https://github.com/microsoft/vscode/issues/70589)

## Summary

Keep open: current main supports extension-defined ordering, categories, and advanced-setting filtering, but does not provide collapsible groups in the main settings pane. This accepted Backlog request has 25 upvotes and remaining scope not absorbed by a verified older canonical.

## Change summary

Make large extension settings collections easier to navigate through better organization and progressive disclosure, rather than requiring a separate extension settings editor.

## Best solution

Build on the existing category, ordering, and advanced-tag mechanisms in the shared Settings editor, with a maintainer-selected next step for progressive disclosure. Preserve the maintainer's direction toward a consistent built-in experience rather than treating custom-editor replacement as the agreed solution.

If collapsible main-pane groups are selected, add targeted settings-tree/editor tests proving collapse and expansion work without making matching settings inaccessible.
- **Behavior:**

  > Users configuring an extension with many settings should be able to navigate meaningful groups without scanning an undifferentiated long list. Existing category ordering and advanced-setting filtering already address part of the request and must remain available. The remaining experience should stay integrated with the shared Settings editor and preserve search, direct setting navigation, keyboard access, and value editing. A planning session must select the next observable improvement rather than assume every historical suggestion is still required.
- **Trace:**

  > The configuration contribution schema in src/vs/workbench/api/common/configurationExtensionPoint.ts already accepts category titles, category order, per-setting order, and advanced tags. Extension category construction and sorting are implemented in src/vs/workbench/contrib/preferences/browser/settingsTree.ts; advanced filtering is implemented by SettingsEditor2 in settingsEditor2.ts. The main settings tree deliberately uses NonCollapsibleObjectTreeModel, whose collapse methods return false, so collapsible main-pane groups remain absent. The maintainer direction at https://github.com/microsoft/vscode/issues/70589#issuecomment-473494230 favors improving the common GUI rather than encouraging replacement editors. Related decisions at https://github.com/microsoft/vscode/issues/115407 and https://github.com/microsoft/vscode/issues/115410 reject narrower approaches, not this entire request. https://github.com/microsoft/vscode/issues/272077 overlaps with grouping and should inform scope coordination, while https://github.com/microsoft/vscode/issues/115409 separately tracks dependent-setting visibility. No execution was performed; the uncertainty is the desired remaining product scope, not whether the existing tree supports collapse.
- **Open decisions:**
  - Should the next improvement introduce collapsible category sections in the main settings pane, or retain expanded sections and address the remaining overload through search and navigation?
  - If collapsible sections are selected, should search results always expand matching groups, and should a user's collapsed state survive clearing a search or reopening the Settings editor?
