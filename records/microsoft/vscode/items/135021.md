# Issue #135021 — Extensions keeping the extension host busy lead to disconnection

[https://github.com/microsoft/vscode/issues/135021](https://github.com/microsoft/vscode/issues/135021)

## Summary

The issue remains necessary: multiple reporters confirmed that long remote extension-host stalls trigger false disconnect/reconnect handling, and a maintainer identified the heartbeat starvation mechanism. The discussion contains later reproductions after the original reporter's apparent resolution, so there is no basis for a completed or not-reproducible close.

## Change summary

Prevent a busy remote extension host from being mistaken for a broken remote connection and disrupting port forwarding or requiring a window reload.

## Best solution

Keep transport liveness independent of the remote extension-host event loop, or otherwise distinguish an extension-host stall from an actual connection loss so the workbench can diagnose the blocking extension without entering a destructive reconnection loop. The remote-agent connection and heartbeat path should preserve genuine network-failure detection.

## Plan brief

- **Likely files:** `src/vs/workbench/services/remote/common/remoteAgentConnection.ts`, `src/vs/platform/remote/common/remoteAgentConnection.ts`, `src/vs/workbench/services/extensions/common/extensionHostManager.ts`
- **Validation:** Add or extend remote-agent connection tests with a simulated extension-host event-loop stall exceeding the heartbeat timeout: the connection must report the host as unresponsive without entering reconnection or discarding forwarding state, while a genuinely closed or unresponsive transport must still enter reconnection.
- **Behavior:**

  > When remote extension-host work blocks its event loop longer than the heartbeat threshold, VS Code must not report a network disconnection or repeatedly reconnect solely because extension-host heartbeats were delayed. The user should retain remote session state and forwarded ports, while VS Code may surface or profile the unresponsive extension host. Genuine socket loss and unreachable remote hosts must continue to trigger reconnection.
- **Trace:**

  > The maintainer diagnosis in comment 24 establishes the failure path: the remote extension-host connection carries a 5-second heartbeat on the same event loop as extensions, and 20 seconds without traffic is interpreted by the UI as disconnection. Large-file operations and extension activity can starve that event loop, so the remote-agent connection enters reconnection even though the management connection and terminal may remain usable. Investigation should trace heartbeat timeout and reconnection handling from src/vs/platform/remote/common/remoteAgentConnection.ts and src/vs/workbench/services/remote/common/remoteAgentConnection.ts into extension-host lifecycle handling in src/vs/workbench/services/extensions/common/extensionHostManager.ts. The boundary is genuine transport failure detection: do not weaken recovery when the socket is actually closed or both remote channels are unavailable. Extension bisect work tracked by https://github.com/microsoft/vscode/issues/112473 and https://github.com/microsoft/vscode/issues/113568 is diagnostic support, not the connection-liveness fix.
- **Open decisions:**
  - Should liveness for the remote extension-host process move to a channel or process that cannot be blocked by extension JavaScript, or should the workbench use the independent management connection to classify extension-host stalls?
  - What user-facing state should replace the reconnect notification when transport remains healthy but the remote extension host is unresponsive?
  - Which remote session resources, especially forwarded ports and terminals, must remain intact while recovering or restarting only the stalled extension host?

## Evidence

- **confirmed root cause:** In comment 24, a VS Code maintainer explains that heartbeats are expected every 5 seconds and that a remotely executing extension blocking the extension-host event loop for 20 seconds prevents heartbeat transmission, causing the UI to enter the reconnection loop.
- **independent reproductions:** Comments 14, 15, 22, and 28 give concrete triggers involving large-file operations; comment 28 reproduced a reconnect loop on VS Code 1.60.0 with all other extensions disabled while permanently deleting a roughly 110 MB file.
- **user impact:** The reporter states that prolonged episodes can require reloading the window and lose UI state and terminal sessions; comment 5 also confirms that forwarded ports are lost during the false reconnection.
- **not resolved by earlier report:** Although the original reporter said the phantom disconnects disappeared in early 2020, later comments through November 2021 report continuing disconnect loops, including a core large-file operation with other extensions disabled.
- **related but separate work:** https://github.com/microsoft/vscode/issues/112473 and https://github.com/microsoft/vscode/issues/113568 concern extension bisect in remote windows; they improve diagnosis but do not address heartbeat starvation or false reconnection itself.
