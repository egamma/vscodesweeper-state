# Issue #135021 — Extensions keeping the extension host busy lead to disconnection

[https://github.com/microsoft/vscode/issues/135021](https://github.com/microsoft/vscode/issues/135021)

## Summary

The discussion establishes a core remote-extension-host failure mode: event-loop stalls suppress heartbeats and trigger a false reconnection loop. This remains a valid, broadly supported Remote Development bug and should be moved to the VS Code team's Remote Development tracker rather than closed.

## Change summary

Prevent remote extension-host event-loop stalls from being misclassified as SSH disconnections that disrupt ports, terminals, and window state.

## Best solution

Move the issue to https://github.com/microsoft/vscode-remote-release and retain its reproductions and reactions. The remote connection design should distinguish an extension-host responsiveness failure from transport loss, preserve the independent management connection, and identify or profile the blocking extension without tearing down healthy remote state.

## Plan brief

- **Likely files:** `src/vs/workbench/services/remote/common/remoteAgentConnection.ts`, `src/vs/workbench/services/extensions/common/remoteExtensionHost.ts`, `src/vs/platform/remote/common/remoteAgentConnection.ts`
- **Validation:** Exercise a Remote-SSH session with a test remote extension that blocks the extension-host event loop for more than 20 seconds; verify the UI reports extension-host unresponsiveness without discarding healthy management state or forwarded ports, then resumes normally when the event loop recovers, while a genuinely severed SSH connection still enters reconnection.
- **Behavior:**

  > When a remote extension blocks the remote extension-host event loop long enough to miss heartbeats, VS Code must not present that condition as an ordinary SSH transport disconnection or repeatedly rebuild otherwise healthy remote state. The UI should distinguish extension-host unresponsiveness from actual connection loss, preserve forwarded ports and terminal/window state where the management connection remains healthy, and recover when the extension host responds again. Genuine transport loss must continue to trigger reconnection.
- **Trace:**

  > The issue discussion identifies two remote connections: a management connection and a remote extension-host connection, each monitored by heartbeats. A 20-second event-loop stall in the remote extension host prevents its heartbeat sender from running, so the local side interprets silence as transport loss and enters reconnection even though the management path can remain usable. Reproductions involving large-file operations and heavy I/O show the same externally visible loop, but the report does not establish that every reproduction has one identical blocker. Keep the boundary on connection-health classification, state preservation, and blocker diagnostics; do not weaken detection of genuinely broken sockets. The issue belongs in https://github.com/microsoft/vscode-remote-release.
- **Open decisions:**
  - What user-visible state should VS Code enter when only the remote extension-host heartbeat stops but the management connection remains healthy: a recoverable unresponsive-extension-host state or the existing full reconnection state?
  - After the remote extension-host event loop recovers, should VS Code resume the existing session automatically, or require an explicit reload after a defined timeout?

## Evidence

- **confirmed root cause:** Maintainer alexdima explains that the remote extension-host and management connections use 5-second heartbeats and enter reconnection after 20 seconds; a remotely executing extension that blocks the extension-host event loop prevents heartbeats and falsely triggers reconnection.
- **independent reproductions:** Multiple commenters reproduced the loop under heavy work, including opening 57 MB/1.5-million-line XML, repeatedly opening a 1.6 MB/170k-line log, and permanently deleting a roughly 110 MB remote file even with other extensions disabled.
- **user impact:** The reporter states that reconnecting loses forwarded ports and can eventually require a window reload that loses UI state and terminal sessions; a later team report says the issue forced developers back to local VS Code.
- **ownership:** Remote-SSH is a VS Code-team-owned extension whose issues are tracked in https://github.com/microsoft/vscode-remote-release, so policy calls for transfer rather than *caused-by-extension closure.
