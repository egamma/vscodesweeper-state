# Issue #135021 — Extensions keeping the extension host busy lead to disconnection

[https://github.com/microsoft/vscode/issues/135021](https://github.com/microsoft/vscode/issues/135021)

## Summary

The core architectural issue — a busy remote extension host blocking keepalive responses, causing the local side to false-timeout — is still present on main despite significant mitigation work (longer timeouts, keepalive messages, LoadEstimator). With 33 upvotes, this remains a real and impactful bug worth keeping open.

## Change summary

Extensions blocking the remote extension host event loop cause false disconnection notifications because the extension host process can't respond to protocol keepalive messages in time.

## Best solution

The raw socket is handed to the extension host child process (via `extensionHostProcess.send(msg, socket)` in `src/vs/server/node/extensionHostConnection.ts`), so protocol-level keepalives run on the same event loop extensions block. A structural fix would separate the protocol/keepalive handling from the extension host's event loop — e.g., keep the socket in the server process and proxy messages, or run the protocol layer on a worker thread within the extension host. The `LoadEstimator` mitigation at lines 1154 and 1201 of `src/vs/base/parts/ipc/common/ipc.net.ts` only suppresses timeouts when the *local* event loop is busy, which doesn't help when the *remote* side is the one blocked.

## Evidence

- **socket handed to ext host process:** In src/vs/server/node/extensionHostConnection.ts line 202, the raw socket is sent to the extension host child process via `extensionHostProcess.send(msg, socket)`. Protocol keepalive handling therefore runs on the same event loop that extensions can block.
- **LoadEstimator is local-only mitigation:** src/vs/base/parts/ipc/common/ipc.net.ts lines 1154 and 1201: before firing a socket timeout, the code checks `this._loadEstimator.hasHighLoad()`. But this only detects load on the side running the check — the local renderer has low load, so it still fires the timeout when the remote extension host is busy.
- **timeout is 20 seconds:** ProtocolConstants.TimeoutTime is 20s (line 300 of ipc.net.ts). Extensions doing heavy tokenization (large files) or language server work can easily block the Node.js event loop for >20s.
- **significant mitigations since 2019:** Multiple commits improved resilience: f148bc6ecabd (doubled timeouts, Oct 2019), b041f460ce698 (show dialog only after 40-50s, Jan 2021), 67473763597 (keepalive every 5s, Aug 2022), c8cdcb16dc3 (dead-connection detection via keepalive, Apr 2026). These reduce false positives but do not eliminate them.
- **community impact:** 33 upvotes on the issue body; multiple reporters confirm the problem across SSH, WSL, and local VM scenarios.
