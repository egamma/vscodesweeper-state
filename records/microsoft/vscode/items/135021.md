# Issue #135021 — Extensions keeping the extension host busy lead to disconnection

[https://github.com/microsoft/vscode/issues/135021](https://github.com/microsoft/vscode/issues/135021)

## Summary

The underlying false-disconnection path remains possible on current main: a busy remote extension host owns the extension-host socket and can stop servicing protocol traffic long enough for the local client to enter reconnection. The accepted bug has substantial confirmation and no older open issue with the same observable symptom was found.

## Change summary

Prevent a busy remote extension host event loop from being mistaken for a broken remote connection, which currently causes reconnection prompts, lost port forwarding, and eventual reloads.

## Best solution

Separate transport liveness from remote extension-host responsiveness, preserving the connection while the extension host is busy and reporting unresponsiveness distinctly; genuine dead sockets must continue to trigger reconnection.

## Plan brief

- **Likely files:** `src/vs/base/parts/ipc/common/ipc.net.ts`, `src/vs/platform/remote/common/remoteAgentConnection.ts`, `src/vs/server/node/extensionHostConnection.ts`, `src/vs/base/parts/ipc/test/node/ipc.net.test.ts`
- **Validation:** Add a deterministic remote-connection or IPC test that stalls extension-host-side protocol processing beyond ProtocolConstants.TimeoutTime while the underlying transport remains alive and asserts that no ConnectionLostEvent is emitted; retain coverage proving that a genuinely dead peer still times out and reconnects.
- **Behavior:**

  > A remote extension that blocks the extension-host event loop for longer than the heartbeat timeout must not make VS Code report that the network connection was lost or discard forwarded ports. VS Code may report the extension host as unresponsive, but the existing remote session should recover when the event loop resumes. A genuinely closed or unreachable transport must continue to enter the reconnection flow.
- **Trace:**

  > PersistentProtocol in src/vs/base/parts/ipc/common/ipc.net.ts emits onSocketTimeout after receiving no data for ProtocolConstants.TimeoutTime. PersistentConnection in src/vs/platform/remote/common/remoteAgentConnection.ts handles that event by immediately entering _beginReconnecting. On the remote side, ExtensionHostConnection._sendSocketToExtensionHost in src/vs/server/node/extensionHostConnection.ts transfers the client socket to the forked extension-host process, tying protocol progress to the event loop that extensions can block. Commit https://github.com/microsoft/vscode/commit/45c70c29e572de3e9ca24d993f0616fd31f05029 protects against a busy event loop on the process evaluating its own timeout, but it does not communicate remote extension-host load to the local client. Preserve genuine dead-peer detection and management-connection behavior; unrelated large-file performance and individual extension defects are outside this issue's boundary.
- **Open decisions:**
  - When the management connection remains healthy but the remote extension-host channel is unresponsive, should VS Code wait indefinitely for recovery or surface a distinct extension-host-unresponsive state with a user-controlled restart action?

## Evidence

- **confirmed root cause:** Maintainer analysis at https://github.com/microsoft/vscode/issues/135021#issuecomment-725403898 explains that the remote extension host connection misses its 5-second heartbeats when an extension blocks the event loop for 20 seconds, causing the UI to enter reconnection.
- **current timeout path:** On current main, src/vs/base/parts/ipc/common/ipc.net.ts still emits an onSocketTimeout event after ProtocolConstants.TimeoutTime without incoming data, and src/vs/platform/remote/common/remoteAgentConnection.ts:597-600 responds by calling _beginReconnecting().
- **extension-host ownership:** src/vs/server/node/extensionHostConnection.ts passes the remote client socket directly to the forked extension-host process in _sendSocketToExtensionHost, so extension-host event-loop starvation still prevents that connection from servicing protocol traffic.
- **related mitigation is incomplete:** Commit https://github.com/microsoft/vscode/commit/45c70c29e572de3e9ca24d993f0616fd31f05029 added a local LoadEstimator for blocked-event-loop timeouts and fixed https://github.com/microsoft/vscode/issues/83672, but the local client's estimator cannot observe load in the separate remote extension-host process.
- **user impact:** Multiple reporters confirmed the behavior through 2021; the original reporter described lost forwarded ports and eventual forced reloads, while later reports tied the loop to large-file operations and heavy remote I/O.
- **canonical search:** The older https://github.com/microsoft/vscode-remote-release/issues/246 is closed and did not establish this extension-host starvation root cause, so it cannot serve as a duplicate canonical under the re-review rules.
