# Issue #130217 — Consolidate zindex for floating elements in the workbench

[https://github.com/microsoft/vscode/issues/130217](https://github.com/microsoft/vscode/issues/130217)

## Summary

The consolidation remains incomplete on current main: major floating surfaces still use independently maintained numeric z-index values, with only partial relative-layering infrastructure. This should remain open as layout debt and be planned around an explicit overlay precedence contract.

## Change summary

Establish a shared, documented layering scheme for floating workbench elements so independently maintained widgets do not overlap incorrectly.

## Best solution

Define and enforce a small set of semantic workbench overlay tiers, including clear precedence among context views, quick input, dialogs, notifications, hovers, and transient toolbars. Component-internal layering should remain local unless it participates in the global workbench stack.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/contextview/contextview.ts`, `src/vs/base/browser/overlayLayoutElement.ts`, `src/vs/base/browser/ui/dialog/dialog.css`, `src/vs/workbench/browser/parts/notifications/media/notificationsCenter.css`, `src/vs/workbench/contrib/debug/browser/media/debugToolBar.css`
- **Validation:** Add a browser-level overlay-ordering test that displays representative context view, dialog, notification, hover, quick-input, and toolbar surfaces together and asserts their agreed computed stacking order; retain the existing context-view layering tests.
- **Behavior:**

  > Floating workbench elements must follow a documented and predictable precedence when displayed concurrently. Context menus, quick input, modal dialogs, notifications, hovers, and transient toolbars must not obscure a surface that is defined to be above them. Acceptance requires a representative automated ordering test and preservation of valid component-local layering.
- **Trace:**

  > Current main has no shared workbench-wide overlay tier definition. ContextView in src/vs/base/browser/ui/contextview/contextview.ts starts at 2575 and supports numeric layer offsets; OverlayLayoutElement in src/vs/base/browser/overlayLayoutElement.ts derives a layer relative to the nearest explicitly layered ancestor. Other surfaces retain unrelated CSS literals, including 2520 for the debug toolbar, 2545 for notifications, 2575 for dialogs, and 10000 for pane/editor overlays. The trace therefore confirms the debt but not a bounded migration path. Keep local intra-component z-index values out of scope unless they interact with the cross-workbench overlay stack. The newer https://github.com/microsoft/vscode/issues/229941 is related editor-only work, not a canonical duplicate.
- **Open decisions:**
  - What user-visible precedence should apply when context views, quick input, modal dialogs, notifications, workbench hovers, and transient toolbars are simultaneously visible?
  - Which floating surfaces are allowed to escape their component stacking context and participate in the global workbench overlay order?

## Evidence

- **current source:** Current main still assigns global-looking layers independently: src/vs/workbench/contrib/debug/browser/media/debugToolBar.css uses 2520, notificationsCenter.css and notificationsToasts.css use 2545, src/vs/base/browser/ui/dialog/dialog.css uses 2575, and paneview.css plus messageController.css use 10000.
- **partial infrastructure:** src/vs/base/browser/ui/contextview/contextview.ts computes context-view layering as `2575 + (delegate.layer ?? 0)`, while src/vs/base/browser/overlayLayoutElement.ts only places an anchored overlay one level above its nearest explicitly layered ancestor. Neither provides a shared workbench-wide tier registry.
- **continuing debt:** The newer open https://github.com/microsoft/vscode/issues/229941 separately tracks editor-local z-index challenges, confirming that layering conflicts remain, but it is newer and narrower than this workbench-wide issue and therefore is not a canonical duplicate under the re-review rule.
