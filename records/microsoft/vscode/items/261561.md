# Issue #261561 — Git extension is very confused by `remote = .` and `merge = [anything not a branch]`

[https://github.com/microsoft/vscode/issues/261561](https://github.com/microsoft/vscode/issues/261561)

## Summary

The built-in Git extension still assumes upstreams are branches, corrupting valid non-branch refs and causing the Source Control Graph to return no history. Keep this report open; the related graph report is newer and cannot replace it under the re-review rules.

## Change summary

Display Git history correctly when a branch tracks a non-branch ref through remote = .

## Best solution

Resolve upstream references without assuming refs/heads/, while preserving existing branch-tracking, pull/push, and public Git API behavior. Establish a compatible representation of non-branch upstreams before changing the shared upstream contract.

Add executable regression coverage for upstream parsing and graph reference resolution.
- **Behavior:**

  > A valid local non-branch upstream must not make the Source Control Graph lose repository history. For main tracking FOO through remote = ., with main one commit ahead, the graph should show the two commits and resolve the upstream to the existing FOO ref. Existing local-branch and conventional remote tracking must continue working. The example needs an explicit branch.main.remote = . assignment; the command printed in the report omits that value.
- **Trace:**

  > Repository.getBranch in extensions/git/src/git.ts reads upstream:remoteref but strips eleven characters regardless of its prefix, making FOO an empty upstream name. getHEADRef and GitHistoryProvider in extensions/git/src/historyProvider.ts then reconstruct refs/heads/ for a local upstream; graph history passes this invalid reference to git log and returns an empty result after failure. The public UpstreamRef in extensions/git/src/api/git.d.ts exposes name without an exact ref identity, and pull methods in extensions/git/src/repository.ts use that same name as a remote-side argument. Preserve existing remote-side naming and ordinary branch behavior; changing only the substring operation does not address the downstream local-branch assumption. The uncertainty is the compatible public representation of arbitrary upstream refs and its adoption by consumers, not whether the reported graph should work. https://github.com/microsoft/vscode/issues/335470 supplies a related mirror-refspec case; https://github.com/microsoft/vscode/issues/70136 documents the distinct tracked-versus-tracking naming problem.
- **Open decisions:**
  - Should API version 1 preserve UpstreamRef.name's existing remote-side branch semantics and expose exact upstream identity separately, or should arbitrary refs be represented through a revised, versioned public contract?
