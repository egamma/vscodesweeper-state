# Issue #290762 — Custom Agents: Models in defined in custom agent do not lead to different models showing in models picker, should they?

[https://github.com/microsoft/vscode/issues/290762](https://github.com/microsoft/vscode/issues/290762)

## Summary

Keep open: current source confirms that the Agents Window can display the session's previous model after selecting a custom agent whose preferred model is applied through the chat-input path. The original question about whether an agent's model list is a preference list or a picker allowlist also remains an unresolved product decision, and this team-authored issue is protected from a judgment close.

## Change summary

Make custom-agent model selection and the model-picker state agree across Chat and the Agents Window, while defining whether declared models constrain or merely initialize the picker.

## Best solution

Use one authoritative effective-model selection when an agent is selected so the Agents Window picker immediately reflects the first available declared model, including fallback past hidden models. A maintainer should first decide whether the agent's model list also filters manual picker choices or remains an ordered preference list.

- **Validation:** Add a focused Agents Window test that selects a custom agent with an ordered model list and verifies that the displayed session model immediately becomes the first available declared model, then hides that model and verifies fallback to the next declared model; include the maintainer-selected picker-catalog behavior in the same acceptance test.
- **Behavior:**

  > Selecting a custom agent in the Agents Window must immediately make the visible model selection match the model that will execute, as it does in ordinary Chat. For an ordered model list, the first available declared model is selected; if it is hidden or unavailable, the next available declared model is selected. The picker must never continue displaying a previous model while requests run with the agent-selected model. Whether non-declared models remain available for manual selection is the product decision the plan must resolve.
- **Trace:**

  > AgentHostAgentPickerContribution in src/vs/sessions/contrib/providers/agentHost/browser/agentHostAgentPicker.ts sends the selected agent through `provider.setAgent` and separately synchronizes ChatInputPart's mode. ChatInputPart observes `mode.model` and applies the first matching model, but the Sessions ModelPicker reads SessionModelSelection, which follows `session.modelId`. BaseAgentHostSessionsProvider.setAgent preserves the existing chat model while changing the agent, leaving these authorities able to disagree. Its getModelsSnapshot method also exposes the full visible session model pool rather than the selected agent's declared list. Preserve request routing, model-visibility settings, and the documented ordered fallback behavior; the plan starts at the unresolved picker-catalog semantics.
- **Open decisions:**
  - Does a custom agent's `model` list only choose the initial/effective model while leaving the full compatible catalog available for manual override, or is it an allowlist that restricts the model picker to the declared entries?
