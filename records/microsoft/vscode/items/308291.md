# Issue #308291 — Agents app: When I get an error notification in the app, I can't tell which session it belongs to or whether this is blocking something from proceeding.

[https://github.com/microsoft/vscode/issues/308291](https://github.com/microsoft/vscode/issues/308291)

## Summary

Keep open: current in-app error producers still omit session context, while the existing session-aware native notifications cover a different surface. The maintainer discussion explicitly separates this remaining UX request from the possibly fixed MCP error that originally exposed it.

## Change summary

Make Agents Window error notifications identify their affected session and explain whether user action is required for work to proceed.

## Best solution

Provide consistent session attribution and actionable impact information for session-related in-app errors, with navigation when an affected session exists. Establish how shared MCP failures are presented without incorrectly attributing them to whichever session happens to be active.

Separately exercise an MCP startup failure while the chat can still proceed without that server, and verify it is not described as a blocked session. Cover the agreed background-failure payload in the sessionsManagementService unit suite and verify keyboard and accessible notification content.
- **Behavior:**

  > Users receiving a session-related error in the Agents Window should be able to determine which session or operation is affected and whether action is necessary for it to proceed. Expanding a notification must provide useful context rather than only an error code or component name. Context must remain correct when another session is active. An optional MCP failure must not imply that the entire conversation is blocked, and errors without an owning session must not invent one.
- **Trace:**

  > SessionsManagementService in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts catches background request failures while retaining the originating session, but its notificationService.error call sends only a generic operation description and error text. McpServer.showInteractiveError in src/vs/workbench/contrib/mcp/common/mcpServer.ts has server and connection context, not an established session-attribution contract. INotification in src/vs/platform/notification/common/notification.ts already supports optional source and actions; generic expansion does not infer missing context. SessionsWindowNotifier already provides session titles and navigation for native OS status toasts, which is separate from the reported in-app surface. Preserve that existing native behavior and shared MCP semantics; never infer ownership from the active session. The uncertainty is the product contract for errors affecting multiple sessions and for communicating partial versus session-blocking failures. https://github.com/microsoft/vscode/issues/331915 is a related, narrower automation-navigation request, not a duplicate canonical.
- **Open decisions:**
  - When an MCP server failure affects multiple sessions or has no unique session owner, should the notification identify the shared server/workspace, enumerate affected sessions, or appear separately within each affected session?
  - What minimum context should every session-related in-app error expose: a session name and operation-impact explanation, or those details plus a navigation action whenever the session can be opened?
