# Issue #339496 — Agents window: Claude Agent SDK is never downloaded for sessions on a remote SSH host (download offer is local-only), Claude target silently does nothing

[https://github.com/microsoft/vscode/issues/339496](https://github.com/microsoft/vscode/issues/339496)

## Summary

Traced in the current source and confirmed: the Claude Agent SDK download-offer banner is deliberately scoped to the window's ambient/local agent-host session type only, and nothing equivalent exists for remote SSH agent-host connections, so a remote Claude session with no SDK cached can never leave `notDownloaded`.

## Change summary

On a remote SSH Agent Host target, the Claude SDK download offer never appears and nothing triggers a lazy download, so Claude silently fails to start.

## Best solution

Extend the SDK setup/download funnel (banner + `AgentSdkSetupService`/`requestDownload`) to cover remote agent-host connections, not just the ambient host — or, if remote Claude harness support is intentionally out of scope for now, surface an explicit message instead of silently swallowing Enter.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSdkSetupNotification.ts`, `src/vs/workbench/services/agentHost/browser/agentSdkSetupService.ts`, `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts`, `src/vs/platform/agentHost/common/agentHostConnectionsService.ts`
- **Validation:** A test asserting that for a remote-scoped Claude session type (e.g. `remote-<authority>-claude`) with the SDK `notDownloaded`, either the setup banner is shown and its download action reaches the correct remote connection's AgentSdkSetupChannel, or an explicit unsupported-remote message is surfaced instead of a silent no-op.
- **Behavior:**

  > A Claude session created against a remote SSH Agent Host whose SDK has never been downloaded should either (a) offer the same 'Download the Claude Agent' banner as a local session, with the download request reaching that specific remote connection, or (b) clearly tell the user remote Claude isn't supported yet instead of letting Enter do nothing. Model picker should populate once the SDK is present and a native/BYOK account is detected.
- **Trace:**

  > The banner in agentHostSdkSetupNotification.ts filters strictly on LOCAL_AGENT_HOST_SCHEME_PREFIX-derived session types (agentSdkSetupSessionType), and AgentSdkSetupService only subscribes to the single ambient IAgentHostService.rootState — neither has any notion of the separate remote agent-host connections tracked by agentHostConnectionsService.ts/agentHostSessionType.ts. On the provider side, claudeAgent.ts's _ensureAuthenticated throws AHP_AUTH_REQUIRED for the proxy-fallback path without ever calling ensureAvailable(); only the setup channel's explicit download-request command (never sent for remote session types) calls it. Do not change the ambient/local banner behavior or the proxy-vs-native transport selection logic — the gap is purely in wiring the setup funnel to remote connections (or deciding not to support it there).
- **Open decisions:**
  - Should the SDK download-offer banner and funnel be generalized to work per remote connection (with per-connection UI/state), or is remote lazy-download handled without any banner (e.g. auto-download on first session create)?
  - If remote Claude harness support is not planned soon, should Session Target or the chat input show an explicit 'not supported on remote hosts yet' message instead of silently failing?
  - Does this generalization apply only to Claude, or to every agent provider that supports lazy SDK download, given the same gap likely affects any future native-SDK agent on a remote host?

## Evidence

- **banner scoping:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSdkSetupNotification.ts: agentSdkSetupSessionType() returns LOCAL_AGENT_HOST_SCHEME_PREFIX + agent, and the banner's sessionTypes filter (line ~208) is built from it — it can only ever match a local/ambient agent-host session type.
- **scheme comment confirms split:** src/vs/platform/agentHost/common/agentHostConnectionsService.ts: LOCAL_AGENT_HOST_SCHEME_PREFIX's own doc comment states remote agent-host session schemes (`remote-<authority>-<provider>`) are handled separately by agentHostSessionType.ts — no download/setup logic was found wired to that path.
- **no remote equivalent:** grep across src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts and the whole repo for AgentSdkSetupNotification/agentSdkSetupSessionType usage returns only the local-scoped file; AgentSdkSetupService (src/vs/workbench/services/agentHost/browser/agentSdkSetupService.ts) binds to IAgentHostService.rootState, which is the single ambient IAgentConnection, not per-remote-connection state.
- **auth throw before download:** src/vs/platform/agentHost/node/claude/claudeAgent.ts _ensureAuthenticated() (line ~758) throws AHP_AUTH_REQUIRED when proxy transport has no handle, before any SDK call; downloadSdk()/ensureAvailable() (line ~681) is only invoked by the AgentSdkSetupChannel's download-request command, which the remote window never sends.
