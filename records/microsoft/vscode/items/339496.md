# Issue #339496 — Agents window: Claude Agent SDK is never downloaded for sessions on a remote SSH host (download offer is local-only), Claude target silently does nothing

[https://github.com/microsoft/vscode/issues/339496](https://github.com/microsoft/vscode/issues/339496)

## Summary

Well-diagnosed, fresh bug report, confirmed against current main source: the Agent Host SDK-download banner is explicitly scoped to local session types only (a deliberate design comment calls out that the Agents window's remote `remote-<authority>-<agent>` session types are 'outside this banner'), and the Claude provider's lazy-download path (`_refreshModels`/`_ensureAuthenticated` in claudeAgent.ts) is gated by `canLoadWithoutDownload()` with no remote-triggering fallback, so a remote Claude session can never leave `notDownloaded` state. No fix or duplicate found.

## Change summary

On a remote SSH host, the Claude Agent SDK download is never offered or triggered, so selecting Claude as the session target in the Agents window silently does nothing.

## Best solution

A maintainer needs to decide the intended remote behavior for Claude SDK setup in the Agents window — either extend the SDK-setup banner / trigger a lazy download for remote session types, or make the UI explicitly report that remote Claude sessions require a pre-downloaded SDK — since current code intentionally excludes remote session types from the local banner (see the comment in agentHostSdkSetupNotification.ts) with no alternate remote path.

- **Trace:**

  > The SDK-setup banner (agentHostSdkSetupNotification.ts) is intentionally keyed to the local `agent-host-<agent>` session type only, per its own comment; the Agents window's remote session types (`remote-<authority>-<agent>`) are explicitly excluded. Separately, ClaudeAgent's `_refreshModels`/`_ensureAuthenticated` only attempt the native SDK path when `canLoadWithoutDownload()` is already true, with no code path that calls `ensureAvailable()` to trigger a download when a session is first created remotely. Where the uncertainty starts: whether the correct fix is to extend the banner/consent flow to remote session types (requiring a remote-safe way to initiate and report the download), to add an unconditional lazy-download trigger in `createSession`, or to leave remote Claude unsupported and surface that explicitly in the Session Target / chat input instead.
- **Open decisions:**
  - Should remote-host Claude sessions in the Agents window be able to trigger/complete the SDK download via the same consent UI used for local sessions, or is remote download out of scope for now?
  - If remote download support is out of scope, should Claude be hidden/disabled as a Session Target option for remote hosts, or should it still appear but show an explicit 'not supported for remote sessions' message instead of silently doing nothing?
