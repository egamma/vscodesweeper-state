# Issue #205269 — Incorrect project tab names

[https://github.com/microsoft/vscode/issues/205269](https://github.com/microsoft/vscode/issues/205269)

## Summary

Keep open with the existing upstream classification: independent reports confirm incorrect macOS native-tab names through VS Code 1.132.0, and the implicated Electron calls remain in current source. A newer report adds useful diagnosis but cannot replace this older, previously reviewed issue.

## Change summary

Creating a native window tab beside a selected middle tab should preserve the correspondence between each tab's title and its project.

## Best solution

Resolve the interaction between automatic macOS tab insertion and Electron's explicit addTabbedWindow call while preserving New Window Tab behavior across OS tab preferences. Use the diagnosis in https://github.com/microsoft/vscode/issues/276577 to support this older report, without treating the proposed alternatives there as an established fix.

## Evidence

- **Confirmed persistence:** The discussion at https://github.com/microsoft/vscode/issues/205269 includes confirmation on 1.86.1, an independent reproduction on a fresh installation of 1.97.2 with no extensions, and another confirmation on 1.132.0 with Electron 42.7.1 on macOS. Installed extensions are not supported as the cause.
- **Maintainer ownership assessment:** The March 7, 2024 comment identifies macOS native tabs as upstream functionality and cites the delegation paths: https://github.com/microsoft/vscode/blob/ff23987823aaca66f5f0064b1200a568e59ba540/src/vs/platform/windows/electron-main/windowsMainService.ts#L1481-L1485 and https://github.com/microsoft/vscode/blob/ff23987823aaca66f5f0064b1200a568e59ba540/src/vs/platform/windows/electron-main/windowImpl.ts#L989-L993.
- **Current source boundary:** src/vs/platform/native/electron-main/nativeHostMainService.ts:1107-1115 sets forceNewTabbedWindow for New Window Tab. src/vs/platform/windows/electron-main/windowsMainService.ts:1616-1620 then calls activeWindow.addTabbedWindow(createdWindow), and windowImpl.ts:1240-1244 delegates directly to Electron BrowserWindow.addTabbedWindow. Independently, windows.ts:204-207 sets tabbingIdentifier when window.nativeTabs is enabled. These are still the relevant native-tab integration paths; source inspection alone does not establish runtime resolution of the naming defect.
- **Verified related report, not an eligible canonical:** https://github.com/microsoft/vscode/issues/276577 is open and describes the same observable symptom: New Window Tab inserts beside the selected project but swaps the new tab's title with another project's title. It was created on November 10, 2025, after this February 15, 2024 report, so the re-review rule bars using it as a duplicate canonical.
- **Additional diagnosis:** https://github.com/microsoft/vscode/issues/276577#issuecomment-3749882938 attributes the mismatch to combining OS automatic insertion through tabbingIdentifier with explicit addTabbedWindow. It explains why skipping the explicit call can break New Window Tab when the OS preference is Never, and links a different approach in https://github.com/posit-dev/positron/pull/11367. This is a useful lead, not proof of a fix adopted by VS Code.
- **Canonical and fix checks:** Read-only searches for native tabs and macOS tab-title/name problems found no verified older open report owning this exact symptom. No concrete fixing commit was established; the recent confirmation and unchanged integration paths do not support a completed or not-reproducible close.
