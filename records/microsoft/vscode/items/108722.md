# Issue #108722 — API to trigger a refresh of the OUTLINE (DocumentSymbols)

[https://github.com/microsoft/vscode/issues/108722](https://github.com/microsoft/vscode/issues/108722)

## Summary

Still a real gap on current main: `DocumentSymbolProvider` has no `onDidChange` event (unlike inlay hints, code lenses, semantic tokens, folding ranges) and there is no refresh command, so an extension cannot invalidate the outline without a document edit or re-registering its provider. Keep open as a backlog feature request (53 upvotes); the natural design is a provider event matching the existing `onDidChange*` precedents.

## Change summary

Give extensions an API to invalidate/refresh the Outline (document symbols) when symbols change for reasons other than a document edit (settings change, background build, dependent file).

## Best solution

Add an optional `onDidChangeDocumentSymbols`-style event to `DocumentSymbolProvider` (mirroring `onDidChangeInlayHints` / `onDidChangeCodeLenses`) and have `OutlineModelService` drop its cache entry for affected models when it fires — rather than the UI-level refresh command that was previously declined.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts`
- **Validation:** An outline model test asserting that firing the provider's change event causes `OutlineModelService.getOrCreate` to re-query the provider for an unchanged text model (cache entry dropped), plus an extension-host API test that the event reaches the main thread.
- **Behavior:**

  > An extension that registers a document symbol provider can signal that its symbols changed without the document changing — after a settings toggle, a finished background build, or a change in a dependent file — and the Outline view, breadcrumbs and `vscode.executeDocumentSymbolProvider` then show freshly computed symbols. Nothing recomputes when no provider signals a change; normal edit-driven refresh and debouncing are unchanged. Acceptance: with an unchanged document, firing the signal causes exactly one new provider invocation and the Outline updates; not firing it leaves current behavior and request counts untouched.
- **Trace:**

  > `DocumentSymbolProvider` in src/vs/editor/common/languages.ts:1766 carries no change event, unlike `CodeLensProvider` (line 2007), `FoldingRangeProvider` (line 2426) and `InlayHintsProvider` (line 2462) which all expose `onDidChange*`; those are the precedent to follow end to end (ext host registration in src/vs/workbench/api/common/extHostLanguageFeatures.ts:2269 and the `$register…`/`$emitDocumentSymbolEvent`-style bridge in mainThreadLanguageFeatures.ts). The staleness is confirmed in src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts:443, where `OutlineModelService.getOrCreate` reuses its LRU entry unless the text model version id or the ordered provider list changed — which is also why re-registering the provider is the current workaround (the registry `onDidChange` listener at line 224 cancels an in-flight create). Boundary: do not add a user-facing 'Refresh Outline' command or UI affordance (https://github.com/microsoft/vscode/pull/160027 was declined), do not change edit-driven refresh, debouncing (`ILanguageFeatureDebounceService`, min 350ms) or the cache's model-removal cleanup, and keep the event optional so existing providers are unaffected. Related: https://github.com/microsoft/vscode/issues/71454 (the closed original) and https://github.com/microsoft/vscode/issues/311971 (separate duplicate-request concern that argues against any always-on invalidation).
- **Open decisions:**
  - Should this be an optional `onDidChange` event on `DocumentSymbolProvider` (matching inlay hints / code lenses / folding ranges), or an extension-callable refresh command as proposed in the declined PR?
  - If an event: does it signal 'all documents for this provider' or carry an optional document/URI scope, and does core recompute eagerly for visible editors or only invalidate the cache so the next request recomputes?
  - Does the API ship first as a proposed API (`vscode.proposed.*.d.ts`) or go straight to stable `vscode.d.ts`?

- **gap on main:** src/vs/editor/common/languages.ts:1766 `DocumentSymbolProvider` has no `onDidChange` member, while `InlayHintsProvider` (onDidChangeInlayHints, line 2462), `CodeLensProvider` (line 2007), `FoldingRangeProvider` (line 2426) and `InlineValuesProvider` (line 344) all do. `src/vscode-dts/vscode.d.ts:3638` likewise exposes no change event.
