# Issue #182441 — Regression: TextEditorEdit.replace does not select empty selection anymore

[https://github.com/microsoft/vscode/issues/182441](https://github.com/microsoft/vscode/issues/182441)

## Summary

The regression remains visible in current source: an empty-range `TextEditorEdit.replace` follows the same collapsed-selection result as an insertion despite `replace` deliberately using different marker semantics. The issue should remain open for an editor API/core decision and regression coverage.

## Change summary

Restore the behavior where replacing an empty editor selection leaves the inserted text selected rather than collapsing the cursor after it.

## Best solution

Restore the documented historical distinction so `replace` on an empty selection selects the inserted text, while `insert` continues moving the cursor after the insertion and non-empty replacements retain their established behavior. Keep the change scoped to extension-driven editor edits and add explicit tests for all three cases.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostTextEditor.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, `src/vs/editor/common/model/intervalTree.ts`, `src/vs/editor/test/browser/commands/sideEditing.test.ts`, `src/vs/workbench/api/test/browser/mainThreadEditors.test.ts`
- **Validation:** Add an editor API test covering `replace` at an empty active selection and assert that the resulting selection spans the inserted text; retain companion assertions that `insert` leaves a collapsed cursor after the text and non-empty replacement behavior is unchanged.
- **Behavior:**

  > When an extension calls `TextEditorEdit.replace` with the editor's empty selection, the inserted text should become selected. Calling `insert` at the same position should continue leaving a collapsed cursor after the inserted text. Replacing a non-empty selection must retain its established selection behavior, including compatibility with the scenario tracked by https://github.com/microsoft/vscode/issues/124154.
- **Trace:**

  > TextEditorEdit in src/vs/workbench/api/common/extHostTextEditor.ts distinguishes `replace` from `insert` through `forceMoveMarkers`, and MainThreadTextEditor.applyEdits in src/vs/workbench/api/browser/mainThreadEditor.ts forwards that distinction to editor-core `executeEdits`. Cursor recovery ultimately depends on tracked ranges updated by `nodeAcceptEdit` in src/vs/editor/common/model/intervalTree.ts. The current side-editing test expects an empty selection at the insertion point to collapse after the new text for both flag values, which reproduces the reported result from source. Historical maintainer guidance at https://github.com/microsoft/vscode/issues/4802#issuecomment-257276166 states that replace should instead expand the selection around inserted text. The boundary is extension-driven `TextEditorEdit.replace`: generic model edits, normal typing, `TextEditorEdit.insert`, and non-empty replacement behavior must not regress.
- **Open decisions:**
  - Should the historical distinction be restored in editor-core marker handling, or should the main-thread editor API provide an explicit resulting cursor state for empty-range replace operations?
  - Should every visible editor showing the same document receive the replacement selection semantics, or only the TextEditor instance through which the extension submitted the edit?

## Evidence

- **current API path:** src/vs/workbench/api/common/extHostTextEditor.ts sends `replace` operations with `forceMoveMarkers: false`, while `insert` uses `true`; src/vs/workbench/api/browser/mainThreadEditor.ts forwards that flag through `executeEdits`.
- **current source behavior:** src/vs/editor/test/browser/commands/sideEditing.test.ts explicitly expects a collapsed selection at the end of an insertion made exactly at an empty selection for both `forceMoveMarkers` values, matching the reported current behavior.
- **marker implementation:** src/vs/editor/common/model/intervalTree.ts handles insertion-time tracked-range movement in `nodeAcceptEdit`; the empty-range path currently does not preserve the historical replace-versus-insert selection distinction.
- **historical contract:** A maintainer described `TextEditorEdit.insert` as moving the selection after inserted text and `TextEditorEdit.replace` as expanding it around inserted text in https://github.com/microsoft/vscode/issues/4802#issuecomment-257276166.
- **related issues are not canonical:** https://github.com/microsoft/vscode/issues/141946 requests different insertion semantics, while https://github.com/microsoft/vscode/issues/124154 concerns an unwanted partial selection after a non-empty replacement; neither fully owns this empty-selection regression.
