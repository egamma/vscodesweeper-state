# Issue #332070 — The tab close button remains stuck in the 'Close Others' state even without pressing Alt.

[https://github.com/microsoft/vscode/issues/332070](https://github.com/microsoft/vscode/issues/332070)

## Summary

Fresh, thinly-described report (0 days old, no comments), but tracing the Alt-hover 'Close Others' swap in multiEditorTabsControl.ts reveals a real synchronization gap between the modifier-key emitter and per-tab hover tracking that plausibly explains a stuck icon after Alt+Tab; keeping open pending confirmation rather than closing on a single 'sometimes' report.

## Change summary

The tab close button can remain visually swapped to 'Close Others' after Alt is released, seemingly triggered by Alt+Tab window switching.

## Best solution

In src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts, `setHoveredTab()` only redraws the previous/new hovered tab's action when `modifierKeyEmitter.keyStatus.altKey` is currently true (line 209); if the Alt state was reset elsewhere (e.g. the window `blur` handler in dom.ts's `ModifierKeyEmitter`) while the mouse was not over the affected tab at that exact moment, the tab's action bar can be left showing the stale 'Close Others' icon indefinitely since later hover changes with Alt already false skip the redraw. The fix should make the hover-swap redraw unconditional (or otherwise track pending swapped tabs) rather than gated on the current Alt state.

## Evidence

- **hover-gated redraw:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:209 — `setHoveredTab()` returns early without redrawing if `!modifierKeyEmitter.keyStatus.altKey`, meaning a tab whose action bar was left in the swapped 'Close Others' state can never be corrected once Alt is already false and the tab is no longer hovered at the moment of the alt-state change.
- **blur-based reset:** src/vs/base/browser/dom.ts:1914-1916 — ModifierKeyEmitter resets key status on window `blur` (Alt+Tab away) and fires an update event, but the corresponding redraw in multiEditorTabsControl.ts only touches the currently-tracked `hoveredTabIndex` at that instant (lines 184-190), so a tab that was hovered when Alt was pressed but is no longer tracked as hovered when the reset fires is skipped.
- **no existing test coverage:** No test file targets multiEditorTabsControl.ts hover/alt interaction (searched src/vs/workbench/test/browser/parts/editor); this path is only exercised manually.
