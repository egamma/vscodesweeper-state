# Issue #230413 — Let compound launch configs be the default

[https://github.com/microsoft/vscode/issues/230413](https://github.com/microsoft/vscode/issues/230413)

## Summary

A real gap remains: compounds can be sorted first with presentation metadata, but launch.json cannot explicitly designate a default configuration independently of the previously selected configuration. The debug owner accepted this as a feature request and it is parked in the Backlog, so it should remain open.

## Change summary

Allow a compound debug configuration to be designated as the default launch entry without creating a duplicate configuration.

## Best solution

Define an explicit, documented default-selection contract for launch configurations and compounds, including its precedence relative to the workspace's persisted last selection. Duplicate names should remain unsupported.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugSchemas.ts`, `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts`
- **Validation:** Add debugConfigurationManager unit coverage showing that the chosen default compound is selected under the agreed initialization and persisted-selection precedence rules, while ordinary configurations and duplicate-name rejection remain unchanged.
- **Behavior:**

  > A workspace can identify a compound as its default launch entry without adding a same-named configuration. When the applicable default-selection condition is met, the Run and Debug selector chooses that compound and starting debugging launches every referenced configuration. Existing workspaces without a declared default retain their current selection behavior, and configuration names remain unique.
- **Trace:**

  > ConfigurationManager.selectConfiguration in src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts restores the selected launch and name from workspace storage, then falls back to the first name returned by AbstractLaunch.getConfigurationNames. That list combines ordinary configurations and compounds and is sorted through getVisibleAndSorted in src/vs/workbench/contrib/debug/common/debugUtils.ts; compound presentation metadata is declared in src/vs/workbench/contrib/debug/common/debugSchemas.ts. The existing presentation.order capability changes ordering but does not express precedence over a valid stored selection. Keep duplicate-name handling and compound execution semantics out of scope; the requested change concerns initial selection only. Related sorting work is documented at https://github.com/microsoft/vscode/issues/82332.
- **Open decisions:**
  - Should a declared default always replace the workspace's persisted last selection when VS Code opens, or apply only when no valid previous selection exists?

## Evidence

- **maintainer direction:** In https://github.com/microsoft/vscode/issues/230413, the debug-area maintainer stated on 2024-10-07 that the duplicate-name workaround is not officially endorsed and accepted tracking a better solution as a feature request.
- **current selection behavior:** src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts restores DEBUG_SELECTED_CONFIG_NAME_KEY and otherwise selects the first value returned by getConfigurationNames(); there is no launch.json property that explicitly marks a configuration or compound as the default.
- **existing partial capability:** src/vs/workbench/contrib/debug/common/debugSchemas.ts exposes presentation.group/order on compounds, and src/vs/workbench/contrib/debug/common/debugUtils.ts sorts entries by that metadata. This can place a compound first but does not override a valid persisted selection.
- **related completed work:** https://github.com/microsoft/vscode/issues/82332 implemented grouping, sorting, and hiding through presentation metadata; it does not define an explicit default launch entry.
- **canonical search:** https://github.com/microsoft/vscode/issues/58189 has a similar title but asks which child debug session becomes active after starting a compound, not which launch entry is selected before starting, and it is closed; it is not a valid canonical duplicate.
