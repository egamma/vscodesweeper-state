# Issue #173838 — Exception when moving views around

[https://github.com/microsoft/vscode/issues/173838](https://github.com/microsoft/vscode/issues/173838)

## Summary

The defect remains visible in current source: an empty view container can retain its composite entry, and dragging over it dereferences a nonexistent last pane. The previous fix was reverted after breaking Reset View Location, so this needs a lifecycle-aware replacement rather than closure.

## Change summary

Moving the last view out of a view container can leave a stale sidebar icon and cause an exception during subsequent drag-and-drop.

## Best solution

Keep empty-container presentation synchronized without treating a still-registered default container as permanently deregistered, and make drag-overlay bounds safe when a container has no panes. Preserve Reset View Location so it can restore and reveal views after the container becomes populated again.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/parts/paneCompositeBar.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/services/views/test/browser/viewDescriptorService.test.ts`
- **Validation:** Run the targeted ViewDescriptorService unit tests and exercise both UI sequences: moving the final Search/Explorer view through the sidebars and panel must leave no stale icon or console exception, while moving Problems to SCM and invoking Reset View Location must restore and reveal Problems.
- **Behavior:**

  > Moving the last view out of a view container must not leave a stale activity/sidebar entry or throw while another view is dragged over that location. Moving a view back into the location must remain supported. Reset View Location must continue to restore and reveal a moved view, including the Problems-to-SCM regression scenario from https://github.com/microsoft/vscode/issues/199537.
- **Trace:**

  > The current drag path in src/vs/workbench/browser/parts/views/viewPaneContainer.ts#getOverlayBounds assumes `this.panes` is nonempty and dereferences the final pane. View movement is coordinated by ViewDescriptorService.moveViewsWithoutSaving in src/vs/workbench/services/views/browser/viewDescriptorService.ts; it removes and adds descriptors but emits no container-removal signal for a now-empty default container. Commit 78038ac0577dbdb3bcc1728cb9c8fca27a6e0cb4 attempted such a signal, but commit 0aff17a7fac9edfb38da8a2d6dde59a0e24b8a0b reverted it because ViewsService and PaneCompositeBar interpret removal as full deregistration, breaking Reset View Location. The plan must preserve registered-container restoration semantics while synchronizing its visible composite state; generated-container cleanup and ordinary nonempty drag-and-drop behavior are outside the requested change.

## Evidence

- **current source:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts:403-427 computes drag-overlay bounds with `this.panes[this.panes.length - 1].element` without handling an empty pane array, matching the reported exception.
- **confirmed scope:** A maintainer reproduced the problem with multiple views, and the latest reporter comment confirms it still reproduced after the first attempted fix.
- **reverted fix:** https://github.com/microsoft/vscode/pull/198526 merged commit 78038ac0577dbdb3bcc1728cb9c8fca27a6e0cb4 to emit a removed-container event after moving the last view, explicitly fixing this issue, but https://github.com/microsoft/vscode/pull/199560 reverted it in commit 0aff17a7fac9edfb38da8a2d6dde59a0e24b8a0b.
- **regression boundary:** https://github.com/microsoft/vscode/issues/199537 documents that the attempted deregistration semantics prevented Reset View Location from showing the restored Problems view. Current consumers in src/vs/workbench/services/views/browser/viewsService.ts and src/vs/workbench/browser/parts/paneCompositeBar.ts treat `onDidChangeViewContainers.removed` as full deregistration.
