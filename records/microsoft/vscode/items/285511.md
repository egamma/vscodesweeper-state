# Issue #285511 — Summarization should show a % or some other indicator that progress is actually happening

[https://github.com/microsoft/vscode/issues/285511](https://github.com/microsoft/vscode/issues/285511)

## Summary

A real summarization UX gap remains: long-running compaction gives insufficient observable progress, and the discussion establishes several possible remedies but no settled product behavior. Keep this open while the chat team chooses between streaming activity feedback, an expanded-thinking-style presentation, background summarization, and eliminating or shortening the request.

## Change summary

Show meaningful activity or progress feedback while a long-running chat summarization request is generating its result.

## Best solution

Design summarization so users can distinguish active generation from a hang without presenting a fabricated percentage; ideally reduce or hide the latency, with streamed token activity or an expanded-thinking-style view as fallback UX for operations that remain long-running.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatContentParts/chatProgressContentPart.ts`, `src/vs/workbench/contrib/chat/browser/chatContentParts/chatThinkingContentPart.ts`, `src/vs/workbench/contrib/chat/browser/chatContentParts/chatProgressPart.ts`, `src/vs/workbench/contrib/chat/browser/chatWidget.ts`
- **Validation:** Exercise a chat session large enough to trigger summarization and verify that, while the summarization request remains active for more than 10 seconds, the UI continues to expose truthful activity without a fabricated completion percentage; completion, cancellation, and failure must clear or transition that state correctly.
- **Behavior:**

  > When chat summarization takes long enough to be noticeable, users can tell that work is still progressing rather than mistaking the session for a hang. Feedback must be truthful and indeterminate unless a reliable total exists; it may expose streamed activity or details, but must not invent a percentage. The state transitions correctly on completion, cancellation, and failure, and short summarizations do not add distracting UI.
- **Trace:**

  > The issue discussion establishes that summarization currently runs as one large LLM request: the client waits for the model and then receives a potentially long token stream, so there is no reliable total from which to calculate a percentage. Existing chat progress and thinking presentation code is likely under src/vs/workbench/contrib/chat/browser/chatContentParts/, with orchestration in chatWidget.ts; the plan should trace the summarization state into those renderers before choosing a surface. The boundary is truthful progress feedback for summarization: do not fabricate completion estimates, and do not conflate this with the separate correctness report at https://github.com/microsoft/vscode/issues/264416. Latency itself is tracked by https://github.com/microsoft/vscode/issues/271740 and may ultimately remove the need for persistent progress UX.
- **Open decisions:**
  - For summarization that remains slow, should users see a compact indeterminate activity indicator, a live token/activity count, or an expandable thinking-style detail view?
  - Should summarization remain a blocking foreground state with visible feedback, or move to background execution so the session remains usable?
  - What delay threshold should suppress progress UI for fast summarizations while ensuring longer waits visibly remain active?
