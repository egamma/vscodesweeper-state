# Issue #330991 — HTML language service does not report unmatched or invalid closing tags

[https://github.com/microsoft/vscode/issues/330991](https://github.com/microsoft/vscode/issues/330991)

## Summary

Confirmed on main: the built-in HTML mode (extensions/html-language-features/server/src/modes/htmlMode.ts) has no `doValidation` at all — only the embedded CSS and JS modes are validated (extensions/html-language-features/server/src/htmlServer.ts, `validateTextDocument`/`isValidationEnabled`). There's no structural HTML tag/attribute checking today, so this is a real, unrouted feature gap rather than a regression.

## Change summary

Requests that VS Code's built-in HTML language service surface diagnostics for basic structural HTML errors (unmatched/mismatched closing tags, invalid attributes on closing tags, invalid attribute values) in the Problems panel.

## Best solution

Add a lightweight `doValidation` to the HTML language mode (extensions/html-language-features/server/src/modes/htmlMode.ts), likely by extending vscode-html-languageservice's parser/scanner to surface tag-mismatch and closing-tag-attribute errors, gated behind an `html.validate` setting analogous to the existing `html.validate.styles`/`html.validate.scripts`. CSS already ships this kind of structural linting via `getLanguageService(textDocument).doValidation` in css-language-features, so there is in-repo precedent for shipping this in core rather than pushing it to an extension.

## Evidence

- **validation only covers embedded css/js:** extensions/html-language-features/server/src/htmlServer.ts `validateTextDocument` iterates `languageModes.getAllModesInDocument` and only invokes `mode.doValidation` for modes that define it — the html mode itself never contributes diagnostics; `isValidationEnabled` only branches on `languageId === 'css'` or `'javascript'`.
