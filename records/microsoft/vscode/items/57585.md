# Issue #57585 — Cancel file operations from opening an editor when closing it

[https://github.com/microsoft/vscode/issues/57585](https://github.com/microsoft/vscode/issues/57585)

## Summary

The large-file confirmation mitigates accidental opens, but current main still does not cancel an in-progress read when its editor closes. This remains an acknowledged, deliberately retained file-I/O enhancement.

## Change summary

Cancel an editor's in-progress file read when the editor is closed, avoiding prolonged resource use or an unresponsive window.

## Best solution

Propagate editor-lifecycle cancellation through text model resolution and the file-service stream while safely handling concurrent consumers. Preserve `workbench.editorLargeFileConfirmation` as prevention, but do not treat it as a substitute for cancellation.

## Evidence

- **current source:** src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts awaits text model resolution and only checks `isDisposed()` after resolution finishes; no editor-lifecycle cancellation token is passed.
- **current source:** src/vs/workbench/services/textfile/common/textFileEditorModel.ts calls `textFileService.readStream` without a cancellation token. src/vs/workbench/services/textfile/browser/textFileService.ts creates cancellation internally but triggers it only when decoding fails, such as detecting binary content.
- **partial mitigation:** Commit 229c95c8ac119df9059491034436bd02be303e67 added `workbench.editorLargeFileConfirmation`, which prevents some accidental large-file opens but does not cancel a read already underway.
- **maintainer assessment:** The discussion at https://github.com/microsoft/vscode/issues/169433 explicitly retained https://github.com/microsoft/vscode/issues/57585 for cancellation and described model-resolution cancellation as complex and potentially risky because multiple clients may share an asynchronous resolve.
- **remaining gap:** A 2024 confirmation reports the warning as useful but still requests cancellation after loading begins; another comment notes that custom editors are not covered by the setting. The issue also carries the maintainer-applied `keep` label.
