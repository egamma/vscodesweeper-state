# Issue #57585 — Cancel file operations from opening an editor when closing it

[https://github.com/microsoft/vscode/issues/57585](https://github.com/microsoft/vscode/issues/57585)

## Summary

Keep open: closing an editor still does not propagate cancellation into its pending file read. The existing large-file confirmation setting reduces accidental opens but does not cancel an operation already underway; this issue remains the canonical request.

## Change summary

Cancel unnecessary in-flight file loading when the editor requesting it is closed.

## Best solution

Support cancellation from editor opening through text-model resolution to cancellable file reads, without aborting a shared resolution still needed by another consumer. Preserve the large-file confirmation safeguard and separately assess custom-editor coverage.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/editors/textFileEditor.ts`, `src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vs/platform/files/common/fileService.ts`
- **Validation:** Add deterministic delayed-provider tests covering editor closure during a pending read: cancellation reaches the provider when no consumer remains, the closed editor is not populated later, and another consumer of the same resource can still finish resolving. Retain existing file-service cancellation tests and text-model-manager lifecycle tests; manually check closing a loading large local and remote text file.
- **Behavior:**

  > Closing an editor while its file is loading should stop unnecessary loading rather than merely suppress the eventual display. If another editor or model consumer still needs the same resource, closing one editor must not interrupt that consumer. Acceptance should cover a delayed read cancelled after the last consumer leaves, successful resolution for a remaining consumer, and unchanged ordinary file opening and large-file confirmation.
- **Trace:**

  > TextFileEditor.setInput receives a cancellation token but checks it only after FileEditorInput.resolve finishes. FileEditorInput resolves through TextFileEditorModelManager and TextFileEditorModel.resolveFromFile, whose TextFileService.readStream call has no external cancellation token; TextFileService.doRead creates its own source for read-error cancellation. FileService already supports externally cancelled streamed and buffered reads, but that support is not connected to editor closure and does not cover every provider branch. TextFileEditorModelManager joins pending resolutions and defers disposal while they run, so shared-consumer ownership is the central design boundary. https://github.com/microsoft/vscode/issues/169433#issuecomment-1365783473 explicitly documents this risk and identifies this issue as the cancellation canonical. Preserve dirty-model protection, remaining consumers, ordinary loading, and existing confirmation behavior; custom-editor loading has not been traced and must not be assumed covered.
- **Open decisions:**
  - Should the initial cancellation contract cover built-in text-editor loading only, or also custom-editor loading initiated through extension APIs?
  - For providers that cannot abort a read, what cancellation guarantee should users receive: immediate abandonment of the editor request with eventual cleanup, or a narrower provider-dependent guarantee?

## Evidence

- **Current editor cancellation boundary:** src/vs/workbench/contrib/files/browser/editors/textFileEditor.ts:102–113 accepts a CancellationToken in TextFileEditor.setInput, calls await input.resolve(options) without that token, and checks cancellation only after resolution completes. Closing the pending editor therefore does not cancel its underlying read through this path.
- **Resolution and read boundary:** src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts:349–389 resolves through textFileService.files.resolve without an editor cancellation token and handles a disposed input only after resolution. src/vs/workbench/services/textfile/common/textFileEditorModel.ts:453–458 calls readStream without cancellation; src/vs/workbench/services/textfile/browser/textFileService.ts:209–238 creates an independent cancellation source and cancels it on decoding errors, not editor closure.
- **Lower-layer cancellation already exists:** src/vs/platform/files/common/fileService.ts:582–640 accepts an external token, parents its cancellation source to that token, and forwards cancellation to streamed or buffered reads. This is partial infrastructure, not completion of editor-close cancellation; the unbuffered provider branch does not receive that token.
- **Existing capability is preventive only:** src/vs/workbench/browser/parts/editor/editorConfiguration.ts:208–214 registers workbench.editorLargeFileConfirmation as a size threshold for asking permission before opening, with an explicit caveat about editor types and environments. FileEditorInput passes size limits through ensureLimits. The reporter discussion acknowledges this workaround but still requests cancellation after loading starts.
- **Shared-model complexity:** src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts:353–360 joins pending resolutions for the same resource, and :575–596 waits for pending resolution before allowing disposal. Cancellation must respect other consumers rather than tying shared model lifetime directly to one tab.
- **Maintainer-defined canonical scope:** https://github.com/microsoft/vscode/issues/169433#issuecomment-1365783473 explicitly assigns editor-close cancellation to this issue and warns about multiple clients awaiting shared model resolution. https://github.com/microsoft/vscode/issues/169433#issuecomment-1370082916 separates IPC improvements from this cancellation request.
- **Related reports consolidate here:** https://github.com/microsoft/vscode-remote-release/issues/6517#issuecomment-1084078932 closes the remote hang report as a duplicate of this issue. https://github.com/microsoft/vscode-remote-release/issues/8338#issuecomment-1522341906 likewise identifies this issue as owning download cancellation. It corroborates a limitation of the workaround, but does not establish that custom-editor loading shares the built-in text-editor cancellation path.
