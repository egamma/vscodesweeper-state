# Issue #180804 — Can we save a couple more pixels in the glyph margin

[https://github.com/microsoft/vscode/issues/180804](https://github.com/microsoft/vscode/issues/180804)

## Summary

The requested density improvement remains unimplemented on current main: each glyph-margin lane still consumes one full line-height of horizontal space. This is distinct follow-up polish rather than a duplicate of the broader multi-decoration work.

## Change summary

Reduce the horizontal space between two glyph-margin decoration lanes without changing the appearance of a single lane.

## Best solution

Define a compact multi-lane layout that preserves the current single-lane appearance, icon alignment, breakpoint hit testing, and accessible pointer targets. The editor owners should first choose whether visual lane width and interactive hit width may differ.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts`, `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/test/browser/config/editorLayoutProvider.test.ts`
- **Validation:** Add editor layout tests covering one and two glyph-margin lanes at representative line heights, then manually verify that adjacent icons remain centered and that adding, removing, and selecting breakpoints works across both lanes.
- **Behavior:**

  > When two glyph-margin lanes are visible, they should consume less horizontal editor space than two full line-height squares. A single glyph-margin lane must retain its existing width and appearance. Icons in both lanes must remain visually centered, distinguishable, and operable with the same breakpoint and decoration interactions. Acceptance includes layout assertions for one- and two-lane cases plus manual pointer interaction across both lanes.
- **Trace:**

  > EditorLayoutInfoComputer in src/vs/editor/common/config/editorOptions.ts derives total glyph-margin width by multiplying line height by lane count. GlyphMargin.render in src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts also advances each lane by line height, while mouse targeting in src/vs/editor/browser/controller/mouseTarget.ts derives the selected lane from the same geometry. The existing layout test helper in src/vs/editor/test/browser/config/editorLayoutProvider.test.ts always supplies one lane, leaving multi-lane geometry uncovered. Preserve the established single-lane layout and do not regress breakpoint or extension-decoration hit testing. The broader design context is https://github.com/microsoft/vscode/issues/179725; this issue is the narrower density follow-up.
- **Open decisions:**
  - Should compact multi-lane icons also have narrower pointer hit regions, or should visual spacing be reduced while preserving larger overlapping or delegated hit targets?
  - Should the compact lane width be fixed to the glyph role or derived from editor line height and font scaling?
  - What minimum separation preserves icon legibility across themes, zoom levels, and accessibility configurations?

## Evidence

- **current layout:** src/vs/editor/common/config/editorOptions.ts computes `glyphMarginWidth = lineHeight * env.glyphMarginDecorationLaneCount`, so two lanes still occupy two complete line-height widths.
- **rendering coupling:** src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts positions every lane at `glyphMarginLeft + laneIndex * lineHeight`; compacting lanes therefore requires coordinated layout, rendering, and interaction handling rather than an isolated spacing adjustment.
- **original design:** https://github.com/microsoft/vscode/issues/179725 remains open for broader multi-decoration behavior, while https://github.com/microsoft/vscode/issues/180531 records that two lanes were intentionally introduced and explicitly notes their additional gutter width. Neither item implements or fully owns this narrower spacing request.
- **existing validation gap:** src/vs/editor/test/browser/config/editorLayoutProvider.test.ts fixes `glyphMarginDecorationLaneCount` at 1 in its layout helper, so it does not currently pin expected geometry for a compact two-lane configuration.
