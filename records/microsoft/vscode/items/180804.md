# Issue #180804 — Can we save a couple more pixels in the glyph margin

[https://github.com/microsoft/vscode/issues/180804](https://github.com/microsoft/vscode/issues/180804)

## Summary

The requested polish remains relevant on current main: each additional glyph-margin lane still consumes a full line-height of horizontal space. The broader multi-decoration tracker explains the lane design but does not settle this focused spacing and hit-target decision.

## Change summary

Reduce the horizontal spacing between multiple glyph-margin icons without changing the appearance of a single glyph-margin lane.

## Best solution

Define a compact multi-lane spacing contract in the editor renderer that preserves the existing single-lane appearance, keeps icons visually distinct, and maintains reliable pointer targeting for each lane.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts`, `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/test/browser/config/editorLayoutProvider.test.ts`
- **Validation:** Extend the Editor ViewLayout - EditorLayoutProvider unit tests with two- and three-lane cases, preserving the existing one-lane width, then run `scripts/test.sh --grep "Editor ViewLayout - EditorLayoutProvider"`; manually verify that clicking each compact lane still selects the corresponding decoration.
- **Behavior:**

  > When an editor needs two or more glyph-margin lanes, the icons should use less horizontal space than one full line-height per lane while remaining visually distinct. A single glyph-margin lane must retain its current width and appearance. Pointer interaction must continue to resolve to the icon lane under the cursor, including at the boundary between adjacent lanes.
- **Trace:**

  > EditorLayoutInfoComputer in src/vs/editor/common/config/editorOptions.ts derives total glyph-margin width by multiplying line height by lane count. GlyphMargin in src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts uses line height again as the horizontal lane stride, while MouseTarget in src/vs/editor/browser/controller/mouseTarget.ts uses that same metric for hit testing. The layout test helper in src/vs/editor/test/browser/config/editorLayoutProvider.test.ts fixes the lane count at one, leaving multi-lane width untested. The broader design history is https://github.com/microsoft/vscode/issues/179725. Keep lane selection, decoration precedence, overflow behavior, icon dimensions, and the one-lane presentation out of scope; uncertainty begins at the compact lane spacing and its pointer-target semantics.
- **Open decisions:**
  - What horizontal spacing and pointer hit-target contract should multiple lanes use—specifically, should the suggested two-pixel visual reduction also shrink each lane's clickable region, or should the larger hit targets be retained?

## Evidence

- **current layout:** src/vs/editor/common/config/editorOptions.ts computes `glyphMarginWidth = lineHeight * env.glyphMarginDecorationLaneCount`, so every additional lane still adds one full line-height of width.
- **rendering path:** src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts positions each widget and decoration at `laneIndex * this._lineHeight`, preserving the full-width spacing shown in the report.
- **interaction boundary:** src/vs/editor/browser/controller/mouseTarget.ts also divides the horizontal offset by `ctx.lineHeight` to identify the clicked lane, so visual compaction must be coordinated with hit testing.
- **related tracker:** https://github.com/microsoft/vscode/issues/179725 is open and tracks the broader multiple-decoration design, including concern about gutter width, but it does not define the requested inter-lane spacing or interaction contract.
- **test gap:** src/vs/editor/test/browser/config/editorLayoutProvider.test.ts currently hardcodes `glyphMarginDecorationLaneCount: 1`, so the layout suite does not pin multi-lane width behavior.
