# Issue #262472 — Perf: showing Chat view on startup is slow

[https://github.com/microsoft/vscode/issues/262472](https://github.com/microsoft/vscode/issues/262472)

## Summary

Keep open as active startup-performance debt. Several partial optimizations merged, but later profiles still measured 55–182 ms in `createChatControl`, and current main retains the eager Chat widget and welcome-rendering paths.

## Change summary

Reduce the 200–300 ms startup cost added when the Chat view is shown in the secondary sidebar.

## Best solution

Profile the current secondary-sidebar startup path, establish a target budget, and reduce or defer nonessential Chat widget, session-list, and welcome-content work while keeping the input promptly usable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/viewsWelcome/chatViewWelcomeController.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentSessionsControl.ts`
- **Validation:** Run the startup performance scenario with identical workspaces and the secondary sidebar enabled versus disabled, compare median startup overhead and `createChatControl` profiles across repeated runs, and verify the result meets the maintainer-approved budget without delaying input usability.
- **Behavior:**

  > Starting a workspace with Chat visible in the secondary sidebar should add only the agreed startup-time overhead, materially below the reported 200–300 ms regression. The Chat input must become usable promptly, and existing empty-state welcome, recent-session, attachment, and restored-session behavior must remain correct. Acceptance requires repeated before/after startup traces showing the secondary-sidebar delta within the approved budget.
- **Trace:**

  > `ChatViewPane.createControls` in src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts synchronously creates the sessions control, welcome controller, and `ChatWidget`; `createChatControl` was still measured as the dominant cost in January 2026. Empty-session setup reaches `ChatWidget.renderWelcomeViewContentIfNeeded` in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts, which may instantiate `ChatViewWelcomePart`; that class synchronously invokes `IMarkdownRendererService` in src/vs/workbench/contrib/chat/browser/viewsWelcome/chatViewWelcomeController.ts. The linked merged PRs removed individual costs but did not establish that the total regression was resolved, and https://github.com/microsoft/vscode/issues/286610 continued to list this initial-render issue as outstanding. Profile current main before selecting a boundary: preserve immediate input interaction and do not remove welcome or recent-session behavior unless the maintainer explicitly chooses that observable tradeoff.
- **Open decisions:**
  - What maximum median startup overhead from showing Chat in the secondary sidebar is the acceptance budget?
  - May welcome and recent-session content appear after the input becomes usable, or must all of that content be present on the first visible frame?

- **confirmed impact:** The issue includes comparative startup traces and perf-bot telemetry showing a 200–300 ms increase with the Chat secondary sidebar enabled; later comments independently measured `createChatControl` at approximately 55 ms and 182 ms.
