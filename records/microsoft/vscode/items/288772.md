# Issue #288772 — Prevent viewType collisions by enforcing extension ID prefixing

[https://github.com/microsoft/vscode/issues/288772](https://github.com/microsoft/vscode/issues/288772)

## Summary

Keep open: current source still uses globally unique, extension-supplied viewType identifiers and rejects collisions rather than disambiguating them. Automatic namespacing or collision-aware selection is a new capability requiring a compatibility decision, not an existing setting the reporter overlooked.

## Change summary

Prevent custom-editor viewType collisions from making different extensions indistinguishable in editor associations and Open With.

## Best solution

Decide a backward-compatible extension-qualified identity contract for custom editors, covering provider registration, editor selection, saved associations, and restored editors. Existing globally unique viewType values and saved user choices should remain usable.

## Evidence

- **Existing contract:** src/vs/workbench/contrib/customEditor/common/extensionPoint.ts defines viewType as a string and explicitly requires global uniqueness, recommending that authors include their extension ID. It does not enforce extension prefixing or provide automatic namespacing.
- **Collision handling remains:** In src/vs/workbench/contrib/customEditor/common/contributedCustomEditors.ts, ContributedCustomEditors.update assigns webviewEditorContribution.viewType directly to CustomEditorInfo.id. Its add method logs an already-registered error and discards the second contribution with that ID.
- **Provider identity:** src/vs/workbench/api/common/extHostCustomEditors.ts stores providers by the bare viewType in EditorProviderStore; add throws when that key already exists. Extension ownership is stored in the entry but is not part of the lookup key.
- **Existing selection surface is insufficient:** CustomEditorService.registerContributionPoints in src/vs/workbench/contrib/customEditor/browser/customEditors.ts registers the contributed ID unchanged with the editor resolver and supplies providerDisplayName as display detail. Display detail cannot recover a colliding contribution already discarded by ContributedCustomEditors; workbench.editorAssociations does not supply a separate extension-qualified identity.
- **Canonical search:** Repository issue searches for custom-editor collisions, duplicate IDs, and viewType prefixing found no verified older canonical owning this request. https://github.com/microsoft/vscode/issues/201884 is older and open, but concerns a mainThreadWebview- prefix exposed by TabInputWebview, not collisions between custom-editor providers, so it is not a duplicate target.
- **Classification and demand:** https://github.com/microsoft/vscode/issues/288772 requests automatic prefixing or a new collision-resolution mechanism. The current uniqueness requirement explains the rejection path; the supplied thread has no maintainer endorsement, comments, or community upvotes. The existing bug label does not justify a decline close.
