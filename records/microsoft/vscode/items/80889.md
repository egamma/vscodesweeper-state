# Issue #80889 — Ability to disable language features provided by extensions

[https://github.com/microsoft/vscode/issues/80889](https://github.com/microsoft/vscode/issues/80889)

## Summary

Keep open: current provider aggregation still lacks the requested per-extension, per-feature control. Existing formatter selection and editor-wide feature settings do not cover mixing language capabilities from several enabled extensions; no qualifying canonical was verified.

## Change summary

Allow users to selectively disable an extension's language features while retaining its other capabilities and features from other extensions.

## Best solution

Define a consistent core configuration contract for selecting which extensions contribute each language feature, preserving today's all-enabled default. Resolve the language/workspace scope and diagnostics semantics before implementing across provider registration and marker handling.

## Plan brief

- **Likely files:** `src/vs/editor/common/languageFeatureRegistry.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDiagnostics.ts`, `src/vs/workbench/contrib/format/browser/formatActionsMultiple.ts`
- **Validation:** Use test extensions with overlapping hover, definition, completion, and diagnostic contributions. Verify that disabling one extension for one feature removes only that contribution, retains its other capabilities and unrelated-language results, and restores existing behavior when configuration is removed; include a fail-before/pass-after automated check for the agreed configuration contract.
- **Behavior:**

  > Users can combine language capabilities from several enabled extensions without unwanted overlapping contributions. Choosing one extension's hovers must not disable another extension's definitions or completions. Diagnostic selection must preserve unrelated-language diagnostics rather than requiring a global Problems text filter. With no configuration, all existing contributions remain enabled. Acceptance should exercise overlapping test extensions and configuration changes under the agreed language/workspace scope.
- **Trace:**

  > LanguageFeatureRegistry in src/vs/editor/common/languageFeatureRegistry.ts matches and orders providers by selector, not a user-selected extension/feature policy. MainThreadLanguageFeatures in src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts registers hover and definition providers without extension identity in their registration signatures, while formatter registration carries identity and DefaultFormatter provides the existing selection precedent. Hover and definition consumers invoke matching providers through the registry. MainThreadDiagnostics in src/vs/workbench/api/browser/mainThreadDiagnostics.ts separately publishes marker collections by owner and uses extension-host origin, so the diagnostics requirement needs its own attribution and behavior assessment. Preserve default aggregation, unrelated extension functionality, and existing formatter behavior. https://github.com/microsoft/vscode/issues/40239 addresses whole-extension enablement and does not absorb this request; https://github.com/microsoft/vscode/issues/91445 supplies another use case for selective contributions.
- **Open decisions:**
  - Should feature exclusions apply to an extension globally, or be independently configurable by language and workspace?
  - For diagnostics, should exclusion suppress publication throughout the editor and Problems surfaces, or only hide selected diagnostics in the Problems view?

## Evidence

- **Requested scope and discussion:** https://github.com/microsoft/vscode/issues/80889 requests Python-extension hovers, mypy diagnostics, and pyright definitions/completions without disabling any entire extension. The maintainer's September 2019 response questions the scenario but does not decline it or settle a configuration design; subsequent comments defend mixing capabilities.
- **Existing capability is partial:** src/vs/workbench/contrib/format/browser/formatActionsMultiple.ts implements DefaultFormatter.configName = 'editor.defaultFormatter' and selects a formatter by extensionId. src/vs/editor/common/config/editorOptions.ts registers editor.hover.enabled and suggestion-kind visibility controls, which affect the feature or result category rather than selecting its contributing extension.
- **Current provider path:** src/vs/editor/common/languageFeatureRegistry.ts selects providers by document-selector score, exclusivity, and registration ordering, without user-configured extension/feature filtering. src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts registers definitions and hovers by handle and selector, without extension identity in those registration signatures. src/vs/editor/contrib/hover/browser/getHover.ts and src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts invoke the ordered matching providers.
- **Diagnostics are a separate surface:** src/vs/workbench/api/browser/mainThreadDiagnostics.ts routes $changeMany(owner, entries) into IMarkerService.changeOne and identifies marker origin by extension-host ID. Diagnostics therefore cannot be assumed to participate in the same provider-selection mechanism as hovers and definitions.
