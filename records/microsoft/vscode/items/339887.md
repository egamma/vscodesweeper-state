# Issue #339887 — Provide way to go back to worktree cleanup

[https://github.com/microsoft/vscode/issues/339887](https://github.com/microsoft/vscode/issues/339887)

## Summary

Reasonable report: the brand-new 'Open Worktree Cleanup' editor (SessionWorktreeCleanupEditor) renders no back/close affordance of its own, and the Agents Window hides the normal editor tab strip in parts of its layout, so once opened from the settings icon there's no obvious way back via UI. Keeping open as a small UX gap in an actively-developed surface.

## Change summary

After opening the worktree cleanup editor from a settings icon in the Agent Sessions window, there is no visible UI control to navigate back.

## Best solution

Add a visible close/back affordance to SessionWorktreeCleanupEditor (or ensure the enclosing sessions chrome always exposes one for this editor), consistent with how the rest of the chrome-reduced Agents Window handles returning from a full-pane editor.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts`, `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditorInput.ts`, `src/vs/sessions/contrib/chat/browser/chat.contribution.ts`
- **Validation:** Manual check: open 'Open Worktree Cleanup' from the Agent Sessions settings icon and confirm a visible, discoverable control (button, Escape, or existing chrome) returns the user to the prior view without using keyboard shortcuts they'd have to already know.
- **Behavior:**

  > After opening the worktree cleanup editor (e.g. via the settings icon or the 'Open Worktree Cleanup' command) in the Agent Sessions window, the user should have a discoverable UI control to return to whatever view they were on before, without needing to know an undocumented shortcut. Existing cleanup functionality (age filter, selection, Clean Up Worktrees button) must be unaffected.
- **Trace:**

  > SessionWorktreeCleanupEditor.createEditor (src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts) builds the editor's content with no close/back button and no Escape handler; it's opened as a pinned editor via IEditorService.openEditor in src/vs/sessions/contrib/chat/browser/chat.contribution.ts (around the 'manageAgentSessionStorage' command). The Agents Window's reduced/alternate chrome (src/vs/sessions/browser/workbench.ts, src/vs/sessions/LAYOUT.md) may hide the usual tab strip depending on layout mode, which is likely why the reporter found no way back. Do not touch the cleanup logic itself (age filtering, selection, cleanup service) — only the navigation affordance.
- **Open decisions:**
  - Should returning be a visible 'Back'/'Close' button inside the editor content, or does it rely on exposing/using existing sessions-window chrome (e.g. a titlebar back control)?
  - Should Escape also close/return from this editor, and would that conflict with other in-editor keyboard handling (e.g. the age-select, checkboxes)?

## Evidence

- **editor has no close/back control:** src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts (SessionWorktreeCleanupEditor.createEditor) renders heading, intro text, controls and a worktree list/cleanup button, but no back/close button, and the only StandardKeyboardEvent handling in the file is for Enter/Space on session links (lines ~266-270), not Escape.
- **chrome-reduced window:** src/vs/sessions/LAYOUT.md and src/vs/sessions/browser/workbench.ts show the Agents Window titlebar/parts can be hidden or restructured depending on layout mode, consistent with the reporter's screenshot showing no normal tab strip to close from.
- **opened as a pinned editor:** src/vs/sessions/contrib/chat/browser/chat.contribution.ts opens SessionWorktreeCleanupEditorInput via IEditorService.openEditor(..., { pinned: true }) from the 'Open Worktree Cleanup' command/settings icon — normal workbench editors would get a tab with a close X, which may not be surfaced the same way in this window.
- **same-day dogfood report:** Issue created same day as linked #339374 and references it directly as 'Testing', indicating this is fresh, in-progress work on this screen rather than an established, stable feature.
