## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/allowedExtensionsService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts`, `src/vs/platform/userDataSync/common/userDataSyncEnablementService.ts`, `build/lib/policies/policyData.jsonc`
- **Validation:** On a managed Windows test device, import the shipped ADMX/ADML, assign a supported policy through Intune, and verify successful deployment and effective organization-managed values. For each selected missing control, define service-level policy tests and observable acceptance checks; bootstrap installation alone must not count as mandatory-extension enforcement.
- **Behavior:**

  > Administrators need centrally enforced controls over extension availability, required extensions, updates, marketplace selection/access, and Settings Sync. Existing allow/deny, update, and marketplace policies should retain their behavior. The remaining work must distinguish first-run provisioning from mandatory installation, and extension blocking from disabling marketplace access. Intune deployment must work through the supported management path rather than requiring the reporter's registry-script workaround.
- **Trace:**

  > AllowedExtensionsService.isAllowed already implements extension selection restrictions, and extensions.contribution.ts declares update and marketplace policies. ExtensionGalleryManifestService reads the configured marketplace URL, so that portion is adopted rather than merely declared. UserDataSyncEnablementService currently derives enablement from environment and storage, without a corresponding policy in the inspected catalog. Documented Windows bootstrap installation permits later uninstallation and is not mandatory-extension enforcement. Intune ADMX ingestion is separately reported at https://github.com/microsoft/vscode/issues/242922 and https://github.com/microsoft/vscode/issues/281840; source inspection cannot establish successful device deployment. Preserve existing policy names and semantics, and separate Windows management-platform constraints from VS Code-owned enforcement gaps.
- **Open decisions:**
  - Should mandatory extensions only be installed automatically, or must they also resist user removal or disabling and be restored when missing?
  - Should disabling marketplace access prohibit discovery and network access, or only installation from that marketplace?

## Evidence

- **Existing extension controls:** build/lib/policies/policyData.jsonc declares AllowedExtensions, ExtensionsAutoUpdate, ExtensionsAutoUpdateDelay, and ExtensionGalleryServiceUrl. src/vs/platform/extensionManagement/common/allowedExtensionsService.ts:isAllowed supports publisher/extension allow and deny entries plus version restrictions; src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts registers update and marketplace policies.
- **Marketplace adoption and boundary:** src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts:133-140 reads the configured marketplace URL and handles private-marketplace access. Blocking extensions with AllowedExtensions is not equivalent to disabling access to marketplace discovery or network services.
- **Preinstallation is not mandatory installation:** https://code.visualstudio.com/docs/enterprise/extensions documents Windows bootstrap extension installation, but explicitly permits users to uninstall those extensions and states that restarting does not reinstall them. This does not deliver an enforced mandatory-extension list.
- **Settings Sync gap:** src/vs/platform/userDataSync/common/userDataSyncEnablementService.ts:isEnabled and canToggleEnablement use the environment sync override, application storage, and sync-store availability. The inspected policy catalog contains no corresponding policy for centrally disabling Settings Sync; the launch override is not the requested enterprise policy.
- **Maintainer direction and deployment evidence:** https://github.com/microsoft/vscode/issues/229861#issuecomment-2841867463 acknowledges expanded policy support and requests Intune experience. https://github.com/microsoft/vscode/issues/229861#issuecomment-3015268437 explains the restricted registry path and supplies a direct-registry workaround; https://github.com/microsoft/vscode/issues/229861#issuecomment-3848761753 independently supplies ADMX ingestion access-denied events.
- **Related issues do not absorb the full request:** Verified https://github.com/microsoft/vscode/issues/242922 and https://github.com/microsoft/vscode/issues/281840 are open Intune-deployment requests created in 2025, after this September 2024 issue. https://github.com/microsoft/vscode/issues/27972 is older and open, but requests general system-wide default/mandatory settings rather than the same specific policy and Intune behavior; none qualifies as a verified canonical for this re-reviewed item.
- **Latest reporter workaround:** The reporter links https://github.com/microsoft/vscode/issues/242922#issuecomment-3928062264, whose PowerShell script directly writes AllowedExtensions and UpdateMode registry values. This bypasses ADMX deployment and does not implement the remaining requested controls.
