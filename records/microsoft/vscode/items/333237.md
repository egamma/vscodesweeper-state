# Issue #333237 — "suggestWidget" reappearing after closing with the Esc "Escape" key

[https://github.com/microsoft/vscode/issues/333237](https://github.com/microsoft/vscode/issues/333237)

## Summary

Detailed, specific reproduction (word-based suggest widget reopening immediately after Escape when only one new character was typed) corroborated by a second, independent commenter; no fix is evident on main, so this stays open for a maintainer/agent to trace precisely.

## Change summary

After Escape closes the word-based suggest widget in a specific one-new-character state, the widget immediately reopens and Escape can no longer close it.

## Best solution

Trace and fix the retrigger race in the suggest auto-trigger pipeline (likely the quick-suggest debounce/cancellation interplay in suggestModel.ts and cancelSuggestWidget in suggestController.ts) so hiding the widget via Escape reliably suppresses any in-flight auto-trigger for that edit.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/suggest/browser/suggestModel.ts`, `src/vs/editor/contrib/suggest/browser/suggestController.ts`
- **Validation:** A test (or manual repro) that types a single new character to trigger word-based quick suggest, presses Escape, and asserts the suggest widget stays hidden (no re-trigger) — should fail before the fix and pass after.
- **Behavior:**

  > After the word-based suggest widget auto-opens from typing a single new character on a line, pressing Escape must close it and keep it closed. Currently it closes and then immediately reopens, so Escape never succeeds in that state; typing two or more characters before Escape does not exhibit the bug. The fix should make Escape's cancel reliably suppress any suggest re-trigger tied to that same edit.
- **Trace:**

  > _doTriggerQuickSuggest() in src/vs/editor/contrib/suggest/browser/suggestModel.ts schedules the auto-trigger on a debounced RunOnceScheduler (`_triggerQuickSuggest`, delay = quickSuggestionsDelay, default 10ms) whose callback only bails out if `_triggerState !== undefined`. cancelSuggestWidget() in suggestController.ts (around line 697) cancels the model and hides the widget but I did not find it cancelling this scheduler. This is a plausible but unconfirmed mechanism — a session should first reproduce against a running build (or add tracing) to confirm exactly which trigger path re-fires after Escape, since the report shows the behavior is sensitive to whether one vs. two+ characters were typed, which the code above doesn't fully explain on its own. The boundary: do not change accept/insert or trigger-character behavior, only the cancel/auto-trigger race for word-based (quick) suggestions. Related: reported at https://github.com/microsoft/vscode/issues/333237.
- **Open decisions:**
  - What exactly re-triggers the widget after Escape — a pending debounced auto-trigger, a cursor-change side effect of hiding the widget, or something else — needs confirmation against a running build before writing the fix.
