# Issue #204007 — Visual Studio Code should support 'Force Run to Cursor'

[https://github.com/microsoft/vscode/issues/204007](https://github.com/microsoft/vscode/issues/204007)

## Summary

The native capability remains absent on current main, while this team-authored request is deliberately assigned to the Backlog. Older requests were closed without implementation, so they provide context but neither a valid duplicate target nor grounds for a judgment close of this protected item.

## Change summary

Add a Force Run to Cursor command that temporarily ignores existing breakpoints and exception triggers, then restores their prior state.

## Best solution

Add a dedicated debug command alongside Run to Cursor, backed by a lifecycle-aware debug-service operation that preserves breakpoint and exception-filter state, runs the focused thread to a temporary target breakpoint, and reliably restores state when the operation completes or is cancelled.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugEditorActions.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/nullDebugService.ts`, `src/vs/workbench/contrib/debug/test/common/mockDebug.ts`
- **Validation:** Add debug-service tests covering suppression and exact restoration of source, function, data, instruction, and exception breakpoints when the target is reached, execution stops early, the session ends, and the user cancels by reactivating breakpoints; run them with `scripts/test.sh --grep "Force Run to Cursor"`.
- **Behavior:**

  > While a debug session is stopped, Force Run to Cursor continues toward the selected source location without stopping at existing source, function, data, instruction, or exception breakpoints. The target remains effective as a temporary breakpoint, and every pre-existing breakpoint and exception-filter enablement state is restored exactly when the operation completes, stops early, terminates, or is explicitly cancelled. Normal Run to Cursor and ordinary breakpoint activation behavior remain unchanged. Acceptance must cover target arrival, an unrelated stop, session termination, and manual reactivation.
- **Trace:**

  > `RunToCursorAction` in src/vs/workbench/contrib/debug/browser/debugEditorActions.ts invokes `DebugService.runTo`, whose implementation in src/vs/workbench/contrib/debug/browser/debugService.ts creates a temporary breakpoint, continues the focused thread, and removes the temporary breakpoint on stopped/inactive state. There is no operation state for temporarily suppressing and restoring other breakpoints. `setBreakpointsActivated(false)` suppresses source, function, data, and instruction breakpoints through their send paths, but activation is global across sessions and `sendExceptionBreakpoints` ignores that flag. The plan must preserve the existing `editor.debug.action.runToCursor` behavior and avoid changing ordinary breakpoint persistence or activation semantics. The uncertainty starts at whether a focused-session operation may temporarily affect concurrent sessions and how the existing activation command should interact with an active forced run.
- **Open decisions:**
  - In a multi-session debug workspace, should Force Run to Cursor suppress breakpoints only for the focused session, or globally for every active session as the current activation model would?
  - If the user invokes Toggle Activate Breakpoints during a forced run, should that cancel the operation's suppression and leave breakpoints active while execution continues?
  - If breakpoints were already globally deactivated before invocation, should Force Run to Cursor preserve that inactive state after completion or be unavailable?

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/debugEditorActions.ts defines only `editor.debug.action.runToCursor`; its action delegates directly to `IDebugService.runTo` and no Force Run to Cursor command is registered.
- **run-to lifecycle:** src/vs/workbench/contrib/debug/browser/debugService.ts implements `runTo` by adding a temporary breakpoint, continuing the focused thread, and removing that breakpoint on `State.Stopped` or `State.Inactive`; it does not suppress or restore existing breakpoints.
- **breakpoint boundary:** `DebugService.setBreakpointsActivated` is global and resends breakpoints to all sessions. Source, function, data, and instruction breakpoint send paths honor the activation flag, but `sendExceptionBreakpoints` does not, so the requested exception-trigger suppression is not an existing composition of the current APIs.
- **older precedent:** https://github.com/microsoft/vscode/issues/130366 requested the same feature and was closed as not planned, while https://github.com/microsoft/vscode/issues/190237 later closed through the Backlog Candidates upvote process. Both are closed and therefore cannot serve as duplicate canonicals; the current member-authored issue was subsequently placed in the Backlog.
- **originating report:** https://github.com/dotnet/vscode-csharp/issues/6843 was redirected here after its observed breakpoint behavior was identified as requiring a VS Code-level Force Run to Cursor feature.
- **workaround only:** The extension linked in https://github.com/microsoft/vscode/issues/204007#issuecomment-3016625562 provides an interim implementation, but the commenter explicitly notes that the requested native debugging experience remains missing.
