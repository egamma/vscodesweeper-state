# Issue #325824 — Support selecting different harnesses per multi-chat in the Agents window

[https://github.com/microsoft/vscode/issues/325824](https://github.com/microsoft/vscode/issues/325824)

## Summary

Keep open: this team-authored feature remains unimplemented on current main. Peer-chat creation still resolves the harness from the parent session, so supporting a different harness per tab requires a deliberate cross-layer contract change.

## Change summary

Let each new multi-chat tab in the Agents window choose and retain a harness independently from its parent session.

## Best solution

Give the New Chat in This Session flow a workspace-compatible harness picker, then preserve the selected harness as chat-level backing so creation, restoration, sending, permissions, and telemetry consistently route that tab through its chosen provider without changing sibling chats.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/newChatWidget.ts`, `src/vs/sessions/contrib/chat/browser/sessionTypePicker.ts`, `src/vs/sessions/services/sessions/common/sessionsProvider.ts`, `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/platform/agentHost/common/agentService.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** Add focused tests in sessionsManagementService.test.ts, localAgentHostSessionsProvider.test.ts, and agentService.test.ts proving that a peer created with a harness different from its parent is routed to that harness, survives restoration with the same backing, and leaves sibling chats unchanged; add an Agents window UI test confirming the harness picker is available during peer-chat creation.
- **Behavior:**

  > Creating a new chat tab within an existing Agents window session offers the harnesses available for that workspace. Selecting a harness different from the source tab creates an isolated chat backed by that harness, and every later interaction and restoration continues to use it. Sibling tabs retain their own harnesses, while workspace and session isolation semantics remain unchanged. Existing single-harness creation remains the default when the user makes no different selection.
- **Trace:**

  > ISessionsManagementService.createNewChatInSession currently resolves one ISessionsProvider from the parent ISession and calls createNewChat with only the session ID. BaseAgentHostSessionsProvider._createAdditionalChat converts that into connection.createChat on the parent's backend URI and carries only model/agent state. AgentService.createChat then resolves the IAgent from the parent session through getProviderForSession and stores peer membership without a separate provider-routing identity. The current architecture consequently supports independent SDK conversations inside one harness, not mixed harnesses inside one orchestrator session. The plan must trace chat-level provider identity through creation, central peer-catalog persistence, restoration, disposal, configuration, permissions, and telemetry while preserving provider-neutral shared Sessions code and the existing behavior of forks and side chats.

## Evidence

- **current Sessions contract:** src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:createNewChatInSession resolves the parent session's provider and calls provider.createNewChat(session.sessionId); src/vs/sessions/services/sessions/common/sessionsProvider.ts exposes no harness or session-type choice on createNewChat.
- **current Agent Host adapter:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:_createAdditionalChat uses the cached parent backend URI and calls connection.createChat with only the inherited model, then records model and agent selections on the new chat.
- **host routing constraint:** src/vs/platform/agentHost/node/agentService.ts:createChat obtains one provider through getProviderForSession(session), and _createChat invokes that provider's chats.createChat. The peer-chat catalog therefore has no independent harness-routing identity.
- **architecture boundary:** src/vs/sessions/SESSIONS.md currently defines creating a chat as a capability-gated operation on the session's owning provider, while src/vs/platform/agentHost/AGENTS.md documents session-level provider routing and chat-addressed operations within that harness.
