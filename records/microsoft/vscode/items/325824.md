# Issue #325824 — Support selecting different harnesses per multi-chat in the Agents window

[https://github.com/microsoft/vscode/issues/325824](https://github.com/microsoft/vscode/issues/325824)

## Summary

The requested per-chat harness selection remains absent on current main: secondary chats are created through the source session's provider and Agent Host harness. This team-authored feature should stay open for a cross-layer design and implementation.

## Change summary

Allow each multi-chat tab in the Agents window to choose and retain a harness independently of the source chat.

## Best solution

Expose an accessible harness picker when creating a secondary chat, then preserve and route that chat's selected harness independently across creation, sending, persistence, restoration, permissions, and telemetry without changing the source chat.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/newChatInSessionWidget.ts`, `src/vs/sessions/services/sessions/common/sessionsProvider.ts`, `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** Add focused Sessions and Agent Host tests that create a secondary chat with a harness different from the source, assert its requests route only to the selected harness, and verify both chats retain their selections after restoration; run the corresponding suites through scripts/test.sh with targeted --grep selectors.
- **Behavior:**

  > When creating a secondary chat in the Agents window, the user can choose any compatible harness available for that workspace. The new tab uses that harness for every interaction and retains the selection after reload, while the source chat's harness and state remain unchanged. The picker must be keyboard accessible, expose a localized accessible name and selection state, and remain discoverable in the existing chat composer.
- **Trace:**

  > NewChatInSessionWidget in src/vs/sessions/contrib/chat/browser/newChatInSessionWidget.ts binds its composer to the active session and sends through its active chat. ISessionsProvider.createNewChat and SessionsManagementService.createNewChatInSession carry only the owning session identity, while BaseAgentHostSessionsProvider._createAdditionalChat uses that session's connection and inherited model. AgentService.createChat in src/vs/platform/agentHost/node/agentService.ts resolves one provider from the owning session before invoking the exact-chat creation seam, so current main has no cross-harness target at this boundary. Preserve provider-neutral Sessions code, existing single-harness behavior, source-chat state, and AHP interoperability; https://github.com/microsoft/vscode/issues/335085 is related comparison work but does not own this per-tab behavior.
- **Open decisions:**
  - Should a different-harness tab remain a peer inside the originating orchestrator session, sharing its lifecycle and aggregate changes, or be represented as a separately owned harness session that the Agents window groups and presents as a tab?

## Evidence

- **current UI path:** src/vs/sessions/contrib/chat/browser/newChatInSessionWidget.ts constructs NewChatInputWidget for the active session and sends through that session's active chat; it does not consume a selected session type to create the peer chat on another harness.
- **provider contract:** src/vs/sessions/services/sessions/common/sessionsProvider.ts defines createNewChat(sessionId, prompt?) without a provider or session-type target, and src/vs/sessions/services/sessions/browser/sessionsManagementService.ts delegates createNewChatInSession solely to the owning session's provider.
- **agent-host routing:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts::_createAdditionalChat uses the existing connection and session and carries over its model; src/vs/platform/agentHost/node/agentService.ts::createChat resolves the harness with getProviderForSession(session) before creating the peer chat.
