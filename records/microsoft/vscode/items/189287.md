# Issue #189287 — Git - Problematic diff with nested repos

[https://github.com/microsoft/vscode/issues/189287](https://github.com/microsoft/vscode/issues/189287)

## Summary

Keep open: current source still resolves an outer repository's diff resource against the deepest open nested repository, even when that repository does not track the file. The Git area is already correctly assigned, and the related detection issue does not replace this report.

## Change summary

Show the outer repository's committed notebook content when comparing a changed file that is ignored by a nested repository.

## Best solution

Make Source Control comparisons resolve historical content in the repository whose change was selected, preserving independent comparisons when repositories overlap. Address this in the built-in Git extension rather than notebook rendering or repository discovery.

Also verify independent baselines when both repositories track the same file, ordinary non-nested comparisons, and submodule comparisons. Manually confirm the reported notebook diff displays the committed cells on the left.
- **Behavior:**

  > Selecting a changed notebook in the outer repository's Source Control view must compare it against that repository's committed or staged baseline, even when an open inner repository ignores it. The original side must contain the existing committed cells rather than appear empty or fail to resolve. When both repositories track a file, selecting each repository's change must use its own baseline. Ordinary comparisons and submodule behavior must remain unchanged.
- **Trace:**

  > ResourceCommandResolver.getLeftResource in extensions/git/src/repository.ts emits a git URI with ref '~' but without its owning repository. GitUriParams in extensions/git/src/uri.ts preserves only path, ref, and optional submoduleOf. GitFileSystemProvider in extensions/git/src/fileSystemProvider.ts resolves that URI through Model.getRepository; getOpenRepository in extensions/git/src/model.ts selects the deepest open ancestor regardless of tracking, conclusively reproducing the wrong-repository selection in source. The inner repository then cannot supply the notebook's HEAD content. The desired baseline is settled by the report and maintainer confirmation; do not broaden this into discovery changes or notebook-renderer changes. Planning must establish compatibility for existing git URIs and enumerate shared producers and invalidation consumers before implementation. The discovery issue at https://github.com/microsoft/vscode/issues/327119 is related but separately scoped.
