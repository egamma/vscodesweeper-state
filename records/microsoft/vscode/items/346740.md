# Issue #346740 — Agents window ignores dev.containers.dockerPath when creating Dev Container sessions with WSL Containers

[https://github.com/microsoft/vscode/issues/346740](https://github.com/microsoft/vscode/issues/346740)

## Summary

Keep open: the core Agents launcher still lacks configurable container-executable support, independently of the Dev Containers extension. Configuration ownership and supported wslc compatibility need a maintainer decision; the Linuxbrew detection issue does not cover this request.

## Change summary

Allow Agents-window Dev Container sessions to use the configured wslc executable instead of defaulting to docker.

## Best solution

Provide a supported container-executable selection for the core Agents launcher, consistently honored by CLI startup, exec, inspection, and lifecycle operations. Decide whether it shares dev.containers.dockerPath or has a core-owned setting, while preserving existing sandbox and network-boundary checks.

- **Behavior:**

  > A Windows project that opens successfully through wslc in the editor should have a supported way to start its Agents-window Dev Container session against that same runtime. Container preparation and subsequent operations must not silently switch to the unavailable default Docker daemon. The default Docker experience should remain unchanged. Acceptance includes the supplied Windows scenario and consistent executable selection across startup and subsequent operations.
- **Trace:**

  > DevContainerAgentHostService in src/vs/platform/agentHost/node/devContainerAgentHostService.ts owns the core startup independently of the extension. _resolveDockerExecutable resolves literal docker; _spawnDevContainer adds no --docker-path; connect invokes configuration reading and up before _getSandboxSupported performs direct inspection. Direct operations also serve discovery, cache/mount handling, and lifecycle management, so a startup-only CLI option would leave inconsistent behavior. DevContainerAgentHostMainService has desktop configuration access, whereas RemoteDevContainerAgentHostService inherits its launcher environment. The source confirms missing executable selection, not complete wslc compatibility. Preserve sandbox enforcement, conservative network-locality handling, and existing default behavior. The discussion at https://github.com/microsoft/vscode/issues/346740#issuecomment-6718437622 leaves configuration ownership unsettled.
- **Open decisions:**
  - Should desktop Agents sessions honor dev.containers.dockerPath, or expose a separate core-owned executable setting, and what precedence should apply if both are configured?
  - Is wslc an explicitly supported Agents container runtime, and what user-visible outcome should apply when its inspection capabilities cannot establish required sandbox support?
