# Issue #341177 — Respect Copilot CLI's enabled/disabled state for plugins discovered from ~/.copilot/installed-plugins/

[https://github.com/microsoft/vscode/issues/341177](https://github.com/microsoft/vscode/issues/341177)

## Summary

Thanks for the detailed report. The gap is real on main: the Copilot CLI installed-plugins store never reads the CLI's `enabled` or `enabledPlugins` state, so plugins disabled in the CLI show as enabled in VS Code. The work touches plugin enablement precedence (CLI user state vs VS Code override vs repo-level), so it needs a maintainer decision before implementation.

## Change summary

Honor Copilot CLI's user-level plugin enabled/disabled state as the default for plugins discovered under ~/.copilot/installed-plugins.

## Best solution

Have the CLI installed-plugins store read per-plugin enabled state from ~/.copilot/config.json and ~/.copilot/settings.json and use it as the default enablement. A VS Code user override or a repository-level enabledPlugins entry (https://github.com/microsoft/vscode/issues/336858) would take precedence.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/plugins/agentPluginEnablement.ts`, `src/vs/workbench/contrib/chat/test/common/plugins/copilotCliAgentPluginDiscovery.test.ts`, `src/vs/workbench/contrib/chat/test/common/plugins/agentPluginEnablement.test.ts`
- **Validation:** A test in copilotCliAgentPluginDiscovery.test.ts or agentPluginEnablement.test.ts asserting that a plugin with `enabled: false` in the CLI config is disabled by default, and that an explicit VS Code override or repo-level enablement wins.
- **Behavior:**

  > A plugin disabled in Copilot CLI (`enabled: false` in ~/.copilot/config.json, or `"<plugin>@<marketplace>": false` under enabledPlugins in ~/.copilot/settings.json) is disabled by default in VS Code. An explicit VS Code user override, or a repository enabledPlugins entry, takes precedence. Plugins enabled in the CLI behave as today.
- **Trace:**

  > CopilotCliInstalledPluginsStore in agentPluginServiceImpl.ts builds ICopilotCliInstalledPlugin records without any enabled flag. The default-enablement computation lives in agentPluginEnablement.ts, which already special-cases the CLI install path. The change needs the enabled state carried on the discovered plugin plus a default in the enablement logic. It must not change enablement for non-CLI plugins. Uncertainty starts at precedence and at whether settings.json is read as well as config.json.
- **Open decisions:**
  - Precedence order between CLI user-level state, a VS Code explicit override, and repository-level enabledPlugins?
  - Which CLI file wins when ~/.copilot/config.json and ~/.copilot/settings.json disagree?
  - Does VS Code keep tracking later CLI enable/disable changes, or only use them as the initial default?

## Evidence

- **current code:** src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts (CopilotCliInstalledPluginsStore, ~lines 1040-1110) parses ~/.copilot/config.json `installedPlugins` but reads only name, marketplace, cache_path, source, version, installed_at and source_sha. It never reads `enabled`.
- **settings.json:** No code reads ~/.copilot/settings.json `enabledPlugins`. The matches for `enabledPlugins` in src/vs are the policy, workspace, marketplace and Claude paths.
- **enablement:** src/vs/workbench/contrib/chat/common/plugins/agentPluginEnablement.ts handles the CLI install path (`/.copilot/installed-plugins/`) for enablement keys, but takes no default from the CLI's own state.
