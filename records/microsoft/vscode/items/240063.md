# Issue #240063 — Please add HTTPS support for serve-web

[https://github.com/microsoft/vscode/issues/240063](https://github.com/microsoft/vscode/issues/240063)

## Summary

The motivating `crypto.randomUUID` failure was fixed, but the distinct request for native HTTPS and certificate support remains unimplemented on main. The suggested issue is younger, closed, and covers only that browser failure, so it cannot absorb this re-reviewed feature request.

## Change summary

Allow `code serve-web` to serve HTTPS using custom certificates or an automatically generated temporary certificate.

## Best solution

Define an opt-in TLS contract for `serve-web`, including certificate/key configuration, HTTP coexistence or redirection behavior, and whether VS Code should generate self-signed certificates. Preserve the lightweight default while making direct LAN access available through a secure browser context.

## Plan brief

- **Likely files:** `src/server-main.ts`, `src/vs/server/node/serverEnvironmentService.ts`, `src/vs/server/node/remoteExtensionHostAgentServer.ts`, `src/vs/server/test/node`
- **Validation:** The plan should end with a server test that starts `serve-web` using test certificate material, successfully loads the workbench over HTTPS, and verifies the corresponding secure WebSocket upgrade while retaining the decided default HTTP behavior.
- **Behavior:**

  > When HTTPS is explicitly configured, `code serve-web` serves the workbench and its WebSocket connection through a secure browser context. Certificate configuration errors fail clearly rather than silently falling back to HTTP. Existing invocations without HTTPS configuration retain the maintainer-selected compatibility behavior. Acceptance includes loading the root workbench resource over HTTPS and completing a secure WebSocket upgrade.
- **Trace:**

  > `src/server-main.ts` owns the network listener and currently creates only a Node HTTP server; request and upgrade handling are delegated through `IServerAPI`. `src/vs/server/node/serverEnvironmentService.ts` defines the public server arguments and currently has no TLS-related options, while `src/vs/server/node/remoteExtensionHostAgentServer.ts` reports an `http://` Web UI URL. Commit ea8aabc6b65d996cdd9ef26118e506f25f38486c fixed the insecure-context UUID failure described in https://github.com/microsoft/vscode/issues/240334, but did not add HTTPS. Keep request routing, authentication tokens, and ordinary HTTP behavior unchanged except where the chosen public HTTPS contract requires otherwise; the uncertainty begins at certificate provisioning and HTTP coexistence semantics.
- **Open decisions:**
  - Should the first supported contract accept only user-provided certificate and private-key files, or also generate and manage a temporary self-signed certificate?
  - When HTTPS is configured, should the existing listener become HTTPS-only, retain a separate HTTP listener, or redirect HTTP requests?
  - What public CLI argument names and certificate formats should be supported, including whether encrypted private keys need a passphrase mechanism?

## Evidence

- **current implementation:** `src/server-main.ts` imports `node:http` and constructs the listener with `http.createServer`; it has no HTTPS server path.
- **missing CLI surface:** `src/vs/server/node/serverEnvironmentService.ts` registers host, port, socket, base-path, and connection-token options, but no TLS certificate, private-key, or temporary-certificate options.
- **motivating bug fixed:** https://github.com/microsoft/vscode/pull/241690 merged as commit ea8aabc6b65d996cdd9ef26118e506f25f38486c and fixed https://github.com/microsoft/vscode/issues/240334 by making `crypto.randomUUID` optional in insecure HTTP contexts.
- **not a duplicate:** https://github.com/microsoft/vscode/issues/240334 was created after this issue and is closed; it addressed the `randomUUID` crash rather than providing HTTPS or certificate configuration. No older open HTTPS canonical was found.
- **remaining gap:** `src/vs/server/node/remoteExtensionHostAgentServer.ts` still advertises the Web UI with an `http://` URL, confirming that native TLS is not exposed on current main.
