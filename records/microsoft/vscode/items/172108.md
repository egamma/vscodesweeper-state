# Issue #172108 — Document Content Providers are being passed URI-unescaped paths when invoked through the DAP

[https://github.com/microsoft/vscode/issues/172108](https://github.com/microsoft/vscode/issues/172108)

## Summary

The defect remains visible in current source: debug source URIs are parsed through `URI.parse`, which percent-decodes the path before the document content provider receives it. This team-authored issue should remain open while the DAP compatibility contract is designed.

## Change summary

Preserve meaningful percent-encoded characters in DAP source URI paths passed to document content providers.

## Best solution

Define a DAP-specific compatibility contract that can preserve encoded path separators for adapters that require them without globally changing established `URI` semantics, then cover encoded separators and Unicode paths with debug source tests.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugSource.ts`, `src/vs/workbench/contrib/debug/test/browser/debugSource.test.ts`, `src/vs/base/common/uri.ts`
- **Validation:** Extend the Debug Source unit suite with DAP URI paths containing `%2F` and encoded Unicode, asserting the contract selected by the maintainer while retaining existing filesystem, HTTP, and debug-source cases.
- **Behavior:**

  > When a debug adapter returns a URI-shaped `Source.path` containing an encoded path separator, the document content provider must receive a URI that still distinguishes that encoded separator from a literal hierarchy separator. Existing adapters using ordinary filesystem paths and normally encoded URI characters must retain their current behavior. Acceptance should cover `%2F`, literal `/`, encoded Unicode, and an ordinary file source.
- **Trace:**

  > `Source` passes DAP paths through `getUriFromSource` in `src/vs/workbench/contrib/debug/common/debugSource.ts`; URI-shaped strings take the `URI.parse(path)` branch. `URI.parse` in `src/vs/base/common/uri.ts` percent-decodes every URI component, making `%2F` indistinguishable from `/`. The resulting URI is forwarded unchanged through `MainThreadDocumentContentProviders` and revived by `ExtHostDocumentContentProviders` before the extension callback. Existing tests in `src/vs/workbench/contrib/debug/test/browser/debugSource.test.ts` cover ordinary paths but not encoded separators. Keep global URI behavior and non-DAP consumers out of scope unless the maintainer explicitly chooses a platform-wide contract; related user impact is documented at https://github.com/microsoft/AL/issues/7386.
- **Open decisions:**
  - Should preservation be an explicit debug-adapter opt-in/capability, or should all URI-formatted DAP `Source.path` values receive the new behavior?
  - Should the contract preserve every percent-encoded path sequence, including encoded Unicode, or only encoded path separators such as `%2F` and `%5C`?

## Evidence

- **current source:** `getUriFromSource` in `src/vs/workbench/contrib/debug/common/debugSource.ts` still handles URI-shaped DAP `Source.path` values with `URI.parse(path)`.
- **confirmed decoding:** `URI.parse` in `src/vs/base/common/uri.ts` calls `percentDecode` for the URI path, so an encoded slash such as `%2F` becomes `/` before the resource is opened.
- **provider path:** `src/vs/workbench/api/browser/mainThreadDocumentContentProviders.ts` forwards the resulting URI components, and `src/vs/workbench/api/common/extHostDocumentContentProviders.ts` revives them before invoking `provideTextDocumentContent`; neither stage restores the original encoded path.
- **maintainer investigation:** The discussion identifies the same `URI.parse` path and leaves the compatibility design unresolved: preserving encoded characters may change handling of other values such as encoded Unicode.
- **affected scenario:** https://github.com/microsoft/AL/issues/7386 confirms the observable failure for source names containing `/`; its closing comment says the AL-side work provides only most of the solution and leaves further improvement dependent on VS Code.
- **no canonical found:** Searches for open VS Code issues covering DAP source paths with percent-encoded separators found no broader canonical issue. The URI discussions linked in the thread are closed and do not own this remaining debug-specific behavior.
