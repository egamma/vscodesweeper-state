# Issue #334444 — CSP blocks loading extension font files when VSCODE_EXTENSIONS points to a network drive

[https://github.com/microsoft/vscode/issues/334444](https://github.com/microsoft/vscode/issues/334444)

## Summary

Real bug traced in current source: when the extensions directory is a UNC path, the browser-facing `vscode-file://` URL for extension assets keeps the UNC host as its authority instead of the app's fallback authority, so its origin no longer matches the workbench page's own `vscode-file://vscode-app` origin — which is exactly why CSP's `'self'` in `font-src` rejects the request. This needs a maintainer decision on the right fix (origin normalization vs. relaxing CSP), so it should be routed to an owner rather than closed.

## Change summary

Extension font (.woff2) assets fail to load with a CSP `font-src` violation when `VSCODE_EXTENSIONS` points at a UNC/network-share path, while the same extensions work fine from a local path.

## Best solution

In src/vs/base/common/network.ts, `FileAccessImpl.uriToBrowserUri` maps `file:` URIs to `vscode-file:` and deliberately keeps a real UNC authority (`uri.authority || FALLBACK_AUTHORITY`), per src/vs/base/common/uri.ts `URI.file()` which parses a `\\server\share\...` path into authority `server`. That makes the resulting resource URL's origin `vscode-file://server` instead of `vscode-file://vscode-app`, so it no longer satisfies `'self'` in the workbench CSP (src/vs/code/electron-browser/workbench/workbench.html font-src). A maintainer needs to decide whether to normalize extension-resource origins back to the fallback authority (carrying the real UNC host via a query/param the way COI headers already do) or to relax the relevant CSP directives to a scheme-only `vscode-file:` source — either fixes this without changing the underlying UNC file-serving logic.

## Evidence

- **origin mismatch source:** src/vs/base/common/network.ts `uriToBrowserUri()`: `authority: uri.authority || FileAccessImpl.FALLBACK_AUTHORITY` — preserves a non-fallback authority instead of always using `vscode-app`.
- **UNC authority parsing:** src/vs/base/common/uri.ts `URI.file()` parses `\\VMHFILE03\User-Folders$\...` into `authority = 'VMHFILE03'`, `path = '/User-Folders$/...'` — so a UNC extensions path yields a non-empty, non-fallback authority.
- **CSP directive:** src/vs/code/electron-browser/workbench/workbench.html font-src allows only `'self' vscode-remote-resource: vscode-managed-remote-resource: https://*.vscode-unpkg.net` — no scheme-only `vscode-file:` entry, so any authority other than the page's own (`vscode-app`) is rejected.
- **local-path contrast:** For a local extensions path, `file://` URIs have an empty authority, so `uriToBrowserUri` falls back to `vscode-app`, matching `'self'` and loading fine — consistent with the reporter's observation that local paths work.
