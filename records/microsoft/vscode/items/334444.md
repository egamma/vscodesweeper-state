# Issue #334444 — CSP blocks loading extension font files when VSCODE_EXTENSIONS points to a network drive

[https://github.com/microsoft/vscode/issues/334444](https://github.com/microsoft/vscode/issues/334444)

## Summary

Traced a real root cause on main: when the extensions directory is a UNC path, `URI.file()` sets the URI `authority` to the UNC server name, and `FileAccessImpl.uriToBrowserUri` (src/vs/base/common/network.ts) preserves that authority instead of falling back to `vscode-app` — producing `vscode-file://<server>/...` instead of `vscode-file://vscode-app/...`. That makes the font request cross-origin relative to the workbench document (`vscode-file://vscode-app`), so the `font-src 'self'` CSP directive rejects it exactly as reported.

## Change summary

Extension font (.woff2) assets fail to load with a CSP `blocked:csp` error when the extensions directory (VSCODE_EXTENSIONS) is a UNC/network path, because the resulting resource URL has a different origin than the main window.

## Best solution

In src/vs/base/common/network.ts `FileAccessImpl.uriToBrowserUri`, keep the browser-facing origin authority pinned to `vscode-app` even for UNC-authority file URIs (encoding the original UNC server elsewhere, e.g. in the path, similar to how `URI.file()` encodes UNC paths) so `'self'` CSP checks keep matching; `protocolMainService.ts`'s `uriToFileUri`/root-matching logic would need the inverse adjustment to still resolve the real UNC path server-side.
