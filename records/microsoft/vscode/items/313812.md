# Issue #313812 — Replace `AgentHostConfigKey.DefaultShell` magic key with a typed client→host channel

[https://github.com/microsoft/vscode/issues/313812](https://github.com/microsoft/vscode/issues/313812)

## Summary

The requested separation remains unimplemented: current main still forwards the shell through RootConfigChanged and reads it from the customization schema. Keep this team-authored debt item open; the merged shell-selection PR introduced the mechanism rather than replacing it.

## Change summary

Replace root-config-based default-shell forwarding with a typed client-to-host contract separate from user-editable customizations.

## Best solution

Establish a typed shell-configuration contract across the workbench and host while preserving existing shell selection, restart synchronization, and compatibility with older clients and headless hosts. Settle the wire contract and remote persisted-config migration before implementation; profile args/env and remote-shell discoverability remain separate work.

- **Behavior:**

  > The workbench's resolved local agent-host shell executable reaches the host through an explicit typed contract rather than user-editable customization configuration. Existing agent-host-profile precedence over the default terminal profile, subsequent profile updates, and restart synchronization remain intact. An inaccessible configured executable still falls back to the system shell. Older or third-party hosts continue working, and local executable paths are not sent to remote machines. Acceptance must include the agreed treatment of existing remote agent-host-config.json shell values; profile args/env support is outside this issue.
- **Trace:**

  > AgentHostTerminalContribution._resolveDefaultShell resolves the local profile and registers DefaultShell with AgentHostRootConfigForwarder. The forwarder's _push performs schema gating and equality checks before dispatching RootConfigChanged; AgentHostTerminalManager.getDefaultShell reads the same key through agentHostCustomizationConfigSchema. The shared enum already links the local key references, but the transport remains a generic config bag rather than a dedicated shell payload contract. The forwarder also handles unrelated keys, so its other forwarding behavior must remain unchanged. Current schema documentation supports remote operators setting defaultShell directly on disk, which makes removing the schema key a compatibility decision rather than only an internal refactor. The issue recommends a typed RPC but leaves the shared protocol surface and migration contract unsettled; interoperability guidance requires support for hosts without optional capabilities. https://github.com/microsoft/vscode/pull/313679 delivered executable selection, while https://github.com/microsoft/vscode/issues/313790 and https://github.com/microsoft/vscode/issues/313809 own separate args/env and remote-configuration work.
- **Open decisions:**
  - Should the typed shell channel be a standard AHP contract available to non-VS Code clients, or an optional negotiated VS Code extension?
  - What supported configuration surface and compatibility window should preserve existing headless and remote agent-host-config.json defaultShell values when client plumbing leaves the customization schema?
