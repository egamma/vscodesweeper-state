# Issue #213028 — Git - Clone and open a repository using 'code' command 

[https://github.com/microsoft/vscode/issues/213028](https://github.com/microsoft/vscode/issues/213028)

## Summary

Keep this accepted Backlog request open: current source does not support cloning and opening a repository from a plain repository URL passed to `code`. Existing clone URI support is a more cumbersome alternative, and the older CLI request is closed rather than an eligible duplicate target.

## Change summary

Allow a single `code` invocation to clone a remote Git repository locally and open the resulting folder.

## Best solution

Provide a first-class CLI clone-and-open workflow backed by the built-in Git extension. Agree on the CLI syntax, destination selection, and opening semantics before implementation, preserving ordinary file and folder arguments.

- **Behavior:**

  > A user can clone a remote Git repository locally and open its working folder with one `code` invocation, rather than separately running git clone and opening the resulting directory. The request proposes a plain repository URL as the argument, but the public CLI syntax and destination behavior need agreement. Acceptance should cover successful clone-and-open, destination selection, failure handling, and unchanged ordinary file/folder opening.
- **Trace:**

  > The native CLI option registry in src/vs/platform/environment/node/argv.ts has no clone entry, and CodeMain.validatePaths in src/vs/code/electron-main/main.ts treats ordinary positional inputs as filesystem paths unless --open-url is present. GitProtocolHandler in extensions/git/src/protocolHandler.ts already accepts /clone application URIs and invokes git.clone. Commands.clone in extensions/git/src/commands.ts delegates to CloneManager, which accepts a parentPath, otherwise prompts using git.defaultCloneDirectory, and handles opening through git.openAfterClone. These existing behaviors establish reusable capability, not coverage of the requested direct CLI interface. Preserve normal path interpretation and existing URI clone behavior; avoid broadening this into remote browsing or Codespaces support. https://github.com/microsoft/vscode/issues/106917 records earlier discussion of bare-URL versus explicit-flag syntax, but its closed status and historical decline do not settle the contract of this subsequently accepted request.
- **Open decisions:**
  - Should cloning require an explicit CLI flag or subcommand, or should a bare repository URL trigger cloning as the reporter proposes?
  - Should the clone destination default to the invoking working directory, follow git.defaultCloneDirectory, or retain an interactive destination prompt?
  - Should the CLI operation always open the cloned folder, or honor git.openAfterClone, including its default confirmation prompt and window-selection behavior?
