# Issue #333131 — Agents window: unable to create PR when remote is not origin

[https://github.com/microsoft/vscode/issues/333131](https://github.com/microsoft/vscode/issues/333131)

## Summary

Real, traceable gap: the create-PR push path in AgentHostPullRequestOperationHandler falls back to a hardcoded 'origin' remote whenever the branch has no upstream tracking ref yet, ignoring the repository's actual GitHub remote name — exactly matching the reporter's log. Milestone is 'On Deck', a holding bin, so it doesn't block judging this on its merits, but the fix is cross-cutting enough that it should stay open for a maintainer/engine pass rather than auto-fix.

## Change summary

Creating a PR from the Agents window silently fails when the working copy's git remote is not literally named "origin".

## Best solution

Surface the resolved GitHub remote's actual git remote name (not just owner/repo) in ISessionGitState (computed in agentHostGitService.ts's _computeSessionGitState, alongside githubHeadOwner), and have AgentHostPullRequestOperationHandler use that name instead of the literal 'origin' fallback when calling gitService.push for a branch with no upstream yet.

## Evidence

- **hardcoded fallback:** src/vs/platform/agentHost/node/agentHostPullRequestOperationHandler.ts:333,337 logs and pushes to `upstreamBranch?.remote ?? 'origin'`; `upstreamBranch` comes from `parseUpstreamBranchName(gitState?.upstreamBranchName)`, which is undefined until the branch already has an upstream tracking ref.
- **push() default:** src/vs/platform/agentHost/node/agentHostGitService.ts:479-497 `push()` appends `options.remote ?? 'origin'` whenever a ref is passed without an explicit remote — so an undefined remote always resolves to the literal string 'origin'.
- **remote name never surfaced:** ISessionGitState (src/vs/platform/agentHost/common/state/sessionState.ts:1584-1613) only exposes `githubOwner`/`githubHeadOwner`/`githubRepo` (parsed via parseGitHubRepoFromRemote in agentHostGitService.ts), never the actual git remote *name* backing them, so the PR handler has no non-'origin' name to fall back on for a brand-new branch.
- **reporter log matches:** The issue's log shows `git push --set-upstream origin <branch>` failing with "'origin' does not appear to be a git repository" — consistent with this hardcoded fallback when the real remote has a different name.
