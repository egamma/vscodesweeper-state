# Issue #94562 — Trim Final Newlines integrates poorly with EditorConfig for Windows files

[https://github.com/microsoft/vscode/issues/94562](https://github.com/microsoft/vscode/issues/94562)

## Summary

The requested zero-final-EOL policy remains unsupported by the existing save settings. Keep this accepted, 25-upvote feature request open; related requests do not meet the stronger duplicate bar for this re-reviewed item.

## Change summary

Support per-file final-EOL policies that can remove every trailing EOL while preserving excluded files and newline-only content.

## Best solution

Provide an explicit per-file final-EOL policy that interoperates with EditorConfig and preserves the requested exceptions, without changing existing trimming defaults. Resolve the public configuration and precedence semantics before implementation in the text-file save pipeline.

Run ./scripts/test.sh --run src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts; separately verify the agreed EditorConfig interaction using representative AHK and ordinary text files.
- **Behavior:**

  > An explicit per-file policy should allow nonempty files to end in zero EOL sequences or exactly one LF, as requested, while excluded binary and patch files remain unchanged. Files containing exactly one EOL must also remain unchanged. Existing save behavior must remain compatible unless users explicitly select the new policy. Acceptance must cover both LF and CRLF input and an EditorConfig-configured file; CR-only handling needs an agreed supported boundary.
- **Trace:**

  > FinalNewLineParticipant and TrimFinalNewLinesParticipant in src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts read resource/language configuration independently and are registered consecutively in the save pipeline. The trimming deletion begins on the line after the last nonempty line, which preserves its terminating EOL; its existing tests explicitly require that behavior. files.contribution.ts exposes Boolean insertion and trimming settings, but no explicit zero-final-EOL policy in this path. This establishes a missing capability rather than a broken implementation of the existing setting. Preserve legacy defaults, undo behavior, and autosave cursor protection. https://github.com/microsoft/vscode/issues/65663 documents the related extension/save-configuration boundary, while https://github.com/microsoft/vscode/issues/111396 tracks broader built-in EditorConfig support; neither settles this request's policy semantics.
- **Open decisions:**
  - Should removing the final EOL require a separate explicit policy, or should an existing insertion/trimming configuration combination acquire that meaning?
  - How should per-file EditorConfig policy take precedence over VS Code save settings, and should this work include native EditorConfig interpretation or only an integration contract?
  - Are extension-based exceptions supplied by users' per-file configuration, or does the requested feature include built-in file-type rules and CR-only preservation?

## Evidence

- **Existing capability and remaining gap:** src/vs/workbench/contrib/files/browser/files.contribution.ts:216–261 registers language-overridable files.eol, files.insertFinalNewline, and files.trimFinalNewlines. The trimming setting explicitly removes newlines after the final newline; disabling insertion does not request removal of an existing final EOL. These settings partially cover the one-EOL policy but not the central zero-EOL request.
- **Current source behavior:** In src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts, FinalNewLineParticipant only inserts an EOL when enabled. TrimFinalNewLinesParticipant.doTrimFinalNewLines starts deletion at lastNonEmptyLine + 1, column 1, preserving the EOL after the final nonempty line. For a nonempty AHK file ending in CRLF, explicit saving therefore retains one CRLF even with files.insertFinalNewline=false and files.trimFinalNewlines=true.
- **Intended behavior, not a regression:** The 'trim final new lines' test in src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts explicitly preserves one existing final EOL and reduces multiple final EOLs to one.
