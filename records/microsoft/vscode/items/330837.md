# Issue #330837 — Agent Sessions: GitHub MCP tools lost permanently after a credential failure — no retry, no reset path, no error surfaced

[https://github.com/microsoft/vscode/issues/330837](https://github.com/microsoft/vscode/issues/330837)

## Summary

Thanks for the detailed root-cause writeup — I traced a concrete, matching bug in the built-in GitHub MCP definition provider: a sticky `_askedForAuth` flag in `GitHubMcpDefinitionProvider.resolveMcpServerDefinition` permanently blocks any further auth attempt after the first resolution (success or failure) for the lifetime of that singleton provider instance, and it is never reset when auth state later changes. This independently reproduces the 'never recovers, no retry' symptom, though I can't fully confirm from source alone that it explains persistence across full app relaunches (which would normally recreate the provider) — some of that may involve Agent Host/CLI-side state outside this repo.

## Change summary

After a GitHub credential handoff failure, Agent Sessions permanently lose the built-in GitHub MCP server with no retry, no reset affordance, and no surfaced error.

## Best solution

In extensions/copilot/src/extension/githubMcp/common/githubMcpDefinitionProvider.ts, stop treating any auth attempt as a permanent 'user declined' state: reset `_askedForAuth` (or replace it with a state that distinguishes an explicit user decline from a token failure) whenever `authenticationService.onDidAuthenticationChange` reports a session becoming available again, so a later healthy re-auth is actually retried instead of short-circuiting into 'User denied authentication'. Separately, the swallow-and-warn catch in `CopilotCLIMCPHandler.addBuiltInGitHubServer` (extensions/copilot/src/extension/chatSessions/copilotcli/node/mcpHandler.ts) should surface the failure somewhere the user can see it (server list state or session UI), not just a trace/warn log.

## Evidence

- **sticky auth flag:** extensions/copilot/src/extension/githubMcp/common/githubMcpDefinitionProvider.ts resolveMcpServerDefinition(): once `_askedForAuth` is set true in the `finally` block of the first no-token resolution attempt, every subsequent call with a missing/invalid accessToken throws 'User denied authentication...' immediately instead of retrying `getGitHubSession`.
- **no reset on auth recovery:** The same file's constructor already listens to `authenticationService.onDidAuthenticationChange` (used only to re-fire `onDidChangeMcpServerDefinitions`), but never resets `_askedForAuth`, so a later healthy sign-in does not unblock resolution.
- **singleton lifetime:** extensions/copilot/src/extension/githubMcp/vscode-node/githubMcp.contribution.ts constructs exactly one `GitHubMcpDefinitionProvider` for the extension host's lifetime via `lm.registerMcpServerDefinitionProvider('github', ...)`, and the Sessions-window gateway path (extensions/copilot/src/extension/chatSessions/copilotcli/node/mcpHandler.ts loadMcpConfigWithGateway) proxies through this same shared registration, matching the 'agent sessions lose GitHub tools' symptom.
