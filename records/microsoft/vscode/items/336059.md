# Issue #336059 — Markdown Preview does not reveal the clicked Search result when it is the default editor for .md files

[https://github.com/microsoft/vscode/issues/336059](https://github.com/microsoft/vscode/issues/336059)

## Summary

The built-in Markdown Preview uses the same custom-editor navigation path tracked by the older, open canonical issue. Both report Search opening the editor without revealing the clicked match, so consolidate this report while preserving its built-in-preview reproduction.

## Change summary

Reveal the clicked Search match when the built-in Markdown Preview is the default editor for Markdown files, including subsequent matches in an already-open preview.

## Best solution

Resolve target-range delivery and handling under https://github.com/microsoft/vscode/issues/289785, with the built-in Markdown Preview included as a consumer and acceptance scenario for both initial opens and subsequent navigation.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/289785 is currently OPEN and was created on 2026-01-22, before this report's 2026-09-13 creation. It explicitly describes the same observable symptom: clicking a global Search match opens a custom editor without navigating to the target line or range. Its scope covers custom editors generally, including the built-in preview.
- **Built-in preview shares the affected path:** extensions/markdown-language-features/src/preview/previewManager.ts registers MarkdownPreviewManager as a CustomTextEditorProvider for StaticMarkdownPreview.customEditorViewType; extensions/markdown-language-features/src/preview/preview.ts defines that ID as vscode.markdown.preview.editor. Built-in ownership therefore does not bypass the custom-editor API path.
- **Missing navigation target in current source:** src/vs/workbench/api/common/extHostCustomEditors.ts calls resolveCustomTextEditor(document, panel, cancellation) without a target range. MarkdownPreviewManager.#resolveCustomTextEditor initializes scrolling from TopmostLineMonitor's previous text-editor position, not the clicked Search match. StaticMarkdownPreview listens for text-editor scroll changes, but has no corresponding Search-target notification.
- **Repeated-match navigation:** src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts, WebviewEditor.setInput, returns immediately when the input matches the existing input and does not deliver selection options to the webview. This supports the reported second-click failure as part of the same missing custom-editor navigation mechanism.
- **Corroborating canonical discussion:** https://github.com/microsoft/vscode/issues/289785#issuecomment-5587491538 describes a default Markdown custom editor opening at the top after a Search click and being unable to identify which match was clicked. This is the same reporter-observable symptom required by the re-review duplicate bar.
- **Other linked report:** https://github.com/microsoft/vscode/issues/301887 describes the same range-delivery gap but is CLOSED following the feature-request community process, so it is not used as the duplicate target.
