# Issue #253297 — Should account name be account authentication url instead of `MCP`

[https://github.com/microsoft/vscode/issues/253297](https://github.com/microsoft/vscode/issues/253297)

## Summary

Keep open: current source still falls back to 'MCP' for unnamed accounts, so the requested improvement remains relevant. This is team-authored, accepted Backlog work with maintainer support; no qualifying fix or duplicate was established.

## Change summary

Use an authentication-host name instead of the generic 'MCP' account label in account selection and sign-out surfaces.

## Best solution

Show a meaningful authentication-host fallback when tokens provide no account name, while retaining genuine account names. Account selection, Accounts-menu entries, and sign-out confirmation should agree without losing existing account preferences or trusted-access associations.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostAuthentication.ts`, `src/vs/workbench/api/test/browser/extHostAuthentication.test.ts`, `src/vs/workbench/services/authentication/browser/authenticationMcpService.ts`, `src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts`, `src/vs/workbench/browser/parts/globalCompositeBar.ts`, `src/vs/workbench/contrib/authentication/browser/actions/signOutOfAccountAction.ts`
- **Validation:** Extend the TokenStore/DynamicAuthProvider tests in src/vs/workbench/api/test/browser/extHostAuthentication.test.ts to cover opaque tokens and tokens without account-name claims, preserving named-account precedence. Verify the PayPal-style account picker, Accounts-menu entry, and sign-out confirmation use the intended host identification, including restored sessions and existing account preferences/trusted access.
- **Behavior:**

  > An MCP account with no usable account-name claims should be identified by its authentication host rather than the generic 'MCP' label. The PayPal example should identify mcp.paypal.com in account selection and account-management/sign-out surfaces. Genuine account names should remain meaningful, and restored sessions should retain their existing preferences and trusted-access associations.
- **Trace:**

  > TokenStore._getSessionFromToken in src/vs/workbench/api/common/extHostAuthentication.ts conclusively retains the 'MCP' fallback when preferred_username, name, and email are absent. DynamicAuthProvider knows the authorization server and provider display label, but its TokenStore construction does not pass host information. AuthenticationMcpService.selectSession renders the account label independently of the provider title; globalCompositeBar and SignOutOfAccountAction consume the same account label. AuthenticationMcpService and AuthenticationExtensionsService also use account labels for persisted preferences and access associations, so the compatibility trace must be completed before treating this as a local display change. Preserve token exchange, scopes, real account-name precedence, and existing authorization decisions. The accepted direction is recorded at https://github.com/microsoft/vscode/issues/253297#issuecomment-3058281494.

## Evidence

- **remaining fallback:** src/vs/workbench/api/common/extHostAuthentication.ts:1086–1116, TokenStore._getSessionFromToken, still assigns claims?.preferred_username || claims?.name || claims?.email || 'MCP', with an explicit 'TODO: Don't say MCP...' comment. Opaque tokens and tokens lacking these claims retain the reported generic label.
- **existing capability is partial:** DynamicAuthProvider already labels the provider using resource_metadata.resource_name or authorizationServer.authority at src/vs/workbench/api/common/extHostAuthentication.ts:515–522. This identifies the provider, not the account: AuthenticationMcpService.selectSession displays session.account.label in rows while using provider.label in the title, matching the distinction reported.
- **account management:** src/vs/workbench/browser/parts/globalCompositeBar.ts:564–583 renders dynamic accounts as account.label (provider.label). src/vs/workbench/contrib/authentication/browser/actions/signOutOfAccountAction.ts uses accountLabel in sign-out confirmation and session matching; the generic account label remains consequential even though current menu wording differs from the original screenshot.
- **maintainer acceptance:** https://github.com/microsoft/vscode/issues/253297#issuecomment-3024220966 extends the request to sign-out identification. https://github.com/microsoft/vscode/issues/253297#issuecomment-3058281494 records TylerLeonhardt's 'Good idea.' - **canonical and history checks:** Open-issue searches for MCP account names and labels, including an older-than-report search, did not establish an older canonical with the same observable symptom. The checkout is shallow with one available commit; its history contains no reference to this issue, so historical fix coverage cannot be inferred.
- **compatibility boundary:** AuthenticationMcpService stores account.label as the account preference and uses account labels for trusted-access updates. TokenStore currently receives persistence, tokens, and a logger but no authorization-host context. Changing the fallback therefore needs more than a cosmetic string replacement.
