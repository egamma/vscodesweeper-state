# Issue #339960 — Copilot SDK sessions: MCP authentication-required tool calls do not trigger native VS Code sign-in

[https://github.com/microsoft/vscode/issues/339960](https://github.com/microsoft/vscode/issues/339960)

## Summary

Real, corroborated gap in the Agent Host / Copilot SDK session's MCP authentication flow: an OAuth-protected MCP tool call surfaces a raw 'requires authentication' error instead of VS Code's native sign-in. A second reporter (eddydee123) reproduced the same symptom independently with logs, but the exact failure boundary overlaps with the narrower, already-assigned issue #340483, so I'm keeping this open rather than guessing at a fix.

## Change summary

Invoking a tool on an OAuth-protected remote MCP server in a Copilot SDK-backed session returns a sanitized auth-required error instead of offering a native VS Code sign-in prompt.

## Best solution

Clarify scope against https://github.com/microsoft/vscode/issues/340483 (assigned, same underlying diagnosis: empty/incomplete protected-resource metadata prevents the renderer from constructing a dynamic auth provider) — either this is the same root cause and should consolidate there, or it covers additional cases (servers that do advertise correct protected-resource metadata) that need separate handling in agentHostAuth.ts's AgentHostAuthenticationRecovery path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostProtectedResourcesService.ts`
- **Validation:** Manual repro: configure a remote HTTP MCP server with OAuth/dynamic client registration and no completed auth, start a Copilot SDK-backed session, invoke a server tool, and confirm a native VS Code sign-in prompt appears and the call is retried after authorization — rather than the raw '/mcp auth' error text.
- **Behavior:**

  > When an MCP tool call fails because the server requires OAuth authentication, VS Code should present a native Sign in prompt, let the user authorize or cancel, and then resume the session and safely retry the read-only call. Currently the assistant only surfaces the sanitized 'requires authentication... Run /mcp auth' text with no sign-in UI. Acceptance: reproducing the steps in the issue results in a native sign-in affordance, and after completing sign-in the original tool call succeeds without the user manually running any CLI command.
- **Trace:**

  > AgentHostAuthenticationRecovery (src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts) and the McpAuthRequirement tracking in copilotAgentSession.ts (src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts, _lastMcpAuthRequirements) exist specifically to drive this native sign-in flow, so the challenge is expected to reach the host — but it doesn't surface for at least some servers. The corroborating comment traces this to the renderer being unable to construct a dynamic auth provider for the authorization server, which https://github.com/microsoft/vscode/issues/340483 attributes to empty/missing `authorization_servers` in a protected-resource-metadata fallback. Do not assume these are definitely the same defect — this issue's report doesn't establish whether the reporter's server advertised protected-resource metadata correctly, so the scope boundary between the two issues needs confirming before changing code.
- **Open decisions:**
  - Is this the same root cause as https://github.com/microsoft/vscode/issues/340483 (should it be consolidated there), or does it also cover servers with correct protected-resource metadata that still don't get a native sign-in prompt?
  - When the renderer cannot construct a dynamic auth provider for an MCP server, should it fall back to a generic/manual sign-in flow, or must protected-resource metadata be fixed upstream first?

## Evidence

- **existing auth-recovery machinery:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts defines AgentHostAuthenticationRecovery, agentHostMcpServerId() and protectedResourceAuthenticationKey() specifically to drive native sign-in from a protected-resource challenge, so the intended flow exists in code.
- **MCP auth requirement plumbing:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts tracks McpAuthRequirement per server (_lastMcpAuthRequirements) and has an onMcpAuthRequest handler type, confirming the SDK session is expected to surface auth challenges back to the host for native handling.
- **independent corroboration:** Comment from eddydee123 reproduces the identical symptom on macOS with two different OAuth MCP servers, including agenthost.log output showing 'the renderer then can't create an auth provider for the authorization server' — a confirmed repro, not just a title-only report.
- **related assigned issue:** https://github.com/microsoft/vscode/issues/340483 (filed by the same corroborating commenter, open, assigned to TylerLeonhardt) attributes this to MCP servers without protected-resource metadata getting an empty authorization_servers fallback — a plausible but narrower root cause than this issue's general framing.
