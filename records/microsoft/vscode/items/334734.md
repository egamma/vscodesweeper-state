# Issue #334734 — Trying to switch to a remote workspace does not work

[https://github.com/microsoft/vscode/issues/334734](https://github.com/microsoft/vscode/issues/334734)

## Summary

Keep open: current main intentionally limits Quick Chat workspace conversion to local `file:` workspaces, so remote Tunnel workspaces remain an unsupported capability. This team-authored Backlog request came directly from exploratory testing and no older issue owns the same observable workflow.

## Change summary

Allow a workspace-less Quick Chat to continue in a remote workspace selected through a VS Code Tunnel.

## Best solution

Support a remote-workspace conversion or handoff that preserves the session identity, title, history, and pending request while continuing execution on the workspace's owning remote Agent Host. Define remote isolation and reconnection behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts`, `src/vs/platform/agentHost/test/node/sessionServerTools.test.ts`, `src/vs/platform/agentHost/test/node/sessionWorkspaceConversion.test.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/REMOTE_AGENT_HOST_SESSIONS_PROVIDER.md`
- **Validation:** Exercise a workspace-less Quick Chat against a Tunnel `vscode-remote` folder and verify conversion succeeds, preserves the same session/chat identity and history, continues the original request on the remote workspace, and survives switching away and reloading; retain focused tests proving unsupported URI schemes are still rejected.
- **Behavior:**

  > A workspace-less Quick Chat can be switched to a folder exposed through a VS Code Tunnel. The existing session identity, title, conversation history, and current request remain intact, and subsequent tools operate in the selected remote workspace. The converted session remains associated with that workspace after navigation and reload. Unsupported workspace targets must still produce a clear error rather than partially converting the session.
- **Trace:**

  > The reported URI reaches `getSetWorkspaceArgs` in src/vs/platform/agentHost/node/shared/sessionServerTools.ts, where every scheme except `file` is rejected. SessionWorkspaceConversionService._validateConversion repeats that local-only restriction, and _convert then asks the existing provider to adopt a local working-directory URI, including local trust and worktree handling. Current tests deliberately lock in rejection of `vscode-remote` URIs. Remote Agent Host routing and identity are owned by the provider layer described in src/vs/sessions/contrib/providers/remoteAgentHost/REMOTE_AGENT_HOST_SESSIONS_PROVIDER.md, so the uncertainty begins at whether conversion transfers the chat to that provider or introduces another remote-directory contract. Do not conflate this with remote folder context attachment tracked by https://github.com/microsoft/vscode/issues/330280.
- **Open decisions:**
  - When a local workspace-less chat selects a Tunnel workspace, should the visible session be handed off to the workspace's remote Agent Host, or should it remain owned by the original host with a remote-working-directory contract?
  - For remote targets, should isolated conversion create and own a worktree on the remote host, or should the workflow initially support only direct-folder conversion?
