## Summary

Keep this accepted, strongly supported request open: browser-based VS Code provides an iPad option, but does not cover the standalone, local/offline experience requested in the discussion. The related native-iPad request is newer, and the Safari tracking issue covers browser usability rather than the full remaining capability.

## Change summary

Provide VS Code on iPad as a standalone development experience, including local projects without requiring another computer or a cloud workspace.

## Plan brief

- **Likely files:** `build/gulpfile.vscode.ts`, `build/gulpfile.vscode.web.ts`, `src/vs/base/common/platform.ts`, `src/vs/workbench/services/extensions/browser/extensionService.ts`
- **Validation:** After agreeing the supported capabilities, validate on an iPad that a local project can be opened, edited, saved and reopened without connectivity or another computer. Separately exercise the agreed extension and execution capabilities, and ensure existing browser and desktop experiences remain unchanged.
- **Behavior:**

  > The discussion requests a standalone VS Code experience on iPad, not only access to a remotely hosted development environment. Existing browser, Codespaces and tunnel options address part of the request but do not settle local/offline project ownership and development. Acceptance must include the agreed local project workflow without another computer or a persistent network connection. Terminal, debugging and extension expectations need an explicit supported-capability contract before implementation.
- **Trace:**

  > The checkout recognizes iPad/iPhone through the web branch of src/vs/base/common/platform.ts, and build/gulpfile.vscode.web.ts packages a browser workbench with web extensions and PWA assets. The native BUILD_TARGETS in build/gulpfile.vscode.ts cover Windows, macOS and Linux, not iPadOS. The browser ExtensionService in src/vs/workbench/services/extensions/browser/extensionService.ts declares hasLocalProcess: false and supports web-worker or remote extension execution; it does not establish local desktop-style execution on iPad. This is a platform/product effort rather than a bounded missing setting or command. Preserve existing desktop and web behavior; do not assume a web wrapper or third-party fork satisfies standalone development. https://github.com/microsoft/vscode/issues/85254 owns related Safari usability work, while https://github.com/microsoft/vscode/issues/255717 is a newer overlapping native request. The uncertainty starts at the supported local filesystem, runtime and extension contract, not at whether browser access already exists.
- **Open decisions:**
  - What local/offline project-access and persistence capabilities must the first supported standalone iPad experience provide?
  - Which terminal, code-execution, debugging and extension capabilities must run locally on iPad, and which may explicitly require a remote host?
