## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts`, `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`

A deliberate unmodified left click must yield a press and release in all four cases; dragging must additionally yield button-held motion in mode 1002, while mode 1003 retains motion reporting. Compare with Windows Terminal using the same shell and probe.
- **Behavior:**

  > The reporter's terminal delivers mouse presses but no matching releases in normal, button-event, or any-event tracking, using both legacy and SGR encodings. Button-held motion is also absent in mode 1002 although mode 1003 motion works. Acceptance requires complete press/release pairs in every supplied case and button-held motion in mode 1002 on current VS Code. Ordinary text selection, modifier-assisted selection, and terminal link activation must retain their existing behavior.
- **Trace:**

  > TerminalInstance connects xterm onData to _handleOnData, which forwards to TerminalProcessManager.write, and separately forwards onBinary to processBinary. Those inspected sites contain no mouse-event-specific filtering. XtermTerminal constructs xterm with documentOverride pointing to the main container's document, while TerminalInstance.attachToElement reopens the existing xterm element after reattachment; document ownership is a diagnostic lead, not a confirmed cause for this report. The open https://github.com/microsoft/vscode/issues/202410 describes the same event omissions specifically in auxiliary windows, whereas this report does not state that condition. Reproduce the supplied matrix before deciding whether that canonical applies or whether a separate integration or upstream defect remains. Keep alternate-buffer wheel handling and Ctrl+click malformed-coordinate behavior outside this issue's initial scope.
