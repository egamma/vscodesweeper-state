# Issue #332831 — AHP 1.0 createSession does not emit session/ready until the first turn

[https://github.com/microsoft/vscode/issues/332831](https://github.com/microsoft/vscode/issues/332831)

## Summary

Traced this in the checkout: for a Copilot-CLI-backed session, `createSession` deliberately defers `SessionReady` until the first turn materializes the SDK backing (a lazy-materialization optimization), which matches the reporter's exact symptom and creates a real deadlock for strict AHP 1.0 clients that wait for readiness before sending a turn.

## Change summary

AHP 1.0 `createSession` withholds `session/ready`/`session/creationFailed` for provisional (lazily-materialized) sessions until the client sends a first turn, contradicting the documented wait-for-ready-before-first-turn ordering.

## Best solution

A maintainer needs to reconcile the AHP 1.0 spec's readiness ordering with the intentional lazy-materialization design in `AgentService.createSession`/`CopilotAgent.createChat` — either the protocol doc needs an explicit provisional-session carve-out, or the host needs a way to signal readiness (or an explicit provisional/pending state) without requiring the client to violate ordering; this is a protocol-conformance decision, not a one-line fix.
