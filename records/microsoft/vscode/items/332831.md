# Issue #332831 — AHP 1.0 createSession does not emit session/ready until the first turn

[https://github.com/microsoft/vscode/issues/332831](https://github.com/microsoft/vscode/issues/332831)

## Summary

Current main conclusively retains the reported lifecycle behavior: provisional sessions remain `creating` until the default chat materializes, normally during the first send. This distinct protocol deadlock should remain open and route to the Agent Host area.

## Change summary

Make AHP session creation reach `session/ready` or `session/creationFailed` before a client must dispatch its first turn.

## Best solution

Reconcile provisional provider initialization with the AHP lifecycle contract so a client can wait for a terminal creation outcome before sending a turn, while preserving lazy provider startup where the protocol permits it.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/test/node/agentService.test.ts`
- **Validation:** Extend the AgentService unit tests with a provisional provider and assert that subscribing after `createSession` observes `SessionReady` or `SessionCreationFailed` without dispatching `ChatTurnStarted`, while existing first-send materialization tests continue to pass.
- **Behavior:**

  > After a successful AHP `createSession`, subscribing to the new session must eventually produce either `session/ready` or `session/creationFailed` without requiring a chat turn. A strict client that waits for readiness before dispatching its first turn must not deadlock. Once ready, the first real turn must still materialize and run normally, and failed initialization must remain terminal and visible.
- **Trace:**

  > In src/vs/platform/agentHost/node/agentService.ts, `createSession` records provider results with `provisional: true` as lifecycle `Creating` and deliberately skips `ActionType.SessionReady`. `_onDidMaterializeChat` is the only normal path that marks that provisional session persisted and dispatches `SessionReady`; provider materialization is deferred until first send. Tests in src/vs/platform/agentHost/test/node/agentService.test.ts explicitly model this first-send persistence and confirm that turn activity can occur while lifecycle remains `Creating`. Preserve provisional-session catalog suppression and lazy provider-resource behavior unless the chosen lifecycle semantics require eager initialization; do not conflate this with the post-dispatch hangs in https://github.com/microsoft/vscode/issues/331118 or https://github.com/microsoft/vscode/issues/336146.
- **Open decisions:**
  - Should `session/ready` mean that the protocol-visible session and default chat are usable while the provider SDK backing remains lazily materialized, or must `createSession` eagerly materialize that backing before emitting readiness?
