# Issue #332831 — AHP 1.0 createSession does not emit session/ready until the first turn

[https://github.com/microsoft/vscode/issues/332831](https://github.com/microsoft/vscode/issues/332831)

## Summary

Traced this in the source and it's real: Copilot (and any provider that returns `provisional: true` from `createSession`) deliberately defers both `sessionAdded` and the `SessionReady` lifecycle dispatch until `onDidMaterializeChat` fires, which itself only fires on the first `sendMessage`. That's an intentional internal optimization for VS Code's own composer UI (which is allowed to send a neutral first turn), but it deadlocks a strict AHP 1.0 client that waits for `session/ready` before sending anything.

## Change summary

For providers that create sessions provisionally (e.g. copilotcli), `session/ready` never arrives until the client sends a first turn, contradicting the documented AHP 1.0 lifecycle contract that clients should wait for readiness before sending.

## Best solution

This needs a product/maintainer decision on how external AHP 1.0 clients are meant to interoperate with the provisional-session optimization: either eagerly materialize (or emit a distinct 'provisional but usable' lifecycle signal) for non-VS-Code clients, or make the documented protocol lifecycle explicitly account for the provisional exception so third-party clients don't deadlock. The relevant code is `AgentService.createSession`/`_onDidMaterializeChat` in src/vs/platform/agentHost/node/agentService.ts and the provisional-session logic in src/vs/platform/agentHost/node/copilot/copilotAgent.ts.
