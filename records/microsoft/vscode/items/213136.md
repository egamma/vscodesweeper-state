## Evidence

- **Confirmed performance reports:** The original report describes CPU saturation on Linux with extensions disabled. Comments 17 and 28 independently report a busy fileWatcher process and continued saturation after a fresh installation with no installed extensions; comment 28 identifies VS Code 1.108.2 on Debian 13. These establish credible observed reproductions, not a source-confirmed defect on current main.
- **Different causes in the discussion:** Comments 9 and 21 identify GitLens in their environments, while comments 10–11 explicitly report that disabling GitLens and extension bisect did not resolve their cases. Other comments implicate different extensions, large watched directories, TypeScript logging, or Git scanning. No single extension attribution covers the original report and these independent confirmations.
- **Current process boundary:** src/vs/platform/utilityProcess/electron-main/utilityProcess.ts, UtilityProcess.doStart, launches configurable entry points through Electron utilityProcess.fork and assigns a service name. src/vs/workbench/services/files/electron-browser/watcherClient.ts, UniversalWatcherClient.createWatcher, launches watcherMain with type 'fileWatcher'; extensionHostStarter.ts and electronPtyHostStarter.ts also use utility-process types. The generic NodeService command line therefore does not establish which workload is consuming CPU.
- **CPU display discrepancy:** src/vs/base/node/cpuUsage.sh divides process CPU-time changes by total system CPU-time changes and emits an integer percentage. This supports comment 26's explanation that one saturated core can appear as a small percentage on a many-core machine; low displayed percentages alone do not disprove the reported saturation.
- **Linked reports are not verified fixes or canonicals:** https://github.com/microsoft/vscode/issues/232699 is closed and concerns high-CPU extension hosts on macOS. https://github.com/microsoft/vscode/issues/237245 is also closed; its reporter closed it pending profiling data, not because a fix was established. Both are younger than this re-reviewed report and neither supplies a verified fix for its Linux file-watcher cases.
- **Canonical-search result:** Searches for NodeService CPU and file-watcher CPU reports did not establish an open canonical. The older open https://github.com/microsoft/vscode/issues/148226 describes a renderer process triggered by search on macOS, not the same observable utility-process failure. https://github.com/microsoft/vscode/issues/259225 is open but requests clearer process arguments; it owns diagnostic usability, not CPU saturation.
- **Diagnostic guidance and inspection limits:** https://github.com/microsoft/vscode/wiki/Performance-Issues recommends Process Explorer and code --status to identify the affected process, testing with extensions disabled, and process-appropriate profiling. Read-only source inspection did not establish the reported hot loop or a concrete fixing commit; no runtime reproduction was attempted and the checkout remained clean.
