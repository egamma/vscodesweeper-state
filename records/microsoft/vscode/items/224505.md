# Issue #224505 — terminal completion provider extension API

[https://github.com/microsoft/vscode/issues/224505](https://github.com/microsoft/vscode/issues/224505)

## Summary

Keep open: terminal completion providers exist, but the extension API remains proposed on current main, so Marketplace adoption is still blocked. The earlier finalization PR predates the reopen and does not establish completion of the remaining API work.

## Change summary

Provide a stable extension API for contributing terminal completions.

## Best solution

Complete the API-owner review of the outstanding registration, shell-selection, and provider-configuration feedback, then finalize the contract for Marketplace extensions. Preserve the documented shell-integration requirement rather than treating unsupported subshell completions as part of this request.

- **Behavior:**

  > Extension authors need a supported, stable terminal completion API that can be used by Marketplace extensions without proposed-API opt-in. Providers should supply contextual completion items, replacement ranges, and documentation under the finalized contract. Acceptance includes a stable-API sample that registers a provider and successfully displays and accepts suggestions in a shell-integrated terminal. Existing shell-integration prerequisites and built-in terminal suggestions must remain intact.
- **Trace:**

  > The declarations remain in src/vscode-dts/vscode.proposed.terminalCompletionProvider.d.ts, and registerTerminalCompletionProvider in src/vs/workbench/api/common/extHost.api.impl.ts still enforces the proposal gate. ExtHostTerminalService.registerTerminalCompletionProvider currently permits one provider per extension, keyed by its extension identifier, while TerminalCompletionService internally supports provider maps and shell-type filtering. The provider configuration remains the shared terminal.integrated.suggest.providers object. The merged https://github.com/microsoft/vscode/pull/271338 predates the verified 2025-11-07 reopening; the subsequent maintainer feedback establishes that promotion alone is insufficient. The uncertainty is the final public registration and configuration contract, not whether a provider implementation exists. Do not expand this work into completions for arbitrary subshells without shell integration; the discussion already establishes that boundary.
- **Open decisions:**
  - What exact public shell-selector contract should be finalized, including shell identifiers, wildcard matching, and behavior when the shell is unknown?
  - What compatibility and migration behavior should extensions and users receive when static provider contributions and the shared terminal.integrated.suggest.providers setting are replaced?
