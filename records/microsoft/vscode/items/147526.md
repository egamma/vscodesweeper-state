# Issue #147526 — [folding] Increase number of foldable regions

[https://github.com/microsoft/vscode/issues/147526](https://github.com/microsoft/vscode/issues/147526)

## Summary

The 65,000-region ceiling remains on current main, and the editor-folding maintainer explicitly invited an implementation. Keep this Backlog request open while deciding the supported upper bound and memory representation.

## Change summary

Allow `editor.foldingMaximumRegions` to be configured above 65,000 for exceptionally large files.

## Best solution

Remove the 16-bit parent-index constraint from `FoldingRegions`, then expose a substantially higher documented maximum while preserving the current 5,000 default and validating memory and navigation behavior above 65,535 regions.

- **Fit:** aligned

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/foldingRanges.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/contrib/folding/test/browser/foldingRanges.test.ts`
- **Validation:** Extend the folding ranges unit suite with more than 65,535 sibling and nested regions, asserting preserved length, line numbers, and parent navigation; add or extend editor-option coverage to confirm `editor.foldingMaximumRegions` accepts the chosen new upper bound.
- **Behavior:**

  > Users can configure `editor.foldingMaximumRegions` above 65,000 and obtain that many foldable regions in sufficiently large files. Folding, unfolding, range lookup, and parent navigation remain correct when region indexes cross 65,535. The default remains 5,000, so ordinary files retain the current performance profile. Values beyond the newly supported contract are clamped or rejected consistently with other integer editor options.
- **Trace:**

  > `src/vs/editor/common/config/editorOptions.ts` caps `editor.foldingMaximumRegions` at 65000. `FoldingRegions` in `src/vs/editor/contrib/folding/browser/foldingRanges.ts` enforces `MAX_FOLDING_REGIONS = 0xFFFF`; `ensureParentIndices` stores a 16-bit absolute parent index across the high bytes of `_startIndexes` and `_endIndexes`, while the low 24 bits hold line numbers. This conclusively explains why the setting cannot be raised without changing the representation. `src/vs/editor/contrib/folding/test/browser/foldingRanges.test.ts` currently validates exactly the old maximum. Preserve the 24-bit line-number behavior, existing fold-state semantics, and the 5,000 default; do not broaden the work into folding-provider or decoration redesign. The maintainer discussion at https://github.com/microsoft/vscode/issues/147526#issuecomment-1110698466 identifies separate parent storage and relative offsets as candidate directions but does not settle the supported public maximum.
- **Open decisions:**
  - What maximum value should `editor.foldingMaximumRegions` publicly support after the 65,000 ceiling is removed: a new finite safety cap or the full range supported by the revised representation?
  - Should exceeding the supported maximum continue to truncate ranges and show the existing limit indication, or should an explicitly configured high value be honored until another documented resource limit is reached?

## Evidence
