# Issue #334073 — Autopilot doesn't work well with folding steps before final response

[https://github.com/microsoft/vscode/issues/334073](https://github.com/microsoft/vscode/issues/334073)

## Summary

Team-authored bug with an active, detailed maintainer investigation (justschen, chryw) confirming the folding heuristic in chatListRenderer.ts picks the wrong final-response run when task_complete/autopilot bookkeeping tools interleave with markdown; no fix has landed and the maintainers are still weighing which heuristic change to make, so this stays open.

## Change summary

In autopilot mode, the chat UI sometimes folds a detailed final response into the 'Task completed' disclosure and shows a shorter task_complete summary as the final answer instead.

## Best solution

A maintainer decides how to special-case autopilot/task_complete (and similar bookkeeping tools like rename_chat) in the contiguous-markdown folding heuristic in getFinalResponseStartIndex (src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts) without regressing the general 'collapse older markdown followed by a tool call' behavior or increasing token cost.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`
- **Validation:** A chatListRenderer test (see chatListRenderer.test.ts's existing getFinalResponseStartIndex suite) asserting that a detailed markdown response followed by a bookkeeping tool call (e.g. rename_chat) and then a shorter task_complete markdown summary is NOT folded into the completed-work disclosure — the earlier detailed response should remain the recognized final response, or both should be surfaced distinctly.
- **Behavior:**

  > When an agent (in autopilot mode) emits a full, detailed final answer and then invokes bookkeeping tools (e.g. rename_chat) followed by task_complete with a shorter summary, the UI should not discard/fold the detailed answer into the 'Task completed' disclosure. The detailed answer should remain visible as (or alongside) the recognized final response. Acceptance: a renderer test with this sequence confirms the detailed markdown is not collapsed under the completed-work summary.
- **Trace:**

  > getFinalResponseStartIndex (src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts:263) walks backward through the response content array and treats the last contiguous run of 'markdownContent' parts as the final response; task_complete is rendered as a root Markdown part (per chryw's Agent Host trace), so when it follows a bookkeeping tool call after the real answer, it becomes its own contiguous run and wins, folding the earlier detailed answer into the completed-work disclosure via getVisibleCompletedResponseItemCount/shouldCollapseCompletedResponsePart logic in the same file. justschen notes the renderer intentionally uses this generic 'contiguous markdown = one response' heuristic because it can't reliably distinguish bookkeeping tools from real ones; the boundary is: do not break the general collapsing heuristic for the common 'text1 -> tool -> text2 shows only text2' case, only add a targeted exception for autopilot/task_complete/todo-adjacent tools. Related: https://github.com/microsoft/vscode/issues/321422 and https://github.com/microsoft/vscode/issues/327923 discussed by chryw as contributing gaps; the previously fixed reconnect-split issue https://github.com/microsoft/vscode/issues/331045 is explicitly ruled out as unrelated to this case.
- **Open decisions:**
  - Should task_complete/autopilot bookkeeping tools (rename_chat, todo tools, etc.) be explicitly excluded from the contiguous-markdown-collapse heuristic, or should the renderer use response semantics (e.g. distinguishing status/event content from true response content) to decide what folds — and is the latter acceptable given the token-cost concern chryw raised?
  - When a real detailed answer precedes a task_complete summary, should the UI show both (detailed answer as final, summary folded into 'Task completed'), or replace/merge them into a single view?

## Evidence
