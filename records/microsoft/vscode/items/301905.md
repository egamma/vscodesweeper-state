# Issue #301905 — Support Updating from a Self-Managed/Internal Update Source

[https://github.com/microsoft/vscode/issues/301905](https://github.com/microsoft/vscode/issues/301905)

## Summary

Keep open: desktop updates still lack a supported administrator-configurable internal source, and the existing update-mode policy does not provide one. The reopened request is accepted in Backlog; its earlier community-vote timeout is not grounds to close it again.

## Change summary

Allow organizations to stage VS Code releases internally and use the integrated update workflow against an administrator-selected source.

## Best solution

Define a supported enterprise update-source contract in the desktop update platform, preserving default Microsoft updates and package verification. Decide which transports, feed format, and fallback behavior are supported before implementation.

- **Reason:** Administrator-controlled updates extend settings fidelity and the existing update experience to restricted enterprise environments without requiring additional default UI.

## Plan brief

- **Likely files:** `src/vs/platform/update/common/update.config.contribution.ts`, `src/vs/platform/update/electron-main/abstractUpdateService.ts`, `src/vs/platform/update/electron-main/updateService.win32.ts`, `src/vs/platform/update/electron-main/updateService.darwin.ts`, `src/vs/platform/update/electron-main/updateService.linux.ts`, `src/vs/platform/update/test/electron-main/abstractUpdateService.test.ts`
- **Validation:** The plan should establish automated update-service checks for default-source compatibility, administrator-selected feed resolution, policy precedence, and the agreed failure/fallback behavior. Acceptance should also exercise staged metadata and packages on supported desktop platforms with public update endpoints unavailable, confirming that checks, notifications, and installation follow the approved contract.
- **Behavior:**

  > Organizations need to select an internal source of approved VS Code releases while retaining the integrated update experience supported on each platform. Unconfigured installations must retain their existing behavior, and internal-source installations must not contact public update endpoints unless the agreed fallback contract permits it. Acceptance must cover staged versions, applicable release channels, source failures, and enterprise policy enforcement. The proposed file-share and HTTP sources are requested alternatives, not an already-settled support contract.
- **Trace:**

  > Desktop feed construction lives in src/vs/platform/update/electron-main/abstractUpdateService.ts:createUpdateURL and the platform buildUpdateFeedUrl implementations, which currently use productService.updateUrl. src/vs/platform/update/common/update.config.contribution.ts exposes update timing through update.mode and UpdateMode policy but no source override. cli/src/update_service.rs separately supports VSCODE_CLI_UPDATE_URL; that does not configure desktop updating. macOS delegates to Electron autoUpdater, Windows uses the request service, and Linux's download action preferentially opens the product download page, so an endpoint change alone does not establish end-to-end support. Preserve existing update scheduling, package verification, and platform installation semantics. The uncertainty begins at the administrator-visible transport, metadata, and fallback contract requested in https://github.com/microsoft/vscode/issues/301905.
- **Open decisions:**
  - Should the initial supported source contract include network file shares, HTTP/HTTPS endpoints, or both?
  - Should source selection be available through user settings as well as enterprise policy, or be administrator-only?
  - Must an unavailable internal source fail closed, or may administrators explicitly enable fallback to Microsoft?
  - Should internal sources implement the existing platform-specific update service protocol, or should VS Code support a documented static manifest format?

## Evidence

- **Existing settings do not cover the request:** src/vs/platform/update/common/update.config.contribution.ts registers update.mode and its UpdateMode policy, which control whether and when updates are checked. Neither update.source nor update.internalSource is registered; update.channel is a deprecated alias for update.mode, not a source selector.
- **Desktop feed selection:** src/vs/platform/update/electron-main/abstractUpdateService.ts:createUpdateURL constructs /api/update/{platform}/{quality}/{commit} beneath a supplied base URL. The Windows, macOS, and Linux buildUpdateFeedUrl implementations all supply productService.updateUrl, not an administrator-configured source. src/vs/platform/product/common/product.ts obtains native product configuration from product metadata.
- **Partial capability is CLI-only:** cli/src/update_service.rs:get_update_endpoint honors VSCODE_CLI_UPDATE_URL. This Rust CLI capability does not configure the desktop TypeScript update services and therefore does not satisfy the requested integrated desktop update workflow.
- **Platform-specific boundary:** src/vs/platform/update/electron-main/updateService.darwin.ts passes its feed to Electron autoUpdater.setFeedURL; updateService.win32.ts requests update metadata through IRequestService. updateService.linux.ts currently opens productService.downloadUrl preferentially when downloading, so redirecting metadata alone would not ensure an internal-only workflow on every platform.
