# Issue #226755 — How should bad/stale providers be handled?

[https://github.com/microsoft/vscode/issues/226755](https://github.com/microsoft/vscode/issues/226755)

## Summary

Keep open: current file search still waits for all participating providers, so one never-resolving provider can withhold otherwise available results. The remaining work needs a product decision about incremental results and stalled-provider handling, not a stale-issue close.

## Change summary

Prevent a nonresponsive search provider from blocking results supplied by other providers.

## Best solution

Let file-search consumers present available results without waiting indefinitely for an unrelated provider. Settle the user-visible completion and stalled-provider policy before changing the search service and Quick Open integration.

- **Likely files:** `src/vs/workbench/services/search/common/search.ts`, `src/vs/workbench/services/search/common/searchService.ts`, `src/vs/workbench/services/search/common/fileSearchManager.ts`, `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`
- **Validation:** Use a multi-root workspace with two registered file-search schemes: one provider immediately returns a matching URI and the other returns a never-settling promise. Verify that Quick Open exposes the available match while the second provider remains pending, then cancel or change the query and verify that obsolete results do not appear. Add automated coverage for the chosen partial-result and completion semantics.
- **Behavior:**

  > A file-search provider that never resolves currently prevents the aggregated search from returning matches supplied by other providers. The goal is to keep available matches usable without waiting indefinitely for the stalled provider. Acceptance should cover a fast provider alongside a never-resolving provider, cancellation, and replacing the active query. The visible pending or completion state requires a maintainer decision.
- **Trace:**

  > The linked test plan https://github.com/microsoft/vscode/issues/226668 establishes file-search providers and Quick Open as the relevant surface. SearchService.searchWithProviders in src/vs/workbench/services/search/common/searchService.ts collects provider promises and awaits Promise.all; doSearch merges their completed results afterward. FileSearchManager awaits provideFileSearchResults before processing that provider's files, and AnythingQuickAccessProvider.doGetFileSearchResults consumes the completion-only searchService.fileSearch API. Caller cancellation is already raced separately and should remain effective; text-search progress support must not regress. Source inspection establishes the barrier, but no runtime reproduction was performed. The uncertainty begins at how partial results should be exposed to consumers and how the UI should represent a provider that never completes.
- **Open decisions:**
  - Should available file matches appear while the query remains pending indefinitely, or should a stalled provider eventually yield a completed partial result?
  - If stalled providers are timed out or skipped, should users see an explicit incomplete-results indication?
