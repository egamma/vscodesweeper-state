# Issue #8050 — additional options for `editor.selectionHighlight` 

[https://github.com/microsoft/vscode/issues/8050](https://github.com/microsoft/vscode/issues/8050)

## Summary

Existing settings address some matching preferences, but do not cover whole-word-selection-only highlighting, keyword exclusion, or identifier-only filtering. Keep this accepted backlog request open; the verified related issues neither absorb its scope nor qualify as older canonicals.

## Change summary

Allow users to restrict automatic highlighting to explicitly selected whole words, non-keywords, or identifiers, with additional matching controls requested in the discussion.

## Best solution

Define a focused highlighting policy that reduces incidental matches while retaining useful explicit-selection highlighting and preserving Find results. Separate selection eligibility from occurrence matching and language-aware filtering before choosing the public configuration contract.

- **Behavior:**

  > Users want useful deliberate-selection highlighting without incidental keyword and short-substring noise while navigating code. Existing case-sensitive matching and disabling cursor occurrence highlights cover only portions of the request. The agreed opt-in policy should specify which selections and token categories qualify, and whether eligible selections match substrings or whole words. Acceptance should exercise these distinctions without changing default behavior or replacing the user's existing Find query.
- **Trace:**

  > SelectionHighlighter._createState in src/vs/editor/contrib/multicursor/browser/multicursor.ts obtains matching behavior through MultiCursorSession.create and getSelectionSearchOptions; its eligibility checks do not require complete-word selections or language token categories. editor.selectedTextMatchMode already supplies independent case-sensitive and case-insensitive substring matching, while findOptions shares Find's matching flags. Caret-only sessions are excluded by SelectionHighlighter, so the original navigation complaint also involves WordHighlighter and its document-highlight providers. The textual fallback in textualHighlightProvider.ts matches words without classifying keywords or identifiers; semantic providers may behave differently. Preserve existing defaults, multicursor command semantics, and Find state, and keep selection-border styling and cross-tab requests outside the initial filtering scope. https://github.com/microsoft/vscode/issues/100530 and https://github.com/microsoft/vscode/issues/11354 are related overlap/color work, not canonical owners of this request. The remaining uncertainty is the user-visible filtering contract and its behavior across language providers.
- **Open decisions:**
  - Should the initial option restrict which selections qualify, restrict matches to whole words, or offer both as independently selectable behaviors?
  - Should keyword exclusion and identifier-only filtering apply to cursor occurrence highlights, explicit-selection highlights, or both, and what should happen when reliable language classification is unavailable?
  - Should minimum selection length be part of this change, or remain a separate follow-up?
