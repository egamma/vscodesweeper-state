# Issue #161969 — Merge UI: Show Accept code lenses in result

[https://github.com/microsoft/vscode/issues/161969](https://github.com/microsoft/vscode/issues/161969)

## Summary

Keep open for a merge-editor UX decision: current source still separates acceptance actions in the inputs from status and removal lenses in the result. This team-authored request has supporting maintainer feedback and a duplicate routed into it; no verified older canonical or completed fix was found.

## Change summary

Offer acceptance actions in the merge result pane, replacing redundant status lenses with actions that reflect which inputs are included.

## Best solution

Resolve whether the result pane should provide a complete set of acceptance and removal actions, then implement the agreed presentation in ActionsSource without changing merge-resolution semantics. Preserve clear representation of combination order and manual resolutions.

- **Behavior:**

  > The request is to resolve conflicts from the result pane using acceptance actions rather than a passive 'No Changes Accepted' lens. After accepting one input, the result should make its inclusion clear and offer removal of that input and acceptance of the other. The proposed presentation should avoid redundant status text while remaining understandable for both-input combinations and manual resolutions. Acceptance checks must cover base, single-input, both-input, and manually edited states; final action placement and status presentation require maintainer agreement.
- **Trace:**

  > ActionsSource in src/vs/workbench/contrib/mergeEditor/browser/view/conflictActions.ts builds input and result action lists separately. getItemsInput constructs acceptance, append, and automatic-combination actions, while resultItems constructs passive resolution-state labels followed by removal actions and, for manual resolutions, Reset to base. Reading these branches establishes that the requested result-pane acceptance surface is still missing without executing the UI. Existing merge.toggleActiveConflictInput1 and merge.toggleActiveConflictInput2 commands provide another way to change inclusion but do not fulfill the requested lens placement. Preserve existing merge state transitions, smart versus non-smart combination semantics, ordering, and manual-resolution handling. The uncertainty is product presentation, not helper selection: the discussion at https://github.com/microsoft/vscode/issues/161969 disagrees about duplicate controls, while https://github.com/microsoft/vscode/issues/162192 was consolidated into this request.
- **Open decisions:**
  - Should acceptance actions remain in both input editors and also appear in the result, or should the result become the primary acceptance surface?
  - Should result lenses replace passive status labels entirely, or retain explicit status for combination order and manual resolutions alongside actionable controls?
