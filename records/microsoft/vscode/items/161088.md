# Issue #161088 — Git - Stop git fsmonitor--daemon beforce closing / renaming / deleting a repo

[https://github.com/microsoft/vscode/issues/161088](https://github.com/microsoft/vscode/issues/161088)

## Summary

Keep open: multiple commenters confirm that Git fsmonitor daemons retain Windows directory or removable-drive handles after VS Code closes, and current Git-extension lifecycle code contains no daemon cleanup. The issue is already correctly routed to git; no verified fix or older canonical report was found.

## Change summary

Release Git fsmonitor daemon handles when closing a repository or workspace, or before renaming, moving, or deleting a repository directory.

## Best solution

Resolve the Git extension's repository-lifecycle gap without disabling the user's fsmonitor configuration globally. Establish safe behavior for daemons shared with another VS Code window or external Git client before implementing cleanup.

## Plan brief

- **Likely files:** `extensions/git/src/main.ts`, `extensions/git/src/model.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** On Windows with supported Git and core.fsmonitor=true, open a disposable repository in VS Code and confirm its daemon starts. Close the workspace/window, then verify the repository and its parent directory can be renamed, moved, and deleted; repeat on removable storage and verify safe ejection after closing. Exercise Explorer rename/delete while the repository is open, and a two-window/shared-client scenario against the agreed ownership policy. Confirm core.fsmonitor configuration remains unchanged.
- **Behavior:**

  > With core.fsmonitor=true, opening a repository in VS Code can leave a Git daemon holding directory handles after the workspace or window closes. Reporters confirm that this prevents Windows folder renaming and removable-drive ejection. The finished behavior should release handles for repository close and repository-directory rename, move, or deletion without changing the user's Git configuration globally. Acceptance must include both the single-window case and the agreed behavior when another window or Git client uses the same daemon.
- **Trace:**

  > Model.openRepository in extensions/git/src/model.ts queues repository.status(); Repository.getStatus in extensions/git/src/repository.ts calls the getStatus implementation in extensions/git/src/git.ts, which runs git status -z and preserves core.fsmonitor. Workspace removal and Model.dispose perform synchronous resource disposal, Repository.dispose only disposes registered resources, and main.ts deactivation currently awaits only telemetry cleanup. No fsmonitor stop integration or pre-rename/pre-delete registration was found in the Git extension. This establishes the missing cleanup path, but Windows handle retention was confirmed from the issue discussion rather than executed locally. The boundary is Git-extension lifecycle handling: preserve ordinary file operations inside repositories, user Git configuration, and other active clients' behavior. https://github.com/tellang/triflux/pull/200 is an external implementation example, not a VS Code fix. The remaining uncertainty is the lifecycle policy for an existing daemon that VS Code does not exclusively own.
- **Open decisions:**
  - Should repository or workspace close stop an existing fsmonitor daemon even when another VS Code window or external Git client may use it, or should automatic cleanup be limited to a defined ownership or last-consumer policy?

## Evidence

- **Confirmed user impact:** The discussion on https://github.com/microsoft/vscode/issues/161088 independently confirms Windows folder-renaming failures after closing VS Code, blocked safe removal of external storage, and accumulating daemon processes in multi-repository workflows. These are credible reported reproductions; no live Windows reproduction was performed during this read-only review.
- **Current startup path:** extensions/git/src/model.ts:690-700 queues repository.status() when opening a repository. extensions/git/src/repository.ts:3107-3120 delegates to the Git repository's getStatus(), and extensions/git/src/git.ts:2794-2820 executes git status -z without overriding core.fsmonitor. The reporter's daemon-starting trigger remains present.
- **Current cleanup gap:** extensions/git/src/model.ts:470-486 disposes repositories after workspace-folder removal; Model.dispose() at 1217 clears repository and extension disposables. extensions/git/src/repository.ts:3651 only disposes registered resources. extensions/git/src/main.ts:35-39 awaits deactivateTasks, whose only registration is telemetry disposal at line 207. Searches of extensions/git found no fsmonitor daemon stop operation or pre-rename/pre-delete file-event registration.
- **Workaround is not a resolution:** The issue proposes git fsmonitor--daemon stop as a targeted workaround. The March 2025 comment instead toggles global core.fsmonitor off and on to prevent accumulation, sacrificing the enabled optimization during the workflow; neither workaround is implemented as VS Code lifecycle handling.
- **External cross-reference:** https://github.com/tellang/triflux/pull/200 is merged, but changes Triflux worktree cleanup and stale-process handling in that separate application. It cites this report as background and does not fix or demonstrate adoption in VS Code.
- **Canonical and history checks:** GitHub searches for fsmonitor, fsmonitor--daemon, Git daemon folder renaming, folder-in-use symptoms, and safe removal found no verified older open issue covering the same observable problem. The checkout is shallow, so its empty git-log search for fsmonitor or 161088 cannot establish that no historical fix exists; current source provides no completed-fix evidence.
