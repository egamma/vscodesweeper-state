# Issue #186961 — Locale independent keybindings (character instead of physical key)

[https://github.com/microsoft/vscode/issues/186961](https://github.com/microsoft/vscode/issues/186961)

## Summary

Keep this accepted, community-supported request open: current keybindings support layout-aware key codes and physical scan codes, but not arbitrary produced-character bindings for Vim-style punctuation chords. The older related issues address different observable behavior and do not establish a duplicate.

## Change summary

Allow extensions to contribute character-based keybindings that follow the character across keyboard layouts rather than requiring layout-specific physical keys and modifiers.

## Best solution

Define a backward-compatible character-binding contract in the core keybinding parser and dispatch pipeline, usable by extension contributions and user bindings. Preserve existing key-code and scan-code semantics while allowing Vim-style punctuation chords to follow the active layout.

## Plan brief

- **Likely files:** `src/vs/base/common/keybindingParser.ts`, `src/vs/base/common/keybindings.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts`, `src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts`, `src/vs/workbench/services/keybinding/test/node/macLinuxKeyboardMapper.test.ts`
- **Validation:** Add parser and keyboard-mapper cases for the approved character-binding contract across US and German macOS layouts, including 'ctrl+w' followed by '>', '<', '+', '-', and '='. Verify command dispatch follows each produced character despite differing physical keys and required modifiers; retain existing key-code, scan-code, and layout-translation tests. Manually confirm the contributed chords outside editor text focus on German macOS.
- **Behavior:**

  > An extension author needs to express Vim-style punctuation chords once, with the second stroke matching the requested character across keyboard layouts. In the originating German macOS example, resizing bindings currently require layout-specific physical keys or explicit Shift combinations, while '=' already works through existing translation. Acceptance requires the same declared character chord to invoke the same command on US and German layouts without per-layout overrides. Existing key-code and explicit scan-code bindings must retain their behavior.
- **Trace:**

  > Extension keybindings enter KeybindingParser.parseKeybinding through src/vs/workbench/services/keybinding/browser/keybindingService.ts. The parser in src/vs/base/common/keybindingParser.ts supports KeyCodeChord and ScanCodeChord, and KeyCodeUtils.fromUserSettings in src/vs/base/common/keyCodes.ts resolves a fixed vocabulary rather than arbitrary produced characters. MacLinuxKeyboardMapper already translates some layout characters into key-code/modifier combinations, explaining why '=' and letter remapping can work without establishing a general character-binding mode. keyboard.dispatch='keyCode' selects FallbackKeyboardMapper and still dispatches key codes, not produced characters. The desired behavior is documented at https://github.com/vscode-neovim/vscode-neovim/pull/1257#issuecomment-1622414216. The uncertainty starts at the public representation and modifier contract for character bindings; preserve all existing bindings rather than redefining their semantics. https://github.com/microsoft/vscode/issues/1240 is related layout-keymap work, not a verified duplicate of this request.
- **Open decisions:**
  - What opt-in syntax or contribution field should identify produced-character bindings without changing the meaning of existing keybindings?
  - For character bindings, how should Shift and AltGr/Option used to produce the character interact with explicitly requested command modifiers, including case-sensitive characters?

## Evidence

- **Accepted community request:** https://github.com/microsoft/vscode/issues/186961 has 24 community upvotes and the Backlog milestone. The December 15, 2023 bot comment explicitly confirms that it passed the community threshold; inactivity is not grounds to retire it.
- **Existing-capability check:** src/vs/base/common/keybindingParser.ts, KeybindingParser.parseChord, constructs either ScanCodeChord for bracketed names or KeyCodeChord through KeyCodeUtils.fromUserSettings. src/vs/base/common/keyCodes.ts:548-559 registers punctuation key names such as '=', '.', and ';', but does not provide arbitrary produced-character bindings for symbols such as '>' or ':'. This is not equivalent to a fully character-based binding contract.
- **Partial layout-aware support:** src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts:587-650 translates layout output into existing key-code/modifier combinations. src/vs/workbench/services/keybinding/test/node/macLinuxKeyboardMapper.test.ts already verifies German-Swiss Y/Z reversal and mapping Cmd+/ to Shift+Cmd+Digit7. Thus existing bindings are not uniformly physical, but this partial translation does not satisfy the request for arbitrary Vim-style character chords.
- **Dispatch setting does not cover the request:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts exposes keyboard.dispatch with only 'code' and 'keyCode'. src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts:61-69 selects FallbackKeyboardMapper for 'keyCode'; that mapper reads keyboardEvent.keyCode and modifier flags, not the produced character. Changing this setting does not add character-binding syntax to extension contributions.

The extension PR was merged despite the localization limitation, as acknowledged at https://github.com/vscode-neovim/vscode-neovim/pull/1257#issuecomment-1785175238; its merge is not a VS Code core fix.
