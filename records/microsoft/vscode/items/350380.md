## Evidence

- **Source-confirmed trigger:** src/vs/platform/browserView/common/browserView.ts:220-222 converts vscode-remote URIs using uri.with({ scheme: Schemas.file, authority: '' }) without changing the path. For the reported //home/user/project path, src/vs/base/common/uri.ts:32-44 explicitly throws when the authority is empty and the path begins with //.
- **Initialization propagation:** src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:189 invokes _updateWindowConfiguration during construction. That method calls _getRemoteNetworks, whose flatMap converts every trusted root without isolating conversion errors; _getTrustedFileRoots includes persisted getTrustedUris(). MainThreadBrowserTunnelProxy constructor-injects this browser service in src/vs/workbench/api/browser/mainThreadBrowserTunnelProxy.ts.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/350432 is verified OPEN and explicitly fixes https://github.com/microsoft/vscode/issues/350380. Its diff normalizes leading slashes in getBrowserViewRemoteFile and adds double/triple-leading-slash coverage. This is proposed work, not a landed fix.
- **Discussion and workaround:** The reporter recovered by removing the affected persisted trust entries, without resetting user data. The November 25 comment reports similar symptoms on macOS, but does not independently establish the same path trigger; the conclusive evidence here is the current source path.
