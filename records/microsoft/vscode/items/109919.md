## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/editor/common/languages/languageConfigurationRegistry.ts`
- **Validation:** After agreeing the API contract, add extension API checks that read a contributed language's comment syntax, observe a runtime setLanguageConfiguration registration and its disposal according to that contract, and verify equivalent results from a remote extension host without reading installation files. Include regex-bearing configuration fields if the approved return type exposes them.
- **Behavior:**

  > Extensions need to read a language's configuration without locating or parsing VS Code installation files. Static manifest enumeration is insufficient because configurations can be registered at runtime, and filesystem workarounds fail across local/container boundaries. Acceptance should cover contributed comment syntax, runtime configuration changes and disposal, and remote access. The returned configuration and its freshness guarantees require an explicit public API contract.
- **Trace:**

  > The public declarations in src/vscode-dts/vscode.d.ts and the languages object in src/vs/workbench/api/common/extHost.api.impl.ts expose setLanguageConfiguration but no getter. ExtHostLanguageFeatures.setLanguageConfiguration serializes runtime contributions through extHost.protocol.ts to MainThreadLanguageFeatures.$setLanguageConfiguration, which registers them with LanguageConfigurationService. LanguageConfigurationService.getLanguageConfiguration already resolves registered configuration plus selected user customizations internally, but that internal representation is not itself a settled extension-facing contract. Preserve existing registration priority, disposal behavior, and editor behavior; this request concerns supported read access, not changes to language syntax. The closed predecessor https://github.com/microsoft/vscode/issues/2871 points to this issue, and the current discussion establishes that file-based libraries do not solve the remote/runtime cases. Uncertainty starts at which resolved values the public getter exposes and how callers observe subsequent changes.
- **Open decisions:**
  - Should the public getter expose the effective editor configuration, including user customizations and defaults, or only the merged language registrations?
  - Should callers receive a point-in-time snapshot and re-query for changes, or should the API also provide a language-configuration change event?

## Evidence

Searching src/vscode-dts found no getLanguageConfiguration declaration; src/vs/workbench/api/common/extHost.api.impl.ts:795-797 exposes only the setter for this configuration.
