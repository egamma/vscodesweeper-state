# Issue #75627 — Extensions using the "type" command (for ex. Vim) have poor performance due to being single-threaded with other extensions

[https://github.com/microsoft/vscode/issues/75627](https://github.com/microsoft/vscode/issues/75627)

## Summary

The affinity setting provides a well-confirmed workaround, but the central request remains: VS Code does not automatically isolate extensions that handle typing from unrelated extension-host stalls. With 273 upvotes and recent reports of residual multi-extension latency, this should remain open rather than be treated as fully implemented.

## Change summary

Prevent extensions that implement the `type` command from becoming unresponsive when unrelated extensions block the shared extension-host thread.

## Best solution

Make latency-sensitive extension placement safer by default, likely by automatically assigning suitable extensions to separate extension-host affinity groups or by exposing a supported extension-declared latency/isolation requirement, while retaining manual `extensions.experimental.affinity` as an override.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionHostKind.ts`, `src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts`, `src/vs/workbench/services/extensions/common/extensions.ts`
- **Validation:** Add extension-host running-location tests proving the chosen automatic-isolation policy places a latency-sensitive/type-handling extension apart from unrelated extensions while preserving explicit affinity overrides, then exercise typing with a deliberately blocking completion provider.
- **Behavior:**

  > Typing routed through an extension-provided `type` command should remain responsive when an unrelated extension blocks its extension host. Users should not need to identify extension identifiers and manually configure affinity for the common case. Explicit affinity configuration must remain predictable, and isolation must not silently break extension dependencies or unsupported hosts.
- **Trace:**

  > The issue demonstrates that `type` command dispatch and completion providers can share one extension-host thread, so a synchronous completion workload delays Vim input. The shipped `extensions.experimental.affinity` mechanism provides manual extension-host grouping, and https://github.com/microsoft/vscode/pull/164150 added corresponding web-worker support; commenters confirm this mitigates the problem. The unresolved boundary is automatic placement: VS Code must know which extensions are latency-sensitive and how strongly to isolate them without excessive host processes or incompatible grouping. Keep the existing explicit affinity behavior and non-type command dispatch semantics unchanged.
- **Open decisions:**
  - Should automatic isolation apply to every extension that registers the `type` command, or require an extension-declared latency-sensitive capability?
  - Is automatic placement a default policy that explicit `extensions.experimental.affinity` overrides, or only a recommendation surfaced to users?
  - What resource limit should constrain additional extension-host processes or workers when several latency-sensitive extensions are installed?

## Evidence

- **existing workaround:** A maintainer documented `extensions.experimental.affinity` in the issue, and multiple commenters confirmed that assigning `vscodevim.vim` to another extension host substantially improves responsiveness.
- **remaining gap:** The issue asks for VS Code to isolate type-handling extensions automatically; manual per-extension affinity configuration does not provide that behavior, and later comments report needing to discover and isolate additional blocking extensions.
- **web support:** https://github.com/microsoft/vscode/pull/164150 extended extension-host affinity to vscode.dev, broadening the workaround without establishing automatic placement.
- **demand:** The request has 273 community upvotes, well above the feature-request backlog threshold, and comments include confirmations across Vim, built-in TypeScript/JavaScript completion, Dart, Pylance, and IntelliCode scenarios.
- **recent evidence:** Later discussion reports that affinity improves the problem but may require isolating more than one extension, supporting the distinction between the shipped manual control and the requested automatic solution.
