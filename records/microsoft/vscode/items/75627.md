# Issue #75627 — Extensions using the "type" command (for ex. Vim) have poor performance due to being single-threaded with other extensions

[https://github.com/microsoft/vscode/issues/75627](https://github.com/microsoft/vscode/issues/75627)

## Summary

Keep open as under discussion: extension-host affinity provides an effective manual mitigation, but it does not fulfill the central request for VS Code to protect latency-sensitive `type` handlers automatically. The request has substantial community demand and remains the best-diagnosed canonical discussion for this extension-host isolation problem.

## Change summary

Prevent blocking work in one extension from delaying keystrokes handled through another extension's `type` command.

## Best solution

Provide a supported way for latency-sensitive extensions to run independently from potentially blocking extension work without requiring each user to discover and maintain `extensions.experimental.affinity` entries. The design must preserve extension dependencies and work consistently across local-process and web-worker extension hosts.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/test/common/extensionRunningLocationTracker.test.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`
- **Validation:** Extend ExtensionRunningLocationTracker tests to verify the selected design isolates a latency-sensitive extension while preserving dependency and explicit-affinity grouping; manually verify through Developer: Show Running Extensions that the extension occupies the intended host on desktop and vscode.dev.
- **Behavior:**

  > An extension whose command handling is latency-sensitive must not have its keystrokes delayed by unrelated blocking work in the default extension host. Users should not need to discover extension identifiers and maintain affinity settings for the common Vim-style typing scenario. Extensions that depend on or deliberately colocate with one another must continue to function, and explicit affinity configuration must retain predictable behavior. Acceptance includes confirming separate host placement on desktop and web and demonstrating that a blocked unrelated host no longer delays the isolated handler.
- **Trace:**

  > Current host assignment is calculated by ExtensionRunningLocationTracker in src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts. `_computeAffinity` groups dependencies and proposed `extensionAffinity` declarations, then creates extra groups only from `extensions.experimental.affinity`; AbstractExtensionService creates hosts up to the resulting maximum affinity. Commits 3740be6c1eb087c2d87c37740a3844d67dd333cd and fc9e85ea3e08b27ef4d6a01459dfec6cb6dbbad1 established the manual desktop mechanism, while https://github.com/microsoft/vscode/pull/164150 added web-worker support. The uncertainty begins at how VS Code can know before initial host allocation that an extension will register a latency-sensitive command, or whether that requirement must instead be declared by extension metadata. The boundary is extension-host placement: do not change editor typing semantics, weaken extension dependency colocation, or silently override explicit user affinity groups.
- **Open decisions:**
  - Should isolation be inferred from runtime command registration, declared in extension metadata, or enabled through a supported extension API?
  - If detection occurs after activation, should VS Code migrate or restart the extension host automatically, defer isolation until reload, or only recommend a configuration change?
  - Which extensions should share an isolated host, and what process-count or memory budget should constrain automatic host creation?
  - How should automatic placement interact with extension dependencies, proposed `extensionAffinity`, and explicit `extensions.experimental.affinity` configuration?

## Evidence

- **existing mitigation:** Commit 3740be6c1eb087c2d87c37740a3844d67dd333cd introduced separate local-process extension hosts based on configured affinity, and fc9e85ea3e08b27ef4d6a01459dfec6cb6dbbad1 exposed `extensions.experimental.affinity` in the settings schema.
- **current source gap:** src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts computes additional host affinities only from explicit `extensions.experimental.affinity` configuration, extension dependencies, and proposed `extensionAffinity` declarations; it does not identify or automatically isolate extensions that handle `type`.
- **confirmed workaround:** Multiple commenters reported that assigning VSCodeVim to a separate affinity substantially improved or resolved the lag, while later reports show that users must sometimes identify and isolate other interacting extensions manually.
- **web support:** Merged https://github.com/microsoft/vscode/pull/164150 extended configured affinity to web-worker extension hosts, and https://github.com/microsoft/vscode/issues/164515 documented successful testing with Vim.
- **remaining scope:** The broader open https://github.com/microsoft/vscode/issues/27378 tracks general zero-latency typing but does not own this issue's diagnosed extension-host contention and isolation requirements; this report remains the stronger canonical item for that root cause.
