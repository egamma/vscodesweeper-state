# Issue #262916 — 3 Way Merge Editor issue with git subtree

[https://github.com/microsoft/vscode/issues/262916](https://github.com/microsoft/vscode/issues/262916)

## Summary

Keep open: the discussion confirms merge-editor failures during subtree updates and folder refactors, and current source retains a plausible failing revision/path lookup. The related reload issue is not a canonical duplicate; a maintainer explicitly requested this separate report.

## Change summary

The three-way merge editor fails to open conflicted files after a subtree update or folder refactor because a requested Git revision/path does not exist.

## Best solution

Make the built-in Git merge-editor input resolution handle subtree prefix changes and renamed conflict paths without requiring the result path to exist in both commits. Establish a minimal conflicting repository to verify the inputs and preserve ordinary merge, rebase, and stash behavior.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/uri.ts`, `extensions/git/src/git.ts`, `extensions/git/src/fileSystemProvider.ts`
- **Validation:** In a disposable repository outside the shared checkout, create an upstream file, import it under client/ with git subtree add, make conflicting local and upstream edits, and run git subtree pull. Open the conflicted file through git.openMergeEditor and verify that base, current, incoming, and result load with the correct contents and that accepting a conflict works. Repeat with a rename-versus-edit rebase and an ordinary same-path merge.
- **Behavior:**

  > A conflicted subtree file must open in the three-way merge editor even when the upstream commit stores it without the local subtree prefix. Folder-move conflicts must likewise display the correct input versions rather than fail on the destination path. Users must be able to resolve individual conflicts and save the result. Ordinary merges, rebases, and stash conflicts must retain their existing input ordering and content.
- **Trace:**

  > Commands.openMergeEditor in extensions/git/src/commands.ts starts with index-stage inputs from toMergeUris in extensions/git/src/uri.ts, then replaces current and incoming with commit-based URIs inferred from directional diffs. Those lookups use a matching originalUri or fall back to the result path; Git.buffer in extensions/git/src/git.ts reads that exact revision/path, and GitFileSystemProvider in extensions/git/src/fileSystemProvider.ts reports a missing object as FileNotFound. This explains why a destination existing on disk can still fail, but the precise subtree diff mapping has not been reproduced in this read-only review. First establish a minimal fixture and inspect its index stages, commit paths, and generated merge URIs before choosing an implementation. Preserve input ordering, normal rename handling, stash semantics, and genuine missing-object errors. The reload report at https://github.com/microsoft/vscode/issues/247828 was explicitly distinguished by a maintainer and should not absorb this work.
