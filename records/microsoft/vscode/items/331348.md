# Issue #331348 — Agents Window: a model picked in the Workbench picker never reaches session.modelId

[https://github.com/microsoft/vscode/issues/331348](https://github.com/microsoft/vscode/issues/331348)

## Summary

The cosmetic model divergence remains source-reproducible on current main: model hydration stops observing the host draft as soon as the initial model is defined. No later fixing commit or canonical issue owns this remaining behavior, so the team-authored issue should stay open.

## Change summary

Keep the Agents Window session model synchronized when the same conversation's model is changed through the Workbench picker.

## Best solution

Make the Agent Host session adapter continue reflecting genuine draft-model changes into the default chat's `session.modelId`, without echo loops or changes to the intentionally one-shot agent hydration. A maintainer should first settle whether model changes published by peer clients participate in that same synchronization contract.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`
- **Validation:** Extend the `LocalAgentHostSessionsProvider` unit suite with a test that publishes an initial draft model and then a different draft model, asserts `session.modelId` and source follow the intended policy, and verifies that an echoed Sessions-originated write does not cause another update loop.
- **Behavior:**

  > When a model is selected in Workbench for an Agent Host conversation, the Agents Window must reflect that conversation model instead of continuing to show an older `session.modelId`. A Sessions-originated model selection echoed through the host draft must settle without looping. Initial resume restoration must remain correct, and agent selection hydration must retain its existing one-shot behavior.
- **Trace:**

  > The default chat subscription is established by `_hydrateModelFromDraft` in `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`. Its callback reads `ChatState.draft.model` only while `cached.modelId` is undefined, then clears its listener as soon as a model exists; this conclusively prevents later Workbench selections from reaching the adapter. `setModel` updates the adapter and writes through `_updateChatSessionState`, so any continuing synchronization must account for that echo. Existing coverage in `localAgentHostSessionsProvider.test.ts` proves initial restore and live-selection precedence but not later draft changes. Keep `_hydrateAgentFromDraft` one-shot and avoid broad changes to model-selection precedence established by https://github.com/microsoft/vscode/pull/331282. The uncertainty starts at peer-client updates: the same chat subscription can publish a model selected by another client, and the record does not settle whether that must move this window's `session.modelId`.
- **Open decisions:**
  - Should a draft-model change published by another live client update this window's `session.modelId`, or should continuous synchronization be limited to changes attributable to the local Workbench surface?
