# Issue #126311 — Workspace Trust - Declared Untrusted Folders

[https://github.com/microsoft/vscode/issues/126311](https://github.com/microsoft/vscode/issues/126311)

## Summary

This remains a valid, well-supported Backlog feature request: current main stores and displays only trusted locations, while maintainers have repeatedly consolidated requests for declared untrusted folders here. No older open canonical or implementing PR owns the work.

## Change summary

Allow users to declare folders that automatically open in Restricted Mode, including exceptions beneath otherwise trusted parent folders.

## Best solution

Extend Workspace Trust's persisted location model and management UI to represent explicit untrusted locations, with documented precedence for nested trusted and untrusted declarations and predictable handling of attempts to trust a declared-untrusted workspace.

## Plan brief

- **Likely files:** `src/vs/platform/workspace/common/workspaceTrust.ts`, `src/vs/workbench/services/workspaces/common/workspaceTrust.ts`, `src/vs/workbench/services/workspaces/test/common/workspaceTrust.test.ts`, `src/vs/workbench/contrib/workspace/browser/workspaceTrustEditor.ts`
- **Validation:** Extend the Workspace Trust management tests to persist trusted and explicitly untrusted locations, reload the stored state, and assert the chosen nested-path precedence; add or identify a UI-level check that both trust states can be created, edited, and removed in Manage Workspace Trust.
- **Behavior:**

  > Users can declare a folder as untrusted so that it opens in Restricted Mode without another startup trust prompt. The declaration persists across restarts and supports an untrusted exception beneath a trusted parent folder. The chosen behavior for manually trusting a declared-untrusted workspace and for conflicting nested declarations must be consistent in the current session and after restart. Existing trusted-folder behavior, remote trust forcing, and automatically trusted virtual resources remain unchanged.
- **Trace:**

  > WorkspaceTrustManagementService in src/vs/workbench/services/workspaces/common/workspaceTrust.ts already stores IWorkspaceTrustUriInfo entries, but loadTrustInfo discards entries with `trusted: false`; doSetUrisTrust removes an entry when passed false, and doGetUriTrustInfo searches the remaining ancestor entries by longest path. IWorkspaceTrustManagementService in src/vs/platform/workspace/common/workspaceTrust.ts exposes only getTrustedUris/setTrustedUris for bulk management. WorkspaceTrustedUrisTable in src/vs/workbench/contrib/workspace/browser/workspaceTrustEditor.ts renders only getTrustedUris() and presents trust-only labels and actions. Existing unit coverage is in src/vs/workbench/services/workspaces/test/common/workspaceTrust.test.ts. Preserve forced remote trust, virtual-resource handling, and existing positive-trust semantics. Related reports were consolidated into https://github.com/microsoft/vscode/issues/126311, including the older https://github.com/microsoft/vscode/issues/121185; they are evidence that this issue is the canonical request, not a duplicate candidate.
- **Open decisions:**
  - When trusted and explicitly untrusted declarations overlap, should the nearest matching location always win, or should an untrusted ancestor remain authoritative over trusted descendants?
  - If a user chooses to trust a workspace under a declared-untrusted location, should that choice be rejected, apply only until the window closes, or persist as a more-specific trusted exception?
  - Should declarations initially support concrete URI/folder ancestry only, or is wildcard matching part of the required public behavior?
