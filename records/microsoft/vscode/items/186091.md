# Issue #186091 — auto jump to first conflict when open file from source control panel

[https://github.com/microsoft/vscode/issues/186091](https://github.com/microsoft/vscode/issues/186091)

## Summary

A real behavior gap remains in the ordinary conflict-marker editor: opening a conflicted resource from Source Control does not reveal its first conflict, although the dedicated merge editor already does. The request is correctly classified and routed, with no verified canonical issue or complete existing capability supporting closure.

## Change summary

Automatically reveal the first merge conflict when a conflicted file is opened from the Source Control view.

## Best solution

Align ordinary conflict-file opening with the dedicated merge editor by revealing the first conflict without a visible post-open jump, while preserving an existing editor view state when appropriate.

## Evidence

- **ordinary editor path:** extensions/git/src/repository.ts ResourceCommandResolver.resolveChangeCommand opens a conflicted resource with `vscode.open` when `git.mergeEditor` is false; extensions/git/package.json declares that setting with a default of false.
- **missing automatic navigation:** extensions/merge-conflict/src/commandHandler.ts registers manual `merge-conflict.next` and `merge-conflict.previous` commands and reveals a range only when navigation is invoked. extensions/merge-conflict/src/services.ts and mergeDecorator.ts register tracking and decoration behavior but no active-editor handler that navigates on open.
- **partial existing capability:** The dedicated merge editor already centers its first conflicting range in src/vs/workbench/contrib/mergeEditor/browser/view/mergeEditor.ts. That behavior was introduced by https://github.com/microsoft/vscode/commit/d1c1592a6d67011cada4a9cbc4253977f6846f0b before this issue, so it does not implement the requested ordinary-editor path.
- **canonical search:** Repository searches for open issues describing an automatic jump to the first conflict when opening from Source Control found no older issue with the same reporter-observable behavior.
- **extension workaround:** The reporter demonstrated that an extension can navigate after opening, but noted visible flicker, leaving a meaningful native integration gap.
