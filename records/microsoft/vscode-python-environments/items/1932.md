# Issue #1932 — Notebook kernel selection hangs after PET resolve burst/timeout; recovery callbacks lose process identity

[https://github.com/microsoft/vscode-python-environments/issues/1932](https://github.com/microsoft/vscode-python-environments/issues/1932)

## Summary

The checkout confirms unsafe PET shutdown and process-state callbacks, so this remains actionable in the environment area. Their contribution to the notebook selection hang is not established; the reported steps suffice for further investigation without an info-needed timeout.

## Change summary

Notebook kernel selection stalls after repeated PET resolutions and a timeout, while recovery callbacks can affect the wrong process generation.

## Best solution

Make PET recovery preserve process and connection identity, then trace the repeated-resolution caller across the Python/Jupyter integration to establish why kernel selection stalls. Treat resolution coalescing as a possible mitigation, not a demonstrated explanation or complete fix.

## Evidence

- **Confirmed shutdown defect:** src/managers/common/nativePythonFinder.ts:522-537 schedules SIGKILL through mutable this.proc and immediately clears that field. An old child that ignores SIGTERM receives no escalation if the field remains empty; if a replacement occupies the field when the timer runs, that replacement is targeted instead.
- **Confirmed stale process callbacks:** src/managers/common/nativePythonFinder.ts:666-686 registers exit and error handlers that unconditionally mutate finder-wide processExited and processExitReason. Neither verifies that the emitting child is still current, so a retired child's delayed event can invalidate a replacement.
- **Request recovery boundary:** NativePythonFinderImpl.resolve() at src/managers/common/nativePythonFinder.ts:364-404 sends separate 30-second resolve requests and handles timeout/connection errors by killing the current shared process without checking the request's connection generation. restart() uses a first backoff of 1000 ms, longer than the shutdown timer's 500 ms; the ordinary timing therefore does not itself prove replacement-before-timer ordering.
- **Report distinguishes observation from causation:** https://github.com/microsoft/vscode-python-environments/issues/1932 provides Remote-SSH/Conda notebook-selection steps, extension versions, timeout/restart excerpts, and controlled fake-process checks of installed methods. The 338 resolutions in two seconds count completions, not request starts; the initial stall, repeated-call origin, and production SIGKILL process identity remain unconfirmed.
- **Integration investigation remains necessary:** resolveCondaPath() in src/managers/conda/condaUtils.ts:819-835 calls nativeFinder.resolve() and converts exceptions to undefined. This is a relevant failure-propagation boundary, but no captured caller trace establishes that it generated the reported burst or explains the notebook picker's pending selection.
- **Related reports are not canonical duplicates:** Verified open https://github.com/microsoft/vscode-python-environments/issues/1795 concerns incomplete Python 3.14 metadata and a Windows kernel-startup helper; https://github.com/microsoft/vscode-python-environments/issues/1925 concerns a startup defaultInterpreterPath warning after configure timeout. Neither owns this report's stale-process recovery callbacks and Remote-SSH notebook-selection failure. Searches for PET restart, kernel hangs, SIGKILL, and resolve timeout found no verified canonical; the open-PR search for 1932 returned no candidates.
