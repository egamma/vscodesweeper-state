# Issue #1617 — No way to configure corporate pip index URL for environment creation / package install UI on Windows

[https://github.com/microsoft/vscode-python-environments/issues/1617](https://github.com/microsoft/vscode-python-environments/issues/1617)

## Summary

Keep this request open and route it to package management: native configuration offers a possible workaround, but the extension does not expose or document a consistent corporate-index configuration across pip installs and uv-backed creation. The reported Windows pip.ini failure is not established by the source.

## Change summary

Provide a supported, documented way for environment creation and package installation to use a corporate package index without accessing public PyPI.

## Best solution

Document and verify manager-native corporate-index configuration for both pip and uv, including uv environment seeding. Decide whether that supported workflow suffices or whether the extension should expose a unified configuration surface; do not assume pip.ini configures uv.

README.md documents backend selection but not corporate-index configuration. Backend selection alone does not deliver the requested documented configuration across both managers.
- **Actual UI installation path:** src/managers/builtin/main.ts registers PipPackageManager. Its manage() method calls managePackages() in src/managers/builtin/utils.ts:274-331, which chooses uv or Python pip and constructs install arguments without an extension-level index override. The command classes in src/managers/builtin/commands/install.ts likewise expose no index configuration.
- **Native configuration is not suppressed:** src/managers/builtin/helpers.ts runPython() and runUV() use spawnProcess() without replacing the environment or supplying configuration-disabling flags. src/common/childProcess.apis.ts explicitly inherits process.env. This does not substantiate the suggested Windows subprocess path-resolution defect.
- **Pip versus uv configuration:** src/managers/builtin/helpers.ts:43-59 selects uv when available under python-envs.alwaysUseUv, and retains uv for tracked uv environments even when that setting is false. https://docs.astral.sh/uv/pip/compatibility/ documents that uv intentionally does not read pip-specific configuration or PIP_INDEX_URL; it supports its own configuration and environment variables instead.
- **Creation has a separate configuration scope:** src/managers/builtin/venvUtils.ts:347-430 invokes uv venv --verbose --seed with the creation root as cwd, then delegates package installation to api.managePackages(). The install path supplies no cwd. https://docs.astral.sh/uv/concepts/configuration-files/ documents Windows user configuration at %APPDATA%\uv\uv.toml and notes that pip-specific uv settings do not apply outside uv pip, so a workaround must also cover seeding.
