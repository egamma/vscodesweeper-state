# Issue #981 — Configure environment via VSCode settings?

[https://github.com/microsoft/vscode-python-environments/issues/981](https://github.com/microsoft/vscode-python-environments/issues/981)

## Summary

Keep open: shareable project-to-environment selection remains distinct from configuring an environment manager. Current main supports python.defaultInterpreterPath as a lower-priority fallback, but it does not cover the requested mapping of projects to specific environments while retaining the configured Pixi manager.

## Change summary

Allow teams to declare each Python project's selected environment in repository-owned VS Code settings so fresh clones and devcontainers need no manual selection.

## Best solution

Define a portable, manager-aware project-to-environment configuration contract that supports third-party managers, multi-root workspaces, and preinstalled devcontainer environments. Document its precedence relative to locally selected environments and existing manager settings.

Manually open a fresh multi-root Pixi workspace and a devcontainer with both system Python and a preinstalled venv; verify the declared environments are selected without interaction, survive reload, and follow the agreed local-override precedence.
- **Behavior:**

  > A fresh clone or devcontainer can declare which existing Python environment each project should use without requiring every developer to select it manually. Different projects may use different named environments supplied by the same third-party manager. Acceptance includes a multi-root Pixi workspace and a container containing both system Python and a venv. Repository configuration must remain portable and its interaction with local selections must follow a documented contract.
- **Trace:**

  > package.json and PythonProjectSettings in src/internal.api.ts expose project paths and manager IDs, but no selected-environment selector. resolvePriorityChainCore in src/features/interpreterSelection.ts prioritizes project/default managers over python.defaultInterpreterPath, and applyInitialEnvironmentSelection asks manager.get for the actual environment. PythonEnvironmentManagers.setEnvironment/setEnvironments in src/features/envManagers.ts delegate selection to the manager and write only manager configuration to settings. Existing tests in src/test/features/interpreterSelection.unit.test.ts cover manager precedence, interpreter paths, and multi-root selection, providing a validation starting point. The unresolved boundary is how a portable selector identifies an environment owned by a third-party manager and how it interacts with local selection; do not replace Pixi's environment lifecycle or assume PET alone defines third-party identities. https://github.com/microsoft/vscode-python-environments/issues/1480 corroborates the requested contract but is closed without an implementation.
- **Open decisions:**
  - Should shared project configuration identify environments by a portable interpreter/environment path, a manager-defined name or identifier, or support both forms?
  - Should a repository-declared environment be an initial default that users can override locally, or an authoritative selection reapplied when the workspace opens or settings change?
