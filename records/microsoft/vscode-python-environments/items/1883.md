# Issue #1883 — Recursively watches the entire /usr/lib on Linux, exhausting inotify watches (~16,000 per window)

[https://github.com/microsoft/vscode-python-environments/issues/1883](https://github.com/microsoft/vscode-python-environments/issues/1883)

## Summary

The package watcher still requests recursive watching rooted at /usr/lib for a system interpreter with sysPrefix=/usr. Route this to package management: the report provides detailed isolation and resource measurements, and the overly broad watcher remains in current main.

## Change summary

Selecting system Python on Linux causes package monitoring to recursively watch unrelated directories under /usr/lib and exhaust shared inotify resources.

## Best solution

Restrict automatic package monitoring to relevant package locations while preserving install/uninstall refresh behavior and manager-provided targets. The missing python314.zip is not required to trigger the broad watcher in the traced code.

## Evidence

- **Reporter isolation:** https://github.com/microsoft/vscode-python-environments/issues/1883 reports 17,175 watches with Python Environments enabled versus 725 with it disabled; disabling Pylance does not reduce the count. The file-watcher error explicitly identifies /usr/lib as the watched path.
- **Source-confirmed broad watch root:** src/managers/common/packageWatcher.ts:getDefaultPackageWatchTargets constructs RelativePattern(path.join(env.sysPrefix, 'lib'), 'python*/site-packages/**/*.dist-info/METADATA') on POSIX in the checkout. With sysPrefix=/usr, the base is /usr/lib and the recursive glob requests recursive watching beneath that base, rather than limiting the watch root to package directories. watchPackageChangesForEnvironment passes this directly to createFileSystemWatcher.
- **Current main verification:** The checkout is shallow and dated August 7, 2026, so live source was also inspected at https://github.com/microsoft/vscode-python-environments/blob/cc8f6acc2771bfa585663a60c3a57b9ed943f028/src/managers/common/packageWatcher.ts. Current main still uses libraryPath=path.join(env.sysPrefix, isWindows ? 'Lib' : 'lib') as the base and the recursive POSIX pattern 'python*/site-packages/{*.dist-info,*.dist-info/**}'. Watcher lifecycle changes have not narrowed this root.
- **Product ownership and suspected cause:** src/managers/builtin/utils.ts:getPythonInfo maps the discovered interpreter prefix directly to sysPrefix; this mapping also remains in live main. The default package watcher uses sysPrefix, not sys.path or a missing-zip parent fallback. The broad root is constructed by this extension; actual Linux inotify counts were not independently measured.
- **Existing mitigation:** package.json declares python-envs.packageWatchers with default=true. registerPackageWatchers on live main returns without registering package watchers when this setting is false. Disabling it is a mitigation that sacrifices automatic package refresh, not a fix for excessive watcher scope.
- **Canonical and implementation search:** Repository searches for inotify, watcher, /usr/lib, and package-watch terms found no open canonical owning this defect. The issue has no comments or linked closing PR, and an open-PR search for 1883 returned no results.
- **Available validation harness:** src/test/managers/common/packageWatcher.unit.test.ts contains the 'Package Watcher' suite, stubs workspaceApis.createFileSystemWatcher, and inspects RelativePattern bases and patterns. Existing POSIX assertions permit the broad lib root; a system-prefix regression can assert that no recursive watcher is rooted at /usr/lib.
