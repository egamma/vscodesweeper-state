# Issue #1931 — Interpreter selection for Python files outside the workspace reverts to system Python (1.38.0, Remote SSH)

[https://github.com/microsoft/vscode-python-environments/issues/1931](https://github.com/microsoft/vscode-python-environments/issues/1931)

## Summary

Keep this report open and route it to environment selection: another user confirms the external-file symptom in Dev Containers, and the current status-bar command still selects workspace projects rather than the active external file. No verified canonical or concrete fix establishes that this selection mismatch is resolved.

## Change summary

Explicit interpreter selection from an external Python file appears ineffective, leaving the status bar on system Python.

## Best solution

Make interpreter selection expose and honor the scope applicable to the active external file without requiring its repository to become a workspace folder. Diagnose the Python Environments command and core Python status-bar integration together, preserving independent workspace selections.

- **Behavior:**

  > With a workspace open, selecting an interpreter while viewing a Python file outside that workspace must not appear successful while leaving that file on system Python. Either the selection applies to the external file's applicable scope, or the picker clearly identifies its workspace scope and provides an effective external-file selection path. Dependency checkouts must not need to be added as workspace folders. Existing workspace environment associations remain independent.
- **Trace:**

  > The October 26 comment on https://github.com/microsoft/vscode-python-environments/issues/1931 independently confirms the external dependency-file symptom and a workaround through disabling integration. PythonStatusBarImpl assigns python-envs.set without a URI; its registration forwards to setEnvironmentCommandInternal, whose undefined-context branch selects registered projects whenever any exist. pickProjectMany silently selects a sole project, and setEnvironmentForProjects updates project URIs rather than global scope. PythonProjectManager does not match sibling files to that workspace project, and EnvironmentManagers uses a global selection key when no project matches. These paths explain a plausible selection/read scope mismatch, but the core Python indicator's exact invocation and subsequent environment lookup have not been traced. Preserve project/global independence and ordinary manager discovery; automatic workspace inheritance is not required by the report.
- **Open decisions:**
