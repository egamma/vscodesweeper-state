# Issue #1583 — CMD shell startup integration overwrites user's existing `HKCU\...\Command Processor\AutoRun` registry value

[https://github.com/microsoft/vscode-python-environments/issues/1583](https://github.com/microsoft/vscode-python-environments/issues/1583)

## Summary

Keep open: current main still replaces a user's existing CMD AutoRun command with the extension's command, permanently losing the prior configuration. This accepted, team-authored issue already has the correct terminal-area labels; no qualifying fix or older same-symptom canonical was found.

## Change summary

Preserve existing CMD AutoRun content during shell-startup setup and remove only the extension-owned segment during teardown.

## Best solution

Make CMD startup integration in src/features/terminal/shells/cmd/cmdStartup.ts preserve unrelated AutoRun commands, remain idempotent, and undo only its own contribution. Verify the issue's merge/removal cases without changing the broader decision to use registry-based activation.

## Evidence

- **Exact destructive source path:** In src/features/terminal/shells/cmd/cmdStartup.ts, setupCmdStartup reads getExistingAutoRun(), but uses its result only to detect whether the extension's batch-file path is present. Existing user content without that path reaches setupRegistryAutoRun(cmdFiles.mainBatchFile), whose reg add command supplies only the extension's invocation and /f. The prior AutoRun string is therefore overwritten rather than retained.
- **Teardown does not restore configuration:** In the same file, removeCmdStartup explicitly leaves the registry AutoRun setting and main batch file untouched; it only removes the marked activation block from the startup file. CmdStartupProvider.teardownScripts calls that function, and src/features/terminal/shellStartupSetupHandlers.ts invokes provider teardown through cleanupStartupScripts.
- **Concrete impact:** The overwritten registry value is user configuration, not merely a transient activation failure. The current write path discards the previous command without storing a recoverable copy, supporting data-loss severity and retaining the existing important designation. This affects Windows CMD shell-startup users with pre-existing AutoRun content.
- **Canonical search:** Repository searches for AutoRun, registry, and CMD startup found no verified older open report of the same overwrite symptom. https://github.com/microsoft/vscode-python-environments/issues/664 is open but reports conda activation and conda-init failures, not loss of an existing AutoRun command. https://github.com/microsoft/vscode-python-environments/issues/244 concerns registry-key logging, and https://github.com/microsoft/vscode-python-environments/issues/243 concerns a startup hang; both are closed and neither owns this report.
