# Issue #1672 — Jupyter kernel startup delayed 30s+ with pixi environment on WSL2 (continuation of locked #1407)

[https://github.com/microsoft/vscode-python-environments/issues/1672](https://github.com/microsoft/vscode-python-environments/issues/1672)

## Summary

Keep this accepted integration defect open and route it to environment and activation owners: multiple reports confirm the Pixi activation timeout, while this report additionally tracks repeated interpreter reselection and probing on WSL2. No verified canonical covers the full report, and no concrete fixing commit was established.

## Change summary

Starting a Jupyter kernel in a Pixi environment incurs repeated 30–35-second activation delays, compounded by automatic interpreter reselection and recurring discovery probes.

## Best solution

Ensure the Python Environments–core Python–Pixi Code integration obtains activated variables without waiting for an interactive shell to exit, while preserving terminal activation behavior. Diagnose the repeated interpreter changes and PET probes separately rather than assuming that resolving the activation timeout necessarily resolves both.

## Plan brief

- **Likely files:** `src/managers/builtin/utils.ts`, `src/managers/builtin/sysPythonManager.ts`, `src/managers/common/nativePythonFinder.ts`, `src/features/pythonApi.ts`
- **Validation:** In WSL2, open a Pixi project containing ipykernel, select its interpreter, and start and restart a notebook kernel with Python Environments enabled. Capture activation commands and timestamps from Python, Python Environments, and Jupyter logs; verify activated-variable collection completes without the 30–35-second timeout, the selected interpreter stays stable without user input, and repeated discovery work does not continually retrigger startup stalls. Compare with the reported disabled-extension control and check that interactive terminal activation/deactivation still works.
- **Behavior:**

  > A notebook using the selected Pixi environment should obtain its activated variables and start without waiting for an interactive shell timeout. Kernel restarts should not repeat the 30–35-second delay. With no user selection change, the kernel should not cycle through different interpreters and repeatedly restart activation. Acceptance requires timing and command evidence on WSL2, plus confirmation that normal interactive terminal activation and deactivation remain functional.
- **Trace:**

  > In src/managers/builtin/utils.ts, refreshPythons excludes NativePythonEnvironmentKind.pixi and recommends Pixi Code, while resolveSystemPythonEnvironmentPath accepts any resolved kind with executable, version, and prefix. getPythonInfo supplies only execInfo.run, and SysPythonManager.resolve in src/managers/builtin/sysPythonManager.ts explicitly treats fallback results as non-activatable. NativePythonFinderImpl.resolve in src/managers/common/nativePythonFinder.ts issues a PET resolve request per call; the source inspected does not explain the caller frequency or PET's internal negative caching. PythonEnvironmentApiImpl in src/features/pythonApi.ts forwards active-environment changes, making that event boundary relevant to the reported reselections, but their origin is not established. https://github.com/microsoft/vscode-python-environments/issues/1712#issuecomment-5802553685 confirms the interactive-shell/chained-command timeout and separates it from the later Windows crash. https://github.com/renan-r-santos/pixi-code/issues/43#issuecomment-4362412275 documents why terminal activation cannot casually be replaced without considering deactivation. The planning session must trace the actual WSL2 command supplier and environment-change callers across core Python and Pixi Code; preserve their interactive terminal contracts and keep the Windows crash investigation separate.
