# Issue #1672 — Jupyter kernel startup delayed 30s+ with pixi environment on WSL2 (continuation of locked #1407)

[https://github.com/microsoft/vscode-python-environments/issues/1672](https://github.com/microsoft/vscode-python-environments/issues/1672)

## Summary

The 30-second Pixi activation delay remains credibly reproduced across WSL2, macOS, and Windows. The failing command appears to cross the API boundary with the core Python extension, while repeated PET fallback probes may be a separate discovery-caching defect, so this should remain open and be routed to API and activation owners.

## Change summary

Pixi-backed Jupyter kernels repeatedly stall while environment-variable discovery runs `pixi shell` as a returning activation command and retries slow conda detection.

## Best solution

Confirm the consumer boundary with microsoft/vscode-python, then make activated-environment-variable collection use the provider's `activatedRun` configuration (`pixi run ...`) rather than chaining commands after `pixi shell`; a maintainer can transfer or link the issue there if confirmed. Separately, avoid repeatedly performing PET's slow conda-package fallback for the same known Pixi environment.

## Evidence

- **confirmed reports:** https://github.com/microsoft/vscode-python-environments/issues/1407 contains independent macOS and Windows confirmations with the same 30-second timeout and `pixi shell ... && ...` command; it was closed for missing information rather than resolution. This report adds matching WSL2 logs on extension 1.36.0.
- **API contract:** src/api.ts distinguishes `activatedRun` from terminal `activation` and specifies that `activatedRun` takes precedence for running Python. The current pixi-code provider supplies `pixi run ... python` as `activatedRun` but `pixi shell` as `activation`.
- **ownership boundary:** src/features/execution/envVariableManager.ts only merges process and .env-file variables; it does not construct the reported `getActivatedEnvironmentVariables` command. src/managers/builtin/utils.ts detects Pixi environments and recommends the external pixi-code provider rather than implementing Pixi activation locally.
- **related upstream tracking:** https://github.com/renan-r-santos/pixi-code/issues/43 remains open for the same delay, but its discussion identifies the extension that consumes activation metadata and builds `pixi shell ... && ...` as the component that should use `pixi run`.
