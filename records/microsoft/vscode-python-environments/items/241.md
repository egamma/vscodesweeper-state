# Issue #241 — Consider activating the environment without environment variables

[https://github.com/microsoft/vscode-python-environments/issues/241](https://github.com/microsoft/vscode-python-environments/issues/241)

## Summary

Keep open: shell-startup activation still transports commands through environment-variable collections. The related cleanup removes variables after activation, but does not deliver this request's variable-free startup mechanism or eliminate collection-change warnings.

## Change summary

Provide shell-startup activation without injecting activation-command environment variables, using a stable, extension-managed startup entry point.

## Best solution

Design a startup mechanism that avoids activation-command collection mutations while preserving correct environment selection and preventing double activation. Coordinate the extension's startup providers with VS Code shell integration; post-activation cleanup is useful but does not replace this work.

Repeat across supported shells, with shell integration enabled and disabled, then check nested shells, separate windows, remote sessions, and extension updates for wrong-target activation or stale startup paths.
- **Behavior:**

  > Shell-startup activation should select the intended Python environment without carrying activation commands in injected environment variables. Opening a terminal should activate once, and changing the selected environment should affect subsequent terminals without activation-command collection-change warnings. A startup entry point must remain usable across extension updates and must not activate unrelated terminals outside VS Code. This request concerns transport variables, not normal environment-manager variables such as VIRTUAL_ENV or PATH.
- **Trace:**

  > src/extension.ts initializes ShellStartupActivationVariablesManagerImpl, whose initializeInternal and handleEnvironmentChange populate collections through platform-specific providers. BashEnvsProvider and PowerShellEnvsProvider store command strings with collection.replace; the corresponding startup providers evaluate those strings. TerminalManager.handleSetupCheck also delegates startup to VS Code shell integration when available, making this a cross-repository consumer contract rather than a profile-only change. https://github.com/microsoft/vscode/pull/292381 cleans variables after activation but leaves the transport intact. The trace establishes the remaining gap, not a viable replacement for conveying window- and workspace-specific selection into each shell. Preserve existing environment-selection semantics, manager-provided activation commands, and command/off modes; the issue's symlink proposal is a design lead, not a mandated patch. https://github.com/microsoft/vscode-python-environments/issues/247 is related file-placement work, not a duplicate.

## Evidence

- **Existing capability check:** package.json declares python-envs.terminal.autoActivationType with command, shellStartup, and off. package.nls.json distinguishes command execution from startup activation; command and off do not provide the requested variable-free shell-startup behavior.
- **Current command transport:** src/extension.ts constructs and initializes ShellStartupActivationVariablesManagerImpl. In src/features/terminal/shellStartupActivationVariablesManager.ts, initializeInternal and handleEnvironmentChange update workspace-scoped environment-variable collections. BashEnvsProvider.updateEnvVariables and PowerShellEnvsProvider.updateEnvVariables call collection.replace with shell-specific activation commands.
- **Startup consumers:** src/features/terminal/shells/bash/bashStartup.ts embeds an eval of the activation variable in the profile; pwsh/pwshStartup.ts similarly uses Invoke-Expression. Both use VSCODE_PYTHON_AUTOACTIVATE_GUARD. TerminalManager.handleSetupCheck in src/features/terminal/terminalManager.ts prefers VS Code shell integration when available, so a replacement must account for both integration and profile paths.

That merged PR adds removal of VSCODE_PYTHON_*_ACTIVATE variables after shell activation in bash, zsh, fish, and PowerShell; its diff does not replace their injection or transport.
