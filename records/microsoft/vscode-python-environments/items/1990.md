# Issue #1990 — Validate npm extension baselines in release PRs

[https://github.com/microsoft/vscode-python-environments/issues/1990](https://github.com/microsoft/vscode-python-environments/issues/1990)

## Summary

Keep open: current checks validate local minimum-version metadata and package consumers, but do not establish that the selected stable extension supplies the required APIs. This is explicitly deferred release-validation work, not covered by the newer root-extension release check.

## Change summary

Add release-PR-only validation of the npm package's selected extension baseline without introducing GitHub lookups into packing or publication.

## Best solution

Establish a required PR gate for npm version or minimum changes that verifies the explicitly selected published baseline and its required API surface. Preserve offline metadata checks and existing publication approvals, and document compatibility limits and manual-release obligations.

## Plan brief

- **Likely files:** `.github/workflows/pr-check.yml`, `api/scripts/check-extension-version.cjs`, `api/test/release-validation.test.cjs`, `CONTRIBUTING.md`
- **Validation:** Extend the Node release-validation tests to cover npm version/minimum changes, unchanged release inputs, branches behind main, unpublished baselines, missing APIs, formatting-only differences, and lookup failures. Verify hosted PR check conclusions cannot pass after failed or canceled baseline validation, while packing and Azure publication perform no GitHub release/source lookups.
- **Behavior:**

  > A PR changing the npm version or minimumExtensionVersion must establish that its explicitly selected stable extension baseline is published and supplies the APIs the package requires. Ordinary development changes must not trigger this additional lookup, and newer extension releases must not invalidate an older valid baseline. Formatting and comment differences must not cause incompatibility failures. Failed lookups or incompatible baselines must block the required release-input check with actionable guidance, without moving network validation into packing or publication.
- **Trace:**

  > The api-compatibility job in .github/workflows/pr-check.yml currently selects work through changed filenames and runs local metadata validation plus compiled package consumer tests. validateMinimumExtensionVersion and validatePackedArtifact in api/scripts/check-extension-version.cjs establish version syntax and artifact consistency, not released API availability. api/test/release-validation.test.cjs explicitly protects offline ordinary validation. CONTRIBUTING.md and https://github.com/microsoft/vscode-python-environments/pull/1987 identify baseline lookup validation as deferred work. The root-manifest release workflow added by https://github.com/microsoft/vscode-python-environments/pull/2003 excludes the npm manifest. Preserve these offline checks and the existing Azure publication conditions and approvals; planning must establish the compatibility guarantee and verify required-check enforcement, which cannot be confirmed from the checkout alone.
- **Open decisions:**
  - What compatibility guarantee must the baseline gate establish beyond required API names: declaration/signature compatibility, runtime availability, or both, and which behavioral guarantees remain explicitly outside its scope?

## Evidence

- **Existing validation is local only:** api/scripts/check-extension-version.cjs validates canonical stable SemVer and packed manifest/compiled-floor consistency. It does not verify that the baseline was published or compare its API surface.
- **Current PR scope differs from the requested gate:** .github/workflows/pr-check.yml scopes API package compatibility by changed filenames, including ordinary shared API, script, and test changes. Its validation remains local; there is no additional baseline lookup gated specifically on npm version or minimumExtensionVersion changes.
- **Explicitly deferred work:** CONTRIBUTING.md, under API versioning and publication, explicitly says automated GitHub release/source-provenance checks are deferred and release authors must confirm the baseline contains required APIs. https://github.com/microsoft/vscode-python-environments/pull/1987 describes removing those lookups while retaining metadata and consumer checks.
- **Related release check does not cover npm:** .github/workflows/release-pr.yml handles root package.json-only release candidates. https://github.com/microsoft/vscode-python-environments/pull/2003 explicitly excludes api/package.json, so it does not resolve this request.
- **Publication boundary:** build/azure-pipeline.npm.yml retains package tests, local packed metadata validation, automatic stable-version publication conditions, and MicroBuild approval. These checks do not establish the selected extension baseline's API compatibility.
