# Issue #1858 — "An Invalid Python interpreter is selected" on startup although a valid venv is selected

[https://github.com/microsoft/vscode-python-environments/issues/1858](https://github.com/microsoft/vscode-python-environments/issues/1858)

## Summary

Keep open and route to environment/API owners: independent reports confirm a false invalid-interpreter warning before startup selection completes, including on 1.42.0. The failing diagnostic crosses into the core Python extension, and no verified canonical or complete fix was established.

## Change summary

Reloading a workspace with a valid interpreter produces an invalid-interpreter warning while initial environment selection is still pending.

## Best solution

Distinguish pending startup resolution from an actually missing interpreter at the Python Environments/core Python integration boundary, without blocking language-server startup. Coordinate the diagnostic fix with microsoft/vscode-python; a maintainer can transfer this there if investigation establishes that the consumer owns the remaining change.

## Plan brief

- **Likely files:** `src/extensionApi.ts`, `src/extension.ts`, `src/features/interpreterSelection.ts`, `src/test/extensionApi.unit.test.ts`
- **Validation:** Reload single-folder and multi-root workspaces with runnable selected venvs while initial resolution takes 2-15 seconds, covering auto-discovery, Poetry and defaultInterpreterPath. Verify no invalid-interpreter popup appears before successful selection, genuinely invalid interpreters still produce diagnostics after resolution, and language-server configuration remains responsive. Extend the existing fake-timer timeout suite to cover an initially empty cache and delayed valid resolution.
- **Behavior:**

  > A valid selected interpreter must not be reported as invalid solely because initial environment selection is pending. This includes cold starts, window reloads and multi-root workspaces. After resolution, the correct environment must remain selected, while genuinely missing or invalid interpreters must still receive actionable diagnostics. Existing nonblocking language-server startup behavior must be preserved.
- **Trace:**

  > PythonEnvironmentApiImpl.getEnvironment in src/extensionApi.ts returns the last-known environment after one second for ordinary managers; PythonEnvironmentManagers.getLastKnownEnvironment in src/features/envManagers.ts reads an initially empty map. src/extension.ts signals manager registration before applyInitialEnvironmentSelection in src/features/interpreterSelection.ts finishes committing selections. The existing timeout tests in src/test/extensionApi.unit.test.ts cover a populated fallback, not this cold-start diagnostic outcome. The macOS confirmation shows that the one-second API timeout cannot explain every occurrence: the core Python extension also times out interpreter reads and _manualDiagnose treats undefined as invalid. Current core source persists interpreter fallback across sessions but still permits an empty cold-start fallback. Determine which consumer check produces each observed warning before choosing the implementation boundary; preserve fast reads, selection precedence and genuine invalid-interpreter diagnostics. Related https://github.com/microsoft/vscode-python-environments/issues/1925 concerns a distinct configuration-resolution warning and is not a canonical duplicate.

## Evidence

- **Confirmed on newer releases:** https://github.com/microsoft/vscode-python-environments/issues/1858#issuecomment-6725859121 confirms the warning on Python Environments 1.42.0 in two workspaces. Initial selection starts at 09:13:23.233, the warning appears at 09:13:25.116, and the correct Poetry environment is assigned at 09:13:26.950. Disabling the rollout integration removes the warning.
- **Independent multi-root confirmation:** https://github.com/microsoft/vscode-python-environments/issues/1858#issuecomment-6798931127 reports the warning in a fresh Windows profile with two workspace folders. It precedes locator refresh completion and valid defaultInterpreterPath selection; the supplied setup and timestamps suffice for retesting.
- **Current timeout and empty-cache path:** src/extensionApi.ts:450-486 still races manager readiness and environment resolution against 1000 ms, then returns getLastKnownEnvironment for ordinary managers. src/features/envManagers.ts:209 initializes an empty selection map, and lines 1210-1214 return its entry without distinguishing pending selection from no environment.
- **Startup ordering:** src/extension.ts:771-786 resolves environmentManagerRegistration before awaiting applyInitialEnvironmentSelection. src/features/interpreterSelection.ts:310-342 awaits priority resolution and manager.get before committing the workspace selection. Manager registration therefore does not establish that an initial interpreter has been selected.
- **Consumer-side race:** https://github.com/microsoft/vscode-python-environments/issues/1858#issuecomment-6278919625 documents a macOS warning only 800 ms after extension-host startup, ruling out the extension's one-second timeout as the sole explanation. Its extracted-method probe demonstrates the core Python interpreter timeout returning undefined before a valid delayed result.
- **Current sibling boundary:** https://github.com/microsoft/vscode-python/blob/main/src/client/interpreter/interpreterService.ts retains timeout fallback, now including persisted interpreter state, which can still be absent on cold startup. https://github.com/microsoft/vscode-python/blob/main/src/client/application/diagnostics/checks/pythonInterpreter.ts::_manualDiagnose maps an undefined active interpreter to the invalid-interpreter diagnostic. Persistence is partial mitigation, not proof that this report is fixed.
- **Canonical search:** Public issue searches for invalid-interpreter and startup-popup symptoms found no verified canonical. https://github.com/microsoft/vscode-python-environments/issues/1925 is newer and concerns a different notification: defaultInterpreterPath resolution failure after locator timeout. https://github.com/microsoft/vscode-python-environments/issues/2000 concerns a configured manager that has no environment, rather than temporarily pending valid selection.
- **Fix provenance limitation:** The checkout is shallow and retains only its current commit, so local history cannot establish a fixing commit. Current source still contains the implicated fallback and startup ordering; the related merged PR in elong0527/yamaa disables this extension in a devcontainer and does not fix its behavior.
