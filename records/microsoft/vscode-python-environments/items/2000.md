# Issue #2000 — Fall back to the next priority when defaultEnvManager has no environment for a scope

[https://github.com/microsoft/vscode-python-environments/issues/2000](https://github.com/microsoft/vscode-python-environments/issues/2000)

## Summary

The requested fallback is still missing on main. Route this to environment/API owners to decide whether a configured manager is a preference or a strict selection when it returns no environment.

## Change summary

Allow a configured environment manager with no environment for a scope to yield to defaultInterpreterPath and auto-discovery.

## Best solution

Establish consistent fallback semantics for project-scoped third-party managers across startup selection and subsequent API reads. Prefer shared extension-owned fallback if approved, rather than requiring every manager extension to implement it independently.

- **Fit:** aligned
- **Reason:** Consistent selection across third-party managers supports the extension's manager-agnostic architecture and public API.

## Plan brief

- **Likely files:** `src/features/interpreterSelection.ts`, `src/features/envManagers.ts`, `src/types.ts`, `docs/README.md`, `docs/startup-flow.md`, `src/test/features/interpreterSelection.unit.test.ts`
- **Validation:** Add mocked-manager checks to the interpreter-selection unit suite for a registered manager returning undefined in global and workspace scopes. Verify approved fallback order, matching selection source, unchanged selection when the manager returns an environment, and consistent subsequent api.getEnvironment(scope) reads; manually retest a Pixi workspace alongside a non-Pixi .venv workspace.
- **Behavior:**

  > A user-level project-scoped manager currently leaves global or unrelated workspace scopes without an interpreter when it returns undefined. The requested outcome is to retain that manager where applicable and otherwise use a configured defaultInterpreterPath, then normal auto-discovery. Acceptance must cover both initial selection and subsequent API reads, while preserving successful manager selections and avoiding settings writes.
- **Trace:**

  > resolvePriorityChainCore in src/features/interpreterSelection.ts stops at a registered configured manager before retrieving its environment; applyInitialEnvironmentSelection retrieves it afterward and accepts undefined. InternalEnvironmentManager.get in src/managers/common/registeredManagers.ts delegates directly to the contributed manager. EnvironmentManager.get in src/types.ts explicitly allows undefined, and isExplicitSelection only classifies an existing result rather than providing fallback. Subsequent reads traverse EnvironmentManagers.getEnvironmentFromManager in src/features/envManagers.ts, where explicit-selection tracking can affect whether another manager's environment is returned. Preserve deliberate user selections and existing settings precedence. The registration recovery in https://github.com/microsoft/vscode-python-environments/pull/1998 is separate from empty-result semantics.
- **Open decisions:**
  - Should a registered configured manager returning undefined trigger extension-owned fallback, or should no selection remain valid and fallback be the manager's responsibility?
  - If extension-owned fallback is adopted, should it apply equally to explicit pythonProjects entries and defaultEnvManager settings, or only to the default-manager preference?

## Evidence

- **Current priority chain:** src/features/interpreterSelection.ts:85–118 returns immediately when a pythonProjects or defaultEnvManager manager is registered, without checking its environment. applyInitialEnvironmentSelection:322 and :366 then calls manager.get(scope), allowing undefined without trying the remaining priorities.
- **Existing capability does not cover the request:** package.json declares python-envs.defaultEnvManager and python-envs.pythonProjects but no empty-manager fallback option. python-envs.setEnvManager, implemented in src/features/envCommands.ts:590–598, configures managers for selected projects; it does not provide the requested user-level preference with per-scope fallback.
- **Public contract permits no selection:** src/types.ts:506–518 explicitly permits EnvironmentManager.get(scope) to return undefined when nothing is selected. docs/README.md:1577 and its example at :1612–1615 likewise do not require managers to return another manager's fallback. docs/startup-flow.md documents manager selection separately from environment retrieval.
- **Subsequent reads matter:** src/features/envManagers.ts:1093–1138 routes getEnvironment through getEnvironmentFromManager. That path returns the routed manager's result unless a different explicit selection exists, so changing startup selection alone may not preserve auto-discovered fallback on later reads.
- **Related work is distinct:** https://github.com/microsoft/vscode-python-environments/issues/1997 and https://github.com/microsoft/vscode-python-environments/pull/1998 address managers registering late, not registered managers returning no environment. https://github.com/microsoft/vscode-python-environments/issues/1925 concerns locator readiness during defaultInterpreterPath resolution; https://github.com/microsoft/vscode-python-environments/issues/1485 asks about global-scope semantics.
