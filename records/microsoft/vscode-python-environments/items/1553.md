# Issue #1553 — About python projects feature

[https://github.com/microsoft/vscode-python-environments/issues/1553](https://github.com/microsoft/vscode-python-environments/issues/1553)

## Summary

The extension deliberately includes every workspace root in Python Projects, but maintainer guidance is inconsistent about whether non-Python roots should appear. Keep this open for an environment-area decision on project membership rather than closing it as designed or redirecting it as a support question.

## Change summary

Clarify why non-Python folders automatically appear as Python projects in multi-root workspaces and whether users should be able to exclude them.

## Best solution

Settle whether workspace roots are unconditional environment-association containers or selectively identified Python projects, then align the Projects view and documentation with that contract. If unconditional membership remains intentional, explain it clearly; if exclusion is supported, it must persist across reloads and cover workspace roots.

- **Evidence:** The durable Python Projects theme explicitly includes the per-file/per-folder/per-project environment model and multi-root and mono-repo workspaces.

  > Thanks for the context. The current extension treats every workspace root as a Python project, regardless of its contents, as documented in https://github.com/microsoft/vscode-python-environments/blob/main/docs/managing-python-projects.md. Workspace roots also cannot currently be removed through the Remove Python Project action. This leaves a product question for mixed-language workspaces: should every root remain an environment-association container, or should non-Python roots be excluded or removable? Keeping this open to settle that behavior and make the documentation consistent.

## Evidence

- **Current behavior:** src/features/projectManager.ts:117-151, PythonProjectManagerImpl.getInitialProjects(), unconditionally adds every workspace root before processing python-envs.pythonProjects overrides; it does not inspect Python files or project markers. initialize() and updateProjects() both use this method.
- **Documented default:** docs/managing-python-projects.md explicitly states that every workspace folder is automatically treated as a project, including in multi-root workspaces. Its definition of a Python Project nevertheless describes runnable Python code needing its own environment.
- **Existing surfaces do not provide root exclusion:** package.json declares python-envs.pythonProjects and python-envs.removePythonProject, but removal is exposed only for python-workspace-removable items. src/features/views/treeViewItems.ts:287-290 delegates that classification to removable() in src/features/views/utils.ts:5-11, which returns false for workspace roots. Empty project overrides also do not suppress roots in getInitialProjects().
- **Discussion leaves the contract unresolved:** The maintainer's June 11 comment on https://github.com/microsoft/vscode-python-environments/issues/1553 asks what should qualify as a Python project, including empty directories, single Python files, and project metadata; it does not establish a final as-designed decision.
- **Conflicting maintainer guidance:** https://github.com/microsoft/vscode-python-environments/issues/1108#issuecomment-4308384016 says a non-Python project should appear only if added and recommends removing it. That advice conflicts with current unconditional root membership and root-removal restrictions. The issue is closed following an information timeout, not a scope decision, so it is neither an open duplicate canonical nor a decline precedent.
