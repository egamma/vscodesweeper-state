# Issue #1657 — Doesn't honor python.defaultInterpreterPath

[https://github.com/microsoft/vscode-python-environments/issues/1657](https://github.com/microsoft/vscode-python-environments/issues/1657)

## Summary

Still present on current main: workspace-scoped `python.defaultInterpreterPath` is read with the correct settings precedence, but a bare relative path such as `.venv/bin/python` is sent to PET without first being resolved against the workspace folder. Routing this confirmed interpreter-selection defect to the environment area.

## Change summary

A workspace-relative `python.defaultInterpreterPath` is reported as unresolvable when the Python Environments extension is enabled.

## Best solution

Resolve non-absolute `python.defaultInterpreterPath` values against the scoped workspace folder before calling `NativePythonFinder.resolve`, while preserving absolute paths and variable expansion. Add an interpreter-selection unit test asserting that `.venv/bin/python` is passed to the finder as an absolute workspace-relative path.

## Evidence

- **settings precedence:** `src/helpers.ts` uses scoped `getConfiguration(section, scope).inspect()` and selects `workspaceFolderValue`, then `workspaceValue`, then `globalValue`, so the workspace setting itself is honored during lookup.
- **source reproduction:** In `src/features/interpreterSelection.ts`, `resolvePriorityChainCore` expands variables but passes the resulting `.venv/bin/python` string directly to `tryResolveInterpreterPath`; that function forwards it unchanged to `nativeFinder.resolve` without resolving it against `scope.fsPath`.
- **missing coverage:** `src/test/features/interpreterSelection.unit.test.ts` covers absolute interpreter paths and `${workspaceFolder}` expansion, but has no case for a bare workspace-relative value such as `.venv/bin/python`.
- **related precedent:** https://github.com/microsoft/vscode-python-environments/issues/660 was closed after absolute and `${workspaceFolder}`-based paths began working, but its closing discussion explicitly identified bare relative `defaultInterpreterPath` values as a separate remaining issue.
