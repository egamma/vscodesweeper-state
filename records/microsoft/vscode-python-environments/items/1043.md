# Issue #1043 — Add ability to exclude Python Environment from Python Extension

[https://github.com/microsoft/vscode-python-environments/issues/1043](https://github.com/microsoft/vscode-python-environments/issues/1043)

## Summary

The unified environment-exclusion capability remains missing: current search-path settings and interpreter defaults do not hide specified environments across selection and API consumers. Route this accepted, team-authored request to the environment and API areas; the reopened discussion explicitly confirms that it is still wanted.

## Change summary

Provide a configurable list of Python interpreter paths to exclude consistently from environment selection and downstream consumers, without removing those interpreters from the container.

## Best solution

Define a shared exclusion contract in Python Environments so container authors can hide tool-owned interpreters consistently from Python and Jupyter environment choices. Settle how that contract affects discovery, API enumeration, and explicitly selected environments before implementation.

## Plan brief

- **Likely files:** `package.json`, `src/features/pythonApi.ts`, `src/common/pickers/environments.ts`, `src/features/views/envManagersView.ts`, `src/features/interpreterSelection.ts`, `src/managers/common/nativePythonFinder.ts`
- **Validation:** Use a dev container with both a tool-owned system interpreter and a usable development environment. Configure exclusion of the system interpreter and verify it is absent from environment choices and API enumeration under the agreed scopes, while the development environment remains selectable and Jupyter honors the shared exclusion. Remove the exclusion and verify visibility returns; separately exercise the agreed behavior for an already-selected or explicitly addressed excluded interpreter.
- **Behavior:**

  > Container authors can specify interpreter paths that should not appear as development-environment choices without deleting interpreters needed by other tools. Exclusion should be consistent across Python environment selection and downstream consumers such as Jupyter, rather than requiring independent picker filters. Non-excluded environments remain available, and removing an exclusion restores visibility. Acceptance checks must cover the agreed workspace scopes and behavior when an excluded interpreter is already selected or explicitly requested.
- **Trace:**

  > package.json exposes search-path configuration but no shared interpreter-exclusion surface. src/managers/common/nativePythonFinder.ts:getAllExtraSearchPaths and buildConfigurationOptions configure additional discovery locations, not an exclusion policy. src/common/pickers/environments.ts:pickEnvironment and src/features/views/envManagersView.ts:getChildren enumerate managers directly, while src/features/pythonApi.ts:getEnvironments separately exposes their results to consumers. src/features/interpreterSelection.ts:resolvePriorityChainCore treats python.defaultInterpreterPath as a selection preference, which does not satisfy hiding. The related Jupyter-only setting is documented at https://github.com/microsoft/vscode-jupyter/issues/13414 and does not cover this shared-source request. Preserve tool-owned interpreter installations and existing non-excluded selection behavior; uncertainty starts at the scope of the exclusion contract and its interaction with explicit selection and discovery.
- **Open decisions:**
  - Should exclusion suppress discovery and probing of matching interpreters, or hide their enumerated choices while preserving explicit resolution?
  - What should happen when an excluded interpreter is already selected, configured through python.defaultInterpreterPath, or explicitly requested through the API or browse action?
  - Should exclusion be shared across the entire remote window or vary by workspace folder, and what should all/global API enumeration return when folder policies differ?
