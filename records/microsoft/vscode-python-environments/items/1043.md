# Issue #1043 — Add ability to exclude Python Environment from Python Extension

[https://github.com/microsoft/vscode-python-environments/issues/1043](https://github.com/microsoft/vscode-python-environments/issues/1043)

## Summary

The shared environment-exclusion capability remains missing on main. Keep this accepted, reopened request open and route it to environment management; interpreter defaults and Jupyter-only filtering do not cover the ask.

## Change summary

Allow configured interpreter paths to be excluded consistently from Python environment selection and downstream extension listings without deleting those interpreters.

## Best solution

Define a shared path-exclusion contract in Python Environments that covers selection and consuming extensions while preserving interpreters required by container tools. Settle API visibility and discovery semantics before implementation.

## Plan brief

- **Likely files:** `package.json`, `package.nls.json`, `src/common/pickers/environments.ts`, `src/extensionApi.ts`, `src/managers/common/nativePythonFinder.ts`
- **Validation:** In a dev container with a required system Python and a preferred development environment, configure the system interpreter as excluded and verify it disappears from environment selection and downstream listings under the agreed API contract, remains installed and usable by container tools, and reappears after removing the exclusion. Verify unexcluded environments remain available.
- **Behavior:**

  > Container authors need to hide interpreters that exist for system tools rather than development, without uninstalling them. Configured exclusions should consistently affect environment selection and consuming-extension listings, rather than only the Jupyter kernel picker. Acceptance includes preserving the interpreter on disk, retaining all unexcluded environments, and restoring visibility when the exclusion is removed.
- **Trace:**

  > package.json has additional search-path settings but no interpreter-exclusion setting or hiding command. src/common/pickers/environments.ts:buildEnvironmentPickItems directly lists manager.getEnvironments('all') results, while src/extensionApi.ts:getEnvironments separately exposes manager results to consumers. src/managers/common/nativePythonFinder.ts:buildConfigurationOptions supplies additional discovery directories, not an exclusion contract. The uncertainty starts at whether exclusions govern listing alone or also discovery and explicit resolution. Preserve interpreters required by system tools and do not equate choosing a default environment with hiding alternatives. https://github.com/microsoft/vscode-jupyter/issues/13414 documents the narrower Jupyter setting; https://github.com/microsoft/vscode-python/issues/26313 provides a newer MSYS2 example of the same selection problem.
- **Open decisions:**
  - Should excluded interpreters remain explicitly resolvable and usable by API consumers and existing project selections, or become unavailable through the shared environment API?
  - Should exclusion only suppress environment visibility, or also prevent discovery work for excluded paths to address the requested Codespaces performance benefit?

## Evidence

- **Accepted and still requested:** The current needs proposal label marks accepted work. In the supplied discussion, a maintainer explicitly confirmed on 2025-12-09 that this remains an ask that the environments extension could handle; the reopened discussion explains why system interpreters cannot necessarily be removed.
- **Existing capabilities do not cover exclusions:** package.json contributes python-envs.globalSearchPaths and python-envs.workspaceSearchPaths but no interpreter-exclusion setting or hiding command. src/managers/common/nativePythonFinder.ts:getAllExtraSearchPaths collects additional search directories, and buildConfigurationOptions passes them as environmentDirectories; these are not a shared exclusion list.
