# Issue #1468 — VS Code not selecting environment in .venv/ on open with Environments extension installed

[https://github.com/microsoft/vscode-python-environments/issues/1468](https://github.com/microsoft/vscode-python-environments/issues/1468)

## Summary

The root cause is confirmed and fixed on current main, but the open PR https://github.com/microsoft/vscode-python-environments/pull/1612 would remove the migration for already-affected users. Keep the issue open until that PR is resolved.

## Change summary

An unintentionally persisted User-level system environment-manager setting prevented project-local .venv environments from being selected automatically.

## Best solution

Retain the prevention from https://github.com/microsoft/vscode-python-environments/pull/1489 and resolve whether the one-time cleanup from https://github.com/microsoft/vscode-python-environments/pull/1527 should remain. Once https://github.com/microsoft/vscode-python-environments/pull/1612 is resolved, this issue can be reconsidered as implemented.

## Evidence

- **confirmed cause:** The reporter found `python-envs.defaultEnvManager: ms-python.python:system` in User settings and confirmed that changing the setting to the venv manager restored automatic .venv selection.
- **prevention fix:** Merged PR https://github.com/microsoft/vscode-python-environments/pull/1489 explicitly says it prevents this issue by stopping the extension from writing environment and package-manager defaults to User scope.
- **existing-user mitigation:** Merged PR https://github.com/microsoft/vscode-python-environments/pull/1527 added a one-time migration; current `src/features/settings/settingHelpers.ts` states that the stale User-level system setting causes all workspaces to ignore local .venv environments and references issue 1468.
- **open implementation decision:** Open PR https://github.com/microsoft/vscode-python-environments/pull/1612 proposes removing that one-time migration, so the linked implementation remains under active review.
