# Issue #1053 — Feature Request: activate default project python/conda environment when launching a task

[https://github.com/microsoft/vscode-python-environments/issues/1053](https://github.com/microsoft/vscode-python-environments/issues/1053)

## Summary

Keep open: existing shell-startup activation and Python-specific task execution do not cover automatic activation of arbitrary project tasks regardless of terminal activation mode. The issue already has the appropriate area labels, and no verified open canonical owns this request.

## Change summary

Automatically activate the project's selected Python or conda environment before tasks from its .vscode/tasks.json execute, independently of the interactive-terminal activation mode.

## Best solution

Provide a supported project-aware task execution experience that makes the selected environment available before the task's first command without injecting commands into a running task. Establish its interaction with disabled auto-activation and non-Python tasks, while treating shellStartup failures as a related but narrower correctness problem.

Include distinct selected environments in a multi-root workspace and confirm each task uses its owning project's environment.
- **Behavior:**

  > Tasks declared in a Python project's .vscode/tasks.json should run with that project's selected environment available before their first command, without requiring each task to hardcode an interpreter or activation command. The request includes tools installed in the environment, not only execution of Python files. Acceptance must cover supported activation modes and task-terminal reuse without interrupting a running task or contaminating stdin. The interaction with explicitly disabled activation needs a maintainer decision.
- **Trace:**

  > TerminalManagerImpl.autoActivateOnTerminalOpen in src/features/terminal/terminalManager.ts follows the interactive-terminal activation setting. TerminalActivationImpl.activate in src/features/terminal/terminalActivationState.ts explicitly excludes task terminals, so removing that exclusion alone would not establish activation before a task's first command and could interfere with running tasks. ShellStartupActivationVariablesManagerImpl contributes workspace-scoped activation variables only in shellStartup mode. runAsTaskCommand and runAsTask resolve an environment and create Python-specific tasks; they do not intercept arbitrary tasks.json tasks. The related closed report https://github.com/microsoft/vscode-python-environments/issues/1040 distinguishes the expected shellStartup behavior from missing command-mode support. Preserve existing interactive-terminal semantics and avoid expanding this request into general .env loading without an explicit scope decision. The trace establishes partial capabilities, but not a supported pre-execution integration point for arbitrary tasks.
- **Open decisions:**
  - When python-envs.terminal.autoActivationType is off, should project tasks still activate automatically as the request implies, or should task activation require a separate explicit enablement?

## Evidence

- **Existing activation capability is partial:** package.json:92-109 declares python-envs.terminal.autoActivationType with command, shellStartup, and off, but no independent task-activation setting. src/features/terminal/terminalManager.ts:autoActivateOnTerminalOpen branches on that setting; src/features/terminal/terminalActivationState.ts:94-97 explicitly returns without activating task terminals. Shell-startup activation therefore does not cover the request to activate tasks regardless of the selected mode.
- **Python task command is not general task integration:** python-envs.runAsTask is registered in src/extension.ts. src/features/envCommands.ts:runAsTaskCommand resolves the environment for a Python file, and src/features/execution/runAsTask.ts:runAsTask creates its own task using execInfo.activatedRun or execInfo.run. This does not activate arbitrary existing shell or process tasks declared in .vscode/tasks.json.
- **Shell-startup contributions depend on mode and workspace:** src/features/terminal/shellStartupActivationVariablesManager.ts initializes activation environment variables only for ACT_TYPE_SHELL, using workspace-scoped collections and api.getEnvironment(workspace.uri). This supplies a narrower existing mechanism, not a mode-independent task contract for each Python project.
