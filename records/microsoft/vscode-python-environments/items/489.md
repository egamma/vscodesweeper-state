# Issue #489 — Environment Manager -> Set as Project Environment should pre-select the environments it's already used in

[https://github.com/microsoft/vscode-python-environments/issues/489](https://github.com/microsoft/vscode-python-environments/issues/489)

## Summary

Keep this accepted, team-authored request open: the project picker still starts unchecked, and deselecting a project does not reset its environment. Current source confirms the requested capability remains missing; no verified canonical owns the same work.

## Change summary

Preselect projects already using the chosen environment and support resetting their selection when they are unchecked.

## Best solution

Make the Environment Managers assignment picker reflect existing project assignments and allow users to edit them without affecting unrelated projects. Agree on the reset behavior for unchecked projects before implementing the assignment-editing workflow.

## Vision fit

- **Fit:** aligned
- **Reason:** Reflecting and editing existing environment assignments directly improves the Python Projects and environment-selection experience.
- **Evidence:** The durable Python Projects theme includes the per-file/per-folder/per-project environment model and Projects workflows; environment lifecycle includes switching environments across supported managers.

- **Likely files:** `src/features/envCommands.ts`, `src/common/pickers/projects.ts`, `src/common/window.apis.ts`, `src/test/features/envCommands.unit.test.ts`
- **Validation:** In VS Code, create four projects and assign one environment to three. Open python-envs.setEnv for that environment and verify exactly those three are checked. Accept unchanged and verify assignments remain unchanged; check the fourth and verify it receives the environment; uncheck an existing assignment and verify the agreed reset behavior. Cancel and verify no changes. Cover these acceptance cases with picker and command unit tests.
- **Behavior:**

  > The assignment picker should show which projects already use the chosen environment: three matching projects out of four should initially be checked. Accepting an unchanged selection must preserve assignments, and newly checked projects must receive the chosen environment. Unchecking a previously assigned project should apply the agreed reset behavior without altering unrelated projects. Cancelling must leave every assignment unchanged.
- **Trace:**

  > python-envs.setEnv is registered in src/extension.ts and reaches the PythonEnvTreeItem branch of setEnvironmentCommand in src/features/envCommands.ts. That branch calls pickProjectMany with all projects but no assignment state; src/common/pickers/projects.ts does not expose preselection, although showQuickPickWithButtons in src/common/window.apis.ts already supports selected items. setEnvironmentForProjects queries current environments only after acceptance and processes selected projects, not removed assignments. This establishes the missing capability without executing the extension. The shared project picker also serves creation and manager-selection workflows, whose existing behavior must remain unchanged. The reporter's reset expectation is tentative; the unresolved product boundary is what an unchecked existing assignment should resolve to.
- **Open decisions:**
  - Should unchecking a project restore that project's normal manager/default environment, or explicitly select system Python even when the project's manager is not the system manager?
