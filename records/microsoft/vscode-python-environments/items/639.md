# Issue #639 — Conda environment activation does not work for R terminals

[https://github.com/microsoft/vscode-python-environments/issues/639](https://github.com/microsoft/vscode-python-environments/issues/639)

## Summary

A real gap remains: current main can inject a Conda activation command into an R REPL, while no existing mode silently activates the environment before R starts. Keep this open for an integration decision; no canonical issue or completed fix owns the R-specific behavior.

## Change summary

Allow R terminals to inherit the selected Conda environment without sending shell activation commands into the R interpreter.

## Best solution

Prevent this extension from treating non-shell REPL terminals as ordinary shells, and coordinate with the R terminal owner so R is launched with the selected Conda environment already applied. The latter likely belongs in the R extension or an explicit cross-extension integration contract.

## Evidence

- **current source:** `src/features/terminal/terminalManager.ts:92-108` handles every ordinary opened terminal, and lines 237-255 invoke command activation without checking whether the terminal hosts a shell or a language REPL.
- **command injection path:** `src/features/terminal/terminalActivationState.ts:186-205` falls back to `terminal.sendText(activationCommands)` when shell integration is unavailable, matching the reported command appearing inside R.
- **shell detection:** `src/features/common/shellDetector.ts:125-169` does not recognize R and ultimately falls back to the configured or platform-default shell, so an R terminal can be treated as bash or another shell.
- **existing capability:** `package.json:92-106` exposes only `command`, `shellStartup`, and `off`; none provides the requested pre-launch activation for an R process.
- **integration boundary:** The open rollout issue https://github.com/microsoft/vscode-python/issues/25291 documents removal of the prior environment-variable activation experiment, but it does not own the R-specific integration and routed this report to the dedicated issue here.
