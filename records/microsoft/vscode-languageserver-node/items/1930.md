# Issue #1930 — Implement native disposables

[https://github.com/microsoft/vscode-languageserver-node/issues/1930](https://github.com/microsoft/vscode-languageserver-node/issues/1930)

## Summary

Native resource disposal remains a real API gap: current disposable objects expose dispose(), not Symbol.dispose. Keep this accepted On Deck request open; package-wide support needs a compatibility and lifecycle design.

## Change summary

Make library-owned disposable resources usable with JavaScript explicit resource management, including using declarations for JSON-RPC connections.

## Best solution

Support standard disposal on library-owned resources while retaining existing dispose() APIs and cleanup semantics. Establish the compatibility contract for consumer-supplied disposables and asynchronous client shutdown before extending support across packages.

- **Behavior:**

  > Library-created disposable resources should support JavaScript explicit resource management without requiring caller-written adapters. The example JSON-RPC connection should be usable in a using declaration and perform its established cleanup when the scope exits, including exceptional exits. Existing dispose() callers must retain their behavior. Package-wide acceptance also needs an explicit contract for resources whose cleanup is asynchronous and for previously valid consumer-supplied disposable objects.
- **Trace:**

  > jsonrpc/src/common/disposable.ts defines the shared dispose-only interface and factory; jsonrpc/src/common/connection.ts constructs a dispose-only MessageConnection. The connection's existing cleanup rejects pending responses and disposes its transports, so native disposal must preserve that boundary rather than introduce unrelated process-ownership changes. Events, cancellation sources, readers and writers expose additional disposal surfaces, and server registrations reuse the shared Disposable contract. BaseLanguageClient.dispose in client/src/common/client.ts returns Promise<void>, establishing an asynchronous boundary absent from the example. Source inspection confirms the missing native hooks, but the record does not settle compatibility requirements for third-party structural implementations or the package-wide asynchronous API. No builds or tests were executed in the read-only checkout.
- **Open decisions:**
  - Must existing consumer-supplied objects implementing only dispose() remain assignable to exported Disposable-based APIs, or may the native disposal contract require a breaking type change?
  - Does the initial package-wide feature include asynchronous resources such as BaseLanguageClient through Symbol.asyncDispose and await using, or is that public API expansion deferred?
  - What compatibility is required for supported runtimes that do not expose native disposal symbols?
