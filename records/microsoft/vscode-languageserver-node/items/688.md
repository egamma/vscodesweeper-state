# Issue #688 — Capture exit code of failing lsp server?

[https://github.com/microsoft/vscode-languageserver-node/issues/688](https://github.com/microsoft/vscode-languageserver-node/issues/688)

## Summary

Keep open: current main logs server exit codes but still lacks the exit callback the maintainer identified. This accepted feature request remains useful; direct process access is a workaround, not a lifecycle-safe replacement for the requested hook.

## Change summary

Expose a language-server process exit hook so extensions can capture failure exit codes programmatically.

## Best solution

Provide a supported exit-observation contract in the Node language client for client-managed server processes, retaining existing logging and restart behavior. Settle its relationship to connection-close handling and its coverage of normal shutdown before implementing it.

## Plan brief

- **Likely files:** `client/src/node/main.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/crashServer.ts`
- **Validation:** In a writable implementation checkout, extend the Node client integration tests and run npm test in client-node-tests after the normal repository build. Trigger test/crash against crashServer and assert that the supported hook receives exit code 100 exactly once for each server process, including after a restart; assert unchanged logging and connection-close behavior, plus the agreed normal-shutdown and signal semantics.
- **Behavior:**

  > Extensions need to capture the exit code of a failing language-server process without parsing output-channel text or replacing client-managed process creation. A supported hook should report the actual failure code once for each affected server process and continue working after restart. Existing output logging and default restart behavior must remain unchanged when the hook is absent. Acceptance checks should use the existing server that exits with code 100 and cover the lifecycle cases agreed with the maintainer.
- **Trace:**

  > In client/src/node/main.ts, LanguageClient.createMessageTransports assigns _serverProcess for built-in launch configurations and attaches an internal exit listener that only logs code and signal. LanguageClient.serverProcess offers direct access after assignment, but handleConnectionClosed clears it before the common client invokes ErrorHandler.closed(), whose signature has no exit information. A custom ServerOptions factory can attach a listener itself, but requires the extension to own process creation; middleware and stdioOptions do not provide process-exit observation. The maintainer explicitly identified the missing ExitHandler at https://github.com/microsoft/vscode-languageserver-node/issues/688#issuecomment-1838769147. The implementation boundary is Node process lifecycle, not the LSP specification or VS Code rendering APIs; preserve existing transport, logging and restart behavior. The existing crash integration test and crashServer fixture establish a concrete validation path, but the thread does not settle which exits are observable or whether the hook participates in restart decisions.
- **Open decisions:**
  - Should the hook observe every client-managed process exit, including intentional stop and restart, or only unexpected termination?
  - Is the hook observational only, with ErrorHandler.closed() remaining responsible for restart policy, or must exit information be available before that policy decision?
