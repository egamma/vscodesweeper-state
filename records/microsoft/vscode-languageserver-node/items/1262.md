# Issue #1262 — Allow clients of the LSP library to capture all errors and show customized / localized message.

[https://github.com/microsoft/vscode-languageserver-node/issues/1262](https://github.com/microsoft/vscode-languageserver-node/issues/1262)

## Summary

Keep open: existing error handlers customize some connection errors, but initialization and restart failures still have user-facing paths that bypass them. The request remains a genuine customization gap; the related error-suppression issue and open PR cover only part of it.

## Change summary

Allow library consumers to intercept errors and present customized or localized user-facing messages while retaining useful diagnostic logs.

## Best solution

Define a consistent consumer-controlled presentation contract in client/ that covers startup, initialization, connection and restart failures while preserving English diagnostic logs and JSON-RPC error semantics. Coordinate the overlapping suppression work with https://github.com/microsoft/vscode-languageserver-node/issues/1608 and https://github.com/microsoft/vscode-languageserver-node/pull/1782 without treating either as full coverage.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `jsonrpc/src/common/connection.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/testServer.ts`
- **Validation:** Extend the existing client integration harness to exercise connection-creation failure, initialization rejection, exhausted restart attempts and failed restart, observing user notifications and output-channel logs. Verify the agreed customization contract handles each selected case without duplicate English notifications, preserves default behavior when unused, and retains PendingResponseRejected codes and pending-request settlement on disposal.
- **Behavior:**

  > Consumers should be able to present their own localized messages for library-originated failures that reach users, rather than being limited to customizing connection read/write and closure errors. Acceptance must cover the reported startup, initialization, restart and disposed-pending-response scenarios according to the agreed scope. Diagnostic logs should remain useful in English, and consumers that do not opt into customization should retain existing behavior. Custom presentation must not alter whether requests reject or whether the client stops or restarts.
- **Trace:**

  > LanguageClientOptions.errorHandler in client/src/common/client.ts supports message and handled results only on connection error and close paths. The start catch forces a notification, initialize includes direct Window.showErrorMessage calls, and failed restart forces another notification; the normal middleware surface does not intercept these internal presentation paths. jsonrpc/src/common/connection.ts produces a coded PendingResponseRejected rejection on disposal and does not own a user interface. The integration suite in client-node-tests/src/integration.test.ts already uses sinon and includes output-channel routing checks, providing a starting harness for presentation checks. Preserve transport error codes, request settlement and lifecycle decisions; the uncertainty is the public customization contract, not whether these bypass paths exist. Coordinate with https://github.com/microsoft/vscode-languageserver-node/issues/1608 and the narrower open https://github.com/microsoft/vscode-languageserver-node/pull/1782 rather than duplicating their stopping-case work.
- **Open decisions:**
  - Should the supported contract cover only vscode-languageclient's user-facing failure presentation, or also provide a structured customization contract for direct vscode-jsonrpc and server consumers such as the reported Theia integration?
  - Should consumers control presentation through a dedicated notification contract independent of lifecycle policy, or through expanded error handlers that also participate in startup, initialization and restart failures?

## Evidence

- **Reported boundary:** The discussion in https://github.com/microsoft/vscode-languageserver-node/issues/1262 identifies English errors displayed in Theia and a VS Code extension, not merely English logs. The maintainer explains that diagnostic messages intentionally remain English; that does not settle whether consumers should control their user-facing presentation.
- **Existing capability is partial:** client/src/common/client.ts:139–210 defines ErrorHandlerResult and CloseHandlerResult with message and handled fields. handleConnectionError and handleConnectionClosed use these fields to customize or suppress certain notifications, but ErrorHandler is documented for connection read/write errors and closure, not every client failure.
- **Presentation paths still bypass handlers:** client/src/common/client.ts:1430 forces the couldn't-create-connection notification; initialize at lines 1555–1574 can call Window.showErrorMessage directly and log Server initialization failed; handleConnectionClosed at line 1887 forces Restarting server failed. LanguageClientOptions.middleware has request/notification interception but no general client-error presentation hook, and revealOutputChannelOn does not suppress force notifications.
- **JSON-RPC error remains structured:** jsonrpc/src/common/connection.ts:1544–1552 rejects pending requests on disposal with ResponseError(ErrorCodes.PendingResponseRejected, 'Pending response rejected since connection got disposed'). This supplies an error code consumers can recognize, but does not itself provide a localization or user-interface presentation contract.
- **Related issue is narrower:** Verified open https://github.com/microsoft/vscode-languageserver-node/issues/1608 concerns error-handler suppression during stopping and includes another consumer reporting an unsuppressible restart notification. The maintainer accepts contribution work and discusses an opt-in contract at https://github.com/microsoft/vscode-languageserver-node/issues/1608#issuecomment-2647169603. Resolving that stopping case would not cover this report's startup and initialization messages.
- **Open PR covers only a subset:** Verified open https://github.com/microsoft/vscode-languageserver-node/pull/1782 proposes treating connection closure during stop() as handled. Its described scope does not deliver interception or localization of all reported failures; the open-PR search for 1262 returned no direct match.
- **Canonical and fix search:** Repository searches for localization, error messages and notification suppression found no verified open canonical owning the full request. https://github.com/microsoft/vscode-languageserver-node/issues/1757 concerns transport metadata interception, not error presentation. The merged downstream https://github.com/EffortlessMetrics/perl-lsp-swarm/pull/5907 describes an extension-specific workspace-state presentation adapter, not a fix to these libraries.
