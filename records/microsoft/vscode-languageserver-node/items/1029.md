# Issue #1029 — Make notebook converter functions public

[https://github.com/microsoft/vscode-languageserver-node/issues/1029](https://github.com/microsoft/vscode-languageserver-node/issues/1029)

## Summary

The notebook conversion helpers remain private on current main, so the requested public API is still missing. Keep this accepted On Deck request open; existing middleware can modify notebook objects but does not expose reusable conversion functions.

## Change summary

Expose notebook conversion helpers publicly so middleware authors can convert VS Code notebook objects into protocol objects.

## Best solution

Provide a supported public notebook conversion API in client/ that preserves the existing conversion semantics and client-specific URI conversion. Agree on its public shape before implementation, consistent with the existing converter APIs.

## Plan brief

- **Likely files:** `client/src/common/notebook.ts`, `client/src/common/codeConverter.ts`, `client/src/common/api.ts`, `client-node-tests/src/converter.test.ts`
- **Validation:** A TypeScript consumer check should import the agreed API through supported language-client entry points. Converter tests should verify notebook identifiers, cells, metadata and change events against the existing notification payloads, including a custom code-to-protocol URI converter.
- **Behavior:**

  > Middleware authors must be able to reuse the client's notebook conversion logic through a supported public API rather than duplicating it or importing private internals. Conversion results should match the protocol objects produced by existing notebook synchronization, including metadata, cell execution summaries and change events. The API must support client-specific URI conversion and leave existing middleware and notification behavior unchanged.
- **Trace:**

  > client/src/common/notebook.ts contains a module-private Converter namespace whose c2p helpers construct the notebook protocol objects used by synchronization. The helpers already accept the base code-to-protocol converter where needed, preserving custom URI handling. BaseLanguageClient.code2ProtocolConverter exposes the separate Converter interface from client/src/common/codeConverter.ts, which has no notebook methods; client/src/common/api.ts likewise exposes no notebook converter. Notebook middleware receives VS Code objects and can forward modified objects, but this does not satisfy direct conversion reuse. The request at https://github.com/microsoft/vscode-languageserver-node/issues/1029 records maintainer support for public access without settling the export shape. Keep conversion semantics and synchronization behavior unchanged; the remaining uncertainty is the supported public contract, not the conversion algorithm.
- **Open decisions:**
  - Should notebook conversions become methods on the existing client.code2ProtocolConverter API, or be exposed as a separately exported notebook converter API?
