# Issue #1661 — Provide a pure ESM build

[https://github.com/microsoft/vscode-languageserver-node/issues/1661](https://github.com/microsoft/vscode-languageserver-node/issues/1661)

## Summary

A real packaging gap remains: the browser server and its protocol/JSON-RPC dependencies still publish CommonJS, despite having export entry points. Keep this accepted Backlog request open and align it with the team's subsequently stated ESM migration direction rather than maintaining parallel builds.

## Change summary

Provide pure ESM artifacts for vscode-languageserver/browser and its dependencies so bundlers can tree-shake unused code.

## Best solution

Deliver a tree-shakable ESM server dependency chain through the planned ESM migration, following the team's stated preference for a final CommonJS release rather than indefinite dual publishing. Validate published-package resolution and supported desktop/browser extension-host scenarios before changing the package contract.

## Vision fit

- **Fit:** aligned

- **Evidence:** The durable themes emphasize not monopolizing the extension host, while the values and guardrails require deliberate, explicitly communicated breaking changes.

## Plan brief

- **Likely files:** `.tsconfigrc.js`, `server/package.json`, `server/src/browser/main.ts`, `server/src/browser/tsconfig.publish.json`, `protocol/package.json`, `jsonrpc/package.json`, `client/package.json`, `build/bin/fix-esm.js`
- **Validation:** In a separate writable implementation checkout, consume published artifacts in an esbuild browser fixture importing a small subset of vscode-languageserver/browser. Inspect the metafile to verify that the server/protocol/JSON-RPC chain is ESM and unused exports are eliminated, and compare minified output against the same CommonJS fixture. Exercise connection initialization and document synchronization in desktop and browser/web-worker host fixtures, and check TypeScript resolution of the supported package entry points.
- **Behavior:**

  > Consumers should be able to bundle vscode-languageserver/browser from ESM artifacts, including its protocol and JSON-RPC dependency chain, so unused exports can be eliminated without a fork. The contributor's measurements establish demand, not a mandatory percentage reduction. Published entry points and declarations must resolve correctly, and supported server/client scenarios must continue working in desktop and browser/web-worker hosts. Follow the team's stated staged migration direction rather than assuming permanent parallel CommonJS and ESM distributions.
- **Trace:**

  > The current gap is in publishing, not protocol behavior or client middleware. .tsconfigrc.js assigns node16/CommonJS publishing to server, protocol, jsonrpc and client; only types and textDocument receive ESM targets. server/package.json maps ./browser to its single lib/browser/main.js artifact, and server/src/browser/main.ts re-exports the protocol browser entry and common server API, extending the packaging boundary into protocol and jsonrpc. types/package.json and build/bin/fix-esm.js demonstrate existing ESM publishing machinery but do not cover the requested chain. The prototype discussion at https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3510428027 does not establish complete test compatibility. The later direction at https://github.com/microsoft/vscode-languageserver-node/pull/1750#issuecomment-4489254189 favors an eventual ESM-only release, while https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3516295286 establishes the web-worker compatibility boundary. The remaining investigation is the coordinated package-resolution and host-compatibility design; runtime protocol semantics are outside the requested change.

## Evidence

- **Current packaging gap:** server/package.json exports ./browser to ./lib/browser/main.js and has no ESM build or import-specific artifact. server/src/browser/tsconfig.publish.json uses module: node16; the package has no type: module. .tsconfigrc.js explicitly states that browser code compiles to CommonJS and relies on webpack, and its projects list assigns ESM publishing only to types and textDocument.
- **Transitive dependency boundary:** server/src/browser/main.ts re-exports vscode-languageserver-protocol/browser and ../common/api. protocol/package.json depends on vscode-jsonrpc; both protocol/package.json and jsonrpc/package.json expose the same single CommonJS artifact layout. types/package.json already publishes lib/esm through browser/module/import conditions, but that does not provide an ESM server dependency chain.
- **Existing-capability check:** LanguageClientOptions and Middleware in client/src/common/client.ts customize runtime requests, notifications and client behavior, not the published module format. Existing package exports select entry points but do not supply the requested ESM artifacts; the reporter explicitly clarified this at https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3152759119.
- **Demand and prototype:** The issue has two upvotes. An independent contributor supplied a prototype and measured minified server output falling from 318.7 KB to 242.6 KB and extension/client output from 425.2 KB to 301.7 KB: https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3503294148. The prototype and its incomplete test integration are described at https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3510428027; these measurements were not independently executed.
- **Maintainer direction:** The maintainer identified web-worker extension-host compatibility as a requirement at https://github.com/microsoft/vscode-languageserver-node/issues/1661#issuecomment-3516295286. A later statement at https://github.com/microsoft/vscode-languageserver-node/pull/1750#issuecomment-4489254189 says the current plan is one final CommonJS release followed by a complete ESM switch, rather than supporting both indefinitely. This advances the requested capability; it does not establish that it has shipped.
