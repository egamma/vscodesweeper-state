# Issue #1522 — Allow customizing the name of the option for enabling tracing

[https://github.com/microsoft/vscode-languageserver-node/issues/1522](https://github.com/microsoft/vscode-languageserver-node/issues/1522)

## Summary

The client still hard-codes the tracing configuration path, and the maintainer explicitly welcomed this enhancement. Keep the accepted request open; account for the current output-channel log-level gate when designing the customization.

## Change summary

Allow extensions to choose the configuration key used for client/server message tracing instead of requiring <clientId>.trace.server.

## Best solution

Support a configurable tracing configuration path in client/ while preserving the existing path for extensions that do not opt in. Establish how the custom setting interacts with the current LogOutputChannel trace-level gate, then cover initialization and configuration changes.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client-node-tests/src/integration.test.ts`
- **Validation:** Add client integration cases exercising a custom setting such as <clientId>.lsp.tracing at startup and after configuration changes, verify that clients without customization retain the existing trace.server behavior, and test both Trace and non-Trace output-channel log levels against the agreed contract. Run these through the existing client-node-tests test runner in an implementation workspace.
- **Behavior:**

  > An extension should be able to select the configuration key from which the language client obtains its message-tracing preference, including a key such as <clientId>.lsp.tracing. Extensions that do not customize it must retain their existing behavior. Acceptance checks should cover startup, subsequent setting changes, and the agreed interaction between that preference and the output channel's log level.
- **Trace:**

  > BaseLanguageClient.refreshTrace in client/src/common/client.ts reads the client-ID configuration section and literal trace.server keys; LanguageClientOptions has no override and Middleware does not intercept this lookup. setTrace changes the active connection's trace level but does not change the configuration source, and later configuration or log-level events call refreshTrace again. refreshTrace currently suppresses tracing unless _traceLogLevel equals LogLevel.Trace, unlike the configuration-only model assumed by the original report. The implementation boundary is the client's tracing configuration and lifecycle; do not change protocol message definitions or unrelated logging behavior. The existing client-node-tests/src/integration.test.ts provides a client/server integration harness. Maintainer acceptance is recorded at https://github.com/microsoft/vscode-languageserver-node/issues/1522#issuecomment-2258418069; the unresolved contract is whether customization only relocates the preference or also changes how tracing is enabled.
- **Open decisions:**
  - Should the custom tracing setting only replace the existing configuration lookup while retaining the LogOutputChannel Trace-level prerequisite, or should it independently enable message tracing as the original request assumes?
