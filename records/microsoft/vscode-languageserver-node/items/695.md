# Issue #695 — Provide a LSP object validation layer

[https://github.com/microsoft/vscode-languageserver-node/issues/695](https://github.com/microsoft/vscode-languageserver-node/issues/695)

## Summary

Keep open: the maintainer accepted a general LSP object-validation direction, and current main still lacks that layer. Existing type guards and interception hooks do not provide comprehensive validation with actionable failure context.

## Change summary

Provide general LSP object validation that identifies invalid properties and includes enough message and server context to diagnose malformed payloads.

## Best solution

Develop a reusable validation layer in protocol/ using the meta model, with client integration that associates failures with the originating language client and message. Settle the validation activation and invalid-message handling contracts before implementation; diagnostics-only improvements would not satisfy the maintainer-expanded scope.

## Plan brief

- **Likely files:** `protocol/metaModel.json`, `tools/src/generator-main.ts`, `protocol/src/common/api.ts`, `client/src/common/client.ts`, `protocol/src/node/test/connection.test.ts`, `client-node-tests/src/integration.test.ts`
- **Validation:** After the contract is settled, add executable protocol connection and client integration checks: send publishDiagnostics with a missing message and assert a structured property failure with client identity, method, URI, and available diagnostic context; exercise malformed payloads for another request/notification and a response; verify valid messages retain their existing delivery and conversion behavior. Verify disabled-mode behavior if validation is optional.
- **Behavior:**

  > A malformed LSP object should produce an actionable validation diagnostic rather than only an incidental handler or conversion exception. The reporter's motivating case is publishDiagnostics with a missing diagnostic message, where identifying the responsible language server and the document is difficult. Acceptance checks should cover that case and other LSP payload kinds, identify the invalid property, and retain available URI, code, and range context. Valid protocol traffic must continue to behave as before; activation and invalid-message handling remain to be agreed.
- **Trace:**

  > The maintainer expanded the scope to general object validation at https://github.com/microsoft/vscode-languageserver-node/issues/695#issuecomment-949414083 and suggested meta-model generation at https://github.com/microsoft/vscode-languageserver-node/issues/695#issuecomment-1339464000. BaseLanguageClient.handleDiagnostics and workDiagnosticQueue in client/src/common/client.ts pass incoming diagnostics to protocolConverter.asDiagnostics before middleware.handleDiagnostics runs. protocolConverter.asDiagnostic accesses message.kind for a non-string message, and the queue catch reports a generic processing failure. Diagnostic.is in types/src/main.ts supplies a partial boolean check, while connectionOptions.messageStrategy exposes interception but supplies no general validator. protocol/metaModel.json is the available protocol description; tools/src/generator-main.ts generates that description, not runtime validators. This is library-side developer tooling, not a request to change the LSP specification or repair the reporter's server; preserve valid traffic, extension fields permitted by the protocol, and client lifecycle behavior. The trace establishes the gap but not a settled public validation contract or the full implementation boundary.
- **Open decisions:**
  - Should validation be enabled by default, explicitly opt-in, or exposed only as a reusable API, and which incoming/outgoing payload categories are covered?
  - When a payload fails validation, should it continue to its handler with a warning, be rejected or dropped, or follow a consumer-configurable policy?
