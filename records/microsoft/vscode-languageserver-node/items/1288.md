# Issue #1288 — meta model should also include a programmatic description of the LSP state machine 

[https://github.com/microsoft/vscode-languageserver-node/issues/1288](https://github.com/microsoft/vscode-languageserver-node/issues/1288)

## Summary

Keep this accepted meta-model request open: the current model describes message and type shapes, but not the initialization and shutdown state transitions. The existing labels are appropriate, and no canonical issue or implementing PR was found.

## Change summary

Include a machine-readable description of LSP initialization and shutdown states and transitions in the protocol meta model.

## Best solution

Define a lifecycle metadata contract in the meta-model tooling and publish it alongside the existing message and type descriptions, without changing ordinary LSP type generation. Base its semantics on the LSP specification; any unresolved protocol semantics belong in microsoft/language-server-protocol.

## Plan brief

- **Likely files:** `tools/src/metaModel.ts`, `tools/src/visitor.ts`, `protocol/metaModel.schema.json`, `protocol/metaModel.json`
- **Validation:** Validate the produced meta model against its JSON schema and check fixtures covering initialization and shutdown sequencing, including permitted and forbidden transitions under the agreed contract; ordinary generated request and notification types must remain unchanged.
- **Behavior:**

  > Consumers should be able to discover the LSP initialization and shutdown lifecycle programmatically from the published meta model rather than infer it from prose. The description should identify states and the events or message outcomes that transition between them. Acceptance requires agreement with the published LSP lifecycle rules and preservation of existing message and type descriptions. The maintainer's stated direction does not require changing ordinary LSP type generation.
- **Trace:**

  > tools/src/metaModel.ts defines the metadata contract, and tools/src/visitor.ts:getMetaModel emits only message and type collections plus version metadata. protocol/metaModel.schema.json and protocol/metaModel.json are the published schema and data surfaces; no dedicated lifecycle representation exists in the inspected source. LanguageClientOptions, Middleware and the internal ClientState in client/src/common/client.ts are runtime surfaces, not an exported protocol state-machine model. The acceptance comment is https://github.com/microsoft/vscode-languageserver-node/issues/1288#issuecomment-1671325519. The diagram reference at https://github.com/microsoft/vscode/issues/4902#issuecomment-368583522 is for debugging, so the plan must establish LSP semantics independently. Preserve runtime client/server behavior and ordinary type generation; uncertainty begins with the public lifecycle metadata contract.
- **Open decisions:**
  - Should the published contract describe lifecycle sequencing only, or also provide an exhaustive account of permitted messages and exceptional outcomes in each lifecycle state?
  - What stable machine-readable representation of states, triggering events and transitions should meta-model consumers be able to rely on?
