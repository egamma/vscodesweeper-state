# Issue #1000 — Allow asWorkspaceEdit to be overridden

[https://github.com/microsoft/vscode-languageserver-node/issues/1000](https://github.com/microsoft/vscode-languageserver-node/issues/1000)

## Summary

Keep open the accepted request for supported custom conversion. General request middleware now exposes raw responses and standard snippet edits are supported, but neither provides the requested replacement of the converter or overrides its internal conversion calls.

## Change summary

Allow extensions to customize code-action workspace-edit conversion without fragile converter monkey-patching or guessing snippet intent from text.

## Best solution

Evaluate whether raw-response normalization through middleware.sendRequest and standard SnippetTextEdit fully replace the reporter's workaround. If custom VS Code conversion remains necessary, settle a supported converter-extension contract in client/ without introducing the per-conversion middleware API the maintainer rejected.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/protocolConverter.ts`, `client/src/common/codeAction.ts`, `client-node-tests/src/converter.test.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/testServer.ts`
- **Validation:** Use the client-node-tests VS Code integration harness to exercise both code-action provision and resolution with an explicitly marked snippet edit and an ordinary edit containing literal $0. Verify snippet interpretation only for the marked edit, unchanged literal text for the ordinary edit, and unchanged default conversion when no customization is configured. The existing General middleware and WorkspaceEdit tests provide relevant starting coverage.
- **Behavior:**

  > An extension needs to interpret explicitly marked snippet edits in code-action responses without guessing from the edit text or depending on private converter internals. Ordinary edits containing $0 must remain literal, while explicitly marked snippets must retain snippet semantics. Assess the existing raw-response middleware and standard snippet representation first; if a conversion extension is still required, its supported contract must cover code-action provision and resolution while preserving default behavior for other consumers.
- **Trace:**

  > CodeActionFeature.registerLanguageProvider in client/src/common/codeAction.ts sends a protocol request and then invokes protocol2CodeConverter.asCodeActionResult or asCodeAction. BaseLanguageClient.sendRequest in client/src/common/client.ts now invokes GeneralMiddleware.sendRequest before those conversions, so its next() result preserves raw extension fields. However, createConverter in client/src/common/protocolConverter.ts uses local functions for nested conversion, and LanguageClientOptions does not accept a replacement converter. Standard SnippetTextEdit conversion is already present; the legacy insertTextFormat field is not its recognized representation. The maintainer preferred converter replacement over per-conversion middleware but identified public API stability concerns at https://github.com/microsoft/vscode-languageserver-node/issues/1000#issuecomment-1158627210. The uncertainty is whether raw protocol normalization is sufficient or a supported custom VS Code conversion contract remains necessary; do not change default snippet or plain-text semantics.
- **Open decisions:**
  - Should the supported customization contract stop at raw protocol-response normalization through middleware.sendRequest, or also allow extensions to replace protocol-to-VS Code conversion for results that cannot be represented by standard protocol types?
