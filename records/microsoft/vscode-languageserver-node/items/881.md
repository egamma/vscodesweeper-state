# Issue #881 — Finding out the server capabilities

[https://github.com/microsoft/vscode-languageserver-node/issues/881](https://github.com/microsoft/vscode-languageserver-node/issues/881)

## Summary

Keep open: the watched-file feature has inspectable state internally, but the public TypeScript getFeature overloads still omit it. The maintainer explicitly accepted exposing this feature, and middleware provides a workaround rather than the requested inspection API.

## Change summary

Let extension authors determine whether the server has registered workspace/didChangeWatchedFiles without replacing the client's internal request handler.

## Best solution

Provide supported, typed watched-file feature inspection in client/, following the maintainer's proposed getFeature direction. Settle how inspection distinguishes server registrations from client-configured file watchers, since the current internal state combines both.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/features.ts`, `client/src/common/fileSystemWatcher.ts`, `client-node-tests/src/integration.test.ts`
- **Validation:** Add a TypeScript consumer check for supported watched-file inspection and an integration scenario covering no registrations, server registration, unregistration, multiple registration IDs, stop/restart, and synchronize.fileEvents without any server registration. Assert the agreed server-versus-client watcher semantics and preserve normal watched-file notification delivery.
- **Behavior:**

  > An extension author needs to determine whether its server currently has a workspace/didChangeWatchedFiles registration without replacing the language client's request handler or independently reconstructing registration history. Inspection should be supported by the public TypeScript API and reflect registration and unregistration transitions. Acceptance must include client-configured watchers without server registrations, multiple server registration IDs, and lifecycle cleanup. Existing watched-file notification behavior must remain unchanged.
- **Trace:**

  > BaseLanguageClient registers FileSystemWatcherFeature internally, and its getFeature implementation retrieves dynamic features by method, but both the class overloads in client/src/common/client.ts and FeatureClient overloads in client/src/common/features.ts omit the watched-file method. FileSystemWatcherFeature.getState() in client/src/common/fileSystemWatcher.ts already exposes whether its _watchers map is nonempty. Server register() and client-side registerRaw() populate the same map; BaseLanguageClient.hookFileEvents uses registerRaw for synchronize.fileEvents, so this state cannot distinguish server registration from local configuration. Registration middleware can observe requests safely through next(), but requires consumer-owned bookkeeping. The maintainer endorsed feature inspection at https://github.com/microsoft/vscode-languageserver-node/issues/881#issuecomment-1009833033. The remaining uncertainty is the public meaning of watched-file registration state; protocol messages, watcher delivery, and unrelated feature APIs are outside the requested change.
- **Open decisions:**
  - Should watched-file inspection identify server-originated registrations separately from synchronize.fileEvents watchers, or expose the existing combined feature state with an explicit limitation that it cannot alone answer whether the server registered?

## Evidence

- **maintainer acceptance:** https://github.com/microsoft/vscode-languageserver-node/issues/881#issuecomment-1009833033 acknowledges that there is no easy inspection mechanism and proposes exposing the watched-file feature through getFeature. This accepted direction and the Backlog milestone preclude a question or as-designed decline.
- **public API gap:** client/src/common/client.ts:1979-2025 and client/src/common/features.ts:791-833 declare getFeature overloads for many features, but none for DidChangeWatchedFilesNotification.method. The string-based implementation retrieves from _dynamicFeatures, but its implementation signature is not an additional callable TypeScript overload.
- **existing internal state:** client/src/common/fileSystemWatcher.ts:32-34 implements getState() as a workspace state with registrations equal to _watchers.size > 0. register() stores server registrations, unregister() removes them, and clear() resets the map; BaseLanguageClient.registerBuiltinFeatures in client/src/common/client.ts registers this feature.
- **state semantics:** client/src/common/client.ts:1944-1959 routes synchronize.fileEvents through FileSystemWatcherFeature.registerRaw(). That method stores client-configured watchers in the same _watchers map as server registrations, so getState().registrations alone does not establish that the server registered the capability.
- **existing-capability check:** LanguageClientOptions.middleware exposes handleRegisterCapability and handleUnregisterCapability in client/src/common/client.ts:309-345. The handlers at 2174-2245 let consumers observe registration requests while forwarding through next(), without overriding onRequest; however, consumers must maintain their own registration state instead of inspecting the client's feature.
- **canonical and PR search:** GitHub searches for watched features, getFeature, registered capabilities, and registration inspection found no open canonical owning this inspection request and no open PR referencing this issue. https://github.com/microsoft/vscode-languageserver-node/issues/1783 concerns watching files outside the workspace, a distinct behavior.
