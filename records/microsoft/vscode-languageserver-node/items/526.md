# Issue #526 — Handle communication between 2 language servers -> language client registry

[https://github.com/microsoft/vscode-languageserver-node/issues/526](https://github.com/microsoft/vscode-languageserver-node/issues/526)

## Summary

Keep open: the client supports request forwarding when both client instances are available, but does not provide the requested cross-extension discovery and binding registry. The Backlog request remains distinct from the related protocol discussion and needs an extension-owned API design decision.

## Change summary

Provide client discovery by identifier and request bindings so cooperating extensions can relay requests between their language servers without workspace-command glue.

## Best solution

Design an opt-in, extension-owned discovery and forwarding contract for client/ that preserves extension control over exposed services and works across separately bundled library versions. Treat https://github.com/microsoft/language-server-protocol/issues/432 as related command-semantics work, not a replacement for this implementation request.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/node/main.ts`, `client/src/browser/main.ts`
- **Validation:** Validate the agreed contract with two independently bundled VS Code extensions and two test servers: an incoming request on client X reaches the opted-in destination client by identifier and returns its response without a workspace command. Check cancellation, unavailable destinations, disposal and restart, including extensions using different vscode-languageclient versions.
- **Behavior:**

  > Cooperating extensions should be able to discover an explicitly exposed destination and relay a server-originated request through it without bespoke workspace-command glue. The report gives both custom Quarkus project-information requests and Java document-symbol requests as examples. Acceptance should demonstrate response and cancellation propagation between two independently bundled extensions, predictable failure when the destination is unavailable, and correct behavior after disposal or restart.
- **Trace:**

  > client/src/common/client.ts exposes BaseLanguageClient.onRequest and sendRequest, which already provide the forwarding primitives when both instances are known. LanguageClientOptions and Middleware expose no cross-extension lookup or binding contract, and the client source search found no registry implementation. The missing boundary is discovery and exposure, not JSON-RPC transport or Java server extensibility. https://github.com/microsoft/vscode-languageserver-node/issues/526#issuecomment-543059136 identifies that boundary explicitly. Preserve extension ownership of integration and do not assume every language provider is a language server, as required by https://github.com/microsoft/vscode-languageserver-node/issues/526#issuecomment-537423291. Separate library copies and versions are a compatibility concern raised in the discussion; their shared discovery behavior remains undesigned. https://github.com/microsoft/language-server-protocol/issues/432 addresses related command semantics but does not supply the requested client API.
- **Open decisions:**
  - Should the supported cross-extension contract expose opted-in LanguageClient instances by identifier, as requested, or only extension-owned service APIs that encapsulate those clients?
  - What discovery guarantees should cooperating extensions receive when they bundle different vscode-languageclient versions, and how should duplicate identifiers or unavailable destinations be represented?
