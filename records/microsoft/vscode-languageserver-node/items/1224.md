# Issue #1224 — UTF-8 support

[https://github.com/microsoft/vscode-languageserver-node/issues/1224](https://github.com/microsoft/vscode-languageserver-node/issues/1224)

## Summary

UTF-8 position support remains missing: the current client advertises only UTF-16 and rejects servers selecting another encoding. Keep this accepted request open; the maintainer has invited an implementation, with conversion cost as the central design concern.

## Change summary

Support negotiating UTF-8 character offsets with language servers and translating positions correctly between the protocol and VS Code.

## Best solution

Implement negotiated UTF-8 positions in client/ while preserving UTF-16 compatibility and correct conversions across requests, responses, notifications and edits. The design must address access to text for unopened response documents without imposing excessive extension-host work; the protocol already defines the negotiation.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/codeConverter.ts`, `client/src/common/protocolConverter.ts`, `client/src/common/textSynchronization.ts`
- **Validation:** The plan should establish executable client/converter checks using lines containing ASCII, multibyte BMP characters and supplementary characters. Verify negotiated UTF-8 request offsets, incoming ranges, incremental document changes and edits, including results referencing unopened documents; verify unchanged UTF-16 behavior and assess conversion cost for large multi-document responses.
- **Behavior:**

  > A server selecting an advertised UTF-8 position encoding should be usable through vscode-languageclient without implementing UTF-16 offsets itself. Character offsets must identify the same text in both directions, including document changes, diagnostics, navigation results and edits. Acceptance checks must distinguish UTF-8 bytes from UTF-16 code units using non-ASCII and supplementary characters, cover unopened result documents, and preserve existing UTF-16 interoperability. Conversion must not introduce excessive extension-host work.
- **Trace:**

  > BaseLanguageClient currently advertises only UTF-16 in client/src/common/client.ts and rejects any other explicit encoding in doInitialize. The shared asPosition/asRange functions in client/src/common/codeConverter.ts and client/src/common/protocolConverter.ts transfer character numbers without document context; protocolConverter.asRanges also constructs ranges directly. LanguageClientOptions exposes no position-encoding converter, and middleware alone does not provide negotiated support. The protocol types already describe UTF-8, so the missing behavior belongs in the client rather than a new specification proposal. The maintainer's concern at https://github.com/microsoft/vscode-languageserver-node/issues/1224#issuecomment-1498739334 is obtaining text for all documents referenced by responses efficiently. The trace establishes the gap but does not yet enumerate every position-bearing conversion path or resolve document-content access and version consistency. Preserve existing UTF-16 behavior and distinguish position units from transport or disk encodings.

## Evidence

- **Current negotiation excludes UTF-8:** client/src/common/client.ts:2150 sets generalCapabilities.positionEncodings to ['utf-16']. BaseLanguageClient.doInitialize at lines 1489–1490 rejects any explicit server positionEncoding other than PositionEncodingKind.UTF16.
- **Converters assume identical character units:** client/src/common/codeConverter.ts:418–445 copies VS Code character offsets into protocol positions and range endpoints without encoding conversion. client/src/common/protocolConverter.ts:399–418 constructs VS Code positions and ranges directly from protocol character values, including the separate asRanges path.
- **Existing-capability check:** LanguageClientOptions and Middleware in client/src/common/client.ts:300–399 expose URI converters and general/per-feature interception, but no negotiated position-encoding conversion facility. stdioEncoding controls stdout/stderr decoding, not Position.character units. A custom feature could alter advertised capabilities, but it would not remove doInitialize's rejection or supply document-aware conversions; middleware therefore does not already deliver the requested library support.
- **Protocol capability already exists:** protocol/src/common/protocol.ts defines PositionEncodingKind.UTF8, GeneralClientCapabilities.positionEncodings and ServerCapabilities.positionEncoding. The positionEncodings documentation at lines 1046–1065 explicitly distinguishes position units and notes that conversion requires file or line content; this is client implementation work, not a missing specification feature.
- **Maintainer acceptance and performance constraint:** https://github.com/microsoft/vscode-languageserver-node/issues/1224#issuecomment-1498739334 invites a good implementation while highlighting the cost of reading every document referenced by responses. The existing help wanted label and Backlog milestone reinforce acceptance; neither supports a decline close.
