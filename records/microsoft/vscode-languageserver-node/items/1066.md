# Issue #1066 — Testing `textDocument/didClose` in extensions requires a three minute timeout

[https://github.com/microsoft/vscode-languageserver-node/issues/1066](https://github.com/microsoft/vscode-languageserver-node/issues/1066)

## Summary

Keep this accepted testing-improvement request open and mark its dependency on VS Code's document lifecycle. The client still forwards document-close events rather than editor-close events; the documented workaround and newer synchronization options do not establish that deterministic integration-test cleanup is implemented.

## Change summary

Allow extension integration tests to exercise document-close behavior without waiting three minutes after closing an editor.

## Best solution

Establish a deterministic way in VS Code core to release retained test documents without changing LSP's document-ownership semantics. Any client-side suppression of unnecessary open notifications must preserve synchronization of hidden buffers and should not be treated as a replacement for testing genuine document closure.

## Evidence

- **maintainer-established boundary:** https://github.com/microsoft/vscode-languageserver-node/issues/1066#issuecomment-1231438827 distinguishes closing an editor from releasing a document buffer: reporting a retained buffer as closed could let the server read stale disk content while VS Code changes its in-memory content.
- **accepted improvement and core dependency:** https://github.com/microsoft/vscode-languageserver-node/issues/1066#issuecomment-1239279930 proposes carefully folding unnecessary open/close events but identifies the three-minute testing timeout as a problem outside LSP. The Backlog milestone and maintainer-proposed improvements preclude a decline close.
- **current close path:** client/src/common/textSynchronization.ts:209-248, DidCloseTextDocumentFeature, subscribes to Workspace.onDidCloseTextDocument and forwards through middleware.didClose. It does not subscribe to tab closure or provide a command to release VS Code's retained buffers; the middleware intercepts an existing close event rather than causing one.
- **existing-capability check:** client/src/common/client.ts:386-398 documents textSynchronization.delayOpenNotifications, and client/src/common/textSynchronization.ts:49-194 implements pending opens. This option delays opens for hidden documents until visibility or subsequent traffic requires them; it does not make an already-synchronized document close when its editor closes.
- **diagnostics alternative is not testing coverage:** client/src/common/diagnostic.ts:1074-1079 cleans up pull diagnostics on visibleDocuments.onClose, independently of the document-close notification. This addresses the reporter's diagnostics motivation, acknowledged at https://github.com/microsoft/vscode-languageserver-node/issues/1066#issuecomment-1237315691, but does not exercise actual didClose behavior in integration tests.
- **workarounds and their limits:** https://github.com/microsoft/vscode-languageserver-node/issues/1066#issuecomment-1369930942 reports using executeCommand('vscode.open', uri, options) instead of openTextDocument followed by showTextDocument. Direct protocol testing is also suggested at https://github.com/microsoft/vscode-languageserver-node/issues/1066#issuecomment-1237770748. Neither establishes a general deterministic cleanup facility for tests that must cover VS Code integration.
- **canonical and PR search:** Verified https://github.com/microsoft/vscode/issues/15178 is closed and concerns access to the open-editor list, not deterministic buffer disposal. https://github.com/microsoft/vscode-languageserver-node/issues/1868 is open but concerns requests overtaking didOpen during startup, a distinct trigger and remaining behavior. Searches for close/visibility and didClose/testing found no verified open canonical or linked open implementation PR that fully owns this request.
