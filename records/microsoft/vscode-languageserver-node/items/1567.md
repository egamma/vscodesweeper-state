# Issue #1567 — Support notification progress instead of only status bar

[https://github.com/microsoft/vscode-languageserver-node/issues/1567](https://github.com/microsoft/vscode-languageserver-node/issues/1567)

## Summary

Keep this accepted customization request open: the client still defaults to silent window progress, and its existing middleware does not provide an integrated request-progress token and UI API. The maintainer explicitly welcomed this feature; Backlog and help wanted are acceptance markers, not grounds for retirement.

## Change summary

Allow extensions to present prominent notification progress for expensive user-initiated operations instead of always using silent status-bar progress.

## Best solution

Provide supported client-side middleware customization that associates extension-controlled progress UI with a workDoneToken supplied to a request, following the maintainer's proposed direction. Preserve silent background progress by default; any server-controlled prominence field would be a separate protocol design question for microsoft/language-server-protocol.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/progress.ts`, `client/src/common/progressPart.ts`, `client/src/common/executeCommand.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/testServer.ts`
- **Validation:** Extend the client-node-tests progress integration coverage with a request carrying an extension-supplied workDoneToken. In a maintainer implementation session, run the client-node-tests suite and verify notification UI receives begin/report/end, cancellation reaches the server, handlers are released when the operation ends, and unrelated background progress remains silent. Also manually verify a slow refactor displays the chosen notification without duplicate status progress.
- **Behavior:**

  > Extensions need a supported way to show prominent progress for expensive user-initiated operations while retaining silent background progress. For the maintainer's proposed request-bound path, an extension must be able to associate its chosen UI with a token supplied to the server and receive the corresponding progress updates. Acceptance should cover begin/report/end, cancellation, operation completion, and absence of duplicate UI. The existing default must remain unchanged for extensions that do not opt into customization.
- **Trace:**

  > ProgressPart.begin in client/src/common/progressPart.ts hard-codes ProgressLocation.Window; ProgressFeature.initialize in client/src/common/progress.ts constructs that implementation for server-created progress. BaseLanguageClient.onProgress and middleware.handleWorkDoneProgress in client/src/common/client.ts already expose progress events, while middleware.sendRequest exposes outgoing parameters, but there is no integrated request-progress customization contract. ExecuteCommandFeature in client/src/common/executeCommand.ts constructs requests without workDoneToken, and its feature-specific next signature has no progress parameter. The maintainer proposes client-created token/UI injection at https://github.com/microsoft/vscode-languageserver-node/issues/1567#issuecomment-2538528787. The existing Progress tests in client-node-tests/src/integration.test.ts exercise event interception, providing a starting harness rather than proof of the requested UI behavior. Preserve initialization behavior, silent background progress, and existing middleware contracts; automatic partial-result support in https://github.com/microsoft/vscode-languageserver-node/issues/528 is related but distinct. The remaining scope question is whether the supported customization also covers server-created out-of-band progress, as the reporter requested, or initially only request-bound progress.
- **Open decisions:**
  - Should the initial public customization contract cover only extension-supplied request-bound progress, following the maintainer's proposal, or also allow extensions to choose prominent UI for server-created out-of-band progress?

## Evidence

- **Accepted implementation direction:** https://github.com/microsoft/vscode-languageserver-node/issues/1567#issuecomment-2538528787 explicitly proposes allowing implementors to create a progress token and corresponding UI in middleware and pass the token to the server, stating that this is not supported in the API. The issue carries feature-request, help wanted, and Backlog.
- **Current progress presentation:** client/src/common/progressPart.ts: ProgressPart.begin calls Window.withProgress with location: ProgressLocation.Window at line 63. client/src/common/progress.ts: ProgressFeature.initialize directly constructs ProgressPart for server-created tokens, with no UI factory or location customization hook.
- **Existing-capability check:** client/src/common/client.ts: LanguageClientOptions exposes progressOnInitialization and middleware, but no general progress UI configuration. middleware.handleWorkDoneProgress intercepts begin/report/end events, middleware.sendRequest can intercept request parameters, and BaseLanguageClient.onProgress registers token-specific handlers. These primitives permit custom plumbing, but do not themselves provide integrated token creation, request association, UI ownership, and cleanup. client/src/common/executeCommand.ts: ExecuteCommandSignature passes only command and arguments to next; its default request does not supply a workDoneToken.
