# Issue #1757 — Message middleware / interceptor API for `vscode-jsonrpc`

[https://github.com/microsoft/vscode-languageserver-node/issues/1757](https://github.com/microsoft/vscode-languageserver-node/issues/1757)

## Summary

Keep open: current MessageStrategy does not cover bidirectional envelope interception, and the maintainer explicitly welcomes this enhancement. Custom reader/writer decorators provide a workaround, but the accepted public API request remains unresolved.

## Change summary

Expose connection-level hooks to decorate outgoing JSON-RPC envelopes and extract metadata from incoming messages without changing method parameters or transport framing.

## Best solution

Provide bidirectional message interception in jsonrpc/ while preserving existing MessageStrategy dispatch and asynchronous-context behavior. Settle the public compatibility contract between the new hooks and handleMessage using the alternatives already proposed in the thread.

The maintainer explicitly welcomes a PR at https://github.com/microsoft/vscode-languageserver-node/issues/1757#issuecomment-4476821209; a decline close would contradict that acceptance.
- **Existing strategy covers incoming dispatch, not outgoing writes:** jsonrpc/src/common/connection.ts:476-495 exposes only MessageStrategy.handleMessage(message, next). Its invocation at lines 737-741 occurs when dispatching the incoming message queue. Outgoing requests, notifications and responses call messageWriter.write directly at lines 1463, 1316, 834 and 843. Despite the thread's description of outgoing coverage, current source has no outgoing MessageStrategy hook.
- **Incoming coverage is not transport-wide:** jsonrpc/src/common/connection.ts:addMessageToQueue handles responses directly when maxParallelism is limited, bypassing MessageStrategy; callback also handles some cancellation notifications before queue dispatch. Existing handleMessage therefore is not an interceptor for every received envelope.
- **Decorator workaround corrects an API premise:** jsonrpc/src/node/main.ts:300-313 accepts caller-supplied MessageReader and MessageWriter instances and constructs stream adapters only for stream arguments. jsonrpc/src/common/messageWriter.ts:19-44 exposes write(Message), events, end and dispose, so a delegating writer can decorate envelopes without reimplementing framing; a reader decorator can similarly intercept its callback. This workaround does not supply the requested ConnectionOptions hook.
- **Client middleware does not fill the gap:** client/src/common/client.ts:313-345 exposes general sendRequest/sendNotification middleware over method signatures and parameters, not complete JSON-RPC envelopes. LanguageClientOptions.connectionOptions.messageStrategy at lines 379-383 exposes the same existing dispatch strategy, not a bidirectional transport interceptor.
- **Public compatibility decision remains:** At https://github.com/microsoft/vscode-languageserver-node/issues/1757#issuecomment-4476817575 the maintainer raises possible MessageStrategy deprecation; at https://github.com/microsoft/vscode-languageserver-node/issues/1757#issuecomment-4476946709 they alternatively suggest directional methods or a direction parameter. The thread has not selected the public contract.
- **Canonical and implementation search:** Repository searches for MessageStrategy, message middleware, interceptor, tracing and metadata found no verified open canonical owning this enhancement and no matching open PR. https://github.com/microsoft/vscode-languageserver-node/issues/943 is closed and concerns preserving AsyncLocalStorage during incoming dispatch, not adding bidirectional envelope hooks. Its behavior is represented by the existing 'Uses custom message handler' test in jsonrpc/src/node/test/connection.test.ts.
