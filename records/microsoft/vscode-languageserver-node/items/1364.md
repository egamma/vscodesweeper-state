# Issue #1364 — Conform to the recommendation in the standard for the socket argument, which is currently `--socket` instead of `--port`

[https://github.com/microsoft/vscode-languageserver-node/issues/1364](https://github.com/microsoft/vscode-languageserver-node/issues/1364)

## Summary

The CLI recommendation and implementation still differ: current main emits and accepts --socket, while LSP 3.17 recommends --port. Keep this accepted Backlog request open; existing customization does not resolve the convention mismatch, and no verified open canonical owns it.

## Change summary

Make the socket transport command-line convention consistent between the LSP implementation recommendations and these libraries.

## Best solution

Agree on a consistent socket CLI convention while preserving compatibility with existing --socket consumers, then align the server parser and client launch arguments with that decision. If the recommendation should instead change, coordinate that documentation change in microsoft/language-server-protocol.

## Plan brief

- **Likely files:** `client/src/node/main.ts`, `server/src/node/main.ts`, `client-node-tests/src/integration.test.ts`
- **Validation:** The plan should end with socket-launch integration checks for Executable, forked NodeModule and custom-runtime NodeModule configurations, plus server startup checks for the agreed CLI forms. Verify successful initialization, the actual bound port, and continued compatibility with existing --socket users; leave stdio and pipe behavior unchanged.
- **Behavior:**

  > The published LSP 3.17 socket recommendation uses --port, but these libraries use --socket. The desired outcome is a consistent, documented convention across the recommendation and built-in client/server behavior. Acceptance must cover both supported argument forms for the chosen spelling and an explicit compatibility contract for existing consumers. Stdio and pipe transport conventions are outside this request.
- **Trace:**

  > client/src/node/main.ts appends --socket in all three built-in socket launch paths, after createClientSocketTransport resolves. server/src/node/main.ts, _createConnection, parses only --socket and --socket= for TCP ports. LanguageClientOptions.middleware intercepts protocol traffic and cannot change this launch convention; function-valued ServerOptions bypasses the built-in path but does not satisfy the standardization request. The reporter explicitly permits either implementation alignment or recommendation alignment at https://github.com/microsoft/vscode-languageserver-node/issues/1364#issuecomment-1813228369. Historical standardization discussion at https://github.com/microsoft/language-server-protocol/issues/483 confirms an established --socket convention but does not settle this newer mismatch. Preserve socket ownership, bound-port handling and unrelated transport lifecycle behavior.
- **Open decisions:**
  - Should --port become the canonical client/server socket argument, with an explicit compatibility contract for existing --socket consumers, or should --socket remain canonical and the specification recommendation be aligned instead?

## Evidence

- **Published recommendation:** https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#implementationConsiderations recommends passing the socket port as the next argument or with --port=. The corresponding specification source, _specifications/lsp/3.17/specification.md:704-708, was retrieved and confirms this is a recommendation, not a mandatory wire-protocol requirement.
- **Current client behavior:** client/src/node/main.ts:426-427, 478-479 and 528-529 append --socket=${transport.port()} for custom-runtime NodeModule, forked NodeModule and Executable socket launches respectively. None emits --port.
- **Current server behavior:** server/src/node/main.ts:195-239, _createConnection, recognizes --socket followed by a port and --socket=port, but has no --port branch. Its connection error guidance also names --socket.
- **Existing-capability check:** LanguageClientOptions and Middleware in client/src/common/client.ts expose protocol interception, not transport CLI rewriting. NodeModule.args and Executable.args in client/src/node/main.ts do not suppress the automatically appended --socket argument. A function-valued ServerOptions can supply custom transports, but that is a workaround rather than alignment of the libraries' built-in convention.
- **Reporter intent and accepted work:** https://github.com/microsoft/vscode-languageserver-node/issues/1364#issuecomment-1813228369 explicitly allows changing the specification recommendation instead; consistency is the central ask. The issue carries feature-request and the Backlog milestone, with no later maintainer decline in the supplied or retrieved discussion.
