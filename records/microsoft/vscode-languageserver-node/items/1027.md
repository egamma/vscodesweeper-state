# Issue #1027 — Support sending and receiving typed arrays

[https://github.com/microsoft/vscode-languageserver-node/issues/1027](https://github.com/microsoft/vscode-languageserver-node/issues/1027)

## Summary

Keep open: default stream serialization still turns typed-array payloads into JSON objects. Custom codecs provide a workaround, but require configuring both endpoints and do not establish built-in typed-array support; the On Deck milestone also protects this accepted request from a question or decline close.

## Change summary

Preserve typed arrays in custom request parameters and results while avoiding indexed-object expansion and costly reconstruction of large binary payloads.

## Best solution

Define a supported typed-array round-trip contract in jsonrpc/ and expose any necessary configuration through client/ without requiring extension authors to take over server-process lifecycle management. Reuse the existing codec extension points and preserve ordinary JSON interoperability; a standardized encoding handshake would additionally require agreement in microsoft/language-server-protocol.

## Plan brief

- **Likely files:** `jsonrpc/src/common/encoding.ts`, `jsonrpc/src/common/messageReader.ts`, `jsonrpc/src/common/messageWriter.ts`, `jsonrpc/src/node/ril.ts`, `client/src/node/main.ts`, `jsonrpc/src/node/test/messages.test.ts`
- **Validation:** Extend the existing MessagePack/stream-message test harness to round-trip a custom request result containing Uint8Array([1, 2, 3]) and a large byte payload under the agreed configuration. Assert the agreed runtime type and exact bytes, measure framed payload size against indexed-object JSON expansion, and verify ordinary JSON messages retain existing behavior.
- **Behavior:**

  > A custom file-reading request returns a typed array, but the JSON stream transport delivers an indexed object instead. The desired supported path preserves the agreed typed-array type and bytes without requiring callers to reconstruct indexed objects. Acceptance should cover a small response, a large binary response, and ordinary non-binary messages. Existing JSON clients and servers must remain interoperable unless they explicitly agree to another serialization contract.
- **Trace:**

  > The default stream writer selects RAL().applicationJson.encoder, implemented with JSON.stringify in jsonrpc/src/node/ril.ts; the matching reader uses JSON.parse without typed-array revival. ContentTypeEncoder and ContentTypeDecoder in jsonrpc/src/common/encoding.ts already permit alternate codecs, and jsonrpc/src/node/test/messages.test.ts demonstrates MessagePack framing. client/src/node/main.ts accepts a ServerOptions function returning MessageTransports, but that integration leaves process lifecycle management to the caller, as confirmed in https://github.com/microsoft/vscode-languageserver-node/issues/553#issuecomment-1569689492. Browser worker messaging uses postMessage and must not be assumed to share the stream limitation. Preserve default JSON behavior and avoid adding a hard dependency on an external codec library. The uncertainty is the public typed-array and configuration contract, not the location of the JSON conversion; https://github.com/microsoft/vscode-languageserver-node/pull/1250 is an unmerged precedent rather than an active implementation candidate.
- **Open decisions:**
  - Should typed-array preservation be offered through an explicitly configured whole-connection codec, or through a supported binary representation within otherwise JSON custom messages?
  - Which typed-array kinds and runtime reconstruction guarantees should the supported contract cover beyond Uint8Array?
  - Must the supported client configuration preserve library-managed server-process lifecycle, rather than requiring a custom MessageTransports factory?

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode-languageserver-node/issues/1027 requests typed-array results for custom file-reading messages: returning Uint8Array([1, 2, 3]) produces an indexed JSON object at the server, increasing transmission size and reconstruction work.
- **Current default serialization:** jsonrpc/src/node/ril.ts:127-146 implements applicationJson with JSON.stringify and JSON.parse, without typed-array tagging or revival. jsonrpc/src/common/messageWriter.ts selects that encoder by default; messageReader.ts:161-164 likewise defaults to the JSON decoder.
- **Existing-capability check:** StreamMessageWriter accepts contentTypeEncoder and StreamMessageReader accepts contentTypeDecoder. client/src/node/main.ts:335-340 accepts a ServerOptions function returning MessageTransports unchanged, allowing paired custom codecs. LanguageClientOptions and Middleware in client/src/common/client.ts expose no built-in typed-array serialization contract; notification/request interception alone does not preserve binary types through JSON.
- **Workaround limitations:** jsonrpc/src/node/test/messages.test.ts:235-270 demonstrates a MessagePack codec round trip, but only for an ordinary request envelope, not typed-array payloads. In https://github.com/microsoft/vscode-languageserver-node/issues/553#issuecomment-1567918482 the maintainer identifies custom MessageTransports as the existing integration path; https://github.com/microsoft/vscode-languageserver-node/issues/553#issuecomment-1569689492 confirms that this path leaves server lifecycle management to the extension and rejects hard dependencies on external codec libraries.
