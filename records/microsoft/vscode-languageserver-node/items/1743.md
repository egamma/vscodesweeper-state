# Issue #1743 — `vscode-languageserver-types` package metadata still steers webpack builds into the UMD entry, causing dependency warnings**

[https://github.com/microsoft/vscode-languageserver-node/issues/1743](https://github.com/microsoft/vscode-languageserver-node/issues/1743)

## Summary

Keep open: current main adds a bundler-oriented module export condition absent from the reported 3.17.5 package, but still retains UMD fallbacks. That improvement needs checking against the reported Docusaurus dependency chain before treating the request for warning-free default bundling as satisfied.

## Change summary

Make vscode-languageserver-types resolve to a statically analyzable build in modern bundlers without consumer aliases or warning suppression.

## Best solution

Establish whether the current types/ export conditions eliminate the warning in the reported Docusaurus build; if not, identify the remaining resolution path and agree on a compatible package-entry contract. Preserve supported non-bundled consumers and coordinate downstream language-service packaging only where the trace demonstrates it is necessary.

- **Behavior:**

  > Docusaurus/Webpack consumers should bundle vscode-languageserver-types without critical-dependency warnings originating in its UMD wrapper and without package-specific aliases or warning suppression. - **Trace:**

  > The published 3.17.5 metadata directs main and the default export condition to lib/umd/main.js, while import and browser select ESM. Current types/package.json adds a module condition targeting ESM but retains both UMD fallbacks; the publish configurations still produce both formats, and build/bin/fix-esm.js marks the ESM directory as a module package. https://github.com/microsoft/vscode-languageserver-node/pull/1386 explains the bundler condition's intended coverage. The remaining uncertainty is which condition or downstream import selects UMD in the Docusaurus build, and whether current metadata already prevents it. https://github.com/microsoft/vscode-languageserver-node/issues/1355 supplies related resolver workarounds, while https://github.com/microsoft/vscode-languageserver-node/pull/1328 records historical AMD compatibility constraints. This is package-publication work in types/, not language-client middleware or an LSP specification change; do not broaden it into ESM conversion of the other modules.
- **Open decisions:**
  - If the current module condition does not satisfy the reported build, must the package continue supporting AMD/UMD consumers through its root fallback, or may that public entry-point contract change?
