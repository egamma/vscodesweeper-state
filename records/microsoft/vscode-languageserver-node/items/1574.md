[https://github.com/microsoft/vscode-languageserver-node/issues/1574](https://github.com/microsoft/vscode-languageserver-node/issues/1574)

## Summary

The missing unsigned-integer bounds check is a concrete case of the general LSP object validation layer already requested in an older open issue. Consolidate there, preserving this formatting example and the maintainer's requirement that validation be configurable.

## Change summary

Provide configurable validation that detects LSP position values exceeding the unsigned-integer maximum instead of silently accepting malformed formatting responses.

## Best solution

Implement the general property-validation layer tracked by https://github.com/microsoft/vscode-languageserver-node/issues/695, including numeric bounds on incoming formatting edits. Carry this issue's configurable-enforcement requirement and Rust u32::MAX example into that work so existing permissive behavior is not changed unexpectedly.

## Evidence

- **Verified canonical and ownership:** https://github.com/microsoft/vscode-languageserver-node/issues/695 is currently open and was created in 2020. Its maintainer explicitly expands the request to a general LSP object validation layer that validates all properties: https://github.com/microsoft/vscode-languageserver-node/issues/695#issuecomment-949414083. Numeric bounds on position properties are part of that same validation mechanism, rather than a separate formatting capability.
- **Current formatting path:** client/src/common/formatting.ts: DocumentFormattingFeature passes the server response directly to protocol2CodeConverter.asTextEdits. In client/src/common/protocolConverter.ts:399-410 and 715-731, asTextEdits calls asTextEdit, which constructs a VS Code TextEdit through asRange without checking LSP unsigned-integer bounds. types/src/main.ts:45-54 defines uinteger.MAX_VALUE as 2147483647 and exposes a bounds predicate, but this conversion path does not invoke it.
- **Existing-capability check:** client/src/common/client.ts:319-405 exposes general sendRequest middleware and per-feature middleware, but no built-in protocol-value validation setting. Custom middleware could implement checks; that is not equivalent to the accepted configurable validation layer requested here.
- **Preserve compatibility requirement:** The maintainer proposes error reporting in https://github.com/microsoft/vscode-languageserver-node/issues/1574#issuecomment-2440739533 and explicitly requires a setting because enforcement can cause unexpected behavior in https://github.com/microsoft/vscode-languageserver-node/issues/1574#issuecomment-2539007411. These requirements should accompany consolidation into the canonical validation request.
- **Downstream change is not a fix here:** https://github.com/redhat-developer/lsp4ij/pull/1169 is merged, but handles Integer.MAX_VALUE as an end-of-line character indicator in IntelliJ's client. It does not add validation to these libraries or address acceptance of Rust u32::MAX, 4294967295.
