# Issue #1574 — Overflow value(exceeding uinteger) passed into jsonrpc  but still work

[https://github.com/microsoft/vscode-languageserver-node/issues/1574](https://github.com/microsoft/vscode-languageserver-node/issues/1574)

## Summary

Optional validation remains an accepted, unimplemented enhancement: formatting responses still reach conversion without enforcing the LSP uinteger limit. Keep this request open; the older validation-layer issue concerns a different observable symptom and does not settle this request's configurable rejection behavior.

## Change summary

Provide configurable detection and reporting of out-of-range LSP numeric values that the VS Code client currently accepts.

## Best solution

Add optional LSP-aware validation in the protocol/client path, preserving existing behavior when disabled and making invalid formatting results diagnosable when enabled. Coordinate with https://github.com/microsoft/vscode-languageserver-node/issues/695 while retaining this report's numeric-boundary and compatibility requirements.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/formatting.ts`, `client/src/common/protocolConverter.ts`, `types/src/main.ts`, `client-node-tests/src/converter.test.ts`
- **Validation:** Extend client integration/converter coverage with a formatting response containing coordinate values 2147483647, 2147483648 and 4294967295. Verify the valid boundary is accepted, invalid values produce the agreed diagnostic/error when validation is enabled, and disabled validation preserves existing behavior; compile client-node-tests before running its VS Code test suite.
- **Behavior:**

  > A server can return a formatting edit with coordinate 4294967295, exceeding the LSP uinteger maximum, without the client diagnosing that violation. The requested outcome is configurable checking rather than an unconditional compatibility change. Acceptance must cover valid and overflowing boundary values, actionable reporting when enabled, and unchanged behavior when disabled.
- **Trace:**

  > DocumentFormattingFeature.registerLanguageProvider in client/src/common/formatting.ts sends the formatting request and forwards its result into protocol2CodeConverter.asTextEdits. That converter calls asTextEdit and asRange, which construct VS Code objects directly from the received coordinates; the existing uinteger.is helper in types/src/main.ts is not called on this path. LanguageClientOptions exposes middleware but no built-in validation setting. Keep generic JSON-RPC transport independent of LSP-specific numeric rules and preserve the existing default behavior. The related general-validation discussion at https://github.com/microsoft/vscode-languageserver-node/issues/695 suggests metamodel-generated validation, but does not settle this feature's scope or failure contract.
- **Open decisions:**
  - Should the initial opt-in validation contract cover numeric coordinates only, or all supported LSP payload properties?
  - When enabled validation finds an invalid server response, should the request fail locally, or should the client report the violation while continuing to accept the result?
