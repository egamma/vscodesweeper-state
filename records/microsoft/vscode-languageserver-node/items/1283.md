# Issue #1283 — Allow initializationOptions, fillInitializeParams, etc to be async

[https://github.com/microsoft/vscode-languageserver-node/issues/1283](https://github.com/microsoft/vscode-languageserver-node/issues/1283)

## Summary

The asynchronous initialization extension points are still missing on current main. This is accepted work in Backlog with help wanted and an explicit maintainer invitation for a PR; existing middleware and feature registration do not cover the asynchronous preparation requested.

## Change summary

Allow asynchronous computation of initialization options, initialization parameters and client capabilities before sending the initialize request.

## Best solution

Support awaited initialization preparation in client/ while retaining synchronous consumers and deterministic feature ordering. Establish the compatible public hook contract, then ensure initialization sends only fully prepared options and capabilities.

- **Behavior:**

  > An extension author must be able to compute initialization options and client capabilities asynchronously during client initialization. The initialize request must contain the completed values, not promises or partially populated parameters. Existing synchronous callbacks and features must retain their behavior and ordering. Acceptance checks should cover delayed preparation, rejection, and preparation on a subsequent client start.
- **Trace:**

  > BaseLanguageClient.initialize in client/src/common/client.ts constructs InitializeParams using unawaited computeClientCapabilities and initializationOptions results, then invokes fillInitializeParams synchronously. StaticFeature and DynamicFeature in client/src/common/features.ts expose void-returning preparation hooks, and both feature loops discard return values. The node LanguageClient override in client/src/node/main.ts calls the base parameter hook before supplying processId. The general sendRequest middleware does not intercept the internal connection.initialize path, so it cannot supply the missing await point. Preserve synchronous consumers, feature ordering and the transport wrapper's immediate request dispatch after preparation. The remaining uncertainty is the public extension contract, not whether a gap exists; the maintainer accepted contributions at https://github.com/microsoft/vscode-languageserver-node/issues/1283.
- **Open decisions:**
  - Should the existing feature and protected initialization hooks explicitly support asynchronous returns, including any resulting subclass contract changes, or should a separate asynchronous preparation extension point preserve those existing public contracts?
