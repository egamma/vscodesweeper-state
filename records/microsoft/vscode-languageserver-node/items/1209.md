# Issue #1209 — Feature request: Expose the sync API to all client/server connections

[https://github.com/microsoft/vscode-languageserver-node/issues/1209](https://github.com/microsoft/vscode-languageserver-node/issues/1209)

## Summary

Keep open: a shared, synchronous server API for client-backed filesystem access is still missing. The maintainer accepted this direction, and the open filesystem implementation candidate provides asynchronous reads, not the requested synchronous facade.

## Change summary

Expose reusable client-backed filesystem access through language-server connections, including synchronous reads of files unavailable on the server's local filesystem.

## Best solution

Coordinate the filesystem protocol contract with https://github.com/microsoft/language-server-protocol/issues/1264 and review the asynchronous foundation in https://github.com/microsoft/vscode-languageserver-node/pull/1825. Preserve this issue's remaining requirement: a reusable synchronous server-facing API with defined runtime and transport support, rather than requiring each server to integrate the VS Code sync packages independently.

## Evidence

- **accepted and protected work:** https://github.com/microsoft/vscode-languageserver-node/issues/1209 is MEMBER-authored and assigned to On Deck. In the supplied discussion, the maintainer agreed with client-backed filesystem access and welcomed continuation of the unfinished LSP filesystem layer; a decline close would contradict that acceptance.
- **existing-capability check:** client/src/common/client.ts:340-410 defines Middleware and LanguageClientOptions without a shared synchronous filesystem option or hook. server/src/common/server.ts:635-685 defines RemoteWorkspace from configuration, workspace folders, file operations and text-document content, but exposes no getSyncFileSystem API. Custom requests and features permit bespoke implementations, not the reusable integration requested here.
- **content-provider direction differs:** client/src/common/textDocumentContent.ts:93-115 implements provideTextDocumentContent by sending TextDocumentContentRequest from the client to the server. It lets the server supply content to VS Code, rather than letting the server synchronously read the client's filesystem.
- **verified open implementation candidate:** https://github.com/microsoft/vscode-languageserver-node/pull/1825 is open and unmerged. Its inspected server/src/common/fileSystem.ts patch exposes workspace.fs.stat, readFile and readDirectory as Promise-returning methods backed by connection.sendRequest. This advances client-backed reads but does not provide synchronous access; its body references the spec issue, not this issue.
- **canonical search and remaining work:** Filesystem-related searches found the verified open spec proposal https://github.com/microsoft/language-server-protocol/issues/1264 and implementation candidate https://github.com/microsoft/vscode-languageserver-node/pull/1825. The spec proposal concerns providing filesystems and remote reads/writes; completing its specification would still require library implementation and a synchronous facade here, so it is an enabling dependency rather than a duplicate target.
- **external sync API is not library adoption:** https://github.com/microsoft/vscode-wasm/blob/main/sync-api-client/README.md describes synchronous filesystem.readFile access from a separate worker using ClientConnection, ServiceConnection and ApiService, with browser/node-specific imports. That existing package requires explicit integration and does not establish that language-server connections in this repository expose the requested API.
