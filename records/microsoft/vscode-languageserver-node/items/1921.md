# Issue #1921 — A request can be sent after `shutdown` when `stop()` starts while `sendRequest` awaits pending document synchronization

[https://github.com/microsoft/vscode-languageserver-node/issues/1921](https://github.com/microsoft/vscode-languageserver-node/issues/1921)

## Summary

The shutdown race remains in current main: requests and notifications can pass their entry-state check, await document synchronization, and send after stopping begins. Keep this open while the explicitly linked implementation candidate is reviewed.

## Change summary

Prevent requests and notifications awaiting document synchronization from being sent after client shutdown begins.

## Best solution

Review https://github.com/microsoft/vscode-languageserver-node/pull/1928 against the request and notification races, preserving normal document ordering and shutdown behavior. Its regression cases should demonstrably suspend an already-running client's send during document synchronization before initiating stop, rather than race startup.

## Evidence

- **Current-source request race:** At checkout HEAD 898f44d0fd2a0e9c182414060fb7084ed39f49bc, client/src/common/client.ts:914–929 checks inactive states only on entry, then awaits $start(), sendPendingOpenNotifications(), and full-text synchronization. Lines 948–968 subsequently invoke middleware or connection.sendRequest without rechecking client state.
- **Shutdown interleaving:** client/src/common/client.ts:1647–1654 sets ClientState.Stopping, performs cleanup, then awaits connection.shutdown() before connection.exit(). A request suspended during document synchronization retains its connection and can resume while shutdown awaits its response. client/src/common/textSynchronization.ts:165–170 awaits each pending open notification, providing the suspension exercised by the reporter's paused-stream trigger.
- **Notification sibling:** client/src/common/client.ts:1020–1075 has the same entry-only state check followed by asynchronous startup/document synchronization and a final connection.sendNotification call. The report explicitly includes notifications, so request-only coverage would not satisfy its scope.
- **Complete reproduction and impact:** https://github.com/microsoft/vscode-languageserver-node/issues/1921 supplies the complete in-memory-stream reproducer, reports shutdown followed by textDocument/documentSymbol in 10/10 runs on both client 10.1.2 and 11.0.0, and reports removal of that message in 5/5 experimental guarded runs. The downstream trigger is breadcrumbs during recovery followed by restart or window close; no data loss or hang is established. This review inspected source without executing the reproducer.
- **Open implementation candidate:** https://github.com/microsoft/vscode-languageserver-node/pull/1928 is verified open and explicitly says Fixes #1921. Its public review flags that the proposed regression tests race $start() instead of establishing a document-sync suspension. An open linked PR requires keeping the issue open and precludes agent readiness.
- **Related issue is not canonical:** https://github.com/microsoft/vscode-languageserver-node/issues/1868 concerns a visible document's request overtaking didOpen during startup. That document-ordering defect does not own preventing sends after shutdown; satisfying its central request would not necessarily resolve this lifecycle race.
- **Discussion boundary:** The complete October 28 comment expands the proposal to cancellation signals, queue drains, and a JSON-RPC shutdown guard, but provides no independent reproduction or maintainer decision. Those suggestions do not establish that generic jsonrpc should acquire LSP-specific shutdown semantics.
