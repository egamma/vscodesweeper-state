# Issue #1595 — `detached` not working as expected

[https://github.com/microsoft/vscode-languageserver-node/issues/1595](https://github.com/microsoft/vscode-languageserver-node/issues/1595)

## Summary

Keep open: detached spawning still does not give the server independent lifetime, and the maintainer accepted extending that behavior. The linked implementation PR was closed without merging because its author could no longer continue, not because the request was declined.

## Change summary

Allow a detached language server to survive extension-host termination and control its own lifetime.

## Best solution

Complete coordinated detached-lifetime support in client/src/node/main.ts and server/src/node/main.ts, using the abandoned PR's review as design context. Honor the maintainer's requested configurable timeout contract while preserving normal non-detached cleanup and distinguishing transport loss from an explicit LSP shutdown/exit.

## Plan brief

- **Likely files:** `client/src/node/main.ts`, `server/src/node/main.ts`, `client-node-tests/src`
- **Validation:** In a maintainer-run session, use the supplied lsp-sample executable/stdio setup on macOS, log both PIDs, terminate the extension host, and verify the server survives beyond the three-second watchdog interval for indefinite detachment. Verify configured finite expiry, unchanged non-detached termination, and explicit shutdown/exit behavior; exercise graceful host termination separately from client.stop(). Repeat lifetime checks on Windows and Linux before declaring cross-platform support.
- **Behavior:**

  > A language server started in detached mode should not be forced to exit merely because its extension host terminates or its transport closes. Its lifetime must follow the agreed detached timeout policy, including an explicit indefinite mode. Non-detached servers must retain existing automatic cleanup. Acceptance must cover abrupt and graceful host termination and distinguish those events from an explicit LSP shutdown/exit.
- **Trace:**

  > On the reported Executable/stdio path, client/src/node/main.ts passes detached to cp.spawn and records _isDetached, but fillInitializeParams still sends the client PID. server/src/node/main.ts independently exits through watchDog.initialize when that PID disappears and through _createConnection's input end/close handlers; neither consults detached state. The initializationOptions workaround does not change the top-level initialize PID. client/src/common/client.ts shutdown explicitly sends shutdown and exit, and server/src/common/server.ts handles exit through watchDog.exit, so protocol shutdown must not be conflated with transport loss. https://github.com/microsoft/vscode-languageserver-node/pull/1603 is an unmerged, abandoned implementation with relevant review feedback and manual macOS/Windows testing claims, not fix provenance. The maintainer requested a boolean-or-number detached contract with -1 meaning indefinite at https://github.com/microsoft/vscode-languageserver-node/pull/1603#discussion_r1963029726; the default timeout duration is not settled in that record. Preserve default non-detached behavior and avoid treating Node process detachment alone as proof of server survival.
- **Open decisions:**
  - What default post-disconnection lifetime should detached: true use, given the maintainer's requested finite default and explicit -1 indefinite mode?

- **existing capability is partial:** client/src/node/main.ts: ExecutableOptions.detached is passed to cp.spawn at lines 495-513, and LanguageClient.shutdown skips checkProcessDied for detached processes at lines 252-261. Therefore initializationOptions: { processId: '' } does not alter the PID consumed by the server watchdog; suppressing that watchdog alone would also leave the stdio end/close exit handlers.
