# Issue #1131 — Support middleware for logMessage and showMessage

[https://github.com/microsoft/vscode-languageserver-node/issues/1131](https://github.com/microsoft/vscode-languageserver-node/issues/1131)

## Summary

Keep the accepted request open: current main still lacks dedicated logMessage and showMessage middleware. The lower-level connectionOptions.messageStrategy can intercept these incoming notifications and preserve their normal handling, but that existing alternative does not justify declining an item accepted with help wanted and Backlog.

## Change summary

Expose middleware for server-initiated window/logMessage and window/showMessage notifications that lets extensions add custom handling while forwarding to the client's default handlers.

## Best solution

Provide the accepted per-message customization surface in client/ while retaining the existing logging and message-display behavior when notifications are forwarded. Document connectionOptions.messageStrategy.handleMessage(message, next) as the currently available lower-level alternative; the related JSON-RPC interceptor proposal does not itself deliver dedicated LanguageClient middleware.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/testServer.ts`
- **Validation:** Extend the client integration suite with server-emitted window/logMessage and window/showMessage notifications. Verify interception receives the original parameters, forwarding retains severity-specific default handling exactly once, and clients without middleware retain existing behavior. Do not execute this validation in the read-only review checkout.
- **Behavior:**

  > Extensions need an idiomatic per-message interception surface for server-initiated log and show notifications. Custom handling must be able to observe the notification and forward it to the client's usual handler without duplicating output or message display. Existing clients without these hooks must behave unchanged.
- **Trace:**

  > BaseLanguageClient.start in client/src/common/client.ts installs the log and show notification handlers directly, while WindowMiddleware currently exposes only showDocument. The existing connectionOptions.messageStrategy reaches incoming JSON-RPC dispatch and can already observe and forward these notifications, so distinguish dedicated middleware ergonomics from a missing transport capability. Registering onNotification is not an equivalent wrapper because the connection stores one handler per method. Preserve severity mapping, existing output-channel behavior and unrelated request handling. The accepted scope is recorded at https://github.com/microsoft/vscode-languageserver-node/issues/1131; https://github.com/microsoft/vscode-languageserver-node/issues/1757 is related transport-layer work, not a replacement for this request.
- **Open decisions:**
  - Should showMessage interception cover only window/showMessage notifications, as described in the report, or also window/showMessageRequest and its returned action selection?

## Evidence

- **maintainer acceptance:** https://github.com/microsoft/vscode-languageserver-node/issues/1131#issuecomment-1330282581 explicitly states that middleware for these messages is missing. The issue carries help wanted, feature-request and Backlog; no later comment withdraws that acceptance.
- **current dedicated middleware gap:** client/src/common/client.ts:302-346 defines WindowMiddleware with only showDocument and defines GeneralMiddleware with outgoing sendRequest/sendNotification hooks. BaseLanguageClient.start at lines 1340-1390 directly installs LogMessageNotification, ShowMessageNotification and ShowMessageRequest handlers without consulting middleware.
- **existing lower-level capability:** LanguageClientOptions.connectionOptions.messageStrategy is exposed in client/src/common/client.ts:379-383 and passed into connection creation at line 1846. jsonrpc/src/common/connection.ts defines MessageStrategy.handleMessage(message, next) and invokes it for queued incoming messages at lines 737-741; filtering by notification method and returning next(message) preserves the built-in dispatch. This covers the body's interception-and-forwarding use case, but is not a dedicated per-message Middleware hook.
- **handler registration is not chaining:** BaseLanguageClient.onNotification registers the supplied handler directly with the connection. jsonrpc/src/common/connection.ts:1321-1333 stores one notification handler per method using Map.set, so registering another window/logMessage handler replaces rather than wraps the default handler.
- **canonical and implementation-candidate search:** GitHub searches for logMessage middleware, showMessage, intercept, server-initiated messages and open PRs mentioning logMessage or 1131 found no verified canonical or open implementation candidate. https://github.com/microsoft/vscode-languageserver-node/issues/1757 requests transport-level JSON-RPC metadata interception, not dedicated LanguageClient window-message hooks, so it is related rather than a canonical duplicate.
- **related work does not complete this request:** https://github.com/microsoft/vscode-languageserver-node/issues/1116 concerns adoption of LogOutputChannel; its discussion explicitly notes the missing server-initiated middleware. https://github.com/dotnet/roslyn/pull/78334 changes downstream Razor log routing, not this repository's client middleware.
