# Issue #1616 — LanguageClient.sendNotification fails due to change in state due to stopping client.

[https://github.com/microsoft/vscode-languageserver-node/issues/1616](https://github.com/microsoft/vscode-languageserver-node/issues/1616)

## Summary

The reported race remains in current main: a notification admitted while running can report 'Starting server failed' after an intentional stop changes the state. Keep this accepted bug open; the source confirms the failure, but the public behavior for notifications overtaken by shutdown still needs a decision.

## Change summary

Prevent a configuration notification racing an intentional client stop from being misreported as a server startup failure.

## Best solution

Define shutdown-race handling in client/ so an intentional stop is distinguished from an actual startup failure, and apply that policy to configuration forwarding. Preserve genuine startup and transport error reporting rather than suppressing notification failures indiscriminately.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/configuration.ts`, `client-node-tests/src/integration.test.ts`, `client-node-tests/src/servers/startStopServer.ts`
- **Validation:** Add and run an integration regression in the existing Server tests suite: start an IPC client, initiate a notification while Running, call stop() before the startup-await continuation resumes, and observe both promises and configuration error logging. Assert the agreed shutdown outcome, no misleading startup-failure diagnostic, no unintended restart or post-shutdown notification, and unchanged genuine startup/shutdown failure behavior. The existing client-node-tests npm test script runs the harness after normal build preparation; no execution was performed during this review.
- **Behavior:**

  > An extension stops a running language client in response to a configuration change while the client's own listener forwards that change. Today the notification can fail with 'Starting server failed' even though startup succeeded and shutdown was intentional. The finished behavior must distinguish this shutdown race from actual startup failure and honor the maintainer-selected notification promise contract. Acceptance checks must exercise the race deterministically, verify its diagnostic behavior, and preserve normal notification delivery and genuine failure reporting.
- **Trace:**

  > BaseLanguageClient.sendNotification() in client/src/common/client.ts checks the state before awaiting $start(); $start() itself awaits start() before consulting activeConnection(). shutdown() changes the state to Stopping synchronously, making activeConnection() return undefined when that continuation resumes and causing the generic startup-failure exception. Configuration forwarding in client/src/common/configuration.ts catches and logs this rejection. The source confirms the interleaving without execution; it does not settle whether this public sendNotification() promise should resolve or reject on intentional shutdown. General sendNotification middleware runs after the failing await, while workspace.didChangeConfiguration middleware is an earlier interception point but does not intrinsically close the race. Preserve real startup failures, transport failures, document-notification ordering, and existing start/stop semantics outside the reported case. The maintainer left the policy open at https://github.com/microsoft/vscode-languageserver-node/issues/1616#issuecomment-2670768834; the related https://github.com/microsoft/vscode-languageserver-node/pull/1782 addresses a different connection-close path.
- **Open decisions:**
  - When intentional shutdown overtakes a notification admitted while Running, should sendNotification() resolve without delivery, or reject with a shutdown-specific outcome that built-in configuration forwarding treats as expected?

## Evidence

- **Current-source race:** client/src/common/client.ts:1021-1038 checks the state before awaiting $start(). At 1824-1833, $start() awaits start() and then calls activeConnection(); activeConnection() at 1292-1293 returns undefined unless the state is Running. shutdown() at 1629 changes the state synchronously to Stopping, so a stop between the await and its continuation produces 'Starting server failed' despite successful prior startup.
- **Configuration trigger and impact:** client/src/common/configuration.ts:185-188 registers the configuration listener; onDidChangeConfiguration() at 211-239 forwards through sendNotification() and catches its rejection by logging 'Sending notification workspace/didChangeConfiguration failed'. This matches the reporter's competing configuration listener calling client.stop(15000); the library path catches the error, so a process crash is not established.
- **Existing extension points do not resolve the race:** middleware.workspace.didChangeConfiguration in client/src/common/configuration.ts:236 can intercept forwarding, but checking isRunning() before next() still leaves the asynchronous state-change window. General middleware.sendNotification is invoked at client/src/common/client.ts:1072-1076 only after $start(), too late to intercept this failure.
- **Maintainer acceptance and unresolved contract:** The issue carries bug and the Backlog milestone. https://github.com/microsoft/vscode-languageserver-node/issues/1616#issuecomment-2670768834 acknowledges the analysis with 'Needs some thinking...', without deciding whether an overtaken notification should resolve without delivery or reject with a shutdown-specific outcome.
- **Canonical and open-PR search:** Repository searches for sendNotification, stopping, the exact startup-failure message, and open configuration/stop PRs found no canonical owning this race or open PR referencing this issue. https://github.com/microsoft/vscode-languageserver-node/issues/1608 and https://github.com/microsoft/vscode-languageserver-node/pull/1782 concern connection-close handling and toast suppression, not the $start()/activeConnection() notification race; shipping that PR would leave this failure intact.
- **Downstream reference is not a fix:** https://github.com/SchneiderDaniel/cheasee-pi/issues/942 is closed and concerns unawaited vscode-jsonrpc notification promises in downstream code. It neither owns this LanguageClient state race nor provides a fixing commit here.
