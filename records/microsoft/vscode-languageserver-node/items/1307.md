# Issue #1307 — Catching unhandled exceptions when starting language server by LanguageClient

[https://github.com/microsoft/vscode-languageserver-node/issues/1307](https://github.com/microsoft/vscode-languageserver-node/issues/1307)

## Summary

Keep open: current main handles the detached stop rejection and preserves startup failures for callers, but does not associate server stderr with the initialization failure. The accepted request needs a decision on that remaining reporting contract, not another fix for the already-handled rejection.

## Change summary

Make server startup failures catchable and expose their stderr context for targeted extension telemetry without scraping the entire output channel.

## Best solution

Preserve the existing startup-promise and rejection-handling improvements, then settle whether client/ should expose initialization failures with associated stderr or explicitly support composing the existing stream hooks. Coordinate the reporting scope with https://github.com/microsoft/vscode-languageserver-node/issues/1185 and https://github.com/microsoft/vscode-languageserver-node/issues/1262; neither verified issue owns this report's entire scope.

- **Behavior:**

  > An extension should be able to handle a failed server startup and obtain the relevant stderr diagnostic without collecting unrelated output-channel messages. Current main already preserves startup rejection and catches the secondary stop rejection. Acceptance should cover both a server refusing initialization and one exiting during initialization, with no library-generated detached rejection. The remaining diagnostic-access contract must be agreed before implementation.
- **Trace:**

  > BaseLanguageClient.start() in client/src/common/client.ts retains and returns its local startup promise; doInitialize() routes non-retried failures through stopAfterFailedInitialize(), which handles stop() rejection. The Node client's shutdown override still owns process termination, so preserve subclass cleanup rather than bypassing stop(). LanguageClientOptions.stdioOptions.stderr in client/src/node/main.ts exposes the stream, but InitializationFailedHandler receives only the error and no library-managed stderr context. Existing middleware does not provide a dedicated startup-failure interception hook. client-node-tests/src/integration.test.ts already covers stream callbacks and refused initialization without unhandled rejection. Related reporting requests are https://github.com/microsoft/vscode-languageserver-node/issues/1185 and https://github.com/microsoft/vscode-languageserver-node/issues/1262; do not assume either owns the complete request.
- **Open decisions:**
  - Should initialization failures expose library-managed stderr context through the failure callback or a client API, or should the supported contract remain extension-managed capture and correlation through stdioOptions.stderr?
