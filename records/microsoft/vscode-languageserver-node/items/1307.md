# Issue #1307 — Catching unhandled exceptions when starting language server by LanguageClient

[https://github.com/microsoft/vscode-languageserver-node/issues/1307](https://github.com/microsoft/vscode-languageserver-node/issues/1307)

## Summary

Keep this accepted improvement open: current main exposes a dedicated stderr hook, but initialization failure still launches cleanup promises that can reject independently of the caller's start() promise. Neither the partial implementation nor the related issues covers the full request.

## Change summary

Allow extensions to handle language-server startup failures and capture relevant stderr without additional unhandled errors or scraping the entire output channel.

## Best solution

Make startup failure handling in client/ observable through caller-controlled error handling without leaking internal cleanup rejections. Use the existing stdioOptions.stderr hook for selective diagnostics, and decide whether any additional initialization-failure diagnostic contract is needed.

No tests were executed in this read-only checkout.
- **Behavior:**

  > An extension must be able to catch a failed language-server startup and record its own failure telemetry without an additional unhandled rejection from the client's internal cleanup. Failure handling must remain explicit rather than reporting successful startup. Relevant server stderr must be capturable independently of unrelated output-channel content. Acceptance checks should cover a server exiting during initialization, initializationFailedHandler returning false, and unchanged successful startup/shutdown behavior.
- **Trace:**

  > In client/src/common/client.ts, BaseLanguageClient.doInitialize catches initialize failures and invokes initializationFailedHandler, but its false branch launches stop() without observing the returned promise. shutdown rejects when the client is still Starting or otherwise non-running, creating an independent rejection outside the extension's await start(). The current concurrent-start failure test in client-node-tests/src/integration.test.ts explicitly stubs stop() to isolate this remaining behavior; crashOnInitializeServer.ts provides a server that exits during initialization. client/src/node/main.ts already offers stdioOptions.stderr, introduced by https://github.com/microsoft/vscode-languageserver-node/commit/2ffaa4db08c043603f257dd155cf6d204d117b3c, which addresses selective stream capture but not cleanup rejection handling. Preserve ordinary startup error propagation, intentional retry support, and successful lifecycle behavior; the Python process's underlying startup failure is outside this library's responsibility. Related https://github.com/microsoft/vscode-languageserver-node/issues/1185 covers diagnostic availability, not the whole request.
- **Open decisions:**
  - Does the existing stdioOptions.stderr hook complete the diagnostic API requirement, or should startup diagnostics also be exposed through initializationFailedHandler or a retained LanguageClient diagnostic surface?
