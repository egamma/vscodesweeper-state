# Issue #174 — Allow to register multiple handlers for shutdown

[https://github.com/microsoft/vscode-languageserver-node/issues/174](https://github.com/microsoft/vscode-languageserver-node/issues/174)

## Summary

Independent shutdown and notification subscriptions remain unsupported; the available emitter and diagnostics hooks cover only parts of the request. Keep this canonical backlog item open for a higher-level subscription design that preserves the maintainer's single-handler connection contract.

## Change summary

Allow independent components to observe shutdown and notifications without replacing previously registered handlers.

## Best solution

Define a higher-level server/client subscription contract that supports independent consumers while retaining one handler and one response per underlying request. Diagnostics consumers should use existing middleware or VS Code diagnostic events; the remaining design must address server cleanup and custom notifications, including completion semantics for shutdown.

## Plan brief

- **Likely files:** `server/src/common/server.ts`, `client/src/common/client.ts`, `jsonrpc/src/common/connection.ts`, `jsonrpc/src/common/events.ts`, `server/src/node/test/connection.test.ts`, `jsonrpc/src/node/test/connection.test.ts`
- **Validation:** After the subscription contract is agreed, use paired client/server connection tests to verify that two independent subscribers both receive the agreed lifecycle or custom-notification event, disposing one preserves the other, and shutdown still produces exactly one response at the agreed completion point. Preserve regression checks for existing single-handler replacement and method-specific versus wildcard notification dispatch.
- **Behavior:**

  > Independent components currently replace each other's shutdown or notification handlers, preventing proxy forwarding and worker cleanup from coexisting and preventing multiple providers from observing custom server updates. The desired higher-level contract should let independent consumers subscribe without disabling existing behavior, while retaining a single underlying request response. Acceptance checks must establish listener delivery, independent disposal and the point at which shutdown completes. Diagnostics-specific observation already has alternatives and is not sufficient evidence that the broader request is implemented.
- **Trace:**

  > server/src/common/server.ts stores one shutdownHandler and exitHandler and invokes those slots from the underlying ShutdownRequest and ExitNotification handlers. jsonrpc/src/common/connection.ts stores one notification handler per method; its wildcard handler runs only when no method-specific handler exists. BaseLanguageClient.onNotification in client/src/common/client.ts also replaces the handler by method. The public Emitter can support application-owned fan-out, but does not compose unknown pre-existing handlers or establish awaited shutdown completion. The maintainer's higher-level event direction is recorded at https://github.com/microsoft/vscode-languageserver-node/issues/174#issuecomment-545828652; preserve the low-level single-handler contract rather than assuming notification registration should change globally. The unresolved boundary is the higher-level subscription contract, not whether current handler replacement is accidental.
- **Open decisions:**
  - Should the supported higher-level subscription surface cover server lifecycle cleanup, arbitrary client/server notifications, or only selected semantic events?
  - For shutdown subscribers, must the shutdown response wait for asynchronous cleanup, and what externally visible result should occur if a subscriber fails?

## Evidence

- **Current server behavior:** server/src/common/server.ts:1504-1546 stores one shutdownHandler, initializeHandler and exitHandler, and each registration overwrites its slot. Lines 1705-1725 invoke only the stored shutdown or exit handler; shutdown is a request, whereas exit is a notification.
- **Current notification behavior:** jsonrpc/src/common/connection.ts:1321-1346 stores one handler per method using notificationHandlers.set. Its handleNotification implementation at lines 946-1001 invokes the method-specific handler or, alternatively, the wildcard handler; the wildcard is not an observer of already-handled notifications. client/src/common/client.ts:1084 onward similarly stores one notification handler per method.
- **Existing-capability check:** jsonrpc/src/common/api.ts publicly exports Emitter, and jsonrpc/src/common/events.ts supports multiple listeners, but applications must own and connect the dispatcher themselves. LanguageClientOptions.middleware and Middleware in client/src/common/client.ts:309-400 expose handleDiagnostics and feature-specific interception, not independent server shutdown or arbitrary incoming-notification subscriptions. These surfaces do not recover or compose handlers registered by another library.
- **Maintainer-supported boundary:** https://github.com/microsoft/vscode-languageserver-node/issues/174#issuecomment-545828652 explicitly preserves one handler on the connection while allowing higher-level server/client events and inviting a client-side PR. This accepted direction prevents treating the entire request as a usage question or declining it solely from the low-level design.
- **Latest guidance is narrower than the issue:** https://github.com/microsoft/vscode-languageserver-node/issues/174#issuecomment-2210327633 reiterates that shared notification handlers are unsupported and recommends languages.onDidChangeDiagnostics, including for pull diagnostics.
