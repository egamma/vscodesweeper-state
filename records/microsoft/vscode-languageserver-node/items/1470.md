# Issue #1470 — Option to control `workspaceFolders` in `InitializeParams`

[https://github.com/microsoft/vscode-languageserver-node/issues/1470](https://github.com/microsoft/vscode-languageserver-node/issues/1470)

## Summary

Keep open for the client-options hook the maintainer endorsed. Current main still populates initialization workspace folders without consulting workspace middleware; existing feature registration offers a workaround, but does not provide the accepted options-level API.

## Change summary

Allow extensions to filter workspaceFolders in InitializeParams, including excluding virtual folders unsupported by their language server.

## Best solution

Provide a supported initialization customization hook in client/ while preserving the current default workspace-folder behavior. Decide whether its public contract is folder-specific or covers the complete InitializeParams; the downstream gopls issue addresses server tolerance, not this extension point.

## Plan brief

- **Likely files:** `client/src/common/client.ts`, `client/src/common/workspaceFolder.ts`, `client-node-tests/src/workspaceFolder.test.ts`, `client-node-tests/src/integration.test.ts`
- **Validation:** Add client tests with file:/// and memfs:/// workspace folders that capture the initialize request and assert the configured filter preserves file folders and excludes virtual folders. Verify unchanged initialization without the hook, empty-folder handling, restart behavior, and unchanged existing workspace-folder request/change middleware.
- **Behavior:**

  > An extension should be able to exclude unsupported workspace folders from the initialize request through a supported client-options extension point, without subclassing the client. With a mixed file and virtual workspace, the server should receive only folders selected by the extension. Clients that do not configure the hook must retain existing behavior. Initialization customization must not silently alter the contracts of subsequent workspace-folder requests or notifications.
- **Trace:**

  > WorkspaceFoldersFeature.fillInitializeParams in client/src/common/workspaceFolder.ts maps VS Code's complete workspace-folder list without invoking workspace middleware. BaseLanguageClient.initialize and fillInitializeParams in client/src/common/client.ts construct the request and invoke registered feature callbacks before sending it; the direct connection.initialize path bypasses general request middleware. StaticFeature.fillInitializeParams already permits a feature-registration workaround, but LanguageClientOptions has no equivalent callback. The maintainer endorsed an options hook at https://github.com/microsoft/vscode-languageserver-node/issues/1470#issuecomment-2095565176. Preserve default initialization, single-folder clients, message ordering, and existing workspace-folder middleware behavior. The remaining uncertainty is the public scope of the new hook, not whether virtual folders are valid protocol input.
- **Open decisions:**
  - Should the supported hook customize only the initial workspace-folder list, or expose the complete InitializeParams for extension customization?
