[https://github.com/microsoft/monaco-editor/issues/3906](https://github.com/microsoft/monaco-editor/issues/3906)

## Summary

Keep open: current upstream source still leaves colorized HTML with theme-dependent token classes when setTheme replaces their color mapping. The supplied theme-switch steps are sufficient; neither related theme-isolation request owns this incorrect-highlighting symptom.

## Change summary

Changing the runtime theme gives previously colorized string tokens incorrect colors.

## Best solution

Address stale token-color mappings for colorizeElement output in the microsoft/vscode standalone editor core, then carry the fix into Monaco. Preserve the shared-theme contract; independently themed elements are a separate request.

## Evidence

- **Reported trigger:** https://github.com/microsoft/monaco-editor/issues/3906 supplies a v0.37.1 playground example: colorizeElement followed by setTheme('vs-dark') makes string tokens red rather than their intended theme color. The March 2024 comment independently reports needing to recolorize after every theme switch.
- **Current colorizer path:** Read https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/colorizer.ts through the GitHub API. Colorizer.colorizeElement writes the result of colorize into innerHTML once; _actualColorize renders encoded tokens, and no theme-change subscription regenerates that HTML.
- **Stale numeric color identifiers:** Read https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/encodedTokenAttributes.ts: TokenMetadata.getClassNameFromMetadata emits mtk plus the encoded foreground index. In https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneThemeService.ts, setTheme invokes _updateThemeOrColorMap, which replaces token CSS using the new theme's color map. https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/languages/supports/tokenization.ts generates .mtkN rules from that map. Previously rendered spans retain the old indices without retokenization, allowing their semantic colors to change incorrectly.
- **Related requests are not canonicals:** Verified https://github.com/microsoft/monaco-editor/issues/3302 is open, but requests simultaneous independent themes and inline styles, not correct highlighting after a global theme switch. https://github.com/microsoft/monaco-editor/issues/1068 is closed and concerns independent element themes; its scope decision does not resolve this bug.
- **Repository boundary:** The checkout's website/src/website/data/playground-samples/creating-the-editor/syntax-highlighting-for-html-elements/sample.js uses colorizeElement, but its implementation lives in the VS Code standalone core. Precise colorizeElement searches in both repositories found no verified open canonical for this theme-switch symptom. Source inspection establishes stale mappings, not a browser-rendered confirmation of the exact red hue.
