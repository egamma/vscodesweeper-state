# Issue #291 — go to definition - different model: loading via http

[https://github.com/microsoft/monaco-editor/issues/291](https://github.com/microsoft/monaco-editor/issues/291)

## Summary

Keep open: registerEditorOpener supports custom navigation, but does not provide on-demand model resolution for definition previews. The 2025 discussion identifies this remaining gap, and current upstream source still requires an existing model.

## Change summary

Support loading remote definition targets on demand and displaying them within the editor without overriding private services.

## Best solution

Provide a supported model-resolution integration in the VS Code standalone editor core that lets embedders supply content asynchronously for definition navigation and previews. Preserve registerEditorOpener for application-specific navigation; creating models inside definition providers remains a workaround rather than a general resolver.

- **Fit:** aligned
- **Reason:** A supported integration for remotely supplied language-service targets fits Monaco's browser-library API boundary.
- **Evidence:** The vision identifies API-based embedder integration and interoperability with the language-server world as durable themes.

## Evidence

- **Remaining user problem:** https://github.com/microsoft/monaco-editor/issues/291#issuecomment-3335652853 describes thousands of lazily fetched files: registerEditorOpener handles navigation, but cmd-hover fails before the target model exists. The edit identifies creating models inside the definition provider as a workaround.
- **Existing navigation API:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneEditor.ts exposes ICodeEditorOpener.openCodeEditor and registerEditorOpener, including asynchronous handlers and target selections. This covers custom opening, not content resolution for previews.
- **Current resolver boundary:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneServices.ts registers InMemoryTextModelService as ITextModelService. https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/services/inMemoryTextModelService.ts resolves existing models through getModel, throws 'Model not found' when absent, and implements registerTextModelContentProvider as Disposable.None.
- **TypeScript workaround is limited:** src/languages/features/typescript/languageFeatures.ts:94-160 and 758-805 show DefinitionAdapter preparing models before returning locations. LibFiles.getOrCreateModel handles existing models, bundled TypeScript libraries, and registered extraLibs; it does not fetch arbitrary remote source URIs.
- **Referenced improvement is partial:** https://github.com/microsoft/vscode/pull/85129 is merged, but its described change resolves already-created models beyond the attached editor model. It does not implement asynchronous remote content loading.
- **Canonical search:** Open-issue searches covering definition fetching, model loading, lazy models, resolvers, and content providers found no verified canonical owning this request. https://github.com/microsoft/monaco-editor/issues/1647 is closed; the open https://github.com/microsoft/monaco-editor/issues/2813 concerns IntelliSense breaking after extraLib model creation, a different behavior.
