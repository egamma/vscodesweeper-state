## Summary

The linked discussion identifies Chromium's device-scale-factor handling as the cause, and Monaco's current editor source includes compensation for affected Chrome versions. Keep open under the upstream rule: these changes are strong resolution leads, but current macOS scrolling was not observed.

## Change summary

Default scrolling on macOS in Chromium became excessively fast compared with native scrolling and other websites.

## Evidence

- **Upstream root cause:** https://github.com/microsoft/vscode/issues/146403#issuecomment-1854538928 traces excessive wheel deltas to Chromium's device-scale-factor changes beginning in Chromium 98. This matches the reporter's macOS/Chromium version boundary and scrolling-speed symptom.
- **Editor-side compensation:** https://github.com/microsoft/vscode/commit/4f338c87ab68833847df18ddcb8a5f5d7ee667fc changes StandardWheelEvent in src/vs/base/browser/mouseEvent.ts to divide Chrome wheelDeltaY, wheelDeltaX, and fallback wheelDelta by 120 * devicePixelRatio instead of 120. This directly compensates for inflated scrolling deltas; the linked fixing PR is https://github.com/microsoft/vscode/pull/200776.
- **Current adoption:** The checkout's package.json pins vscodeRef c132f72ae9f5ff80093e7d722c36f03755865b20. At that revision, https://github.com/microsoft/vscode/blob/c132f72ae9f5ff80093e7d722c36f03755865b20/src/vs/base/browser/mouseEvent.ts retains compensation for Chrome <=122 and documents the browser fix in Chrome 123. src/vs/base/browser/ui/scrollbar/scrollableElement.ts constructs StandardWheelEvent in its wheel listener and consumes its normalized deltas in _onMouseWheel.
- **Historical improvement, not current reproduction:** The Monaco reporter confirmed slower scrolling in the proposed VS Code build at https://github.com/microsoft/vscode/issues/146403#issuecomment-1854712813. This is historical evidence of improvement, not a current Monaco/macOS reproduction attempt.
- **Canonical search:** https://github.com/microsoft/vscode/issues/146403 is closed, so it cannot serve as a duplicate canonical. The verified open follow-up https://github.com/microsoft/vscode/issues/202324 concerns remaining acceleration and precision differences after the speed correction, rather than independently establishing that the original excessive-speed regression persists.
