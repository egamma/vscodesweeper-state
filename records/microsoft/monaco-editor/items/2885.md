# Issue #2885 — [Feature Request] Get notified when a language features are ready

[https://github.com/microsoft/monaco-editor/issues/2885](https://github.com/microsoft/monaco-editor/issues/2885)

## Summary

The request for a supported readiness signal remains actionable: language activation events do not guarantee tokenizer readiness, and the current grammar tests still yield through a timeout. Route to tokenization and editor-api; the related newer report does not qualify as a canonical for this re-reviewed issue.

## Change summary

Expose a supported way to await language-feature readiness before calling editor.tokenize without timing-based workarounds.

## Best solution

Define a public tokenizer-readiness contract in the VS Code standalone editor API that Monaco inherits. Preserve synchronous editor.tokenize while allowing callers to await its prerequisites; distinguish tokenizer readiness from readiness of unrelated language features.

## Evidence

- **Current local test workaround:** src/languages/definitions/test/testRunner.ts awaits loadLanguage for each language, then awaits timeout(0) before calling editor.tokenize. src/languages/definitions/_.contribution.ts implements loadLanguage through the lazy loader and temporary model creation; this helper is not a general public language-feature readiness contract.
- **Existing API boundary:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneLanguages.ts implements onLanguage and onLanguageEncountered as activation-request callbacks, not completion notifications. https://github.com/microsoft/vscode/blob/main/src/vs/monaco.d.ts declares editor.tokenize as synchronous and exposes neither TokenizationRegistry nor a tokenizer-readiness promise.
- **Partial alternative is not full coverage:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneEditor.ts starts TokenizationRegistry.getOrCreate without awaiting it in tokenize, then falls back to null tokenization when support is unavailable. https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/colorizer.ts awaits tokenizer creation for editor.colorize, but that API returns HTML rather than tokens and does not provide general language-feature readiness.
- **Related report, not an eligible canonical:** https://github.com/microsoft/monaco-editor/issues/3448 is open and describes tokenize returning incomplete tokens until initialization finishes. At https://github.com/microsoft/monaco-editor/issues/3448#issuecomment-1350920690 a maintainer clarifies that TokenizationRegistry is exposed only through vs/editor/common/languages. That issue is newer, has no milestone and no reactions, so it does not meet the stronger canonical-ownership bar for closing this re-reviewed item.
- **Ownership:** src/editor.ts re-exports monaco-editor-core/esm/vs/editor/editor.api. The public readiness contract and synchronous tokenize implementation belong to the VS Code standalone editor core, rather than a Monaco-only language-loader patch.
