# Issue #527 — feature-request: Support Matching Tag Editing for HTML/XML

[https://github.com/microsoft/monaco-editor/issues/527](https://github.com/microsoft/monaco-editor/issues/527)

## Summary

Keep open: linked editing exists in the editor core, but Monaco's bundled HTML integration still does not supply linked-editing ranges. Explicit rename support does not cover automatic synchronization while typing, and no qualifying duplicate was found.

## Change summary

Synchronize matching HTML/XML opening and closing tag names when either name is edited.

## Best solution

Complete the bundled HTML language-service integration with the existing linked-editing capability rather than changing the editor core. Settle the XML support boundary separately, since XML is not registered by the bundled HTML service.

## Plan brief

- **Likely files:** `src/languages/features/html/htmlMode.ts`, `src/languages/features/html/htmlWorker.ts`, `src/languages/features/html/register.ts`, `src/languages/features/common/lspLanguageFeatures.ts`
- **Validation:** In the playground with linked editing enabled, change div to span from both the opening and closing tag in <div><p>Content</p></div>; verify the counterpart updates without changing the nested p tags or content. Verify disabled linked editing and explicit rename retain their existing behavior.
- **Behavior:**

  > Editing either name in a matching tag pair should update the counterpart during typing, without invoking explicit rename. For <div><p>Content</p></div>, changing either div name to span should produce <span><p>Content</p></span> while preserving nested tags and content. Acceptance should cover editing from both ends, disabled linked editing, and existing explicit rename behavior. The original request also includes XML, whose supported scope needs agreement.
- **Trace:**

  > src/features/linkedEditing/register.js already loads the VS Code contribution, whose activation requires both an enabled option and a registered provider. Monaco's src/languages/features/html/htmlMode.ts supplies explicit rename through RenameAdapter, while htmlWorker.ts exposes doRename but no linked-editing ranges. The upstream HTML language service exposes findLinkedEditingRanges, but this worker does not adopt it. src/languages/features/html/register.ts controls provider configuration and registers HTML, Handlebars, and Razor, not XML. The gap is in Monaco's language integration, not the editor-core synchronization engine; preserve existing rename, completion, and highlighting behavior. The maintainer adoption direction is recorded at https://github.com/microsoft/monaco-editor/issues/527#issuecomment-328441134. Runtime behavior was not executed in this read-only review.
- **Open decisions:**
  - Should this issue deliver bundled HTML support first, or must completion include XML support with an explicitly supported XML language-service contract?
  - Should the bundled linked-editing provider be available by default while remaining controlled by the editor's linkedEditing option, and should embedders receive a separate modeConfiguration switch?
