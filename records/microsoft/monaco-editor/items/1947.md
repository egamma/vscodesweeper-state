# Issue #1947 — Allow Submenus in Context Menu

[https://github.com/microsoft/monaco-editor/issues/1947](https://github.com/microsoft/monaco-editor/issues/1947)

## Summary

A real public-API gap remains: Monaco renders submenus internally, but the current `addAction` descriptor can register only flat context-menu commands. The issue is already correctly classified and remains the focused canonical request.

## Change summary

Allow embedders to register nested context-menu actions through a supported public API.

## Best solution

Extend the standalone editor API in `src/vs/editor/standalone/browser/standaloneCodeEditor.ts` within microsoft/vscode with a supported submenu descriptor and disposable child registrations, then expose it through the next Monaco source cut. This needs API design review but is reasonable open-for-PR material.

## Evidence

- **public API gap:** Current vscode main defines `IActionDescriptor` in https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneCodeEditor.ts with flat `contextMenuGroupId` and `contextMenuOrder` fields but no submenu or child-action field; `addAction` consequently registers a single `IMenuItem`.
- **internal capability:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/contrib/contextmenu/browser/contextmenu.ts already converts internal `SubmenuItemAction` entries into rendered `SubmenuAction` objects, showing that rendering exists while supported standalone registration does not.
- **unsupported workarounds:** The issue discussion's working examples import internal `MenuRegistry`, `MenuId`, or `SubmenuAction` modules and access private contribution services; later commenters explicitly confirm they still cannot place a submenu in the default editor context menu through public API.
- **canonical search:** https://github.com/microsoft/monaco-editor/issues/4588 is a newer, adjacent request for moving and deleting existing menu entries, but it does not subsume this focused request to add nested custom actions.
