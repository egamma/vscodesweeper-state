# Issue #3955 — [Feature Request] Why not provide  `getDocumentSymbols` api ?

[https://github.com/microsoft/monaco-editor/issues/3955](https://github.com/microsoft/monaco-editor/issues/3955)

## Summary

A supported, language-independent document-symbol retrieval API remains a distinct request. Existing provider registration and private outline access do not cover it, and the related open navigation issue is not a matching canonical.

## Change summary

Expose a public API for retrieving a model's document symbols.

## Best solution

Consider a supported model-level symbol retrieval API in the VS Code-derived standalone editor API. It should consume registered document-symbol providers without requiring embedders to import private outline services.

## Vision fit

- **Fit:** aligned
- **Reason:** A supported symbol retrieval API fits Monaco's API-based integration boundary and enables external outlines without introducing an application platform.
- **Evidence:** The vision's library guardrail identifies API surface and language-worker integration as the aligned form of embedder capabilities.

## Evidence

- **Existing-capability check:** The published declarations at https://github.com/microsoft/monaco-editor/blob/gh-pages/node_modules/monaco-editor/monaco.d.ts expose registerDocumentSymbolProvider and DocumentSymbolProvider.provideDocumentSymbols, but no getDocumentSymbols or public provider-execution API. Registering a provider does not retrieve symbols from all providers registered for a model.
- **Private workaround:** https://github.com/microsoft/monaco-editor/issues/2959#issuecomment-1095212411 retrieves symbols through StandaloneServices, ILanguageFeaturesService and OutlineModel.asListOfDocumentSymbols. README.md explicitly says only monaco.d.ts specifies the versioned API; other internals may break with any release. That closed issue therefore demonstrates a workaround, not delivery of the requested public contract.
- **Related request is closed:** https://github.com/microsoft/monaco-editor/issues/2314 requested the same model-level retrieval capability but is closed. Its only comment, https://github.com/microsoft/monaco-editor/issues/2314#issuecomment-766298933, suggests issuing an LSP textDocument/documentSymbol request, which requires a language-client integration and does not expose Monaco's registered providers generally.
- **Canonical search:** Open-issue searches for symbols, document symbols and getDocumentSymbols found https://github.com/microsoft/monaco-editor/issues/778 as the relevant older open report. It requests direct navigation to a named symbol instead of opening quick outline, not retrieving a document-symbol list; it does not meet the same-observable-request bar for this re-reviewed item.
- **Ownership and demand:** README.md identifies the editor as generated from VS Code sources. The requested standalone editor API belongs in that upstream surface rather than Monaco's language-specific workers. The issue has three upvotes and a commenter independently requesting the same capability.
