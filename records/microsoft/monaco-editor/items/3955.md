# Issue #3955 — [Feature Request] Why not provide  `getDocumentSymbols` api ?

[https://github.com/microsoft/monaco-editor/issues/3955](https://github.com/microsoft/monaco-editor/issues/3955)

## Summary

This remains a valid, correctly routed API gap: Monaco exposes document-symbol provider registration but no supported public API for consumers to retrieve the resulting symbols.

## Change summary

Expose a public API that returns document symbols for a model.

## Best solution

Add a supported asynchronous retrieval API to the vscode standalone editor API so it flows into Monaco, invoking the matching DocumentSymbolProvider instances without requiring consumers to import internal services or commands.

## Vision fit

- **Fit:** aligned
- **Reason:** A supported symbol-query API strengthens Monaco's intended embedder-facing API surface without adding app-level functionality.
- **Evidence:** The vision describes Monaco as a browser library whose embedders integrate through its API and language workers.

## Evidence

- **current public API:** The shipped v0.56.0 declaration at https://unpkg.com/monaco-editor@0.56.0/monaco.d.ts exposes languages.registerDocumentSymbolProvider and DocumentSymbolProvider.provideDocumentSymbols, but no getDocumentSymbols or executeDocumentSymbolProvider API for consumers.
- **internal capability:** Current vscode editor-core source implements the internal `_executeDocumentSymbolProvider` command in https://github.com/microsoft/vscode/blob/0235590c8a6c9372396ce48901ca19723d1d9507/src/vs/editor/contrib/documentSymbols/browser/documentSymbols.ts, showing that retrieval exists internally but is not a supported Monaco API.
- **canonical search:** https://github.com/microsoft/monaco-editor/issues/2314 requested the same public capability but was closed by its reporter after receiving a direct language-server workaround; https://github.com/microsoft/monaco-editor/issues/778 remains open but asks for the narrower operation of navigating to a symbol.
