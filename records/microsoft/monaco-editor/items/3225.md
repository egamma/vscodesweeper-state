# Issue #3225 — [Bug] Using incorrect lib in setCompilerOptions causes unexpected autocomplete failures

[https://github.com/microsoft/monaco-editor/issues/3225](https://github.com/microsoft/monaco-editor/issues/3225)

## Summary

The issue remains correctly classified as upstream: Monaco passes `CompilerOptions.lib` to TypeScript, whose programmatic API does not normalize or diagnose the uppercase value. No open canonical TypeScript issue was found, so this should remain open as the downstream tracking issue.

## Change summary

Invalidly cased `CompilerOptions.lib` values silently remove standard-library types and cause misleading completion failures.

## Best solution

TypeScript should validate or normalize `lib` values supplied through its programmatic compiler API; Monaco can then consume that behavior through its bundled TypeScript worker. Stronger typing in Monaco would not fully protect JavaScript callers or dynamically constructed options.

## Evidence

- **maintainer diagnosis:** A Monaco maintainer traced the failure to TypeScript receiving `ESNext` in `pathForLibFile`, where lookup failed, and identified it as a TypeScript bug: https://github.com/microsoft/monaco-editor/issues/3225#issuecomment-1204135488
- **current API surface:** Current main still declares `lib?: string[]` in `src/languages/features/typescript/register.ts` and passes the resulting options directly to the TypeScript language service through `src/languages/features/typescript/tsWorker.ts`.
- **current upstream behavior:** TypeScript's current `src/compiler/commandLineParser.ts` validates textual configuration through a lowercase-keyed `libMap`, while direct `CompilerOptions` values reach program creation without that configuration-parser normalization.
- **workaround:** The issue's playground reproduction works when `ESNext` is changed to lowercase `esnext`, confirming that casing rather than the union type itself triggers the missing-library and completion behavior.
