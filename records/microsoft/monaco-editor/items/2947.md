# Issue #2947 — [Bug] Multiple editor instances only latest created instance is working properly

[https://github.com/microsoft/monaco-editor/issues/2947](https://github.com/microsoft/monaco-editor/issues/2947)

## Summary

Keep open: current VS Code standalone source still lets the last registered addCommand keybinding run in another editor. This issue is already the maintainer-selected canonical; addAction provides a workaround, not a fix to addCommand.

## Change summary

Commands registered on an editor instance should execute for that instance rather than the last editor registering the same keybinding.

## Best solution

Restore instance-scoped command dispatch in the VS Code standalone editor core, preserving explicitly global command APIs, then deliver it through a Monaco release. Retain this issue as the canonical report and document addAction as the interim workaround.

## Evidence

- **Current command registration:** In https://github.com/microsoft/vscode/blob/eed41ffe7badc68947f39cd80e8e876e635d9f54/src/vs/editor/standalone/browser/standaloneCodeEditor.ts, StandaloneCodeEditor.addCommand creates a unique command ID but passes only the caller-supplied context to addDynamicKeybinding. With the report's omitted context, neither registration is restricted to its owning editor.
- **Source-traced trigger:** https://github.com/microsoft/vscode/blob/eed41ffe7badc68947f39cd80e8e876e635d9f54/src/vs/editor/standalone/browser/standaloneServices.ts registers StandaloneKeybindingService as a singleton at line 1147, attaches it to all editor containers, and appends dynamic bindings to one list. In https://github.com/microsoft/vscode/blob/eed41ffe7badc68947f39cd80e8e876e635d9f54/src/vs/platform/keybinding/common/keybindingResolver.ts, _findCommand scans matching bindings backwards and accepts an absent when clause. Consequently, the second Ctrl/Cmd+Shift+F registration wins even when the first editor has focus.
- **Existing workaround is partial coverage:** StandaloneCodeEditor.addAction in the same pinned upstream source adds an editorId equality precondition and an editor-specific command ID. Reporters confirm this workaround at https://github.com/microsoft/monaco-editor/issues/2947#issuecomment-1639608153 and https://github.com/microsoft/monaco-editor/issues/2947#issuecomment-1942542927; it does not change addCommand's behavior.
- **Canonical ownership:** A maintainer closed https://github.com/microsoft/monaco-editor/issues/3345 as a duplicate of this issue at https://github.com/microsoft/monaco-editor/issues/3345#issuecomment-1466340896, and similarly closed https://github.com/microsoft/monaco-editor/issues/3084. Focused open-issue searches found no verified replacement canonical. The younger https://github.com/microsoft/monaco-editor/issues/3378 concerns suggestion settings, not the same observable command-dispatch failure.
- **Regression and impact:** Independent confirmation identifies the change between v0.31.1 and v0.32.0 at https://github.com/microsoft/monaco-editor/issues/2947#issuecomment-1036345510. The wrong-editor save consequence is described at https://github.com/microsoft/monaco-editor/issues/2947#issuecomment-1326893106, and persistence through v0.51.0-dev-20240807 is reported at https://github.com/microsoft/monaco-editor/issues/2947#issuecomment-2340184668.
