# Issue #2098 — addExtraLib() method is adding the library to all editor available in a page

[https://github.com/microsoft/monaco-editor/issues/2098](https://github.com/microsoft/monaco-editor/issues/2098)

## Summary

Keep open: the bundled TypeScript/JavaScript language service still shares extra libraries across editors of the same language. Existing customization APIs do not directly provide the requested isolation, and the thread shows sustained demand.

## Change summary

Support independent extra-library environments for multiple editors on the same page without changing other editors' IntelliSense or diagnostics.

## Best solution

Design a supported isolation contract in Monaco's TypeScript language integration while preserving existing global defaults. Resolve whether library environments belong to editor views, models, or explicitly grouped projects before implementing the API.

## Plan brief

- **Likely files:** `src/languages/features/typescript/register.ts`, `src/languages/features/typescript/workerManager.ts`, `src/languages/features/typescript/tsMode.ts`, `src/languages/features/typescript/tsWorker.ts`, `src/languages/features/typescript/languageFeatures.ts`
- **Validation:** Use a two-editor browser sample with the same language and conflicting ambient declarations assigned to independent environments. Verify environment-specific completions and diagnostics simultaneously, stability across focus changes, and that updating or disposing one environment does not affect the other; also check unchanged legacy global-default behavior.
- **Behavior:**

  > Two editors on the same page need different extra-library environments simultaneously. Each must receive completions and diagnostics from its own declarations without declarations leaking from the other environment. Focusing an editor, updating its libraries, or disposing its environment must not change the other editor's results. Existing applications using global language defaults must retain their current behavior.
- **Trace:**

  > LanguageServiceDefaultsImpl in src/languages/features/typescript/register.ts owns a shared extra-library map, exposed through singleton TypeScript and JavaScript defaults. setupMode in tsMode.ts gives the language providers one WorkerManager, whose workerManager.ts creation and update paths forward that shared map. TypeScriptWorker in tsWorker.ts constructs one language service and includes all extra libraries in getScriptFileNames. customWorkerPath permits subclassing but does not establish separate environments in the built-in providers. This is Monaco-owned language integration, not a vscode editor-core change. The focus-switching workaround in https://github.com/microsoft/monaco-editor/issues/2098 fails to preserve simultaneous diagnostics; https://github.com/microsoft/monaco-editor/issues/2976 supplies related global-leakage evidence but is not a duplicate canonical. The unresolved boundary is the public ownership and inheritance contract for isolated environments; preserve legacy global defaults.
- **Open decisions:**
  - Should an isolated library environment attach to an editor view, a model, or an explicit project containing multiple models, and what should happen when two views share a model?
  - Should isolated environments inherit globally registered extra libraries or replace them, and which declaration takes precedence when paths overlap?

## Evidence

- **Existing API remains global:** src/languages/features/typescript/register.ts exports singleton typescriptDefaults and javascriptDefaults. LanguageServiceDefaults.addExtraLib(content, filePath) and setExtraLibs(libs) mutate their shared _extraLibs map; neither accepts an editor, model, or environment identifier.
- **Shared language-service path:** src/languages/features/typescript/tsMode.ts setupMode creates one WorkerManager for each language's defaults and shares its worker accessor among the registered providers. workerManager.ts initializes and updates that worker using defaults.getExtraLibs(); tsWorker.ts getScriptFileNames combines mirrored models with the complete extra-library map.
- **Customization is not built-in isolation:** https://github.com/microsoft/monaco-typescript/pull/65 is merged and introduces customWorkerPath for subclassing the TypeScript worker. Current register.ts, workerManager.ts, and tsWorker.ts still configure that customization through shared language defaults; implementing separate environments inside a custom worker is additional application work, not an existing per-editor addExtraLib capability.
- **Workaround loses simultaneous correctness:** The discussion at https://github.com/microsoft/monaco-editor/issues/2098 reports that switching setExtraLibs on focus makes diagnostics in other editors incorrect. Other commenters report using a fork or showing only one editor, and the issue has 13 upvotes.
- **Related isolation report is not a canonical:** https://github.com/microsoft/monaco-editor/issues/2976 is open but newer, has six upvotes and no milestone, and primarily reports duplicate-variable diagnostics across models. Its moduleDetection workaround does not isolate ambient globals, as https://github.com/microsoft/monaco-editor/issues/2976#issuecomment-2345435531 explains. It does not meet the stronger duplicate bar for this re-reviewed extra-library request.
- **Supplied candidates concern different work:** https://github.com/microsoft/monaco-editor/issues/3465 concerns consecutive setExtraLibs calls retaining an old interface definition; https://github.com/microsoft/monaco-editor/issues/264 requests JSX support. Neither owns independent library environments. Searches for extra libraries, per-editor configuration, and isolation found no verified canonical for this request or open PR referencing it.
