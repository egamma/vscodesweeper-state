- **Trace:**

  > src/languages/definitions/python/register.ts loads the Monaco-owned python.ts grammar. Its tokenizer.root uses one context-free @keywords lookup, combining import keywords and builtin names such as sum while assigning other names identifier tokens. python.test.ts exercises tokenization through definitions/test/testRunner.ts and editor.tokenize. The f-string-only diff at https://github.com/microsoft/monaco-editor/commit/a845ff6b278c76183a9cf969260fc3e1396b2b0b leaves this path unchanged. Custom tokenizer/theme APIs provide an embedder workaround, not shipped coverage. The uncertainty is the intended token and theme contract; do not broaden this into TextMate integration or global theme changes without a maintainer decision.
- **Open decisions:**
  - Which distinctions should the shipped Python import example expose among import keywords, module names, builtin names, and imported identifiers, and must those distinctions be visible in the existing default themes without embedder customization?

## Evidence

- **Remaining import behavior:** In src/languages/definitions/python/python.ts, tokenizer.root classifies every identifier through the same @keywords lookup, with no import-specific state. For the supplied `from functions import sum, average`, `from`, `import`, and `sum` receive keyword.python, while `functions` and `average` receive identifier.python; builtin names and import keywords are not distinguished.
- **Partial implementation:** Current python.ts includes async/await and f-string states.
