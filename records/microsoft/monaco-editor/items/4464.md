# Issue #4464 — [Feature Request] Support for package.json conditional exports map, for extra libs typings acquisition

[https://github.com/microsoft/monaco-editor/issues/4464](https://github.com/microsoft/monaco-editor/issues/4464)

## Summary

A real API gap remains: Monaco bundles TypeScript 5.9 with modern package-exports resolution, but its public compiler-option enums still expose only legacy module modes. Route this to the TypeScript multifile area for end-to-end conditional-exports support.

## Change summary

Allow TypeScript extra libraries to resolve package subpaths through package.json conditional exports.

## Best solution

Update the copied TypeScript enums in src/languages/features/typescript/register.ts and ensure the worker host resolves extra-lib package.json exports under Node16, NodeNext, and Bundler modes. The reported DataCloneError should also be covered by sanitizing any non-cloneable TypeScript completion data returned across the worker boundary.

## Evidence

- **public API gap:** src/languages/features/typescript/register.ts exposes ModuleResolutionKind with only Classic and NodeJs, while its CompilerOptions.moduleResolution property uses that restricted enum.
- **bundled capability:** package.json currently depends on TypeScript ^5.9.3, and src/languages/features/typescript/lib/typescriptServices.d.ts includes Node16, NodeNext, and Bundler resolution kinds plus resolvePackageJsonExports.
- **worker transport:** src/languages/features/typescript/tsWorker.ts returns TypeScript completion objects directly from getCompletionsAtPosition and getCompletionEntryDetails; the reporter observed a DataCloneError when conditional-export metadata included a function.
