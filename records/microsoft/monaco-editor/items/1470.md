# Issue #1470 — Feature request: support JSONSchema with YAML

[https://github.com/microsoft/monaco-editor/issues/1470](https://github.com/microsoft/monaco-editor/issues/1470)

## Summary

Official JSON Schema validation for YAML remains missing on current main. Keep this accepted Backlog request open: syntax highlighting and third-party integrations do not cover the requested built-in capability.

## Change summary

Provide official JSON Schema validation for YAML documents, including schema associations and references.

## Best solution

Plan an officially supported YAML schema-validation experience in Monaco's language-service integration, with explicit configuration and modern worker-loading guidance. Decide the public configuration contract before implementation; preserve existing JSON validation and lightweight YAML highlighting.

## Plan brief

- **Likely files:** `src/languages/definitions/yaml/register.ts`, `src/languages/features/json/register.ts`, `src/languages/features/json/jsonWorker.ts`, `src/languages/features/common/lspLanguageFeatures.ts`, `package.json`
- **Validation:** In the playground, configure the two schemas from the issue using the agreed YAML API and create its YAML model. Verify diagnostics for p1: "v3" and p2: false, then verify they clear for p1: "v1" and p2 containing q1: "x1". Verify referenced-schema resolution, model edits, and unchanged behavior in the original JSON schema demo.
- **Behavior:**

  > YAML documents should receive JSON Schema validation through an officially supported Monaco integration. The issue's sample should report an enum violation for p1 and an object-type violation for p2, including resolution of the referenced second schema. Correcting those values should clear the diagnostics. Existing JSON validation and YAML highlighting must remain unchanged.
- **Trace:**

  > src/languages/definitions/yaml/register.ts registers only basic YAML language support. src/languages/features/json/register.ts binds jsonDefaults and mode activation to 'json', while DiagnosticsAdapter in src/languages/features/common/lspLanguageFeatures.ts filters models by that language identifier. JSONWorker.doValidation in src/languages/features/json/jsonWorker.ts parses JSON through vscode-json-languageservice, so changing fileMatch cannot make it validate YAML. This is a Monaco language-service integration gap, not a defect in the generated editor core. The existing third-party integration is https://github.com/remcohaszing/monaco-yaml; current LSP infrastructure offers another integration mechanism but does not settle the official configuration or delivery contract. Preserve existing JSON semantics and avoid expanding the scope to unrelated YAML highlighting defects.
- **Open decisions:**
  - Should YAML schema associations share the existing JSON defaults API, or have a separate officially supported configuration API?
  - Should official YAML validation be delivered as an optional bundled language worker or as a documented LSP integration requiring a separately supplied YAML language server?

## Evidence

- **Existing capability boundary:** src/languages/definitions/yaml/register.ts registers YAML extensions, aliases, MIME types, and a tokenizer loader, but no schema-validation service. src/languages/features/json/register.ts constructs jsonDefaults with languageId 'json' and initializes its mode only through languages.onLanguage('json').
- **Validation path:** src/languages/features/common/lspLanguageFeatures.ts DiagnosticsAdapter ignores models whose languageId differs from its configured language. src/languages/features/json/jsonWorker.ts JSONWorker.doValidation calls vscode-json-languageservice.parseJSONDocument; associating a schema with a YAML URI does not provide YAML parsing or attach JSON diagnostics to YAML models.
