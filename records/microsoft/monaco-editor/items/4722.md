# Issue #4722 — [Feature Request]Support replace the decoration with customized dom element

[https://github.com/microsoft/monaco-editor/issues/4722](https://github.com/microsoft/monaco-editor/issues/4722)

## Summary

A real API gap remains: decorations can inject styled text, and content widgets can render DOM near a position, but neither replaces a model range with arbitrary DOM. Route this editor-core request to the API and rendering areas.

## Change summary

Allow an editor decoration to visually replace a text range with a custom DOM element while preserving the underlying model text.

## Best solution

Design a range-replacement view primitive in the VS Code editor core, including cursor, selection, accessibility, layout, and disposal semantics, then inherit it in Monaco. The existing injected-text and content-widget APIs are useful building blocks but do not cover the central request.

## Vision fit

- **Fit:** rejected
- **Reason:** A Monaco-only editor rendering primitive conflicts with the generated-from-VS-Code model; the capability would need to land in the VS Code editor core first.
- **Evidence:** The README guardrail says Monaco is "generated straight from VS Code's sources with some shims around services the code needs to make it run in a web browser."

## Evidence

- **decoration API gap:** Current VS Code editor-core IModelDecorationOptions supports CSS classes and before/after InjectedTextOptions, whose content is strictly a single-line string; it exposes no HTMLElement replacement: https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/model.ts
- **partial alternative:** IContentWidget accepts an HTMLElement but is positioned near an editor position rather than replacing a model range: https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/editorBrowser.ts
- **Monaco capability history:** CHANGELOG.md documents injected-text support since v0.26.0 through IModelDecorationOptions.before/after, but this is text injection rather than arbitrary DOM replacement.
