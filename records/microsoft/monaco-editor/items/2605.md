# Issue #2605 — Use native approach to load web workers

[https://github.com/microsoft/monaco-editor/issues/2605](https://github.com/microsoft/monaco-editor/issues/2605)

## Summary

Native module-worker defaults now cover the bundled language services, but the broader request for plugin-owned worker setup without a host-maintained label switch remains unresolved. Keep open to establish the remaining public integration contract; no verified canonical owns that scope.

## Change summary

Let language plugins supply native module workers so embedders do not have to configure worker routing themselves.

## Best solution

Retain the bundled language-worker defaults and decide how third-party language plugins can provide equivalent defaults while preserving host overrides. Separate any remaining editor-worker changes into the VS Code core, and update the integration documentation to describe the supported contract.

- **Reason:** Reducing embedder-specific worker configuration through reusable language integration APIs supports modern ESM packaging.
- **Evidence:** The durable themes identify packaging and bundler integration and bundled language experiences as continuing investments; the library boundary favors APIs over framework-specific forks.

## Evidence

Its shared getWorker change invokes descriptor.createWorker after checking host overrides. This addresses bundled language defaults, not the complete plugin-registration request.
- **Current capability and boundary:** src/languages/features/{css,html,json,typescript}/workerManager.ts retain native worker factories. src/internal/common/workers.ts prioritizes MonacoEnvironment.getWorker/getWorkerUrl, then uses the supplied factory. Its createWebWorker helper is internal; src/index.ts and src/editor.ts do not expose a registerWorker API. Existing factories therefore provide partial coverage rather than a public label-registration contract.

Native factories are connected to the ESM packaging path, although no bundler execution was performed.
