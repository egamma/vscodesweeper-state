# Issue #1885 — API to talk with the language server of a language

[https://github.com/microsoft/monaco-editor/issues/1885](https://github.com/microsoft/monaco-editor/issues/1885)

## Summary

Keep open: the bundled HTML service still lacks a public accessor for querying its existing worker from custom UI. The related adapter-exposure and LSP-migration issues do not track the same requested capability.

## Change summary

Expose typed access to bundled language services so embedders can build custom outlines and documentation views.

## Best solution

Provide supported access to the bundled services' document-symbol and hover results without requiring a separate language-service instance. Decide the public contract alongside the planned CSS/JSON/HTML LSP migration, while retaining this issue's embedder-facing acceptance criteria.

## Plan brief

- **Likely files:** `src/languages/features/html/register.ts`, `src/languages/features/html/htmlMode.ts`, `src/languages/features/html/workerManager.ts`, `src/languages/features/html/htmlWorker.ts`, `src/languages/features/css/register.ts`, `src/languages/features/json/register.ts`
- **Validation:** A typed browser integration sample should query document symbols and hover information for an HTML model through the supported public API, repeat after editing the model, and observe updated results while normal editor providers continue functioning. Repeat for each bundled service included in the agreed contract.
- **Behavior:**

  > Embedders need to query bundled language services to populate custom outlines and documentation views without duplicating the service or relying on private editor registries. HTML is the concrete missing example: document symbols and hover information should be accessible for an open model and reflect subsequent edits. Existing editor language features must retain their behavior. The contract should distinguish querying features a service already supports from adding new language capabilities.
- **Trace:**

  > src/languages/features/html/register.ts registers services lazily and returns only defaults and disposal. htmlMode.ts setupMode creates a WorkerManager whose accessor is retained locally and passed to document-symbol and hover adapters. HTMLWorker.doHover and HTMLWorker.findDocumentSymbols implement the requested queries, and WorkerManager.getLanguageServiceWorker synchronizes model resources before returning its proxy. TypeScript exports public worker getters, while JSON exposes a narrower typed getWorker surface and CSS lacks an equivalent getter. This is Monaco-owned language integration, not a generated editor-core change. https://github.com/microsoft/monaco-editor/issues/2043 concerns adapter reuse rather than worker querying; https://github.com/microsoft/monaco-editor/issues/5066 plans LSP migration without settling this public contract. Preserve service configuration, model synchronization, and lifecycle behavior; the unresolved boundary is what supported query API embedders receive.
- **Open decisions:**
  - Should embedders receive language-specific typed worker access, or a transport-independent feature-query API that remains stable through LSP migration?
  - Should the public contract expose all supported worker operations, or initially guarantee document-symbol and hover queries across the bundled services?

## Evidence

- **Existing capability and remaining gap:** src/languages/features/typescript/register.ts exports getTypeScriptWorker and getJavaScriptWorker. src/languages/features/json/register.ts exports getWorker, but its public IJSONWorker interface only declares parseJSONDocument and getMatchingSchemas. The HTML and CSS register.ts modules expose no equivalent worker accessor.
- **HTML service trace:** src/languages/features/html/register.ts exposes LanguageServiceRegistration with defaults and disposal only. htmlMode.ts setupMode creates a WorkerManager and retains its worker accessor locally for editor providers. htmlWorker.ts already implements doHover and findDocumentSymbols; workerManager.ts getLanguageServiceWorker synchronizes requested model resources before returning the proxy.
- **Low-level workaround is not equivalent:** src/languages/features/html/htmlMode.ts exports WorkerManager, but constructing one creates independently managed worker state rather than exposing the already registered service. Provider registration APIs likewise supply editor features rather than a public query interface for custom UI.
- **Verified related issue, not a duplicate:** https://github.com/microsoft/monaco-editor/issues/2043 is open, younger, unscheduled, and has no body upvotes. Its author explicitly distinguishes exposing adapter classes from this issue's direct worker access at https://github.com/microsoft/monaco-editor/issues/2043#issuecomment-659675959; the next comment agrees they serve different purposes.
- **Related architectural work:** https://github.com/microsoft/monaco-editor/issues/5066 is open in Backlog and proposes replacing language-feature adapters with the Monaco LSP client. It does not specify public access to bundled services for custom outlines or documentation, so it is a design dependency rather than a verified duplicate.
- **Demand:** https://github.com/microsoft/monaco-editor/issues/1885 describes custom outline and selected-element documentation UI; the supplied comment adds an independent request for access supporting code lenses.
