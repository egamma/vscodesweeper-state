# Issue #4228 — [Bug] Make insertText, insertTextRules, label available for tsMode suggestions

[https://github.com/microsoft/monaco-editor/issues/4228](https://github.com/microsoft/monaco-editor/issues/4228)

## Summary

The built-in TypeScript completion adapter still couples display labels and insertion text to entry.name. Keep this customization request open and route it to typescript and suggest; existing provider APIs are a workaround, not coverage of the requested worker-entry mapping.

## Change summary

Allow customized TypeScript worker completions to supply distinct display labels, insertion text, and insertion rules.

## Best solution

Extend the Monaco-owned TypeScript completion adapter with a defined mapping for supported completion metadata while preserving the original entry identity for detail resolution. Decide the custom-worker contract explicitly: TypeScript exposes insertText and isSnippet, but not Monaco's label and insertTextRules fields.

## Evidence

- **Current adapter limitation:** src/languages/features/typescript/languageFeatures.ts:468–492 maps worker entries into suggestions with label: entry.name and insertText: entry.name, without forwarding entry.insertText or insertion rules. This directly matches the customization limitation described in https://github.com/microsoft/monaco-editor/issues/4228.
- **Completion contract and resolution:** src/languages/features/typescript/lib/typescriptServices.d.ts:10933–10979 declares CompletionEntry.insertText, isSnippet, and labelDetails, rather than Monaco label or insertTextRules fields. languageFeatures.ts:503–520 uses myItem.label to request completion details and subsequently assigns details.name as the label, so display customization also needs a deliberate identity contract.
- **Existing-capability check:** src/languages/features/typescript/register.ts:235–239 exposes ModeConfiguration.completionItems, and tsMode.ts:64–70 conditionally registers SuggestAdapter through languages.registerCompletionItemProvider. Disabling the built-in provider and registering a replacement permits custom completions, but requires replacing the adapter rather than honoring metadata from an extended TypeScript worker.
- **Related issue is not a canonical duplicate:** https://github.com/microsoft/monaco-editor/issues/2521 was verified open and predates this report, but describes duplicate suggestions from parallel built-in and custom providers. It does not report the same observable symptom of worker-supplied insertion metadata being discarded.
