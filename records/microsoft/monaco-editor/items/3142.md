# Issue #3142 — [Bug] monaco-editor-webpack-plugin does not split/reuse chunks properly

[https://github.com/microsoft/monaco-editor/issues/3142](https://github.com/microsoft/monaco-editor/issues/3142)

## Summary

Keep open: the webpack plugin still builds workers separately and explicitly limits each to one chunk, so the requested shared-chunk capability remains missing. The upstream discussion explains the current architecture's limitation but does not resolve sharing between Monaco workers.

## Change summary

Allow plugin-generated language and editor workers to reuse shared chunks instead of duplicating common dependencies.

## Best solution

Design shared-chunk support in the webpack plugin, distinguishing worker-to-worker reuse from reuse with the application's main bundle. Establish compatibility expectations for webpack 4 and 5 while preserving existing worker-loading behavior.

- **Behavior:**

  > The plugin currently emits duplicated dependencies across editor and language-worker bundles, including custom workers. The desired capability is reusable chunks that reduce emitted duplication without breaking worker startup or language functionality. Acceptance should inspect emitted assets and exercise workers that import a shared dependency; main-thread sharing must be evaluated separately from worker-to-worker sharing.
- **Trace:**

  > webpack-plugin/src/index.ts:createPlugins maps each worker to an AddWorkerEntryPointPlugin with LimitChunkCountPlugin({ maxChunks: 1 }). In webpack-plugin/src/plugins/AddWorkerEntryPointPlugin.ts:getCompilerHook, every invocation creates its own child compiler and registers one entry, establishing separate compilation boundaries. The reporter's experiment at https://github.com/webpack/webpack/discussions/15963#discussioncomment-2985227 reports reduced duplication with multiple entries and dependOn, but it is not the shipped plugin implementation and was not executed in this review. Worker URLs and cross-origin handling are generated by createLoaderRules in index.ts and must remain functional. webpack-plugin/package.json promises webpack 4 and 5 support, so adopting native webpack 5 worker handling introduces a public compatibility question. test/smoke/package-webpack.ts supplies an existing packaging fixture to extend after the scope is settled.
- **Open decisions:**
  - Should the supported capability cover sharing only among Monaco workers, or also sharing dependencies between workers and the application's main bundle?
  - Must shared-chunk support work on both currently supported webpack major versions, or may it be a webpack-5-only opt-in while webpack 4 retains existing behavior?

## Evidence

This architecture does not provide the requested shared worker compilation.
