# Issue #5067 — Ship two esm variants

[https://github.com/microsoft/monaco-editor/issues/5067](https://github.com/microsoft/monaco-editor/issues/5067)

## Summary

Keep this packaging proposal open and route it to ESM. Current main still produces one ESM variant with CSS imports and packaged dependencies; newer tree-shakeable entry points do not satisfy the two-variant request.

## Change summary

Ship complementary ESM distributions for bundlers with external dependencies and for direct browser loading with bundled dependencies and browser-compatible CSS handling.

## Best solution

Agree on the public distribution contract, then provide supported bundler and browser consumption paths through Monaco's packaging pipeline. Preserve component-level CSS elimination for bundlers and resolve dependency-update semantics, stylesheet ownership, and worker loading for the browser variant.

## Plan brief

- **Likely files:** `build/esm/rollup.config.mjs`, `build/esm/build.script.ts`, `build/shared.mjs`, `build/build-monaco-editor.ts`, `scripts/ci/build-monaco-editor-pkg.ts`, `package.json`, `docs/integrate-esm.md`, `test/smoke/package-esbuild.ts`
- **Validation:** After agreeing on the contract, build/package the distributions and exercise bundler fixtures that omit unused features and resolve external dependencies. Serve a plain module-script fixture using the browser distribution and verify editor styling and language-worker operation without consumer-side source rewriting; check dependency metadata against the implementations actually shipped.
- **Behavior:**

  > Embedders need supported ESM consumption paths for both optimizing bundlers and direct browser loading. The bundler path should retain component-associated CSS and use replaceable external npm dependencies. The browser path should load without consumer-side CSS-import removal and use bundled dependencies as requested. Acceptance must cover correct styling, language-worker operation, selective bundling, and truthful dependency metadata.
- **Trace:**

  > build/build-monaco-editor.ts invokes buildESM once, and build/esm/build.script.ts runs one JavaScript Rollup configuration followed by declaration generation. build/esm/rollup.config.mjs preserves modules and CSS imports while resolving dependencies; build/shared.mjs maps those dependency modules into the emitted package. package.json exposes this single ESM tree, while scripts/ci/build-monaco-editor-pkg.ts separately copies dependency metadata for CVE tracking. Source inspection confirms that modern register entry points do not establish the requested distribution split. The uncertainty starts at the public package/default-entry-point contract and browser stylesheet-loading contract discussed in https://github.com/microsoft/monaco-editor/issues/5067. Keep generated editor behavior unchanged; the unrelated mouse-handler patch in the consumer workaround is outside this packaging task.
- **Open decisions:**
  - Should the variants be separate export paths or separate npm packages, and which consumption contract should the default import preserve?
  - Should the browser distribution expose separately loaded CSS or use CSS module imports with an explicit stylesheet-adoption contract, including document and ShadowRoot ownership?
  - What dependency version and update guarantees should each distribution expose so installed dependency metadata accurately represents external versus bundled implementations?

## Evidence

- **Existing capability and remaining gap:** build/esm/rollup.config.mjs emits only out/monaco-editor/esm, uses preserveModules, keepCssImports, and nodeResolve, and does not externalize npm dependencies. build/shared.mjs maps resolved node_modules files into external/ inside the generated distribution; that directory name does not mean runtime npm dependencies are externalized.
- **Public entry points:** package.json routes ESM exports into the same esm/vs tree. CHANGELOG.md documents v0.56.0's editor and per-feature/per-language register entry points, which support selective inclusion but do not provide separate browser-ready and external-dependency variants.
