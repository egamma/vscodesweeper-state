# Issue #2451 — Make monaco-editor use monaco-editor-core and friends

[https://github.com/microsoft/monaco-editor/issues/2451](https://github.com/microsoft/monaco-editor/issues/2451)

## Summary

Keep open: the newer modular entry points support selective imports, but monaco-editor still embeds its own copy of monaco-editor-core rather than sharing a runtime dependency with third-party plugins. No verified canonical owns the requested package-composition change.

## Change summary

Make monaco-editor compose separately published core and language packages so plugins targeting monaco-editor-core also work with monaco-editor.

## Best solution

Establish a supported shared editor-module identity for plugins and both distributions, with an explicit compatibility contract for core and language packages. This belongs in Monaco's packaging and build; selective entry points alone do not settle the cross-package interoperability request.

## Vision fit

- **Fit:** aligned
- **Reason:** Shared modular dependencies would advance packaging interoperability and composable language support without requiring an independent editor core.
- **Evidence:** The durable themes include packaging and bundler integration and bundled language experiences; the guardrail favors ESM-first, tree-shakeable entry points.

- **Trace:**

  > package.json declares core as a development dependency, while src/editor.ts and src/index.ts import it during the build. build/esm/rollup.config.mjs resolves core into the package, and build/shared.mjs maps its modules into the distribution; build/esm/rollup-types.config.mjs similarly incorporates its declarations. Thus the current source imports do not establish shared runtime module identity across installed packages. - **Open decisions:**
  - Should monaco-editor guarantee that plugins importing monaco-editor-core share its runtime editor modules, and which core-version combinations will that guarantee support?

## Evidence

- **Runtime dependency gap:** package.json lists monaco-editor-core under devDependencies, with no regular dependencies on the requested core and language packages. build/build-monaco-editor.ts copies this manifest into the published package rather than establishing the requested runtime dependency composition.
- **Core remains embedded:** src/editor.ts re-exports monaco-editor-core/esm/vs/editor/editor.api, but build/esm/rollup.config.mjs resolves that dependency into the output. build/shared.mjs maps node_modules/monaco-editor-core/esm/ into the distribution itself, and build/esm/rollup-types.config.mjs explicitly includes core declarations. Source-level reuse is therefore not a shared installed runtime dependency.
- **Existing capability is partial:** CHANGELOG.md documents v0.56.0's monaco-editor/editor and per-feature/per-language register entry points. These enable selective bundles within monaco-editor, but do not make a plugin importing monaco-editor-core use the same published editor modules as monaco-editor.
- **Related reports do not supersede this request:** https://github.com/microsoft/monaco-editor/issues/2460 is closed and concerns incorrect declaration imports. https://github.com/microsoft/monaco-editor/issues/5507 is open and concerns unwanted editor-feature registration; https://github.com/microsoft/monaco-editor/issues/5148 is open and concerns worker API removal. None owns the full package-composition request or reports the same observable problem.
- **Plugin interoperability evidence:** https://github.com/remcohaszing/monaco-yaml/issues/50#issuecomment-893614275 explicitly describes choosing monaco-editor over monaco-editor-core and depending on monaco-editor's build output. https://github.com/remcohaszing/monaco-yaml/pull/282 is closed, unmerged, and addresses worker API compatibility rather than package composition.
