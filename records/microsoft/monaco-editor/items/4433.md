# Issue #4433 — [Feature Request]  The monaco editor gets the configuration of the registration language

[https://github.com/microsoft/monaco-editor/issues/4433](https://github.com/microsoft/monaco-editor/issues/4433)

## Summary

The supported API still lacks a getter for registered language configurations and tokenizers. Route this request to editor-api; the existing loader workaround does not establish a supported extension contract.

## Change summary

Expose existing C++ language definitions so embedders can retain the defaults while adding keywords and editing configuration.

## Best solution

Decide whether to support retrieving bundled language definitions for customization, clearly distinguishing Monarch keywords from editing configuration. Any general registered-language getter belongs in the VS Code-derived API; Monaco owns the bundled C++ definition and its loading.

## Evidence

- **Existing-capability check:** https://github.com/microsoft/vscode/blob/c132f72ae9f5ff80093e7d722c36f03755865b20/src/vs/monaco.d.ts declares getLanguages(), setLanguageConfiguration(), and setMonarchTokensProvider(), but no language-configuration getter. ILanguageExtensionPoint contains registration metadata, not a public loader. This is the vscodeRef pinned in the checkout's package.json.
- **Bundled definition:** src/languages/definitions/cpp/cpp.ts exports conf and language; keywords belong to language, while conf holds comments, brackets, autoclosing, and folding. src/languages/definitions/cpp/register.ts loads this module, and _.contribution.ts installs its tokenizer and editing configuration. Accessing the bundled module does not retrieve arbitrary registered or subsequently overridden configurations.
- **Unsupported workaround:** https://github.com/microsoft/monaco-editor/issues/1927#issuecomment-694175679 explicitly warns that the loader-based approach is not public API and may break in future updates.
