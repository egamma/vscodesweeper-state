# Issue #3448 — [Bug] monaco.editor.tokenize does not return correct results

[https://github.com/microsoft/monaco-editor/issues/3448](https://github.com/microsoft/monaco-editor/issues/3448)

## Summary

The public synchronous tokenize API still races asynchronous token-provider initialization. The issue already has the correct feature-request and tokenization routing, and no broader canonical owns the requested readiness API.

## Change summary

Provide a supported way to await language tokenization initialization before calling monaco.editor.tokenize.

## Best solution

Expose an awaitable public tokenization-readiness API, or an asynchronous tokenize variant, through the vscode standalone editor API and Monaco's lazy language registration. The existing internal loadLanguage helper demonstrates the required sequence but is not a supported public entry point.

- **Reason:** A supported readiness API strengthens Monaco's bundled language experience and its browser-embedding API surface.
- **Evidence:** The durable themes explicitly include bundled language experiences, while the README describes Monaco as the VS Code editor adapted to run as a browser library.

## Evidence

- **current editor-core behavior:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/browser/standaloneEditor.ts calls the asynchronous TokenizationRegistry.getOrCreate(languageId) without awaiting it, then immediately performs synchronous tokenization, preserving the reported initialization race.
- **tokenization contract:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/languages.ts declares TokenizationRegistry.getOrCreate(languageId) as returning a Promise, confirming that provider creation can be asynchronous.
- **internal workaround:** src/languages/definitions/_.contribution.ts:55-61 contains an internal loadLanguage helper that awaits the lazy language loader and creates a temporary model to trigger tokenizer creation, but the supported per-language register entry points only register the lazy provider.
- **related report:** https://github.com/microsoft/monaco-editor/issues/3105 confirms a similar lazy-initialization symptom for JSON colorization, but it is narrower than this request and therefore is not a canonical duplicate.
