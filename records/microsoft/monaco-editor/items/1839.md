# Issue #1839 — Add better support for imports suggestion

[https://github.com/microsoft/monaco-editor/issues/1839](https://github.com/microsoft/monaco-editor/issues/1839)

## Summary

Keep this accepted Backlog request open: package.json registration is a credible workaround, but it does not establish that the original unwrapped @types submodule example is covered. No verified open canonical or concrete Monaco fix was found.

## Change summary

Suggest import module paths for unwrapped declaration files registered through addExtraLib.

## Best solution

Establish reliable module-path completion for ordinary external declarations in Monaco's TypeScript worker, with a playground example documenting any required package metadata. First compare the exact original @types submodule setup with the reported package.json workaround; distinguish module-path suggestions from automatic insertion of imports.

## Plan brief

- **Likely files:** `src/languages/features/typescript/tsWorker.ts`, `src/languages/features/typescript/languageFeatures.ts`, `src/languages/features/typescript/register.ts`
- **Validation:** In the current playground, register the issue's two unwrapped @types/test declaration files, create a file:///main.ts model, and request completion inside an import module string. Compare against the wrapped control and against adding file:///package.json dependencies; verify that test/file1 and test/file2 are suggested and selected imports resolve.
- **Behavior:**

  > The requested outcome is module-path suggestions for ordinary exported declarations registered through addExtraLib, without rewriting them into declare module wrappers. Compare the original nested @types paths with the package.json workaround on the current release. Acceptance should cover both suggested module names and successful resolution after selection. Automatic insertion of import statements is a separate capability.
- **Trace:**

  > TypeScriptWorker in src/languages/features/typescript/tsWorker.ts exposes registered extra libraries as script filenames and supplies their contents through readFile and fileExists. SuggestAdapter in src/languages/features/typescript/languageFeatures.ts forwards completion requests to that worker. The public configuration surface is in src/languages/features/typescript/register.ts. The reported package.json workaround has an independently merged application example at https://github.com/Effect-TS/website/pull/681, but that application uses a custom worker and does not establish coverage of the original @types submodule paths. Uncertainty starts at TypeScript's discovery of those module specifiers with the stock worker; no runtime reproduction was performed in this read-only review. Preserve existing wrapped declarations and avoid expanding this work into the separate auto-import-edit request at https://github.com/microsoft/monaco-editor/issues/2582.
- **Open decisions:**
  - Should registering unwrapped package declarations alone make their module paths discoverable, or should explicit virtual package.json dependency metadata be part of the supported contract?

## Evidence
