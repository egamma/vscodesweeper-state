# Issue #5049 — [Bug] `createWebWorker` is broken in minimal distributions

[https://github.com/microsoft/monaco-editor/issues/5049](https://github.com/microsoft/monaco-editor/issues/5049)

## Summary

The compatibility gap remains in current source: the minimal editor entry exposes the core worker API, while the moduleId/createData adapter remains internal. Keep this report open; the related worker redesign and bundle-size report do not establish a qualifying duplicate.

## Change summary

Minimal Monaco distributions cannot use the moduleId-based createWebWorker API without importing the full editor.

## Best solution

Provide a supported, tree-shakeable custom-worker integration in Monaco-owned entry points without registering unrelated editor features. The team should settle compatibility expectations alongside the worker redesign before accepting the contributor's proposed public API changes.

## Plan brief

- **Likely files:** `src/editor.ts`, `src/index.ts`, `src/internal/common/workers.ts`, `test/smoke/smoke.test.ts`
- **Validation:** Add a minimal ESM browser fixture to the Playwright smoke harness. Verify that the supported custom-worker API initializes createData, resolves getProxy(), synchronizes a model through withSyncedResources(), and disposes successfully without importing editor.main or registering unselected editor contributions; also check the public TypeScript declarations.
- **Behavior:**

  > An embedder selecting only the editor API and individual features cannot currently use the legacy moduleId/createData worker integration through that minimal entry. The supported custom-worker path should initialize and expose its proxy, synchronize models, and dispose without loading unrelated editor features. Acceptance must cover a minimal ESM bundle rather than the full-editor playground. The precise compatibility surface needs a maintainer decision.
- **Trace:**

  > src/editor.ts directly re-exports the core editor API, and src/index.ts adds no worker adapter export. src/internal/common/workers.ts contains the moduleId/createData conversion and is called by the CSS, HTML, JSON and TypeScript worker managers, but imports the full monaco-editor-core root. The pinned VS Code standaloneEditor.createWebWorker forwards options to standaloneWebWorker, whose IInternalWebWorkerOptions requires worker; this confirms the mismatch for the reporter's legacy options. Preserve the core worker contract and avoid pulling unrelated feature registrations into minimal bundles. The contributor proposes compatibility exports and dispatch in https://github.com/microsoft/monaco-editor/issues/5049#issuecomment-5436855377, while https://github.com/microsoft/monaco-editor/issues/5148 explores replacing the worker abstraction. https://github.com/microsoft/monaco-editor/issues/5507 tracks the separate full-root import side effect; it is related implementation context, not a duplicate of this report.
- **Open decisions:**
  - Should supported minimal Monaco entry points retain moduleId/createData compatibility on editor.createWebWorker, expose a separately named helper, or require migration to a replacement worker API?

## Evidence
