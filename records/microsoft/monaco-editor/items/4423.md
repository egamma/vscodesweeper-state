# Issue #4423 — [Bug] The setMonarchTokensProvider rule matches incorrectly

[https://github.com/microsoft/monaco-editor/issues/4423](https://github.com/microsoft/monaco-editor/issues/4423)

## Summary

The requested whole-word highlighting is supported through Monarch's documented keyword cases. The suffix highlighting follows its substring-based matching model, so this is a tokenizer-configuration question rather than a new defect.

## Change summary

Highlight only the standalone word Stop, not Stop within longer words or digit-prefixed strings.

## Best solution

Match complete word-character sequences and classify them with an @keywords case, leaving non-keywords unstyled. This covers all supplied examples without changing Monarch's matching semantics.

- **Proposed comment:**

  > Thanks for the report. Monarch evaluates rules against the remaining substring, so after consuming the prefix of QdStop, the rule sees only Stop. A leading word boundary or negative lookbehind therefore cannot inspect the consumed prefix.
  > 
  > For your examples, match the complete word first and classify it using keyword cases:
  > 
  > ```javascript
  > monaco.languages.setMonarchTokensProvider('mySpecialLanguage', {
  >   keywords: ['Stop'],
  >   tokenizer: {
  >     root: [
  >       [/\w+/, { cases: { '@keywords': 'keyword', '@default': '' } }]
  >     ]
  >   }
  > });
  > ```
  > 
  > This highlights standalone Stop while leaving QdStop, 11Stop, and the suffixed examples unstyled. This is the documented configuration pattern rather than a new editor defect; the same matching behavior is explained at https://github.com/microsoft/monaco-editor/issues/890#issuecomment-392540348.
  > 
  > Further usage questions belong on StackOverflow's monaco-editor tag: https://stackoverflow.com/questions/tagged/monaco-editor.

## Evidence

- **Current matching path:** https://github.com/microsoft/vscode/blob/main/src/vs/editor/standalone/common/monarch/monarchLexer.ts: MonarchTokenizer._myTokenize matches against line.substr(pos), consumes one character when no rule matches, and advances pos. For QdStop, the prefix is consumed until the remaining input is Stop; the negative lookbehind then has no preceding character to inspect. The trailing lookahead still sees suffix characters, explaining the reported asymmetry.
- **Documented existing capability:** website/static/monarch-static.html:617–655 documents matching complete identifiers and using cases with @keywords and @default. For this sample, /\w+/ with keywords: ['Stop'] and cases: { '@keywords': 'keyword', '@default': '' } consumes QdStop, 11Stop, and StopSS as complete non-keywords while highlighting standalone Stop.
- **Maintainer explanation of identical boundary behavior:** https://github.com/microsoft/monaco-editor/issues/890#issuecomment-392540348 explains why /\bint\b/ highlights the suffix of print: Monarch retries rules on successively shortened substrings. The reporter confirmed the keyword-cases alternative worked at https://github.com/microsoft/monaco-editor/issues/890#issuecomment-391581679.
- **Related capability request:** https://github.com/microsoft/monaco-editor/issues/3441 is open and requests positive-lookbehind support for context-dependent matching. That capability request is related, but this report's standalone-keyword goal is already covered by documented cases.
