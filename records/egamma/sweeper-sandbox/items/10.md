# Issue #10 — Count only the selection when text is selected

[https://github.com/egamma/sweeper-sandbox/issues/10](https://github.com/egamma/sweeper-sandbox/issues/10)

## Summary

This is an unimplemented, explicitly in-scope statistics feature. The issue already carries the correct feature-request and status-bar labels, and no separate open issue owns the same work.

## Change summary

Show statistics for selected text in the status bar, returning to document-wide statistics when the selection is cleared and defining behavior for multiple selections.

## Best solution

Define whether the status bar replaces the document count or shows selected and total counts together, then update the selection-driven status-bar flow in src/extension.ts while keeping counting and formatting logic pure in src/stats.ts. The implementation should cover empty, single, and multiple selections without changing existing document-wide counting behavior.

## Plan brief

- **Likely files:** `src/extension.ts`, `src/stats.ts`, `test/stats.test.ts`
- **Validation:** Run `npm test && npm run lint`, then use an Extension Development Host to verify that selecting one paragraph updates the displayed statistics, clearing it restores the document total, and multiple selections follow the chosen aggregation semantics.
- **Behavior:**

  > When an editor has selected text, Note Stats should present statistics for that selection; when all selections are empty, it should return to the whole-document statistics. The displayed form for selected and total counts and the handling of multiple selections must follow the maintainer's chosen semantics. Acceptance checks should cover one selection, clearing the selection, multiple cursors with and without selected ranges, and the existing showCharacters setting.
- **Trace:**

  > In src/extension.ts, refresh() always computes statistics from editor.document.getText(), and the registered listeners cover active-editor and document-content changes but not text-selection changes. src/stats.ts already exposes computeStats(text) and formatStats(), so the pure counting boundary can remain independent of the VS Code API; test/stats.test.ts currently pins only document-text counting and the existing label format. Preserve the documented whitespace-counting semantics, toggle visibility behavior, inactive-editor hiding, and both existing settings. No other open issue found in the canonical search owns selection counting.
- **Open decisions:**
  - Should a non-empty selection replace the document count or be displayed alongside it, such as `120 of 2,340 words`?
  - Should multiple non-empty selections be added together, and if selected ranges overlap, should overlapping text be counted once or once per selection?
