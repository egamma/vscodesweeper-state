# Issue #13 — Make Note Stats work on vscode.dev as a web extension

[https://github.com/egamma/sweeper-sandbox/issues/13](https://github.com/egamma/sweeper-sandbox/issues/13)

## Summary

This is a real, currently unimplemented web-extension capability that the project explicitly lists as in scope. The issue already has the correct feature-request and web labels, and no other open issue owns the work.

## Change summary

Package Note Stats so it can activate and provide its status-bar and command functionality on vscode.dev and github.dev.

## Best solution

Design and add a browser-compatible build and package entry point while preserving the desktop extension and keeping the shipped bundle free of runtime dependencies. The web build should expose the same status item, settings, and commands without changing the pure helpers in src/stats.ts.

## Plan brief

- **Likely files:** `package.json`, `package-lock.json`, `tsconfig.json`, `src/extension.ts`
- **Validation:** Build and package both entry points, then launch the packaged extension in a VS Code Web Extension Development Host and verify that the status item appears and all three `noteStats.*` commands execute; also run the existing `npm test` suite to preserve helper behavior.
- **Behavior:**

  > Note Stats should load on vscode.dev and github.dev and expose the same user-facing status item, commands, and settings available on desktop. Opening an editable document should show its word count, and Toggle Status Bar Item, Insert Timestamp, and Slugify Current Line should work. Desktop behavior and the existing pure-helper tests must remain unchanged, and the shipped extension must not require Node APIs, a server, an account, or network access.
- **Trace:**

  > package.json currently declares only `main: ./out/src/extension.js`; there is no `browser` entry or browser build script. tsconfig.json emits CommonJS and includes Node types because the same project compiles the node:test suite. The runtime path in src/extension.ts uses the `vscode` API and imports src/stats.ts, while src/stats.ts has no vscode or Node imports; the visible Node-only import is in test/stats.test.ts. The uncertainty begins at packaging: the project must decide how desktop and browser artifacts share source and build configuration while preserving its dependency-free runtime and small-code guardrails. No other open issue found by the canonical search owns this work.
- **Open decisions:**
  - Should the package retain separate desktop `main` and web `browser` artifacts, or use one bundled browser-compatible artifact for both extension hosts?
  - How should the browser bundling configuration be structured so Node-only test compilation remains separate and the shipped extension has no runtime dependencies?

## Evidence

- **manifest gap:** package.json defines only the desktop `main` entry point (`./out/src/extension.js`) and has no `browser` entry point or web-bundle script.
- **build configuration:** tsconfig.json emits CommonJS directly into out; package.json has no bundler dependency, and the tracked build configuration contains no esbuild or webpack setup.
- **source boundary:** src/extension.ts imports the `vscode` API and the pure helpers from src/stats.ts; it contains no direct Node API use. Node-specific imports are confined to test/stats.test.ts, so the runtime source appears suitable for a browser bundle.
- **canonical search:** A search of all open egamma/sweeper-sandbox issues for web, browser, vscode.dev, and github.dev found only https://github.com/egamma/sweeper-sandbox/issues/13.
- **existing surface:** package.json currently contributes the status-bar toggle, Insert Timestamp, and Slugify Current Line commands plus the two noteStats settings, but none provides web activation or packaging.
