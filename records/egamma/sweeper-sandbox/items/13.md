# Issue #13 — Make Note Stats work on vscode.dev as a web extension

[https://github.com/egamma/sweeper-sandbox/issues/13](https://github.com/egamma/sweeper-sandbox/issues/13)

## Summary

This is a real, unimplemented web-extension capability that the project explicitly lists as in scope. The issue already has the correct feature-request and web labels, and no older canonical issue owns the work.

## Change summary

Make Note Stats load and provide its existing status bar and command functionality in vscode.dev and github.dev.

## Best solution

Add a browser-compatible extension bundle and manifest entry while preserving the existing desktop behavior and dependency-free runtime. The implementation should include a repeatable web-extension build and a web-host validation path covering activation, the status bar, and both editing commands.

## Plan brief

- **Likely files:** `package.json`, `package-lock.json`, `.vscode/launch.json`, `.vscodeignore`, `src/extension.ts`
- **Validation:** Build the desktop and browser extension outputs, run the existing unit tests, then launch the browser bundle in a VS Code web extension host and verify activation, status-bar updates, Note Stats: Insert Timestamp, and Note Stats: Slugify Current Line.
- **Behavior:**

  > Note Stats should activate on vscode.dev and github.dev as well as desktop VS Code. In a web editor, the status bar item must show and update document statistics, and the existing toggle, timestamp, and slugify commands must retain their current behavior. The extension must remain usable without a server, account, network service, or Node runtime API.
- **Trace:**

  > package.json currently exposes only the CommonJS desktop entry at `./out/src/extension.js` and defines no browser build or web-host validation. `.vscode/launch.json` likewise exercises only the desktop extension host. The runtime source is promising: `src/extension.ts` uses the VS Code API and local helpers, while `src/stats.ts` is pure and has no Node or VS Code imports. Preserve the existing command IDs, settings, desktop entry behavior, status-bar semantics, and dependency-free runtime; the uncertainty is in the web build, packaging, and validation setup rather than the product behavior.

## Evidence

- **missing web entry point:** package.json declares only `main: ./out/src/extension.js`; it has no `browser` entry, web bundle, or web build script, so the shipped extension does not expose a browser extension host entry point.
- **browser-compatible source surface:** src/extension.ts imports only `vscode` and the local pure helpers from src/stats.ts; src/stats.ts has no `vscode` or Node runtime import. The current source therefore presents no evident Node-only runtime dependency, although the build and package paths remain desktop-only.
- **current validation gap:** .vscode/launch.json defines only a desktop `extensionHost` launch using compiled CommonJS output, and package.json has no web-extension build or web-host test command.
- **canonical search:** Repository searches for `web`, `vscode.dev`, and `browser` found only https://github.com/egamma/sweeper-sandbox/issues/13, so there is no older open canonical issue to absorb this request.
